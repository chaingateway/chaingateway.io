Créer un portefeuille crypto avec une API : guide 2026

Créez des portefeuilles crypto via une API : choix de garde, sécurité des clés, conception des adresses, webhooks et plan de mise en œuvre pas à pas.

Chapitres
C
Chaingateway Team
Experts blockchain

Relu par Maurice Sobiera

Une API de portefeuille crypto est un service qui crée des adresses et des paires de clés, indique les soldes, envoie des transactions et prévient votre application des dépôts. Vous l’appelez depuis votre backend, au lieu d’exploiter vous-même des nœuds et du code de signature. Trois choix de conception comptent : qui détient les clés, comment vous protégez vos identifiants et comment vous détectez les paiements.

Ce guide traite ces trois points, avec les compromis qu’une équipe de production doit trancher avant le lancement.

TL;DR

  • Une API de portefeuille génère des clés et renvoie une adresse. Vos vrais choix de conception sont la garde, le stockage des clés et la détection des paiements.
  • Attribuez à chaque utilisateur ou à chaque facture sa propre adresse, et enregistrez chaque hachage de transaction entrante comme clé unique dans votre base de données.
  • Utilisez des webhooks signés plutôt que du polling, vérifiez chaque signature et rendez votre gestionnaire idempotent.
  • La génération des clés doit s’appuyer sur une source aléatoire cryptographiquement sûre. Les clés de production appartiennent à un stockage non exportable, comme un HSM.
  • Une API multi-chaînes unifiée vous évite d’exploiter des nœuds et de maintenir une intégration distincte par réseau.

Que fait une API de portefeuille ?

Un portefeuille blockchain est un logiciel qui gère des clés. L’aperçu de la technologie blockchain du NIST le décrit comme un outil capable de stocker des clés privées, des clés publiques et des adresses, et qui aide les utilisateurs à manipuler les actifs que ces clés contrôlent. Une API de portefeuille déplace ce travail de l’appareil de l’utilisateur vers votre backend.

Une API de portefeuille remplit quatre fonctions :

  1. Créer : générer une nouvelle paire de clés et renvoyer l’adresse pour un réseau donné.
  2. Lire : indiquer les soldes et l’historique des transactions de cette adresse.
  3. Envoyer : construire, signer et diffuser un transfert, avec une estimation des frais.
  4. Notifier : prévenir votre application quand quelque chose se produit sur l’adresse.

Le guide du développeur Bitcoin sur le traitement des paiements fait une remarque valable pour toutes les chaînes : avant de demander un paiement, votre application doit créer une adresse ou en obtenir une ailleurs, et chaque étape du processus peut être confiée à des API tierces. Externaliser est un choix d’ingénierie légitime. Vous cédez du contrôle sur l’infrastructure en échange de vitesse et de moins de pièces mobiles.

La plupart des startups et des agences qui développent des fonctions de paiement veulent la ligne du milieu. Les utilisateurs déposent sur des adresses que votre application contrôle, votre backend envoie les versements, et personne n’a à exploiter un nœud ni à écrire du code de signature pour six réseaux.

La garde peut avoir des conséquences juridiques, qui dépendent de votre pays et de votre modèle d’activité. Si vous détenez des fonds pour des clients, consultez un avocat qui connaît les règles sur le transfert de fonds et les actifs virtuels dans votre juridiction avant le lancement. Cet article ne traite que du volet technique.

Un mot sur l’abstraction de compte

Si vous développez sur Ethereum, vous rencontrerez des portefeuilles à contrat intelligent. La feuille de route d’Ethereum sur l’abstraction de compte décrit des comptes dotés d’une sécurité programmable et d’une meilleure expérience utilisateur, au lieu de dépendre d’une seule clé privée brute. Cela permet des fonctions comme la prise en charge des frais de gaz par un tiers et une récupération flexible. C’est un bon choix pour les applications grand public où les utilisateurs possèdent leurs portefeuilles. Pour un backend qui crée des milliers d’adresses de dépôt et centralise les fonds, le compte classique à détention externe reste le modèle le plus simple, et c’est celui qui fonctionne de la même façon sur Bitcoin, Tron et les chaînes EVM. La documentation d’Ethereum explique elle-même les deux types de comptes, comptes à détention externe et comptes de contrat, si vous avez besoin d’un rappel.

Comment créer mon premier portefeuille via une API ?

Les points d’accès exacts varient selon le fournisseur : lisez la référence de l’API que vous choisissez. La séquence ci-dessous reste la même.

1. Obtenir des identifiants et les garder côté serveur

Inscrivez-vous, obtenez une clé API et, si le fournisseur signe les requêtes, un secret. Ces identifiants peuvent déplacer de l’argent : traitez-les comme des mots de passe de base de données. Chargez-les depuis un gestionnaire de secrets, jamais depuis du code côté client, jamais depuis un dépôt public. Les recommandations de l’OWASP pour les tests de SDK conseillent de vérifier que les identifiants sont limités à un périmètre et révocables. C’est une bonne règle pour toute intégration : si une clé fuite, vous devez pouvoir la désactiver sans reconstruire votre application.

2. Créer le portefeuille ou l’adresse

Appelez le point d’accès de création pour le réseau voulu. Vous recevez une adresse et, en général, un identifiant que votre système peut utiliser pour désigner le portefeuille plus tard. Enregistrez tout de suite trois éléments dans votre propre base de données :

  • l’adresse,
  • le réseau auquel elle appartient,
  • l’utilisateur, la commande ou la facture interne à laquelle elle est liée.

Ne stockez pas vous-même la clé privée, sauf si vous avez construit le stockage sécurisé pour la conserver. Avec un modèle hébergé, c’est le travail du fournisseur.

3. Afficher l’adresse et prévenir les erreurs

Affichez l’adresse avec le nom du réseau en toutes lettres. Le ticket de support le plus fréquent dans les paiements crypto concerne un utilisateur qui a envoyé un jeton sur le mauvais réseau. Une adresse USDT sur Ethereum et une sur Tron ne se ressemblent pas du tout, mais les utilisateurs se trompent quand même. Ajoutez le nom du réseau à côté du code QR, et envisagez une courte étape de confirmation avant l’affichage.

4. S’abonner aux événements de cette adresse

Enregistrez un webhook pour que votre backend apprenne les dépôts sans polling. La section suivante explique comment construire la partie réceptrice en toute sécurité.

5. Tester d’abord sur un réseau de test

Exécutez toute la boucle sur un testnet : créez une adresse, envoyez des fonds de test, recevez l’événement, créditez le compte, puis envoyez un versement. Ensuite seulement, passez les identifiants et le réseau sur le mainnet, en commençant par de petits montants.

À quoi cela ressemble-t-il avec Chaingateway ?

Chaingateway crée une adresse avec POST /api/v2/{chain}/addresses. La requête a deux modes, que la spécification de l’API appelle non sécurisé et sécurisé. La documentation sur la gestion des portefeuilles explique les compromis. Sans mot de passe, la réponse contient la clé privée, et vous devez la stocker vous-même. Avec un mot de passe, Chaingateway stocke la clé privée chiffrée sous ce mot de passe et ne renvoie que l’adresse. Il ne stocke pas le mot de passe et ne peut pas restaurer un portefeuille si vous le perdez.

Un appel réussi renvoie le statut 201 avec la nouvelle adresse dans data.address. Vous transmettez ensuite le même password à la place d’une clé privée chaque fois que vous envoyez une transaction depuis cette adresse. L’en-tête X-Network: testnet exécute l’appel sur le réseau de test. Conservez le mot de passe dans votre gestionnaire de secrets : c’est le seul moyen d’utiliser l’adresse. Si vous possédez déjà une clé, POST /api/v2/{chain}/addresses/import l’enregistre sous un mot de passe. Pour la suite, voyez comment fonctionnent les webhooks de paiement crypto.

Une adresse par utilisateur ou une par facture ?

La réutilisation d’adresses est le raccourci qui cause des problèmes de comptabilité plus tard. Le guide du développeur Bitcoin décrit l’approche standard : donner à chaque demande de paiement sa propre adresse, pour qu’un paiement entrant corresponde clairement à la commande qui l’a provoqué.

Les schémas courants :

  • Une adresse par facture. Rapprochement le plus net. Idéal pour les parcours de paiement avec un montant attendu et un délai d’expiration.
  • Une adresse par utilisateur. Simple pour les fonctions de dépôt, comme une recharge de solde. Chaque transfert entrant crédite le même compte.
  • Adresse mutualisée avec mémo ou tag. Uniquement pour les réseaux et actifs qui le prennent en charge, et plus difficile à réussir.

Si vous générez les adresses à partir d’un schéma déterministe hiérarchique, la structure est normalisée. BIP 44 définit l’organisation du chemin : objectif, type de monnaie, compte, change et index. Une seule graine produit ainsi une arborescence d’adresses prévisible. Une API hébergée s’en charge normalement pour vous, mais connaître cette organisation aide lors d’un audit ou d’une migration.

Comment protéger les clés privées ?

Ce n’est que rarement le protocole réseau qui fait pirater un produit de portefeuille. Une graine prévisible mène à une compromission silencieuse et totale, car un attaquant peut reconstruire les clés hors ligne. La méthodologie de test de l’OWASP pour les SDK demande aux testeurs de vérifier que la génération des clés utilise le générateur de nombres aléatoires cryptographiquement sûr de la plateforme.

Trois règles pratiques en découlent.

Ne développez jamais votre propre génération de clés. Utilisez une bibliothèque éprouvée ou un fournisseur dont c’est le métier. Une graine issue de Math.random() est un désastre qui attend sa date.

Gardez les clés de signature dans un stockage non exportable. La NIST SP 800-63C indique que les implémentations de portefeuille devraient utiliser un stockage de clés non exportable. Pour tout ce que vous exploitez vous-même, cela mène à un HSM ou à un élément sécurisé comparable, pas à des variables d’environnement ni à une colonne de base de données.

Protégez aussi le côté humain de l’accès. Des clés de sécurité matérielles pour les comptes d’administration qui peuvent créer des clés API, modifier des URL de webhook ou valider des versements écartent une large catégorie de risques d’hameçonnage. Séparez les rôles, pour que la personne qui déploie le code ne puisse pas aussi débloquer des fonds.

Pour l’hygiène quotidienne de l’API, notre propre liste de conseils de sécurité pour utiliser une API blockchain est un bon complément.

Comment détecter les paiements avec des webhooks ?

Créer l’adresse n’est que la moitié du travail. Vous devez aussi savoir quand quelqu’un la paie. Interroger chaque adresse à intervalles réguliers gaspille des requêtes et retarde la confirmation. Les webhooks vous envoient l’événement dès que le fournisseur le voit. Nous détaillons un flux complet dans comment traiter automatiquement les dépôts avec des webhooks.

C’est dans le point de réception que se produisent les erreurs de sécurité : construisez-le avec soin. La fiche pratique OWASP sur la sécurité des webhooks est la référence à suivre. En voici les points principaux :

  • Vérifiez la signature de chaque livraison. Recalculez le HMAC sur le corps brut avec votre secret partagé et comparez-le à l’en-tête de signature. Utilisez une comparaison à temps constant pour éviter les attaques par mesure du temps.
  • Exigez HTTPS. Une signature prouve qui a envoyé le message, mais ne le chiffre pas : toute personne sur le chemin réseau peut lire une livraison en HTTP simple.
  • Gardez les secrets hors de l’URL. Les URL se retrouvent dans des journaux de répartiteurs de charge et de proxys que vous ne contrôlez peut-être pas. Placez l’authentification dans les en-têtes.
  • Traitez les événements de façon idempotente. Les livraisons peuvent se répéter après des nouvelles tentatives réseau. Un même paiement ne doit jamais être crédité deux fois.

Ce dernier point mérite un schéma concret. Stockez le hachage de transaction comme clé unique et indexée. Le conseil de rapprochement du guide Bitcoin, qui convient à toutes les chaînes, est de chercher dans votre base de données un hachage existant avant toute logique de crédit, au lieu de supposer que chaque rappel arrive exactement une fois. En SQL, cela donne une contrainte d’unicité sur le hachage et une insertion qui ignore les doublons.

Un gestionnaire fiable suit cet ordre :

  1. Lire le corps brut de la requête avant tout traitement.
  2. Vérifier la signature HMAC. Rejeter en cas de différence.
  3. Insérer le hachage de transaction. S’il existe déjà, renvoyer un succès et s’arrêter.
  4. Attendre le nombre de confirmations exigé par votre politique de risque avant de créditer les fonds.
  5. Créditer le compte dans la même transaction de base de données que l’insertion.
  6. Répondre vite avec un code de succès, et confier le travail lent à une file d’attente.

Notre page sur les webhooks blockchain et notifications d’événements montre comment cela fonctionne sur les réseaux pris en charge.

Qu’est-ce qui change si je prends en charge plusieurs chaînes ?

Un portefeuille qui fonctionne sur une seule chaîne est facile. Sur plusieurs chaînes, le coût d’intégration grimpe, car chaque réseau a son propre format d’adresse, son propre modèle de frais et ses propres standards de jetons.

  • Frais. Sur les chaînes EVM, un transfert de jeton exige la monnaie native pour le gaz. Une adresse fraîchement créée qui reçoit des USDT ne peut pas les envoyer tant qu’elle ne détient pas aussi la monnaie native de la chaîne pour les frais, comme l’ETH sur Ethereum ou le BNB sur BNB Smart Chain. Prévoyez une étape d’approvisionnement pour les versements et les regroupements.
  • Nouveaux comptes Tron et ressources. Selon le modèle de ressources de TRON, une transaction qui crée un nouveau compte brûle 0,1 TRX si la bande passante stakée ne la couvre pas. Les transferts TRC-20 consomment aussi de l’énergie. Testez ce cas tôt.
  • Standards de jetons. ERC-20, BEP-20 et TRC-20 se ressemblent pour les utilisateurs, mais diffèrent par les appels de contrat et les formats d’événements. Les NFT ajoutent ERC-721 par-dessus.
  • Données décodées. Les journaux bruts de transaction sont en hexadécimal. Si votre fournisseur renvoie des valeurs décodées, vous évitez d’écrire l’analyse ABI pour chaque jeton.

Nous expliquons la différence entre fournisseurs de nœuds, indexeurs et API unifiées dans Blockchain APIs Compared: 6 Types and When to Use Each, et les cas d’usage plus larges dans les cas d’usage d’une API blockchain.

Notre point de vue

Nous observons le même schéma chez la plupart des équipes qui viennent nous voir. Elles sous-estiment la plomberie et surestiment la cryptographie. Générer une clé est un problème résolu. Ce qui fait échouer les projets, c’est un mois passé sur la synchronisation des nœuds, les particularités de frais d’une chaîne, un gestionnaire de webhook qui crédite deux fois un dépôt, ou un montant décodé faux d’un facteur dix à cause des décimales du jeton.

C’est pourquoi nous avons construit Chaingateway comme une seule API REST pour plusieurs réseaux, plutôt qu’une intégration par chaîne. Vous créez des adresses, envoyez des transferts de jetons et lisez des transactions décodées avec le même style de requête sur chaque réseau. Les notifications webhook sont signées en HMAC et informent votre backend des paiements : vous n’avez donc pas besoin d’exploiter vos propres nœuds ni de faire du polling.

Notre conseil est simple. Décidez d’abord de la garde. Donnez à chaque payeur sa propre adresse. Rendez votre gestionnaire de webhook idempotent dès le premier jour, pas après le premier crédit en double. Et testez toute la boucle sur un testnet avant qu’une seule vraie pièce ne bouge.

Liste de contrôle avant le lancement

Avant la mise en production, confirmez chaque point :

  • Les identifiants API sont dans un gestionnaire de secrets et peuvent être renouvelés.
  • Chaque adresse est stockée avec son réseau, son propriétaire et sa date de création.
  • Votre point d’accès webhook utilise HTTPS, vérifie les signatures et les compare en temps constant.
  • Une contrainte d’unicité sur le hachage de transaction empêche les crédits en double.
  • Vous attendez un seuil de confirmations adapté au montant en jeu.
  • Les portefeuilles de versement sont approvisionnés avec la monnaie native nécessaire aux frais.
  • Les comptes d’administration utilisent une authentification multifacteur solide, idéalement avec des clés matérielles.
  • Vous avez noté par écrit qui peut valider les versements et comment révoquer une clé compromise.
  • Vous avez pris un avis juridique sur la garde si vous détenez des fonds pour d’autres.
