Envoyer des tokens ERC-20 : portefeuille, code et API

Envoyez des tokens ERC-20 depuis un portefeuille, avec ethers.js ou via une API REST : gas, décimales, risques liés au contrat et transferts sûrs.

Chapitres
C
Chaingateway Team
Experts blockchain

Relu par Maurice Sobiera

Envoyer un token ERC-20 revient à appeler la fonction transfer du contrat intelligent du token. Vous pouvez le faire depuis un portefeuille, depuis votre code avec une bibliothèque comme ethers.js, ou via une API REST. L’expéditeur paie les frais de réseau en ETH, pas en tokens. Ce guide couvre chaque méthode et les erreurs qui font perdre des fonds.

TL;DR

  • Un transfert ERC-20 est un appel au contrat du token, et non un transfert de valeur simple comme l’ETH. L’adresse du destinataire et le montant sont placés dans les données d’appel.
  • Le portefeuille expéditeur a besoin d’ETH pour le gas, même s’il détient beaucoup de tokens. Sans ETH, la transaction échoue.
  • N’envoyez jamais de tokens directement vers un contrat qui n’a pas de code pour les gérer. Utilisez approve et transferFrom pour les interactions avec des contrats.
  • Dans le code, gérez les décimales des tokens et les tokens qui ne renvoient pas de booléen standard. Encapsulez les appels avec une bibliothèque sûre.
  • Si vous développez une application qui envoie des tokens pour ses utilisateurs, une API REST supprime le travail lié au nœud, au nonce et au gas. Nous le détaillons plus bas.

Ce qui se passe quand vous envoyez un token ERC-20 ?

Envoyer de l’ETH transfère une valeur native entre deux comptes. Envoyer un token ERC-20 modifie un registre de soldes stocké dans le contrat du token. Votre portefeuille crée une transaction adressée au contrat du token, et ce contrat met à jour les soldes de l’expéditeur et du destinataire.

Le standard ERC-20 définit les méthodes que chaque token conforme expose : totalSupply, balanceOf, transfer, transferFrom, approve et allowance. Cette interface commune permet à un même portefeuille ou à un même code de gérer des milliers de tokens différents. La spécification d’origine est EIP-20, publiée en novembre 2015.

Cette conception a plusieurs conséquences :

  • Le champ to de la transaction est le contrat du token, et non la personne que vous payez. Le véritable destinataire est encodé dans les données d’appel.
  • Les données d’appel commencent par le sélecteur de fonction 0xa9059cbb, c’est-à-dire les quatre premiers octets du hash de la signature transfer(address,uint256). L’adresse du destinataire et le montant suivent, encodés comme le décrit la spécification ABI de Solidity.
  • ERC-20 est un standard de token, et non Ethereum lui-même. L’ETH est la monnaie native du réseau. Des tokens comme l’USDT sont des contrats qui fonctionnent dessus. Pour une vue d’ensemble du gas et de l’ETH, voir notre présentation d’Ethereum.

Le même format existe aussi sur d’autres chaînes EVM. Notre article sur le standard de token ERC20 détaille son fonctionnement, et le guide des adresses ERC20 explique le format des adresses et la consultation des soldes.

Que vérifier avant d’envoyer ?

La plupart des transferts perdus viennent d’une préparation omise, et non d’une panne technique. Vérifiez d’abord les points suivants.

  1. Vous détenez le token et le montant voulu. Confirmez le solde avec balanceOf ou dans votre portefeuille.
  2. Vous détenez de l’ETH pour le gas. Les frais sont payés dans la monnaie native du réseau, et non déduits des tokens envoyés. Sur Polygon ou BNB Chain, la même logique s’applique avec la monnaie native de cette chaîne. Un portefeuille qui détient des tokens mais pas d’ETH ne peut rien envoyer.
  3. Vous avez l’adresse exacte du destinataire. Copiez-la et collez-la plutôt que de la taper. Le centre d’aide de MetaMask met en garde contre l’empoisonnement d’adresses, où un attaquant injecte dans votre historique une adresse ressemblante.
  4. Vous connaissez le réseau. Le même format d’adresse fonctionne sur plusieurs chaînes EVM. Un token envoyé sur le mauvais réseau n’arrive pas là où le destinataire l’attend.
  5. Le destinataire peut le recevoir. Envoyer vers une adresse de dépôt d’un échange sur le mauvais réseau, ou vers un contrat qui ne sait pas gérer les tokens, peut entraîner une perte définitive.
  6. Vous testez d’abord avec un petit montant. Pour un nouveau destinataire ou une nouvelle intégration, envoyez un petit montant et confirmez son arrivée avant d’envoyer la somme complète.

Méthode 1 : envoyer depuis un portefeuille

Pour des transferts ponctuels, un portefeuille est la voie la plus simple. Le guide Etherscan sur l’envoi d’ETH ou de tokens décrit le même parcours que suivent la plupart des portefeuilles :

  1. Ouvrez le portefeuille et choisissez l’option d’envoi.
  2. Sélectionnez le token à envoyer. S’il n’apparaît pas dans la liste, ajoutez-le en collant l’adresse du contrat du token.
  3. Collez l’adresse du destinataire.
  4. Saisissez le montant.
  5. Vérifiez les frais de réseau. Le portefeuille les estime pour vous.
  6. Confirmez, puis suivez le hash de la transaction sur un explorateur de blocs jusqu’à sa confirmation.

Deux détails posent souvent problème. D’abord, l’adresse du contrat que vous collez pour ajouter un token personnalisé doit être la bonne, car des faux tokens utilisent le même nom et le même symbole. Vérifiez-la sur le site officiel du projet. Ensuite, les frais affichés sont en ETH : le solde ETH du portefeuille doit donc couvrir ces frais en plus de l’ETH que vous voulez envoyer.

Méthode 2 : envoyer avec du code (ethers.js)

Les développeurs qui doivent automatiser les transferts peuvent appeler directement le contrat. Le tutoriel ethereum.org sur l’envoi de tokens avec ethers.js présente le schéma de base. Un pas-à-pas ethers.js distinct explique la différence essentielle avec l’ETH : la transaction ne transfère aucune valeur, elle appelle la fonction transfer du token avec une destination et un montant.

Les étapes sont les suivantes :

  1. Créez un provider connecté à un nœud Ethereum, le vôtre ou un point d’accès hébergé.
  2. Créez un signataire à partir d’une clé privée ou d’un portefeuille que vous contrôlez.
  3. Instanciez le contrat du token avec son adresse et une ABI minimale contenant transfer, balanceOf et decimals.
  4. Convertissez le montant lisible en unités de base à l’aide des décimales du token.
  5. Appelez transfer(recipient, amount) et attendez le reçu.

Le tutoriel ethers.js indique que la bibliothèque peut envoyer une transaction EIP-1559 sans réglage manuel du gas, en choisissant une limite de gas et des frais de priorité par défaut. Elle gère aussi le nonce lorsque vous utilisez un signataire.

Bien gérer les décimales

Les tokens stockent les montants sous forme d’entiers. Un token à 18 décimales représente 1,0 token par 1000000000000000000 unités de base. Le champ decimals fait partie du standard, mais différents tokens le fixent à des valeurs différentes, et le texte de l’EIP-20 le traite comme une métadonnée facultative. Lisez toujours decimals depuis le contrat au lieu de supposer 18. Une valeur codée en dur et fausse envoie un montant décalé de plusieurs ordres de grandeur.

Ne faites pas confiance aveuglément à la valeur de retour

Le standard indique que transfer renvoie un booléen. Tous les tokens en circulation ne se comportent pas ainsi. Certains ne renvoient rien, et d’autres échouent de façon inattendue. L’interface IERC20 d’OpenZeppelin sert de référence au standard, et la bibliothèque SafeERC20 d’OpenZeppelin encapsule les appels pour que les tokens atypiques ne cassent pas votre logique. Si votre smart contract déplace des tokens, utilisez-la. Si votre backend envoie des tokens, vérifiez le statut du reçu de transaction et l’événement Transfer émis, au lieu de supposer que tout a réussi.

Limites de gas

Un transfert d’ETH simple utilise une limite de gas de 21 000, selon les recommandations de MetaMask. Un transfert de token est un appel de contrat : il en demande davantage. Estimez le gas avec la fonction d’estimation de votre bibliothèque avant chaque envoi, au lieu de coder une valeur en dur, car le coût dépend du code du contrat du token et de l’état des soldes concernés.

Méthode 3 : envoyer via une API REST

Exécuter le code décrit plus haut convient à un script. Dans un produit, cela devient une liste de tâches : exploiter ou louer un accès à un nœud, gérer les clés, suivre les nonces pour que les envois simultanés n’entrent pas en collision, estimer le gas, relancer les transactions bloquées, décoder les logs pour savoir si un paiement est arrivé, et refaire tout cela pour chaque chaîne.

Comment les transferts ERC-20 tournent-ils mal ?

Envoyer des tokens vers un contrat

La fonction transfer n’a pas été conçue pour déposer des tokens dans des smart contracts. Si un contrat n’a aucune logique pour réagir aux tokens reçus, ceux-ci restent dans son solde sans moyen d’en sortir. La page ERC-20 de ethereum.org décrit ce risque, y compris pour les tokens envoyés au contrat du token lui-même. Elle indique qu’au moins 83,7 millions de dollars de tokens ERC-20 ont été perdus de cette façon au 20 juin 2024. Si vous écrivez des contrats, ajoutez une fonction qui permet de récupérer les tokens envoyés par erreur. Si un contrat doit recevoir des tokens d’un utilisateur, le schéma standard est le suivant : l’utilisateur appelle approve pour le contrat, puis le contrat appelle transferFrom.

Zéro ETH pour le gas

La transaction échoue si l’expéditeur n’a pas de monnaie native, quel que soit le nombre de tokens dans le portefeuille. Les équipes produit s’en aperçoivent souvent tard : un utilisateur reçoit des tokens, essaie de les déplacer, et n’y parvient pas. Les options sont de recharger le portefeuille avec un peu d’ETH, ou de concevoir le flux autour de cette contrainte avec des autorisations signées.

Mauvais réseau ou mauvaise adresse

Les blockchains n’annulent pas les transactions. Vérifiez le réseau et l’adresse avant de confirmer, et faites un petit test pour tout ce qui est nouveau.

Confondre le token avec le réseau

L’USDT, par exemple, existe sur plusieurs chaînes. Quand quelqu’un dit détenir de l’USDT, demandez sur quel réseau. L’adresse peut sembler identique sur chacun, mais les fonds ne vivent que sur une seule chaîne.

Puis-je envoyer des tokens sans détenir d’ETH ?

Une option qui gagne du terrain pour l’onboarding consiste à laisser l’utilisateur signer un message, puis à faire soumettre la transaction par un tiers qui paie le gas. EIP-3009, Transfer With Authorization, définit des fonctions qui permettent à un détenteur de déléguer le paiement du gas, et d’exécuter des transferts via des signatures EIP-712. Seuls les tokens dont les contrats implémentent ce standard prennent en charge cette approche : vérifiez-le avant de concevoir un flux autour. Pour une startup, cela peut supprimer l’obstacle du premier transfert, c’est-à-dire l’acquisition d’ETH.

Pourquoi traiter un transfert comme un flux de travail ?

L’appel transfer lui-même demande une après-midi d’écriture. Le temps part dans tout ce qui l’entoure : savoir quand un paiement est arrivé, gérer une transaction échouée ou bloquée, estimer les frais et protéger les clés. Un flux de paiement sans événements de confirmation oblige à interroger la chaîne en boucle. Un flux de dépôt sans données décodées oblige à analyser des logs bruts.

Commencez par un petit transfert sur un réseau de test, vérifiez les décimales et les reçus, abonnez-vous aux événements pour la confirmation, et ne montez en volume qu’ensuite.

Puis-je automatiser les transferts avec Chaingateway ?

Oui. Pour les paiements, retraits ou dépôts dans une application, utilisez l’API blockchain avec des webhooks qui vous préviennent lorsque les paiements arrivent. Les webhooks ne sont pas relancés automatiquement : listez les notifications échouées avec GET /api/v2/ethereum/webhooks/notifications/failed et renvoyez-les avec l’endpoint de relance. Comment vérifier que le transfert a fonctionné ?

Soumettre une transaction n’équivaut pas à finaliser un paiement. Après l’envoi :

  1. Enregistrez immédiatement le hash de la transaction.
  2. Vérifiez le statut du reçu. Une transaction minée peut quand même avoir échoué.
  3. Recherchez l’événement Transfer émis par le contrat du token, avec l’expéditeur, le destinataire et le montant attendus. Cet événement fait partie de l’interface ERC-20.
  4. Attendez autant de confirmations que votre politique de risque l’exige avant de livrer des biens ou de créditer un solde.
  5. Réconciliez régulièrement avec balanceOf pour détecter ce que votre écouteur aurait manqué.

L’interrogation convient à un petit script. En production, s’abonner aux notifications signifie que votre système réagit aux événements au lieu de les demander sans cesse.
