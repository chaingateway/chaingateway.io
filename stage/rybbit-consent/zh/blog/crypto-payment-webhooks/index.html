加密货币支付 Webhook：工作原理与构建指南

了解加密货币支付 Webhook 如何检测存款、如何验证签名、处理重试与重复请求，以及在上线前如何测试您的端点。

加密货币支付 Webhook 是区块链服务在链上发生事件（如存款到达客户钱包）的那一刻发送到您服务器的 HTTP 请求。您无需每隔几秒询问网络支付是否到账，而是向提供商提供一个 URL，由它来调用您。要在生产环境中运行此功能，您需要四样东西：公开端点、签名验证、重复事件的幂等处理，以及针对错过投递的备选方案。本指南涵盖了每一项。

TL;DR

  • 当支付或钱包事件发生时，Webhook 会将事件推送到您的服务器，因此您可以跳过持续轮询及其给系统带来的负载。
  • 在信任请求中的任何字段之前，请使用签名头和原始请求体验证每个请求。
  • 快速返回 2xx 响应，然后在后台作业中执行实际工作。
  • 将每个事件视为可能重复：存储事件 ID 并使您的订单更新具有幂等性。
  • 为待处理支付保留一个缓慢的对账作业，以便错过的投递永远不会导致订单卡住。

什么是加密货币支付 Webhook

Webhook 是一种回调。您注册一个 URL，告诉提供商您关心哪些事件，当事件发生时，提供商会发送一个包含描述该事件的 JSON 正文的 POST 请求。对于加密货币支付，这些事件通常包括监控地址的传入转账、您发起的传出转账、合约上的代币转账，或已见交易的确认数更新。

替代方案是轮询。您的服务器按定时器调用 API 并将结果与上次看到的内容进行比较。轮询编写简单但运行浪费。每个未返回新数据的请求都会消耗您的速率限制、算力和延迟，而支付与您反应之间的延迟等同于您的轮询间隔。随着多条链和数千个客户地址，调用次数会迅速增加。

Webhook 反转了方向。提供商监视链，将交易与您订阅的地址匹配，并仅通知您一次。反应时间降至秒级，您自己的基础设施在有事可做前保持空闲。如果您想了解应用于存款的此模型的更详细论证，我们在 Webhook 如何自动处理存款 中进行了阐述。

Webhook 与轮询一览

标准轮询Webhook
谁发起交互您的服务器提供商
响应时间取决于您的间隔，最慢接近实时
浪费的请求大部分无
成本随什么增长地址数量 × 频率实际事件数量
故障模式检测延迟错过或重复投递
最佳用途对账和安全网主要信号

最后一行给出了实用的答案。Webhook 应作为主要信号，而轮询应作为缓慢的后备手段，仅检查仍处于待处理状态的付款。运营加密货币结账的开发者常描述这种搭配：Webhook 优先，并定期检查待处理发票以捕获从未到达的事件，正如这篇 Node.js 轮询与 Webhook 对比演示 所示。

Webhook 如何检测加密货币付款

提供商端是您不可见的部分，但理解它能解释您在测试中遇到的大多数行为。

  1. 订阅。 您创建钱包或注册地址，然后通过提供商的 API 将其订阅到事件。订阅包含您的回调 URL 和事件类型。
  2. 监控。 提供商为每条支持的链运行节点并读取每个新区块。每笔交易都会与订阅地址匹配，对于代币，还会与合约转账日志匹配。
  3. 解码。 原始链上数据不友好。以太坊上的代币转账是编码的日志条目，比特币则有输入和输出而非发送方和接收方。优秀的提供商将其解码为包含金额、资产、发送方、接收方和交易哈希的可读载荷。
  4. 投递。 提供商对载荷签名并发送到您的 URL。若您的服务器未返回成功代码，将按计划重试。

这就是为什么当载荷被标准化时，链的差异比您预期的要小。Chaingateway 通过一个 REST API 覆盖 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Chain 和 Arbitrum，提供预解码数据，因此您的处理程序无论付款来自哪个网络都能读取相同字段。支持 ERC-20、BEP-20 和 TRC-20 等代币标准，这很重要，因为大多数实际支付都是稳定币转账而非原生币。

值得订阅的事件

从窄处着手。大多数支付流程仅需几个事件：

  • 传入转账至客户存款地址。 这是记账或标记发票已付的核心事件。
  • 传出转账状态。 当您发起付款或归集资金时，您想知道何时广播、何时确认。
  • 确认数变化。 交易可能在区块中被看到很久，但您自己的规则决定何时视为最终。
  • 代币和 NFT 转账。 适用于发行自有代币或销售数字物品的应用。

设置和处理 Webhook 端点

端点是您服务器上一个普通的 HTTPS 路由。演示与生产处理程序的区别在于几个习惯。

端点要求

URL 必须可通过公共互联网经 HTTPS 访问。本地地址和私有网络无法接收调用，因此在开发期间你需要一个隧道来暴露本地端口。保持路由专用于 Webhook，仅接受 POST 请求，且不要将其置于登录界面或会拒绝机器请求的 CSRF 中间件之后。

处理程序应快速响应。通用指导原则正如 OpenAI 的 Webhook 文档所明确指出的：使用公共 URL、验证签名、快速返回 2xx 响应并将繁重工作交给后台工作进程。同样的规则适用于加密货币事件。如果你在回答之前更新数据库、发送邮件并调用会计系统，缓慢的下游服务会让提供方认为投递失败并再次发送事件。关于生产系统对端点的期望，这篇关于业务系统中的事件驱动集成的文章从 ERP 角度阐述了相同的即时响应原则。

可靠的模式如下：

  1. 以字节形式读取原始请求体。
  2. 验证签名。
  3. 将事件及其 ID 写入队列或事件表。
  4. 返回 200。
  5. 让工作进程处理队列中的事件。

验证签名

任何找到你 URL 的人都可以向其发送 JSON。如果你的处理程序因为请求称存款到账而给账户记账，伪造的请求就是盗窃。签名验证关闭了这扇门。

典型方案是 HMAC。提供方使用仅你和它知道的密钥对载荷计算哈希，并将结果放在请求头中发送。你重新计算哈希并比较。有三个细节容易让人掉坑：

  • 使用原始字节。 如果你解析 JSON 并重新序列化，空白字符和键的顺序可能发生变化，导致哈希不匹配。OpenAI 的文档指出验证使用原始请求字节，任何 HMAC 方案均适用此原则。
  • 以常量时间比较。 使用语言提供的安全比较函数，而非普通的相等性检查。
  • 在提供时间戳时检查它。 拒绝旧时间戳可限制被捕获请求的重放攻击。

Chaingateway 使用 HMAC 对请求签名，我们在产品演进过程中撰写了关于增强 Webhook 安全性的文章。将密钥存储在环境变量或密钥管理器中，切勿存入代码库，若其曾出现在日志中请轮换密钥。

处理重试、重复与缓慢确认

网络故障、部署重启服务器、提供方重试。结果是你的处理程序最终会看到相同事件两次，有时事件还会乱序。从一开始就为这种情况设计。

使处理幂等

每个事件都携带标识它的信息，通常是事件 ID，或交易哈希与输出索引或日志索引的组合。在采取行动前，用唯一约束保存该标识符。若插入因键已存在而失败，说明你已见过该事件，可直接返回 200 而不做任何处理。

然后让业务动作本身也能安全地重复执行。“将发票 1042 标记为已支付，交易为 X” 是幂等的。“给余额增加 50” 则不是。优先采用第一种形式，或者在单个数据库事务中将余额变更与唯一事件记录绑定。

尊重确认深度

交易出现在区块中，并不等同于可以据此发货的支付确认。不同链的区块变得难以回滚所需的速度不同，合适的阈值取决于金额和资产。按链和按订单大小制定策略，并记录每笔支付的状态：已检测、确认中、已确认、失败。宣布检测到支付的 Webhook 应将订单移至“已见支付”状态，而非“已履行”。

欠付、超付与错误代币

客户发送错误金额的情况比预期的要频繁得多。处理程序应将收到的金额和资产与发票进行比对，并分支处理：完全匹配、金额不足、金额超额、或意外的代币。提前决定是自动记账差额、挂起人工审核、还是退款。包含独立的资产和金额字段的解码载荷，能让这种比对只需几行代码，而非繁琐的解析工作。

保留安全网

即使有重试机制，投递失败的时间也可能长到提供商放弃。运行一个定时任务，每隔几分钟检查那些超过合理时间仍处于待定状态的发票，并通过 API 查询其地址余额或交易历史。当它发现 Webhook 从未上报的支付时，将其送入相同的处理流程。双源单一代码路径，意味着只有一套 Bug。

测试、监控与故障排查

分层建立信心。

本地测试。 编写一个小脚本，用测试密钥对示例载荷签名并发送到你的端点。确认有效签名能通过，篡改过的请求体会失败，过期的时间戳会失败（如适用）。

测试网实测。 在测试网创建钱包，订阅它，并从水龙头发送一笔小额转账。你将看到真实的事件序列，包括检测到确认之间的延迟，这是任何示例载荷都无法教会你的。

重复演练。 连续发送五次相同的有效事件。你的发票应仅变更一次，日志应显示四次跳过的重复项。

故障演练。 故意让处理程序返回 500，然后恢复它。检查提供商的重试是否到达并被仅处理了一次。

上线后，记录每一个传入的事件 ID、验证结果、处理结果和耗时。针对三件事设置告警：签名失败（密钥配置错误或遭受攻击）、队列积压（工作进程跟不上）、发票待定时间远超正常（静默投递问题）。

我们为何将 Webhook 构建进统一 API

大多数找到我们的团队都已经尝试过 DIY 路线：每条链一个节点、一个区块扫描器、针对每种代币标准的解码器，外加一个队列把它们粘在一起。这套方案在第二、三条链之前还能跑通，之后每条链都会带来自己的怪癖和自己的值班传呼机。

我们设计 Chaingateway 的初衷是让开发者能够创建钱包、订阅其事件，并接收已签名、预解码的通知，而无需运行上述任何基础设施。我们的目标是让 Tron 上 USDT 存款的载荷对只处理过 Ethereum 的人来说也显得熟悉，且在向外发送资金时费用估算是自动完成的。

我们相信 Webhook 是支付场景下的正确主信号，并围绕这一信念构建产品：HMAC 签名请求、一套覆盖 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Chain 和 Arbitrum 的 REST API，以及无需编写解码器即可直接使用的事件数据。

常见问题

使用 Webhook 后我还需要轮询吗？

需要，但只需轻量级轮询。将 Webhook 作为主信号，并定期检查仍处于待处理状态的支付，以免未送达的通知导致订单卡住。检查发现的任何支付都应推送至与 Webhook 事件相同的处理代码中。

如何确认 Webhook 真的是来自我的服务商？

使用共享密钥对原始请求体验证签名头，拒绝验证失败或携带过期时间戳的请求。切勿信任未签名请求的内容，即使其 URL 是保密的。

我的端点应返回什么？

在验证并存储事件后尽快返回 2xx 状态码。将发送邮件、账本更新、第三方调用等耗时操作放入后台 Worker 处理。缓慢或失败的响应会招致重试和重复投递。

一套 Webhook 配置能覆盖多条区块链吗？

如果服务商对数据进行了标准化，则可以。通过统一 API（如覆盖 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Chain 和 Arbitrum 的 Chaingateway），一个处理器即可处理所有链的事件，并在您自己的逻辑中应用各链的确认规则。
