实时加密货币提醒：价格提醒与 Webhook 交易提醒

实时加密货币提醒分为两类：面向交易者的价格通知，以及面向应用的 Webhook 事件。文章说明您需要哪一类，如何构建后者，包括签名校验、时间戳、幂等处理，以及避免重复入账的做法，并列出选择提醒方案时应比较的链覆盖、载荷质量、安全模型和运维负担。

实时加密货币提醒是关于加密货币活动的通知，分为两类。价格提醒会在某种资产突破某一价位时告知用户。交易提醒通过 Webhook 送达，会在充值到账的那一刻告知您的服务器。本指南两者都会介绍，然后深入讲解后者：事件驱动的提醒如何工作、需要校验什么，以及如何避免重复入账。

TL;DR

  • 价格提醒面向关注市场的人。它只是信息性的，提示用户去看屏幕。
  • 交易提醒面向软件。Webhook 把事件推送到您的后端，使其可以为账户入账、解锁订单或标记转账，无需人工介入。
  • 已签名的 Webhook 能证明发送方的身份，但不能证明它是新的。您还需要时间戳、事件 ID 和幂等处理。
  • 把每条提醒都视为提示，并在转移资金或发货之前，通过 API 读取来确认当前状态。
  • Chaingateway 通过一个 REST API，在 Ethereum、Bitcoin、Tron、Polygon、BNB Chain 和 Arbitrum 上提供经 HMAC 签名的 Webhook。Solana 没有 Webhook。

什么是实时加密货币提醒？

这个词会被两类截然不同的读者使用，因此它有两种含义。

第一类是交易者或持有者。当某种资产达到某一价位时，他们希望收到推送、邮件或短信。大多数交易所应用都提供这一功能。提醒与自选列表和预设的价格触发条件相关，通过推送、应用内消息或邮件送达。它告知的是人，不会触发任何自动化操作。

第二类读者是开发者或产品负责人。他们的问题不同：“我的应用如何在几秒钟内得知，有 150 USDT 刚刚到达我为这位客户生成的地址？”没有任何价格应用能回答这个问题。答案是一条区块链事件流，它会向您控制的端点发送消息。

如果您属于第一类，请在您已经使用的应用中设置一个阈值，然后就可以不必再读下去了。如果您属于第二类，本文其余部分正是为您准备的。

最后两行说明了为什么第二类值得认真的工程投入。错过价格提醒只是错失机会，处理失当的付款提醒则会造成资金损失。

事件驱动的加密货币提醒如何工作？

其机制描述起来很简单，自己运行却相当繁琐。

  1. **您注册一个或一组地址。**通常为每位客户或每笔订单生成一个充值地址。
  2. **提供商监视区块链。**必须有人读取新区块，找出涉及您地址的转账，并加以解析。
  3. **提供商解码事件。**原始交易只是字节。EVM 链上的代币转账是一条合约日志，需要被解析为发送方、接收方、代币和金额。解码后的数据让您无需为每条链维护 ABI 和解析器。
  4. **提供商向您的端点发送 POST。**您的服务器会收到描述该事件的 JSON。
  5. 您的代码校验、去重并采取行动。

第 2 和第 3 步正是自建成本高昂之处。您要么为每条支持的链运行节点，要么订阅节点级的数据流并自行编写解码逻辑。在以太坊上，草案 EIP-8072 提议对 eth_subscribe 进行扩展，使客户端在交易被打包进区块时收到通知。但这只适用于一条链。比特币的 UTXO 模型、Tron 的资源体系和 Solana 的账户模型，各自的行为都不相同。

若您想了解各种选项的全貌，我们的文章六类区块链 API 及各自的适用场景说明了节点访问、索引数据和事件通知各自适用的情形。

实际示例：确认一笔充值

假设一个结账页面接受某种稳定币。客户看到一个地址和一个金额。以下是一套稳健的集成所遵循的流程。

  1. 您的后端为订单创建一个钱包地址，并把预期金额、代币和链与订单号一起存储。
  2. 客户发送资金。
  3. 您的 Webhook 端点收到针对该地址的事件。
  4. 您的处理程序先校验签名；若提供商对时间戳签名，则再校验其新鲜度；然后检查您是否已经处理过该事件，例如依据交易 ID。
  5. 它查找订单，将代币、链和金额与预期比较，并从提供商的 API 读取权威的交易状态。
  6. 在一次数据库事务中，把订单标记为已付款，并记录事件 ID。
  7. 它迅速返回 2xx 响应，并把耗时的工作（例如发送邮件）放入队列中执行。

上述列表中没有什么特别的内容。每一步都是为了防范某种具体的失败方式而存在的，下文会逐一说明。关于充值场景的更深入讲解，请参阅我们关于使用 Webhook 自动处理充值的文章。

已签名的 Webhook 能证明什么？

已签名的 Webhook 证明发送方掌握共享密钥，且负载未被更改。许多团队到此为止，认为“请求带有 HMAC 签名，所以是安全的”。签名是必要的，但并不充分。

HMAC 签名可以让您确认负载来自掌握共享密钥的人，并且在传输过程中未被篡改。但它无法告诉您这条消息是否新鲜。攻击者，或者仅仅是一个不断重试的网络，都可能把同一条有效消息发送两次。OWASP Webhook 安全备忘单直接指出了这一点：校验签名并不能阻止重放，因此应将其与经过认证的时间戳和事件 ID 配合使用，并以幂等方式处理事件，使重试不会产生副作用，例如重复付款。

在实践中，这意味着：

  • **在解析之前，对原始请求体校验签名。**使用恒定时间比较。
  • **若提供商对时间戳签名，则拒绝过期的时间戳。**选定一个容忍窗口，丢弃超出窗口的内容。
  • **存储事件 ID。**对 Chaingateway 而言，自然的键是交易 ID。若您已经见过它，就直接返回成功，不做任何操作。
  • **让处理程序具备幂等性。**为账户入账应当是可以安全地运行两次的操作。

在您设置个人密钥之后，Chaingateway 会以 X-Signature 请求头为 Webhook 签名。根据我们的 Webhook 安全指南，该签名是由交易 ID 和该密钥构成的 HMAC。它不包含时间戳，因此上面的新鲜度检查并不适用于它。请改为按交易 ID 去重，并结合接收地址和代币进行判断；相关功能背景见我们关于 Webhook 安全的文章。无论您使用哪家提供商，这些检查都应在您这一侧完成。

假设事件会延迟、重复或乱序到达

许多 Webhook 提供商采用至少一次投递：如果您这一侧超时，发布方就会重试，因此一笔转账可能产生两次投递。Chaingateway 不会自动重试失败的 Webhook。失败的通知会列在 /webhooks/notifications/failed 下，并在您请求时重新发送，因此手动重试之后仍可能出现重复。关于同一笔付款的两个事件，也可能以错误的顺序到达。

OWASP 的指导是假设投递可能乱序，不要依据到达顺序来决定状态转换。收到通知时，应从提供商的 API 获取对象的当前状态，而不是只信任负载。同一份备忘单建议把传入的 Webhook 视为不可信数据，依据您自己的记录进行校验，并把履约操作包裹在原子数据库事务中（例如使用行锁），以防止竞态条件。

OWASP 第三方支付网关集成备忘单得出了相同的结论：在履约订单之前，通过网关的 API 在服务器端核实付款状态，并比对预期的金额、币种和订单号。对于加密货币，还应把链和代币合约加入这份清单。一笔恰好带有相同代号的错误代币转账，是让订单被错误标记为已付款的典型方式。

观点：提醒是输入，而不是结论

我们为将加密支付纳入产品的开发者构建服务，所见到的模式始终如一：团队把提醒当成答案。我们认为它其实是问题。Webhook 说的是“这个地址上发生了某件事”。您的系统仍须判断这件事是否与某个订单相符，金额和代币是否正确，以及它是否已经被计入。

这就是为什么我们专注于那些能减少繁琐工作、同时又不剥夺您控制权的部分。预先解码的数据意味着您的处理程序读取的是发送方、接收方、代币和金额，而不必解析日志。跨多个网络的统一 API 意味着您处理以太坊充值的程序，与处理 Tron 充值的程序看起来相似。经过 HMAC 签名的 Webhook 则为您叠加自己的幂等性检查提供了基础。

我们不会承诺仅凭 Webhook 就能让支付系统变得安全。它做不到，任何暗示能做到的提供商都是在回避难点。应先构建校验循环，再扩大规模。

消费级提醒在产品场景中的不足

人们很容易用手边的任何提醒工具来做原型：价格机器人、把消息推送到聊天频道的钱包追踪服务、移动应用。对于演示而言，这些工具可以胜任。但对于产品来说，它们会以可预见的方式失效。

  • **没有可编程的契约。**聊天消息不是 API。您无法可靠地解析、重试或认证它。
  • **是自选列表逻辑，而非账户逻辑。**消费级工具追踪的是您手动添加的资产或公开地址，而不是一个在线产品所生成的成千上万个按客户划分的地址。
  • **没有签名。**没有任何机制能让您的服务器证明消息的真实性。
  • 没有为您的数据库结构设计的、已解码的结构化负载。

在加密领域，您希望事件流从头到尾都是机器可读的。

如何选择提醒方案？

当您比较如何把实时链上事件接入应用时，请依据以下要点进行判断，而不是依据宣传中的延迟数字。

链覆盖范围

列出您今天需要的网络和代币标准，以及您明年可能增加的。如果您将在多个网络上接受稳定币，就需要以相同的方式处理 ERC-20、BEP-20 和 TRC-20。Chaingateway 在 Ethereum、Bitcoin、Tron、Polygon、BNB Chain 和 Arbitrum 上提供 Webhook，并支持 ERC-20、BEP-20、TRC-20 和 ERC-721 代币标准。Solana 由 API 覆盖，但没有 Webhook。

载荷质量

要求查看一份事件样本。代币是否已被识别？金额是否已按 decimals 换算？转账方向是否清楚？您需要自行解码的内容越多，您自己需要维护和测试的代码就越多。

安全模型

检查是否采用签名请求、是否有书面的校验方法，以及是否有可用于防范重放的时间戳或 ID。然后为您自己的幂等性层预留时间。

运维负担

自行运行节点意味着在每条链上都要打补丁、同步、监控并支付存储费用。托管 API 则把这些成本换成了订阅费。请坦率地判断，您宁愿承担哪一种成本。

随用量计价的定价

随 API 用量扩展的套餐，比必须过度配置的基础设施更容易预测。Chaingateway 套餐起价为每月 49 欧元（每年 490 欧元），并提供无需绑定银行卡的 7 天免费试用。价格页面列出了所有档位。

合规与风险提醒是独立的一层

有些团队在搜索实时提醒时，指的是另一回事：对交易进行制裁风险或可疑模式的筛查。那是合规职能，通常由专业的分析供应商提供，并通过 API 接入您的工作流程。它与付款事件通知并存，而不是取代后者。您的付款 Webhook 告诉您一笔转账已经到达。合规层则告诉您是否应该接受它。

如果您的业务受到监管，两者都需要规划。请与您的合规顾问或具备资质的反洗钱负责人讨论，您所在辖区的要求是什么，因为规则因国家和牌照类型而异。

如果您担心的是对自身产品的滥用，例如反复注册或支付工具的重复使用，OWASP 业务逻辑安全备忘单列出了一些值得在应用内部设置提醒的有用模式，它们与链上的任何事物都无关。

需要避免的常见错误

  • **在处理程序中执行耗时工作。**应尽快确认接收，并在队列中处理；否则发送方可能在您仍在工作时就重试。
  • 信任负载中的金额，而不与您创建的订单比对。
  • **忽略少付和多付。**在上线之前就确定政策：部分入账、退款，还是暂停并等待人工审核。
  • **为多个订单复用同一地址。**这会使匹配变得模糊。应为每笔订单或每位客户生成地址。
  • **没有死信路径。**如果您的端点宕机，应通过列出失败通知并经由 API 读取近期交易来进行对账。
  • **记录密钥。**将 HMAC 密钥排除在日志和代码仓库之外，并定期轮换。

常见问题

加密货币价格提醒与交易提醒有什么区别？

价格提醒告诉用户某种资产突破了某一价位，通常通过推送、邮件或应用内消息送达。交易提醒则告诉软件某个特定地址上发生了某件事，通常以已签名的 HTTP 请求的形式送达。前者帮助您决定是否交易，后者让您的应用能够针对一笔付款采取行动。

不运行自己的节点，能否获得实时加密货币提醒？

可以。托管的区块链 API 会替您监视各条链，并把事件发送到您的端点。您仍然要负责校验和业务逻辑，但无需为每个网络运维节点。Chaingateway 在 Ethereum、Bitcoin、Tron、Polygon、BNB Chain 和 Arbitrum 上提供 Webhook。

仅靠 HMAC 签名的 Webhook 是否足够安全？

不够。签名能确认发送方身份，并证明负载未被改动，但它无法阻止一条有效消息被重放。OWASP 建议将签名与经过认证的时间戳、事件 ID 和幂等处理结合使用，并在采取行动之前从提供商重新读取当前状态。

Webhook 会按顺序到达吗？

不要假设如此。重试和网络状况可能导致投递乱序或重复。请设计您的处理程序，使最终状态在任何到达顺序下都是正确的，方法是在收到通知时通过 API 获取权威状态。

付款应用应使用哪种提醒类型？

对于任何涉及资金流动或订单履约的事项，都应使用 Webhook 事件提醒。价格提醒可以作为仪表板或财务团队的补充信号，但它们无法确认充值。
