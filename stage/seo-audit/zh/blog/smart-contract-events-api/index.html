智能合约事件 API：读取、过滤与订阅

智能合约事件 API 的工作原理：日志、topic 与 ABI 解码，历史事件与实时事件的区别，以及何时使用 Webhook、WebSocket 或轮询。还说明了读取历史事件、订阅新事件和处理链重组时各需注意的问题，并给出分步的事件监控设置。

章节
C
Chaingateway Team
区块链专家

审核： Maurice Sobiera

智能合约事件 API 是一种接口，让您的应用以结构化方式读取合约写入的日志，无需自行扫描每一笔交易。您按合约地址和事件签名查询历史日志，并在新区块到达时订阅新日志。您可以使用原始节点 RPC、ethers.js 等库，或带有 Webhook 的托管 API。

本指南说明每条路径的工作原理、各自会在哪里出问题，以及如何选择。

要点速览

  • 合约事件是交易被打包进区块时写入的日志条目。您的应用之后读取它。合约本身无法读取它。
  • 历史事件来自日志查询（eth_getLogs 或 queryFilter）。实时事件来自订阅或 Webhook。节点订阅不会回放历史。
  • 只有已索引的参数可以用作过滤条件。解码需要合约的 ABI。
  • WebSocket 订阅会随连接一起断开，处理过慢时也可能被丢弃。带队列和幂等处理程序的 Webhook 更能经受重启。
  • 托管 API 免去了节点、ABI 和重连的工作。Chaingateway 就是为支付和代币事件提供这一服务的。

什么是智能合约事件？

事件是合约与外部世界对话的方式。根据 ethereum.org，事件让合约与前端或其他订阅应用通信。交易通过验证并被打包进区块之后，这些应用就可以处理所记录的信息。

由此产生三点结论，它们解释了搜索结果中的大部分困惑：

  1. 事件是输出，而不是可以在 Solidity 中查询的存储。 合约代码会写入日志，但无法再读回。这就是为什么询问合约如何访问历史事件的讨论，最终总是归结为“在链下处理”。
  2. 事件只在被打包后才出现。 仍在内存池中的交易没有对应的日志。
  3. 事件发出成本低，搜索成本也低。 这就是为什么 ERC-20 的 Transfer 和 Approval 事件、NFT 铸造和 DEX 兑换都通过日志追踪，而不是通过读取状态来追踪。

智能合约事件 API，指任何能让您的后端以结构化方式访问这些日志的工具：节点的 JSON-RPC、对它的库封装、索引器，或是会通过 Webhook 发送数据的托管服务。

事件日志包含什么？

要正确过滤或解码日志，您需要了解它的结构。根据 Solidity ABI 规范，一条日志包含合约地址、最多四个 topic 和一个数据段。匿名事件则不包含事件签名哈希。

对于普通事件：

  • Topic 0 是事件签名的 Keccak-256 哈希，例如 Transfer(address,address,uint256)。
  • Topic 1 至 3 保存已索引的参数。
  • 数据 保存未索引的参数，经 ABI 编码。

ABI 把参数分为两类：已索引的参数以哈希 topic 存储，便于高效过滤；未索引的参数则以二进制数据存放在日志中。

有一个值得了解的陷阱。同一规范（见 v0.8.3 版本）指出，动态长度的已索引参数，例如字符串和字节数组，存储的是特殊编码的 Keccak 哈希，而不是原始值。您无法从日志中还原原始字符串，只能检验某个候选值是否与之匹配。

具体示例：ERC-20 Transfer

代币转账日志的 topic 0 是 Transfer 签名，topic 1 是发送方地址，topic 2 是接收方，金额位于数据字段中。如果您想获取发往某一客户地址的每笔充值，就按 topic 0 和 topic 2 过滤。我们在ERC-20 Transfer 事件指南中详细说明了这一做法。

如何读取历史事件？

历史读取是一次查询，而不是订阅。标准的 JSON-RPC 方法是 eth_getLogs。它接收一个过滤对象，包含区块范围、可选的合约地址以及可选的 topic 数组。Coinbase 开发者文档中的 eth_getLogs 参考展示了其结构：fromBlock、toBlock 和 topics，并指出区块哈希可以替代区块范围。

库会对此进行封装。在 ethers.js 中，contract.queryFilter(event, fromBlock, toBlock) 会返回匹配的事件。ethers v5 合约文档说明，只有已索引的参数可以过滤。留空的参数则匹配任意值。

历史查询的实用规则如下：

  • 始终限定范围。 许多服务商会限制每次调用的区块跨度或结果数量。请分块分页查询（例如每次几千个区块），遇到错误时将分块大小减半。
  • 至少按地址和 topic 0 过滤。 不加过滤的日志查询，是最快触发速率限制的方式。
  • 保存已处理的最后一个区块。 这个检查点让您能在崩溃后继续，既不留下缺口，也不产生重复。
  • 使用正确的 ABI 解码。 如果您只有 topic 0，可以查找事件签名，但代理合约可能会发出在其实现合约中定义的事件，因此应使用实现合约的 ABI。

如果您想复习如何直接与节点通信，我们的 JSON-RPC 指南（含 PHP、Python 和 JavaScript 示例）介绍了请求格式。

如何订阅新事件？

实时部分的工作方式不同，许多首次实现都在这里出问题。

go-ethereum 实时事件文档说明，订阅使用持久的 WebSocket 或 IPC 连接，通常通过 eth_subscribe 发起，并在节点处理事件时将其推送给您。以下两点限制很重要：

  • 不回放。 订阅通知只涵盖当前事件，不包括过去的事件。如果您的进程停机十分钟，订阅不会补给您错过的内容。您需要通过日志查询进行回填。
  • 与连接耦合。 订阅绑定在单个连接上。连接关闭时，其上的所有订阅也随之关闭。

同一页面还提到，节点会缓存通知。如果您的客户端处理速度跟不上，缓存达到上限后连接可能被关闭（Geth 的示例为 10,000 条）。在处理程序中直接同步写入数据库，正是导致这种情况的典型原因。

行之有效的模式

将两种机制结合起来：

  1. 启动时，读取您的检查点区块。
  2. 使用 eth_getLogs 从检查点回填到当前链头，分块进行。
  3. 打开订阅，并按交易哈希加日志索引去重。
  4. 将每个事件交给队列并立即确认。由工作进程处理。
  5. 连接断开时，回到第 1 步。

即使连接断开（它迟早会断开），这一模式也能保持正确。

链重组时会发生什么？

如果链发生重组，您在最新区块中看到的日志可能会消失。对于涉及资金的任何事件，不要在首次看到时就为用户入账。请等待与链和金额相匹配的确认深度，并处理以太坊类节点为孤立区块中的日志附加的“removed”标记。保存已处理的事件 ID，并使您的处理程序具备幂等性，这样被重放或修正的事件就不会重复入账。

应使用 Webhook、WebSocket 还是轮询？

这三种方式都能投递事件。它们的区别在于由谁维护连接，以及由谁承担故障模式。

方式工作原理优势劣势
轮询您的代码按定时器从上一个检查点调用 eth_getLogs简单、无状态、易于恢复延迟等于您的轮询间隔，并且消耗请求额度
WebSocket 订阅持久连接从节点推送日志延迟最低随连接断开，不回放，有缓存上限
Webhook服务监控链上数据，并向您的端点发送 HTTP POST无需维护长连接，可配合无服务器架构使用需要公网端点、签名校验和重复处理

轮询适用于低频的后台任务。WebSocket 适合必须在一个区块内做出反应、且能容忍缺口的仪表板或机器人。Webhook 适合付款流程，因为您希望每个事件都有一次可靠的推送，并在其后接一个工作队列。我们关于 Webhook 与 WebSocket 的接收、队列和扇出模式的文章更深入地讨论了其中的权衡。

正确处理 Webhook 投递

无论由谁发送 Webhook，接收端都应以相同的方式构建：

  • 在根据负载采取行动之前，先验证签名。
  • 快速返回 2xx，并异步处理。
  • 以交易哈希和日志索引为键，使处理程序具备幂等性。
  • 预期会出现重复和乱序的投递。
  • 记录失败，以便之后通过日志查询进行对账。

投递行为本身是一个独立的设计主题。我们关于 Webhook 投递保证的文章涵盖了重复、顺序和漏发通知的问题。

分步设置事件监控

以下是针对单个 EVM 合约的最小路径，无论您使用哪种工具。

  1. 获取 ABI。 可以从已验证的合约源代码或您自己的构建产物中获取。没有 ABI，您看到的只是原始的 topic 和十六进制数据。
  2. 选定事件。 列出您关心的签名，例如 Transfer、Approval，或您自己的 OrderPaid。
  3. 确定过滤条件。 包括合约地址、topic 0，以及任何已索引的参数，例如接收方。请记住，只有已索引的值可以过滤。
  4. 回填。 从部署区块或您的业务起始日期开始，分块查询。
  5. 上线运行。 通过 WebSocket 订阅，或注册 Webhook。
  6. 解码并规范化。 使用代币的小数位数转换十六进制金额，并存储区块号、交易哈希、日志索引和合约地址。
  7. 等待终局性。 先将事件标记为待处理，再标记为已确认。
  8. 监控监控程序本身。 当长时间没有事件到达，超过该链的正常间隔时，或当您的检查点落后于链头时，发出警报。

跨链的事件

Topic 和 ABI 解码数据的 EVM 模型适用于以太坊、Polygon、BNB Chain 和 Arbitrum，因此同一个解码器只需配合不同的 RPC 端点和确认规则，即可在它们之间通用。其他网络并不共享这一模型。比特币完全没有合约日志，因此您需要监控地址和交易。Tron 和 Solana 有各自的格式和 API。

实际结论是，多链产品最终需要为每个网络系列维护一个适配器，每个适配器都有各自的重连、解码和终局性代码。这正是大多数团队低估的部分。如需了解各种选项的概况，请参阅我们对六种区块链 API的比较，以及关于区块链 API 与运行节点的说明文章。

应自己构建，还是使用托管 API？

自建技术栈意味着需要一个节点（或付费的 RPC 端点）、一个日志扫描器、一个 ABI 注册表、一个重组处理程序、一个队列以及告警设置。如果事件是您的核心产品，或您需要跨数千个合约进行定制索引，这样做是合理的。

如果事件只是达成目的的手段，例如为充值入账或确认订单，那么自建就不太合理。在这种情况下，您需要把解码后的事件投递到您可以控制的端点，而无需运维其他任何东西。

我们的看法

我们见过的大多数事件处理错误，并不在于读取日志本身，而在于围绕日志发生的事情：部署期间漏掉了一条通知，重试后重复入账，某个代币的小数位换算出错，或者连接在夜间悄然断开。

因此，我们围绕三个判断来构建。第一，应用应收到解码后的结构化数据，而不是需要自行解读的原始 topic。第二，对于付款，推送优于轮询，前提是每条消息都经过签名并可以验证。第三，开发者不应为了得知一笔付款已到账，就必须运行节点或维护各链特定的端点。

这就是为什么 Chaingateway 在 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Chain 和 Arbitrum 上提供统一的 REST API，并提供解码后的交易和 gas 价格。Webhook 在此基础上运作，并经过 HMAC 签名，因此您的处理程序能收到事件，而您的团队可以把注意力放在产品上。无论选择哪种方案，都请保留检查点、幂等键和确认规则。这三者决定了您的数字是否正确。

常见问题

智能合约能读取自己的历史事件吗？

不能。合约可以发出日志，但之后无法访问它们，因此事件数据供链下使用者读取。如果您的合约需要在链上使用历史数据，请改为将该值存入合约状态，但会产生更高的 gas 成本。

服务离线期间错过的事件，如何补回？

从您最后处理的区块到当前链头执行一次日志查询。节点订阅只发送当前事件，因此重新连接不会回放任何内容。每处理完一个区块后保存检查点，并按交易哈希和日志索引去重。

为什么无法按事件中的某个参数过滤？

只有已索引的参数会存储为 topic，而只有 topic 可以被过滤。未索引的值位于数据字段中，因此您必须获取日志，并在自己的代码中过滤。如果您控制该合约，请将需要搜索的字段标记为已索引，每个事件最多三个。

付款通知应使用 Webhook 还是 WebSocket？

对于付款，带队列的 Webhook 通常更易于运维，因为您不需要保持可能断开的连接。当亚秒级反应很重要，且您能够回填缺口时，再使用 WebSocket。两种情况下，都应以幂等方式处理事件，并在入账前等待足够的确认数。
