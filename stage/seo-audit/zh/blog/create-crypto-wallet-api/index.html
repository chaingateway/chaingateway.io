如何通过 API 创建加密钱包：2026 指南

了解如何通过 API 创建加密钱包：托管方式的选择、密钥安全、地址设计、Webhook，以及面向开发者的分步构建计划。文中还说明如何在测试网上完整演练一次流程，再切换到主网，并解释密钥存储、地址归属与付款入账的基本做法与常见错误。

审核： Maurice Sobiera

加密钱包 API 是一项服务，用于创建钱包地址和密钥对、报告余额、发送交易，并在地址发生充值时通知您的应用。您在后端调用它，而无需自己运行节点或编写签名代码。真正重要的设计选择包括：谁持有密钥、如何保护您的凭证，以及如何检测付款。

要点速览

  • 钱包 API 生成密钥并返回地址。您真正需要做的设计选择是托管方式、密钥存储和付款检测。
  • 为每位用户或每张发票分配独立的地址，并将每笔入账交易的哈希作为唯一键记录在数据库中。
  • 使用经签名的 Webhook 代替轮询，验证每一个签名，并让处理程序具备幂等性。
  • 密钥生成必须使用密码学安全的随机源，生产环境的密钥应存放在不可导出的存储中，例如 HSM。
  • 统一的多链 API 让您无需运行节点，也无需为每个网络维护一套独立的集成。

钱包 API 做什么？

区块链钱包是管理密钥的软件。NIST 区块链技术概述将其描述为一种可以存储私钥、公钥和地址，并帮助用户处理这些密钥所控制资产的工具。钱包 API 则把这项工作从用户设备转移到您的后端。

钱包 API 涵盖四项任务：

  1. 创建： 生成新的密钥对，并返回指定网络上的地址。
  2. 读取： 报告该地址的余额和交易历史。
  3. 发送： 构建、签名并广播转账，包括手续费估算。
  4. 通知： 当该地址发生事件时告知您的应用。

比特币开发者指南中关于支付处理的部分指出了一个适用于所有链的要点：在您请求付款之前，您的应用必须创建一个地址，或从其他地方获取一个地址，并且该流程中的每一步都可以外包给第三方 API。外包是一项合理的工程选择，它以对基础设施的控制权为代价，换取速度和更少的运行部件。

谁应该持有密钥？

每一次钱包集成都从一个问题开始：谁能签署交易？下表列出了三种模式。

大多数构建支付功能的初创公司和代理机构需要中间一行。用户向您的应用控制的地址充值，您的后端负责支付，且无需有人为六条网络运行节点或编写签名代码。

托管可能带来法律后果，具体取决于您所在的国家和业务模式。如果您要替客户持有资金，请在上线前咨询熟悉您所在司法管辖区货币转移和虚拟资产规则的律师。本文只讨论工程层面。

关于账户抽象的说明

如果您在以太坊上构建，就会遇到智能合约钱包。以太坊账户抽象路线图描述的是让账户具备可编程的安全性和更好的用户体验，而不是依赖单一的原始私钥。这可以支持赞助 gas、灵活恢复等功能。对于用户拥有自己钱包的消费级应用来说，它非常契合。而对于一个需要创建数千个充值地址并归集资金的后端来说，经典的外部拥有账户仍然是更简单的模型，并且它在比特币、Tron 和 EVM 链上的运作方式相同。如需复习，以太坊自己的文档解释了两种账户类型：外部拥有账户和合约账户。

如何通过 API 创建第一个钱包？

各服务商的具体端点不同，因此请阅读您所选 API 的参考文档。下面的步骤顺序保持不变。

1. 获取凭证，并将其保存在服务器端

注册账号，获取 API 密钥，如果服务商使用请求签名，还需获取一个密钥。这些凭证可以转移资金，因此应像对待数据库密码一样处理。请从密钥管理服务中加载它们，切勿放在客户端代码中，也不要放进公开仓库。OWASP 的 SDK 测试指南建议检查凭证是否有范围限制且可以撤销，这对任何集成都是一条好规则：一旦密钥泄露，您应能在不重建应用的情况下使其失效。

2. 创建钱包或地址

为您所需的网络调用创建端点。您会获得一个地址，通常还有一个标识符，供您的系统之后引用该钱包。请立即在您自己的数据库中保存三项内容：

  • 地址，
  • 它所属的网络，
  • 与其关联的内部用户、订单或发票。

除非您已经建成了用于保存私钥的安全存储，否则不要自己保存私钥。在托管模式下，这是服务商的职责。

3. 显示地址，并防范错误

用通俗的语言显示地址及其网络名称。加密支付中最常见的支持工单，就是用户通过错误的网络发送了代币。Ethereum 上的 USDT 地址与 Tron 上的地址看起来完全不同，但用户仍然会犯错。请在二维码旁边添加网络标签，并考虑在显示地址之前加入一个简短的确认步骤。

4. 订阅该地址的事件

注册 Webhook，使您的后端无需轮询即可获知充值。下一节将说明如何安全地构建接收端。

5. 先在测试网上测试

在测试网上完整运行一遍流程：创建地址，发送测试资金，接收事件，为账户入账，然后发起一次支付。只有到那时，才将凭证和网络切换到主网，并从小额开始。

在 Chaingateway 上是什么样的？

Chaingateway 通过 POST /api/v2/{chain}/addresses 创建地址。该请求有两种模式，API 规范将其称为非安全模式和安全模式。钱包管理文档解释了其中的权衡。不设置密码时，响应中包含私钥，您必须自行保存。设置密码后，Chaingateway 会以该密码加密存储私钥，只返回地址。它不会保存您的密码，如果您丢失了密码，它也无法恢复钱包。

调用成功时返回状态码 201，新地址位于 data.address 中。此后，每当您从该地址发送交易，都传入相同的 password 而不是私钥。X-Network: testnet 请求头使调用在测试网上运行。请将密码保存在您的密钥管理服务中，因为它是使用该地址的唯一途径。如果您已经持有一个密钥，可以使用 POST /api/v2/{chain}/addresses/import 在密码保护下将其注册。下一步请参阅加密支付 Webhook 的工作原理。

每位用户一个地址，还是每张发票一个地址？

复用地址是一种捷径，但之后会带来对账麻烦。比特币开发者指南介绍了为每个付款请求分配独立地址的标准做法，这样一笔入账付款就能清晰地对应到引发它的订单。

常见模式如下：

  • 每张发票一个地址。 对账最清晰。最适合带有预期金额和有效期的结账流程。
  • 每位用户一个地址。 对于充值功能（例如余额充值）很简单。每一笔入账转账都会计入同一个账户。
  • 共用地址加备注或标签。 仅适用于支持该功能的网络和资产，且更难正确处理。

如果您使用分层确定性方案生成地址，其结构是标准化的。BIP 44 定义了 purpose、coin type、account、change 和 index 的路径布局，使一个种子能够生成可预测的地址树。托管 API 通常会替您处理这些，但了解这一布局有助于审计或迁移。

如何保护私钥？

真正让钱包产品遭到入侵的，很少是网络协议本身。可预测的种子会导致悄无声息的全面失陷，因为攻击者可以离线重建密钥。OWASP SDK 测试方法要求测试人员验证密钥生成是否使用平台提供的密码学安全随机数生成器。

由此可以得出三条实用规则。

切勿自行实现密钥生成。 使用经过验证的库，或由专门从事这项工作的服务商来完成。以 Math.random() 作为种子，迟早会酿成灾难。

将签名密钥保存在不可导出的存储中。 NIST SP 800-63C指出，钱包实现应使用不可导出的密钥存储。对于您自己运行的任何系统，这意味着使用 HSM 或类似的安全元件，而不是环境变量或数据库字段。

保护人员的访问环节。 为能够创建 API 密钥、修改 Webhook URL 或批准支付的管理员账户配备硬件安全密钥，可以消除大量钓鱼风险。同时划分角色，使部署代码的人无法同时放行资金。

对于日常的 API 使用规范，我们自己的使用区块链 API 的安全建议清单是很好的参考。

如何通过 Webhook 检测付款？

创建地址只是完成了一半工作。您还需要知道何时有人向它付款。按计划轮询每个地址既浪费请求，又会延迟确认。Webhook 则会在服务商看到付款的那一刻把事件推送给您。我们在如何通过 Webhook 自动处理充值中介绍了完整流程。

接收端是安全错误最容易出现的地方，因此请仔细构建。OWASP Webhook 安全速查表是应遵循的参考，其要点如下：

  • 验证每一次投递的签名。 使用您与服务商共享的密钥，对原始请求体重新计算 HMAC，并与签名请求头进行比较。使用恒定时间比较，以避免计时攻击。
  • 要求使用 HTTPS。 签名能证明发送方的身份，但并不加密内容，因此网络路径上的任何人都能读取明文 HTTP 投递的内容。
  • 不要把密钥放在 URL 中。 URL 会被记录在您可能无法控制的负载均衡器和代理日志中。应将身份验证放在请求头中。
  • 将事件视为幂等。 网络重试之后，投递可能会重复。一笔付款绝不能入账两次。

最后一点值得给出一个具体模式。将交易哈希存为一个唯一的索引键。比特币指南中的对账建议同样适用于所有链：在执行任何入账逻辑之前，先检查数据库中是否已存在该哈希，而不是寄希望于每次回调都恰好到达一次。在 SQL 中，这意味着对哈希设置唯一约束，并使用忽略重复项的插入语句。

一个可靠的处理程序遵循以下顺序：

  1. 在任何解析之前，先读取原始请求体。
  2. 验证 HMAC 签名。不匹配则拒绝。
  3. 插入交易哈希。如果已存在，则返回成功并停止。
  4. 在为资金入账之前，等待您的风险政策所要求的确认数。
  5. 在与插入相同的数据库事务中为账户入账。
  6. 快速返回成功状态码，并把耗时的工作交给队列处理。

我们在区块链 Webhook 与事件通知页面上展示了这一流程在各支持网络上的运作方式。

同时支持多条链时，有哪些变化？

只支持一条链的钱包很容易做。当它要支持多条链时，集成成本就会上升，因为每个网络都有自己的地址格式、手续费模型和代币标准。

  • 手续费。 在 EVM 链上，代币转账需要原生币来支付 gas。一个刚创建、接收了 USDT 的地址，在它也持有该链的原生币（例如以太坊上的 ETH 或 BNB 智能链上的 BNB）用于支付手续费之前，无法转出 USDT。请为支付和归集规划一个注资步骤。
  • Tron 的新账户与资源。 根据 TRON 资源模型，如果质押的带宽不足以覆盖，创建新账户的交易会燃烧 0.1 TRX。TRC-20 转账还会消耗能量。请尽早测试这一路径。
  • 代币标准。 ERC-20、BEP-20 和 TRC-20 对用户来说看起来相似，但在合约调用和事件格式上有所不同。NFT 则在此基础上增加了 ERC-721。
  • 已解码的数据。 原始交易日志是十六进制的。如果您的服务商返回已解码的值，您就无需为每种代币编写 ABI 解析代码。

应自建还是购买钱包基础设施？

您可以自行运行节点和签名服务。有些团队确实应该这样做。以下是这一决策通常的权衡方式。

因素自建技术栈使用统一钱包 API
创建第一个钱包所需时间每条链数周数小时
基础设施每条链的节点、索引器和监控您这边无需任何设施
密钥管理由您设计并审计由服务商处理，您的凭证需要妥善保护
成本结构工程时间与服务器可预测的订阅费用
控制权完全控制以 API 提供的功能为限

如果钱包是您产品的核心差异化优势，或者监管要求您把密钥保存在自己的环境中，那就自建。如果钱包只是支持收款、充值或支付的功能，那么省下的集成时间更适合用在其他地方。

我们的看法

与我们接触的大多数团队都呈现出相同的模式。他们低估了管道工程，却高估了密码学。生成一个密钥是已经解决的问题。真正拖垮项目的，是花费一个月在节点同步上、在某条链的手续费怪癖上、在一个会把同一笔充值入账两次的 Webhook 处理程序上，或者因为代币小数位数而使解码后的金额差了十倍。

这就是为什么我们把 Chaingateway 构建为服务多个网络的统一 REST API，而不是每条链一套集成。在每个网络上，您都以相同风格的请求来创建地址、发送代币转账并读取已解码的交易。Webhook 通知经过 HMAC 签名，并告知您的后端付款情况，因此您无需运行自己的节点，也无需轮询。

我们的建议很简单：先决定托管方式。为每位付款人分配独立的地址。第一天就让您的 Webhook 处理程序具备幂等性，而不是等到第一次重复入账之后。并在任何真实的币转移之前，先在测试网上测试完整流程。

上线检查清单

在正式上线之前，请逐项确认：

  • API 凭证保存在密钥管理服务中，并且可以轮换。
  • 每个地址都与其网络、所有者和创建时间一同保存。

  • 如果您替他人持有资金，已就托管问题征询了法律意见。

常见问题

不运行节点，能否通过 API 创建加密钱包？

可以。托管式钱包 API 为您运行节点和签名基础设施，并通过 REST 调用返回地址。您仍然需要保护自己的 API 凭证和 Webhook 端点，因为它们现在是通往您资金的大门。

通过 API 创建的钱包属于托管钱包吗？

在托管模式下通常是的，即服务商存储密钥，而您的凭证授权操作。Chaingateway 是非托管的。在法律意义上您是否因此成为托管方，取决于您是否替客户持有资金，以及您所在的司法管辖区。在面向公众上线之前，请咨询处理虚拟资产监管事务的律师。

我如何知道充值何时到账？

为该地址订阅 Webhook 通知。验证 HMAC 签名，将交易哈希记录在带唯一索引的列中，并且只有在满足确认数要求后才为账户入账一次。由于投递可能会重复，正是哈希检查使您不会重复付款。

应每位用户一个地址，还是每笔付款一个地址？

每笔付款一个地址的对账最清晰，因为每个地址对应一个订单。每位用户一个地址则更便于余额充值。除非网络支持备注或标签并且您能正确处理，否则应避免让许多付款人共用一个地址。

生产环境中私钥应存放在哪里？

存放在 HSM 或安全元件等不可导出的存储中，或交由替您运营该存储的服务商保管。环境变量、配置文件和普通数据库记录都不适合保存能控制真实资金的密钥。
