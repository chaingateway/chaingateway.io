Polygon Webhooks：实时获取链上事件

Polygon Webhook 的工作原理，PoS 网络上需要注意的事项，包括链重组、确认数和重复事件，并说明如何为 USDC 和 POL 构建安全、幂等的充值处理程序，以及上线前应检查哪些内容。代币与原生 POL 的差异，以及对账为何仍然必要，也在其中说明。

章节
C
Chaingateway Team
区块链专家

审核： Maurice Sobiera

Polygon Webhook 是一种 HTTP 回调。当 Polygon 链上发生某个事件时（例如有 USDC 充值到您的某个地址），服务会把它发送到您的服务器。您注册一个 URL，服务商监控链上数据，您的后端接收带签名的 POST 请求，而不必轮询 RPC 节点。本指南涵盖处理程序的设计与 Polygon 的边界情况。

要点速览

  • Webhook 取代轮询：服务商监控 Polygon，并把事件（充值、转账、代币流动）推送到您的端点。
  • Polygon 会在数秒内完成交易的最终确定，但在入账之前，您仍需要确认数策略。
  • 把每次投递都视为可能重复、延迟或乱序：验证签名，保存事件 ID，并以幂等方式处理。
  • 快速确认接收，在队列中完成处理，并按计划与链上数据对账。Chaingateway 不会自动重试失败的通知。
  • Chaingateway Webhooks 投递经 HMAC 签名的 Polygon 事件，发送方、接收方、代币合约和金额均已完成解码，您无需运行节点或解析日志。

什么是 Polygon Webhook？

Polygon PoS 是一条 EVM 链。每一笔 ERC-20 转账（无论是 USDC、USDT，还是您自己发行的代币）都会发出一条 Transfer 日志。原生 POL 则作为价值转账转移，而不是 ERC-20 Transfer 日志。原始 RPC 以不同形式提供两者：代币是日志，原生币是交易数据。若您想知道客户是否已付款，就必须自己把这些信息拼合起来。

Webhook 服务负责完成这一拼合。您订阅一个地址（或一组地址），当匹配的事件发生时，服务会向您的 URL 发送 JSON 负载。一个有用的负载会包含交易哈希、发送方、接收方、代币合约、金额、区块号以及唯一的事件标识符。这就是“一条带十六进制 topic 的日志”与“客户 4812 付了 250 USDC”之间的区别。

人们以这个关键词搜索的内容，实际上是三种不同的工具：

  • 地址和付款 Webhook：资金到达这些地址时通知我。付款流程需要的正是这种。
  • 合约事件 Webhook：某个智能合约发出某个事件时通知我。dApp 后端和数据分析需要的是这种。
  • 协议级 Webhook：Polygon 某个产品就其自身运营发出的通知。这些属于该产品的文档，而不属于通用的链监听器。

本文讨论第一种，并附带第二种的说明。

为什么在 Polygon 上 Webhook 优于轮询？

如果您轮询 RPC 端点获取新区块，并自行过滤日志，就会面临一个没有好答案的权衡：

  • 每隔几秒轮询一次，您会耗尽速率限制，并为大多是空的响应付费。
  • 每分钟轮询一次，客户付款后要盯着转圈等上一分钟。
  • 重启后漏掉一段区块范围，账本里就会出现无声的缺口。

Webhook 颠倒了这一局面。服务商承担监控和区块记账工作，您的任务缩减为运行一个能正确处理事件的端点。我们在关于 Webhooks 与 WebSockets 的文章中更深入地讨论了架构权衡，包括我们推荐的接收、队列和扇出模式。

在 Polygon 上需要多少个确认数？

请等待终局性，Polygon 在数秒内即可达到。在交易首次被发现时触发的 Webhook 速度很快，但尚未最终确定。在放行货物或为余额入账之前，请先确定您要等待什么。

Polygon 终局性文档称，自 Heimdall v2 升级以来，确定性终局可在 2 到 5 秒内达成。Milestone 无需等待以太坊上的检查点即可提供这种终局性。已最终确定的区块不可逆，因此此后不存在链重组风险。您可以使用标准的 eth_getBlockByNumber 方法和 "finalized" 区块标签查询最近的已最终确定区块。

一种实用的选择方法，是把策略与风险金额挂钩：

付款金额建议处理方式理由
小额（数字商品、打赏）收到第一个事件即入账，标记为“待处理”体验快，罕见链重组造成的损失小
中等（订阅、充值）达到适度的区块深度后入账兼顾速度与安全
大额（发票、提现）仅在区块已最终确定后入账链重组风险比速度更重要

本表是我们建议的策略，并非 Polygon 的规则。请选择符合您自身风险承受能力的数值，并将其写下来。

在数据模型中，为每笔收款设置状态，例如 detected、confirming 和 final。向客户立即展示第一种状态，只在最后一种状态时才动用资金。保存首次事件中的区块号。通过定时器，将其与最新已最终确定区块的编号比较，当已最终确定区块超过它时，把付款转为 final。

安全的 Polygon Webhook 处理程序是什么样的？

Polygon 开发者文档中包含一份接收 Webhook 指南，适用于 Polygon 自有的一款产品。其原则适用于所有 Webhook 集成：验证投递，处理时不重复执行，也不应用过期状态。OWASP Webhook 安全速查表列出了相同要点。下面是针对链上事件的同一套做法。

1. 先验证签名，再做任何其他事

任何找到您 URL 的人都可以向它发送 POST 请求。若不验证，攻击者就能伪造一条“收到 250 USDC”的通知，然后拿走您的商品。请以 401 拒绝未签名或签名错误的请求，并且不要再解析请求体。

Chaingateway 使用 HMAC-SHA256 为 Webhook 签名。X-Signature 请求头中保存的是负载中交易 ID（txid）经 Base64 编码的 HMAC 值，以您的个人密钥作为键计算。请重新计算，并使用恒定时间比较来对比两个值。签名文档提供了多种语言的代码，我们关于增强 Webhook 安全性的新功能的文章则说明了设置方法。

2. 让处理具备幂等性

假设通知可能不止一次到达，例如您重新发送失败的通知时。为每个事件保存唯一键，最好使用交易哈希，或服务商提供的事件 ID。在数据库中为其添加唯一约束：

如果插入影响的行数为零，说明您已经见过该事件。请返回 200 并停止处理。将插入操作与余额更新放在同一个数据库事务中，这样崩溃就不会只留下其中一个。

3. 快速确认，之后再处理

在事件通过验证并安全保存后，立即返回 2xx。把耗时的工作，例如给客户发邮件、更新账本和调用其他服务，放入队列中执行。如果您的处理程序很慢，发送方可能会超时，而您将不得不调试失败的通知。

4. 不要依赖顺序

关于同一笔付款的两个事件，可能以任意顺序到达，例如在最初的检测事件之前收到确认数更新。请比较区块号或序列字段，忽略比您已持有的状态更旧的任何内容。切勿让迟到的“detected”事件覆盖“final”记录。

5. 验证负载声称的内容

检查接收方是否为您签发的地址，代币合约是否为您接受的合约，金额是否与发票一致。这在 Polygon 上比许多人预期的更重要，因为任何人都可以部署一个名为“USDC”的代币，并将其发送到您的地址。请比较合约地址，切勿比较代币符号。

6. 为故障做好准备

您的服务器迟早会宕机。请提前决定如何恢复：

  • 检查失败通知列表。Chaingateway 不会自动重试这些通知。它们列在 GET /api/v2/polygon/webhooks/notifications/failed，您可以通过 POST /api/v2/polygon/webhooks/notifications/{id}/retry 逐条重新发送。
  • 运行对账任务，例如每隔几分钟一次，检查您地址的余额或近期转账，并标记 Webhook 日志从未见过的任何记录。
  • 当长时间没有事件到达时发出警报。在繁忙的系统中，沉默本身就是信号。

Webhook 是您的快速通道，对账是您的安全网。两者都要运行。

哪些代币和边界情况在 Polygon 上很重要？

USDC 和 USDT。 稳定币付款是开发者设置 Polygon Webhook 的主要原因，因为手续费低、结算快。请确保您知道每种稳定币在 Polygon 上使用的合约，并且如上所述只允许这些地址。

原生 POL。 根据 Polygon 文档，POL 是 Polygon Chain 的原生代币。原生转账不是 ERC-20 Transfer 事件，因此只基于这些事件构建的监听器会漏掉它们。在 Chaingateway Polygon Webhook API 中，type 过滤器接受 MATIC、ERC20 和 ERC721。MATIC 值对应原生币类型，因此在依赖它处理 POL 付款之前，请先测试。

合约到地址的付款。 付款可能来自智能合约钱包或多签钱包，而不是普通账户。不要假设发送方就是客户。应通过您为客户生成的接收地址来关联付款，而不是通过发送方。

失败和回滚的交易。 回滚的交易会消耗 gas，但不转移任何资产。只对代表成功转账的事件采取行动。

粉尘和垃圾代币。 未经请求的代币经常出现在地址中。请忽略未加入白名单的合约。

我应该自己构建，还是使用统一 API？

实现 Polygon 事件通知有三条切实可行的路径：

  1. 运行自己的节点和监听器。 控制力最强，但您要负责节点升级、存储增长、日志解码、链重组处理和正常运行时间。当链基础设施本身就是您的产品时，这才合理。
  2. 使用通用节点或数据服务商，并自行编写过滤逻辑。 运维负担较轻，但您仍需构建订阅、重试、解码和签名层。
  3. 使用面向支付的 API，它投递经解码且已签名的事件。 您只需编写端点和业务逻辑，其余无需操心。

对于希望在其产品中收付加密货币的团队，第三条路径通常最快进入生产环境。我们在区块链 API 对比：6 种类型及各自适用场景中更深入地比较了这些方案。

我们的看法：Webhook 是账本问题，而不只是通知问题

我们看到的大多数集成错误，并不在于接收 HTTP 请求，而在于之后发生的事情。团队把 Webhook 当作触发器（“付款已到账，发货吧”），而它实际上是账本的一项输入，必须在重试、链重组和重启的情况下保持正确。

这决定了我们如何构建 Chaingateway。我们投递解码后的事件，因此您的代码读取的是金额和代币合约，而不是十六进制编码的日志 topic。我们使用 HMAC 为每个 Webhook 签名，以便您的端点拒绝伪造请求。我们还通过同一个 REST API 同时支持 Polygon、以太坊、Tron、比特币、Solana、BNB Chain 和 Arbitrum，因此在您增加第二条链时，处理逻辑保持不变。

我们的建议是：先编写幂等性和对账代码，再编写正常路径。如果您能把同一事件重放十次、打乱三个事件的顺序，最终仍得到正确的余额，那么其余部分就很简单。我们关于使用 Webhook 自动处理充值的文章完整介绍了这一流程。

如何通过 Chaingateway 获取 Polygon Webhook？

借助 Chaingateway Webhooks，您可以通过 API 创建钱包或注册地址，订阅付款事件，并在您的端点接收经签名的通知。Polygon API 页面介绍了在 Polygon 上收发 USDC 和 USDT，区块链 API 页面则涵盖受支持链上的钱包、转账、已解码交易和 gas 价格。

上线检查清单

在将生产流量指向您的端点之前，请逐项检查：

  • 仅使用 HTTPS，并配有有效证书。
  • 针对 txid 验证 X-Signature，使用恒定时间比较。
  • 事件键上设有唯一约束。
  • 在几秒内返回 2xx，并将工作转入队列。
  • 合约地址通过列表允许，金额和接收方经过验证。
  • 状态模型包含待处理和最终状态，并记录了确认数阈值。
  • 对账任务，以及缺失事件的警报。
  • 密钥存放在代码仓库之外，并且可以在不停机的情况下轮换。
  • 重放测试：在预发布环境中多次发送同一事件，并打乱顺序发送。

常见问题

Polygon Webhook 对原生 POL 和代币都会触发吗？

这取决于服务商。代币转账会发出易于追踪的日志，而原生转账需要交易层面的监控。在 Chaingateway Polygon Webhook API 中，type 过滤器接受 MATIC、ERC20 和 ERC721，因此在依赖它处理 POL 付款之前，请先用一笔小额转账测试原生币类型。

在 Polygon 上应等待多少个确认数？

没有统一规则，但 Polygon 的最终确定速度很快。Polygon 终局性文档称，Milestone 通常在 2 到 5 秒内使交易最终确定，而 finalized 区块标签返回最新的不可逆区块。小额付款通常会先以待处理状态入账。请让阈值与风险金额相匹配。

事件触发时我的端点宕机，会怎样？

通知不会自动再次发送。Chaingateway 会列出失败的通知，您可以通过重试端点逐条重新发送。同时请运行您自己的对账任务，将您的记录与链上数据比较，以免缺口未被发现。

同一个 Webhook 会不会到达两次？

请假设会，例如您重新发送失败的通知时。请为事件保存带有数据库约束的唯一事件键，并对已处理过的事件返回 200。
