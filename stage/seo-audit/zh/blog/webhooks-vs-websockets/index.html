Webhook 与 WebSocket：何时使用哪一种

从连接模型、重试、扩展性和安全性角度比较 Webhook 与 WebSocket，附决策清单，以及 Webhook、队列到 WebSocket 的扇出模式。文中还说明如何在不自建投递系统的情况下获得可靠的 Webhook 投递。

章节
C
Chaingateway Team
区块链专家

审核： Maurice Sobiera

Webhook 是服务器在事件发生时向您的 URL 发出的单向 HTTP 请求。WebSocket 是用于持续双向通信的持久连接。服务器之间的事件（例如付款确认）适合使用 Webhook，实时的浏览器更新适合使用 WebSocket。许多系统会同时使用两者。

TL;DR：

  • Webhook 非常适合第三方服务向服务器发送通知，但需要一个可公开访问的 URL、安全的签名以及快速的响应。
  • WebSocket 更适合与浏览器或应用进行实时的双向通信，但需要管理连接并处理状态，包括重连逻辑。
  • 将 Webhook 与 WebSocket 结合，可以构建具有韧性的架构：Webhook 负责接收事件，WebSocket 则高效地把实时更新送达客户端。
  • 扩展 WebSocket 需要通过粘性会话或共享消息代理来管理大量打开的连接，而 Webhook 借助无服务器的无状态处理和队列，可以轻松扩展。
  • Webhook 安全依赖于轮换签名和 TLS；WebSocket 安全则强调连接认证和逐条消息校验，以防止未授权访问。

什么是 Webhook，它如何工作？

Webhook 从注册开始。您向服务提供商（支付处理商、Git 托管平台、区块链节点）提供一个 URL。当相关事件触发时，提供商会向该 URL 发送一个携带 JSON 负载的 HTTP POST。无需轮询，也无需保持一个闲置的打开连接。它是基于标准 HTTP 的事件驱动推送，因此很容易接入您已经在运行的架构。

难点在于投递保证。许多 Webhook 提供商采用至少一次（at-least-once）语义：如果您的端点没有足够快地返回 2xx 响应，提供商就会重试，而有些会重试数小时甚至数天。因此，您的处理程序必须具备幂等性，即能够处理同一次投递两次而不产生重复扣款或重复数据库记录。OWASP Webhook 安全备忘单正是出于这一原因，建议以事件 ID 为键实现幂等处理程序。并非每个提供商都会重试。Chaingateway 不会自动重试失败的 Webhook，但会列出失败的通知，并在您请求时重新发送。

由于 Webhook 需要一个可访问的 URL，它们还带来自己的运维检查清单：

  • 一个能经受防火墙和负载均衡器配置的公开端点
  • 签名校验（通常为 HMAC），以确认请求确实来自提供商
  • 记录投递 ID，以便追踪重复或遗漏的投递
  • 足够快的响应时间，以免对仍在处理中的请求触发重试

您会在付款确认、CI/CD 流水线触发、Git 推送通知和充值提醒背后看到 Webhook。它们也非常适合无服务器后端，因为两次调用之间无需保持连接状态。

WebSocket 连接如何工作？

WebSocket 连接最初是一个普通的 HTTP 请求，随后升级。客户端发送 Upgrade: websocket 请求头，服务器同意后，双方便可通过同一个 TCP 连接互相发送消息，这由 RFC 6455 规定。因此它是全双工的：服务器和客户端可以随时推送数据，而不只是响应请求。

棘手之处不在握手，而在握手之后。连接会断开，网络会不稳定，标签页会进入休眠。客户端代码需要重连逻辑，而且您需要关注 bufferedAmount，以免出站消息的排队速度超过套接字的发送速度。MDN 在其 WebSockets API 指南中记录了完整的生命周期。

在服务器端，WebSocket 是有状态的。每个打开的连接都会占用一个文件描述符和一些内存。在多个服务器实例下，您需要粘性会话或消息代理（Redis pub/sub、NATS），以便在一个实例上发布的消息能够到达连接在另一个实例上的客户端。

常见用例包括：

  • 聊天应用和协同编辑器
  • 实时仪表板和行情播报
  • 多人游戏状态同步
  • 在线状态指示（“用户正在输入”）

若您需要更强的背压处理或基于流的 API，可以了解 WebTransport 和 WebSocketStream。两者都针对经典 WebSocket API 的不足，但浏览器支持情况不同，依赖之前请先查看 MDN 的兼容性表格。

实际含义是：Webhook 把投递问题交给了发送方（而您必须以幂等方式处理重试），而 WebSocket 则把连接管理问题交给了您。从抽象角度看，两者都谈不上“更容易”。这取决于您更愿意编写无状态的 HTTP 处理程序，还是运行有状态的连接池。

何时使用 Webhook，何时使用 WebSocket？

在选择架构之前，请先回答以下问题：

  1. **事件从哪里产生？**如果来自第三方系统（支付网关、区块链网络、Git 托管平台），您需要使用 Webhook。您无法对不受自己控制的服务打开 WebSocket。
  2. **您能容忍多大的延迟？**亚秒级的界面更新适合 WebSocket。后端记录更新延迟几秒钟，使用 Webhook 即可。
  3. **规模形态如何？**许多独立的事件生产者向一个后端提供数据，适合 Webhook。一个后端向数千个已连接的客户端扇出更新，适合 WebSocket。
  4. **您的服务器拓扑是怎样的？**可缩容至零的无服务器函数与 Webhook 天然匹配。若您已经在运行长期有状态的服务器，WebSocket 带来的额外复杂度较小。
  5. **防火墙或网络限制是否阻止入站连接？**若您的基础设施无法暴露公开端点，WebSocket（由客户端主动向外连接）能完全绕过这一问题。

对应到具体场景：付款通知和充值提醒使用 Webhook。来自外部工具的分析事件接收也使用 Webhook。聊天和协同编辑使用 WebSocket。实时交易仪表板在最后一段链路上需要 WebSocket，即使底层价格数据是通过 Webhook 送达的。

专业提示： 先用 Webhook 加上前端简单轮询来做原型。速度较慢，但可以在投入连接管理之前验证事件模型。只有在确认用户确实需要亚秒级更新之后，再添加 WebSocket，而不是更早。

扩展性与运维考量

WebSocket 会改变您的容量计算。每个打开的连接都占用一个文件描述符和一部分内存。超过一个服务器实例之后，您就需要粘性会话或共享的发布/订阅层，才能让消息送达任何实例上的客户端。这是真正的基础设施，而不是一个配置开关。

Webhook 的扩展方式不同，因为它们在两次调用之间不保持状态，这正是它们适合无服务器和可缩容至零环境的原因。函数启动、处理 POST，然后消失。

在生产规模下，有几种模式可以让这两种模型保持稳定：

  • 将入站 Webhook 经由队列（SQS、Pub/Sub、RabbitMQ）路由，使突发的事件不会压垮您的处理程序
  • 当大量事件在短时间内触发时，对 WebSocket 广播进行批处理或防抖
  • 对多次幂等处理仍然失败的 Webhook 投递使用死信队列
  • 监控 WebSocket 服务器的连接流失，以及 Webhook 一侧重试队列的深度；两者都是客户察觉任何问题之前的早期预警信号

安全差异与推荐防护措施

Webhook 与 WebSocket 的失败方式不同，因此需要不同的防护。Webhook 安全的核心是证明请求确实来自可信方：请求头中的 HMAC 签名、用于阻止重放攻击的时间戳，以及严格的 TLS。WebSocket 安全的核心则是连接本身。OWASP WebSocket 安全备忘单指出，WebSocket 没有内置认证；它建议在每次握手时依据白名单校验 Origin 请求头，并警告生产环境中不要使用未加密的 ws:// 连接。它还指出，消息可能携带注入负载，因此应在认证之后再对其进行校验。

以下防护措施值得从第一天起就纳入设计：

  • 定期轮换 HMAC 密钥，并记录每次投递尝试及其签名状态
  • 拒绝时间戳过旧的 Webhook 负载，以阻止重放；提供商会对时间戳进行签名
  • 使用 wss://，并在每次 WebSocket 握手时校验 Origin 请求头
  • 限制每个客户端的并发 WebSocket 连接数，并对消息频率进行限流
  • 即使在认证之后，也要在服务器端校验负载，因为有效的令牌并不保证消息有效

Chaingateway 在您于个人资料中设置专属密钥后，会使用 HMAC 为 Webhook 签署 X-Signature，具体见 Webhook 安全指南。重新生成密钥会立即生效，因此请同时更新您的接收端。签名由交易 ID 和密钥计算得出，不包含时间戳，因此重放防护必须通过按交易 ID 去重来实现。相关背景请参阅我们的功能介绍文章。

一个真实模式：Webhook 驱动 WebSocket 扇出

在生产环境中反复出现的模式是：接收 Webhook，校验，入队，然后由工作进程通过 WebSocket 将结果扇出给已连接的客户端。它在接收端提供了至少一次 HTTP 投递的持久性，在界面端提供了持久连接的低延迟。

步骤如下：

  • 接收 Webhook POST，并在处理负载之前校验 HMAC 签名
  • 将已校验的事件入队，使缓慢的下游工作进程永远不会阻塞 HTTP 响应
  • 处理事件（更新数据库记录，将付款标记为已确认）
  • 将结果发布到您的 WebSocket 服务器订阅的发布/订阅通道或代理
  • 把更新推送给所有已连接且对该事件感兴趣的客户端

这一模式将接收与投递解耦：Webhook 是入站机制，代理位于中间，WebSocket 负责送达浏览器或应用的最后一段。Chaingateway 的事件通知 Webhook 投递的是已解码、带 HMAC 签名的通知，这在该流程中省去了一步，因为您在采取行动之前无需解析原始的区块链数据。

默认选择与接下来需要关注的内容

对于服务器之间的一切通信，默认使用 Webhook，尤其是在无服务器基础设施上，保持连接打开毫无架构意义。当有人正盯着屏幕，等待某个内容在一秒之内发生变化时，默认使用 WebSocket。大多数真实系统最终会两者结合使用，而不是教条地二选一，这并非妥协，通常正是正确的设计。

请关注 WebTransport 和 WebSocketStream。两者都尚未完全取代 WebSocket，但它们针对背压和流处理方面的缺口，而正是这些缺口让原始 WebSocket 代码难以正确编写。

常见问题

什么正在取代 WebSocket？

目前尚无任何技术完全取代 WebSocket。WebTransport 和 WebSocketStream 是新兴的替代方案，旨在更干净地处理背压和多路复用流。浏览器支持仍不完整，因此就今天而言，WebSocket 仍是大多数实时功能的实用默认选择。

ChatGPT 使用的是 SSE 还是 WebSocket？

在浏览器中流式输出 AI 响应通常使用服务器发送事件（SSE）进行单向的 token 流式传输，因为客户端大多只需接收、无需发送持续的数据。一些实时语音或多轮交互功能则改用 WebSocket，因为其中双向交换更加重要。

使用 Webhook 有哪些缺点？

Webhook 需要一个可公开访问的端点，这会带来防火墙和安全方面的考量；而且投递通常是至少一次，这意味着您的处理程序必须能够容忍重复事件。如果事件触发时您的端点宕机，且重试已经过期，该事件可能会悄无声息地丢失，除非您为此建立了监控。

Webhook 有哪些例子？

常见例子包括付款确认通知、Git 推送和拉取请求事件、CI/CD 流水线触发，以及区块链网络上的充值或交易提醒。Chaingateway 的基于 Webhook 的充值处理是一个具体示例，它无需轮询区块链节点即可自动确认资金到账。
