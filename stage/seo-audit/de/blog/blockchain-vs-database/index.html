Blockchain vs. Datenbank: Die wichtigsten Unterschiede

Wie sich eine Blockchain von einer klassischen Datenbank unterscheidet: Schreibmodell, Konsens, Latenz, Kosten pro Schreibvorgang und ein Hybridmuster.

Kapitel
C
Chaingateway Team
Blockchain-Experten

Geprüft von Maurice Sobiera

Eine Blockchain ist ein Hauptbuch, das auf vielen unabhängigen Nodes kopiert wird. Diese Nodes müssen sich über jeden neuen Block einig sein. Eine Datenbank ist ein Speicher, den ein einziger Betreiber führt, der entscheidet, wer lesen und schreiben darf. Der Unterschied liegt im Vertrauen: Eine Blockchain funktioniert ohne vertrauenswürdigen Betreiber, eine Datenbank setzt auf einen. Die meisten Anwendungen brauchen eine Datenbank.

Die beiden Begriffe werden noch immer gleichgesetzt, oder man sagt, „Blockchain ist nur eine weitere Datenbank“. Diese Sicht führt zu Architekturfehlern, denn die Technologien beantworten unterschiedliche Fragen. Eine Datenbank beantwortet, wie Daten effizient gespeichert und abgefragt werden. Eine Blockchain beantwortet, wie sich mehrere Parteien, die einander nicht trauen, auf gemeinsame Daten einigen können.

Dieser Artikel vergleicht beide in einer Tabelle mit zehn Zeilen und betrachtet danach jeden Unterschied einzeln. Er endet mit dem Muster, das die meisten produktiven Systeme nutzen: Datenbank und Blockchain arbeiten zusammen.

Was ist eine Blockchain (und eine „Blockchain-Datenbank“)?

Eine Blockchain ist ein verteiltes Hauptbuch: ein Protokoll von Transaktionen, das in einem Peer-to-Peer-Netz auf vielen unabhängigen Nodes repliziert wird. Jeder Node wirkt an der Verwaltung des Hauptbuchs mit. Wenn neue Daten hinzukommen sollen, muss zuerst die Mehrheit der Nodes einen Konsens erreichen. Dieser Einigungsschritt macht Manipulation so schwer: Ein Angreifer müsste die Mehrheit des Netzwerks überwältigen, nicht einen einzelnen Server hacken.

Jede Transaktion erhält einen Zeitstempel und eine Position in der Kette. So kann jeder Node die gesamte Historie nachverfolgen und prüfen. Diese Kombination aus Replikation und Prüfbarkeit meinen Menschen, wenn sie von einer „Blockchain-Datenbank“ sprechen. Der Begriff ist unscharf. Wie wir sehen werden, gibt eine Blockchain die meisten Eigenschaften auf, die eine Datenbank im Alltagssinn ausmachen.

Was ist eine klassische Datenbank?

Eine klassische Datenbank nutzt eine Client-Server-Architektur. Clients verbinden sich mit einem zentralen Server, und dessen Betreiber entscheidet, wer lesen und schreiben darf. Der Administrator prüft die Identität eines Nutzers, bevor er Zugriff gewährt, und kann jeden Datensatz jederzeit ändern.

Zentralisierung ist zugleich Schwäche und Stärke. Wird die zentrale Instanz kompromittiert, ist der gesamte Datenbestand betroffen. Deshalb gibt es Backups. Weil eine Partei alles kontrolliert, sind Daten leicht zu verwalten, schnell abzufragen und günstig zu speichern. PostgreSQL und MySQL betreiben die meisten Anwendungen, die Sie nutzen.

Der Rest des Artikels erläutert die Zeilen, die Architekturen entscheiden: Kontrolle, Schreibmodell und Leistung.

Kontrolle

Der größte Unterschied zwischen Blockchain und Datenbank ist, wer das Sagen hat. In einer klassischen Datenbank prüft eine zentrale Instanz Nutzer, bevor sie Zugriff erhalten. Die Macht über die Daten liegt bei einer Partei oder einer kleinen Gruppe.

Eine Blockchain hat keine solche Instanz. Jeder Node trägt zum Betrieb des Hauptbuchs bei, und die Nodes tauschen Informationen ohne überwachenden Administrator aus. Neue Daten gelangen erst in die Kette, wenn die Nodes einen Konsens erreicht haben. Niemand kann einen Datensatz heimlich umschreiben, weil alle anderen eine Kopie halten, die etwas anderes sagt.

Architektur

Eine traditionelle Datenbank läuft als Client-Server-Architektur. Das Modell skaliert vom Laptop bis zum Rechenzentrum. Die gesamte Kommunikation läuft über eine Verbindung zum zentralen Server. Einen Konsensschritt gibt es nicht, weil das Wort des Administrators endgültig ist.

Eine Blockchain läuft als Peer-to-Peer-Netz. Peers verbinden sich direkt miteinander und arbeiten zusammen, um den nächsten Block über einen Konsensalgorithmus zu vereinbaren. Der klassische ist Proof of Work. Dabei setzen Teilnehmer Rechenleistung ein, um Transaktionen zu validieren.

Bitcoin nutzt ihn laut dem Bitcoin-Whitepaper weiterhin. Ethereum ist 2022 auf Proof of Stake umgestiegen. Das ersetzt das Rechenrennen durch wirtschaftliche Sicherheiten. In beiden Fällen gibt es den Einigungsschritt eben deshalb, weil kein Administrator existiert, dessen Wort endgültig sein könnte.

Schreibmodell: CRUD vs. Append-only

Eine zentrale Datenbank unterstützt die vier CRUD-Operationen: anlegen, lesen, aktualisieren, löschen. Die Datenverarbeitung ist einfach, weil alles bearbeitbar ist.

Eine Blockchain unterstützt zwei: lesen und schreiben. Sobald eine Transaktion in der Kette steht, folgt kein Update und kein Delete. Diese Unveränderlichkeit ist der Zweck, denn sie verhindert Manipulation und gibt jedem Teilnehmer eine prüfbare Historie. Sie wirkt aber in beide Richtungen. Ein Fehler, der falsche Daten schreibt, lässt sich nicht mit einer UPDATE-Anweisung beheben. Personenbezogene Daten, die auf Anfrage löschbar sein müssen (Art. 17 DSGVO), gehören überhaupt nicht auf die Chain.

Leistung und Kosten pro Schreibvorgang

Traditionelle Datenbanken sind schneller, und zwar deutlich. Ein Datenbank-Schreibvorgang ist eine Plattenoperation auf einer Maschine. Ein Blockchain-Schreibvorgang durchläuft Signaturprüfung, Konsens und Replikation auf jeden Node, bevor er zählt. In öffentlichen Chains dauert das Sekunden bis Minuten, nicht Millisekunden.

Schreibvorgänge kosten außerdem Geld. Jede Blockchain-Transaktion kostet eine Gebühr in der nativen Münze der Chain. Die Gebühr soll die Nodes für ihre Prüfarbeit entschädigen.

Gebühren schwanken je nach Chain und Auslastung. Auf TRON verbraucht ein Token-Transfer Energy und Bandwidth, die Sie entweder staken oder mit TRX bezahlen. Ein Datenbank-Schreibvorgang auf Hardware, die Sie ohnehin besitzen, kostet nichts, das Sie einzeln abrechnen würden. Liegt Ihre Last bei Tausenden Schreibvorgängen pro Sekunde, entscheidet diese Frage allein zugunsten der Datenbank.

Wie lange dauert es, bis ein Schreibvorgang abgeschlossen ist?

Ein Datenbank-Commit dauert Millisekunden. Bei einer Blockchain hängt die Zeit bis zur Finalität von den Konsensregeln der Chain ab. Die Tabelle nennt die beiden Chains, die dieser Artikel als Beispiele verwendet.

Durchsatzwerte von Chains sind schwerer zu vergleichen. Veröffentlichte Angaben zu Transaktionen pro Sekunde nennen oft theoretische Spitzenwerte, und sie hängen vom Transaktionsmix ab. Deshalb listen wir sie nicht auf. Chains ändern außerdem ihre Parameter mit der Zeit. Prüfen Sie daher die eigene Dokumentation der Chain, bevor Sie sich auf eine Zahl verlassen.

Der Abstand zur Datenbank bleibt groß. Selbst Chains mit Abwicklungszeiten von wenigen Sekunden verlangen eine Gebühr pro Schreibvorgang und eine Konsensrunde dafür. Chains konkurrieren untereinander um diese Zahlen. Mit Datenbanken konkurrieren sie nicht.

ACID vs. Konsens-Finalität

Datenbank-Leute und Blockchain-Leute sagen beide „die Transaktion ist durchgegangen“ und meinen unterschiedliche Garantien.

In einer Datenbank sind die Garantien die ACID-Eigenschaften. Atomarität: Alle Änderungen einer Transaktion werden angewendet, oder keine. Konsistenz: Constraints gelten vor und nach der Transaktion. Isolation: Parallele Transaktionen sehen nicht die halb erledigte Arbeit der anderen. Dauerhaftigkeit: Nach dem Commit überlebt der Datensatz einen Absturz, weil er auf Platte im Write-Ahead-Log landete. Alle vier werden zum Zeitpunkt des Commits erfüllt, Millisekunden nach Ihrer Anfrage.

Eine Smart-Contract-Chain kommt bei den ersten drei erstaunlich nah heran. Ein Contract-Aufruf ist atomar. Schlägt ein Schritt fehl, wird die gesamte Transaktion zurückgesetzt. Konsistenz liegt im Contract-Code statt in Schema-Constraints. Die Isolation ist die stärkstmögliche: Der Konsens zwingt jede Transaktion in eine globale Reihenfolge. Genau deshalb ist der Durchsatz begrenzt, denn eine Gesamtreihenfolge lässt nichts sicher parallelisieren.

Bei der Dauerhaftigkeit trennen sich die Modelle. Ein Datenbank-Schreibvorgang ist beim Commit dauerhaft. Ein Blockchain-Schreibvorgang in einem frischen Block kann dagegen noch verschwinden, weil konkurrierende Blöcke gewinnen und die Kette reorganisieren können.

An die Stelle der Dauerhaftigkeit tritt die Finalität. Das ist der Moment, ab dem das Protokoll garantiert, dass die Transaktion nicht mehr verdrängt werden kann. Auf TRON dauert das 19 Blöcke, etwa 57 Sekunden.

Auf Ethereum dauert es zwei Epochen mit Validator-Attestierungen, etwa 15 Minuten. Blöcke dazwischen sind wahrscheinlich sicher, aber nicht beweisbar sicher. Daraus folgt direkt die Regel für Zahlungssysteme: Schreiben Sie einem Kunden bei der Finalität gut, nicht bei der ersten Aufnahme. Sonst bauen Sie eine Umkehrlogik, die Sie aufwendig testen müssen.

Wo passt CAP?

Das CAP-Theorem besagt: Ein verteiltes System muss sich bei einer Netzwerkpartition entscheiden, ob es konsistent oder verfügbar bleibt. Ein einzelner Postgres-Server umgeht die Frage völlig, weil es nichts zu partitionieren gibt. Das ist ein unterschätzter Grund, warum Einzelknoten-Datenbanken angenehm zu betreiben bleiben. Verteilte Datenbanken treffen eine Wahl und dokumentieren sie.

Blockchains sind verteilte Systeme und müssen sich ebenfalls entscheiden. Longest-Chain-Designs wie Bitcoin wählen Verfügbarkeit. Bei einer Partition erzeugen beide Seiten weiter Blöcke. Die Konsistenz wird danach repariert, wenn ein Zweig gewinnt. Genau das ist eine Reorganisation.

Finalitätsbasierte Designs neigen zur anderen Seite. Sind zu viele Validatoren nicht erreichbar, finalisiert Ethereum nicht mehr, und die Super Representatives von TRON solidifizieren keine Blöcke mehr. Sie opfern Fortschritt, um keine widersprüchlichen endgültigen Antworten zu geben. Keine der beiden Wahlen ist falsch. Es heißt aber: „Blockchain“ entkommt den Zielkonflikten verteilter Systeme nicht. Sie ist eine bestimmte Auswahl davon, bezahlt mit Latenz und Gebühren.

Was jede Seite gut kann und was sie kostet

Die Stärken der Datenbank verstärken sich gegenseitig. Abfragen in Millisekunden und günstige Schreibvorgänge sind der sichtbare Teil. Darunter liegen Jahrzehnte an Werkzeugen: Backups, Point-in-Time-Recovery, Replikation, Migrationen und Indizes, die auf Ihre Abfragemuster abgestimmt sind. Daten bleiben standardmäßig privat und lassen sich auf Anfrage löschen, was die Regulierung manchmal verlangt.

Der Preis dieser Bequemlichkeit ist konzentriertes Vertrauen. Der Betreiber kann alles ändern. Ein Audit-Trail ist deshalb nur so glaubwürdig wie der Betreiber. Zwei Unternehmen, die einander nicht trauen, können keinen gemeinsamen Postgres als Quelle der Wahrheit nutzen, denn eines von beiden müsste ihn hosten.

Die Stärken der Blockchain sind genau dieses fehlende Stück. Niemand betreibt sie allein, also kann niemand sie allein umschreiben. Jeder mit einem Node kann die Historie prüfen, auch Außenstehende, die Sie nie eingebunden haben. Für Zahlungen bietet sie eine Abwicklungsschiene, über die jede Wallet jede andere bezahlen kann, ohne dass ein Vermittler beide Seiten genehmigt.

Die Kosten spiegeln die Bequemlichkeiten der Datenbank. Jeder Schreibvorgang wird über Gebühren abgerechnet und vom Konsens getaktet. Der Speicher ist nur anhängbar, und alles ist öffentlich, sofern Sie nichts dagegen konstruieren. Das operative Sicherheitsnetz fehlt: Kein Support-Ticket macht eine Transaktion rückgängig, und ein verlorener Schlüssel ist verlorener Wert, kein Passwort-Reset.

Die beiden Listen überschneiden sich kaum, deshalb gewinnt keine nach Punkten. Eine Frage entscheidet: Hat Ihr System einen vertrauenswürdigen Betreiber, oder muss es ohne einen funktionieren?

Wann was nutzen: eine Entscheidungsliste

  • Wenn eine Partei die Daten kontrolliert und ihre Nutzer das akzeptieren, nutzen Sie eine Datenbank. Sie ist schneller, günstiger und leichter zu betreiben.
  • Wenn mehrere Parteien in gemeinsamen Zustand schreiben müssen, ohne einander oder einem Vermittler zu trauen, rechtfertigt eine Blockchain ihren Aufwand. Das ist die eine Aufgabe, die Datenbanken nicht erledigen können.
  • Wenn Datensätze für Außenstehende nachweislich unverändert sein müssen (Audits, Abwicklung zwischen Unternehmen), liefert eine Blockchain das ohne Notar.
  • Wenn Sie Updates und Löschungen brauchen oder personenbezogene Daten speichern, die Löschanfragen unterliegen, bewahren Sie sie in einer Datenbank auf.
  • Wenn Sie niedrige Latenz oder hohen Schreibdurchsatz brauchen, dann Datenbank, ohne Diskussion.
  • Wenn Sie Krypto-Zahlungen annehmen oder senden, ist die Abwicklungsschicht eine Blockchain, ob Ihnen das gefällt oder nicht. Der sinnvolle Schritt ist, alles andere außerhalb der Chain zu halten. Das führt zum Hybridmuster.

Drei Architekturen im Durchgang

Abstrakte Kriterien werden leichter greifbar, wenn Sie sie an konkreten Systemen durchspielen. Hier sind drei, jeweils eine pro Architektur.

Ein Treueprogramm: reine Datenbank

Ein Händler gibt Punkte aus, Kunden lösen sie an der Kasse ein, und das Marketingteam passt Salden an, wenn eine Aktion schiefgeht. Alle Eigenschaften dieses Systems zeigen in dieselbe Richtung. Eine Firma kontrolliert die Punkte, und die Kunden akzeptieren das. Es gibt also keine Vertrauenslücke zu überbrücken. Das Schreibvolumen ist hoch, die Latenz an der Kasse muss unsichtbar bleiben, und Kontodaten fallen unter Löschregeln.

Postgres erledigt all das ohne Aufhebens. Eine On-Chain-Version würde pro gutgeschriebenem Punkt eine Gebühr zahlen und an der Kasse auf den Konsens warten. Sie könnte eine DSGVO-Löschanfrage nicht erfüllen. Auf einer Blockchain wird alles schlechter, deshalb dauert die Entscheidung etwa eine Minute.

Eine dezentrale Börse: rein on-chain

Kehren Sie nun jede Annahme um. Eine DEX existiert, damit Fremde handeln können, ohne dass ein Betreiber ihre Gelder hält. Fügen Sie einen vertrauenswürdigen Datenbankbetreiber hinzu, und das Produkt hat keinen Grund mehr zu existieren.

Deshalb lebt die gesamte Zustandsmaschine in Contracts: Salden, Pool-Reserven und die Swap-Logik. Jeder Handel läuft über den Konsens und zahlt dafür. Die Einschränkungen der Chain prägen dann das Design. Klassische Orderbücher brauchen Orders, die so oft platziert, geändert und storniert werden, dass gebührenpflichtige Schreibvorgänge zu teuer würden. Das ist ein großer Grund, warum automatisierte Market Maker on-chain die Oberhand gewonnen haben.

Nutzer zahlen Gebühren und warten Sekunden auf Trades, weil Vertrauenslosigkeit das Produkt ist, für das sie gekommen sind. Beachten Sie, was die DEX trotzdem nicht on-chain legt: Ihr Web-Frontend, Analysen und Preischarts laufen auch hier auf gewöhnlichen Servern und Datenbanken.

Krypto-Einzahlungen für ein SaaS: der Hybrid

Der übliche kommerzielle Fall liegt zwischen den Extremen. Ein SaaS möchte USDT von Kunden weltweit annehmen. Seine Abos, Rechnungen und Nutzerkonten liegen bereits in einer Datenbank und sollten dort bleiben.

Die Chain ist genau einmal unvermeidlich, bei der Abwicklung. Alles andere wird bewusst von ihr ferngehalten. Dieses dritte Szenario ist das Muster, das die meisten Teams tatsächlich bauen. Deshalb bekommt es die ausführliche Durchsicht im nächsten Abschnitt.

Das Hybridmuster: Datenbank außerhalb der Chain, Abwicklung on-chain

Produktive Zahlungssysteme entscheiden sich fast nie für das eine oder das andere. Sie teilen die Arbeit auf: Die Blockchain wickelt Werte ab, die Datenbank erledigt alles andere. Kundendaten, Bestellungen, Salden und Session-Daten liegen in PostgreSQL oder MySQL, wo sie abfragbar und bearbeitbar sind. Nur die eigentliche Bewegung von Geld berührt die Chain, und das über eine API. So betreibt die Anwendung nie einen eigenen Node.

Ein konkreter Einzahlungsablauf sieht so aus:

  1. Ein Kunde möchte zahlen. Ihr Backend weist ihm über einen API-Aufruf eine eigene Einzahlungsadresse zu und speichert die Zuordnung von Adresse zu Kunde in Ihrer Datenbank.
  2. Der Kunde sendet USDT an diese Adresse. Sie fragen die Chain nicht ab. Stattdessen wird ein Webhook ausgelöst, sobald der Transfer erkannt ist.
  3. Ihr Endpunkt prüft den Header X-Signature des Webhooks, schreibt die Einzahlung in Ihre eigene Datenbank und schreibt dort das Guthaben des Kunden gut.

Der Handler ist mit Absicht unspektakulär:

Die Webhook-Nutzlast enthält txid, from, to, amount, contractaddress und blocknumber. Der Insert braucht also nichts über den Request-Body hinaus. Ab diesem Punkt liest Ihre Anwendungslogik Salden aus Ihren eigenen Tabellen, mit Datenbankgeschwindigkeit und Datenbankkosten. Die Chain wird nur wieder befragt, wenn Geld abfließt.

Chaingateway signiert Webhooks mit einem Header X-Signature, sobald Sie ein persönliches Geheimnis setzen. Details stehen unter Webhook-Signaturen prüfen. Webhooks werden nicht automatisch wiederholt. Fehlgeschlagene Zustellungen stehen unter GET /api/v2/tron/webhooks/notifications/failed. Jede senden Sie mit POST /api/v2/tron/webhooks/notifications/{id}/retry erneut. Vergangene Benachrichtigungen lassen sich über GET /api/v2/tron/webhooks/notifications abrufen, um nach einem Ausfall abzugleichen.

Das vollständige Setup steht im Webhook-Leitfaden. Der Schnellstart behandelt den ersten API-Aufruf.

Welcher gewinnt also?

Jede Seite ist besser in dem, was die andere nicht kann. Die Datenbank gewinnt eindeutig bei der Verarbeitung von Daten: Leistung, Skalierbarkeit, Abfragekraft und Betriebskosten. Die Blockchain gewinnt dort, wo kein vertrauenswürdiger Betreiber existiert. Sie ist manipulationsresistent, von jedem prüfbar und leicht zu automatisieren, weil jede Wallet dasselbe Protokoll spricht.

Die praktische Antwort für die meisten Teams lautet: beides, verbunden durch eine API. Datenbank für die Anwendung, Blockchain für die Abwicklung. Zur Auswahl dieser API-Schicht siehe unseren Vergleich von Blockchain-API-Anbietern. Die Tarife für Chaingateway stehen auf der Preisseite.

Häufig gestellte Fragen

Nur im weitesten Sinne: Sie speichert Daten dauerhaft. Der Alltagsdefinition genügt sie nicht. Einträge lassen sich nicht aktualisieren oder löschen, Abfragen sind begrenzt, und Schreibvorgänge kosten Geld und brauchen Sekunden bis zur Finalität. „Vertrauensmaschine mit angeschlossenem Speicher“ trifft es besser als „Datenbank“.

Für eine normale Anwendung nein. Latenz, Gebühren pro Schreibvorgang und die fehlenden Operationen UPDATE und DELETE schließen sie als primären Datenspeicher aus. Eine Blockchain ersetzt die Abwicklungsschicht und den Notar, nicht Postgres.

Der Begriff meint meist das Hauptbuch selbst: die Transaktionshistorie, repliziert über die Nodes. Manche Produkte indexieren Chain-Daten zusätzlich in einer gewöhnlichen Datenbank, damit man sie mit SQL abfragen kann. Das ist nützlich, aber dann fragen Sie wieder eine Datenbank ab, nicht eine Blockchain.

Weil jeder Schreibvorgang signiert, verbreitet, vom Konsens bestätigt und auf jeden Node repliziert werden muss, bevor er final ist. Ein Datenbank-Schreibvorgang ist eine Maschine, die auf die eigene Platte schreibt. Die Langsamkeit ist der Preis für den Wegfall des vertrauenswürdigen Betreibers, kein Implementierungsfehler, der mit Optimierung verschwindet.

Teilweise. Eine Smart-Contract-Transaktion ist atomar (sie wird vollständig angewendet oder vollständig zurückgesetzt), Contract-Code erzwingt Konsistenz, und der Konsens liefert eine Gesamtreihenfolge. Das ist stärkere Isolation, als die meisten Datenbanken verwenden. Die Ausnahme ist die Dauerhaftigkeit: Eine Transaktion ist erst bei der Finalität abgewickelt, je nach Chain Sekunden bis Minuten nach der Aufnahme. Bis dahin kann eine Reorganisation sie verdrängen. Systeme, die Geld gutschreiben, sollten sich an der Finalität orientieren, nicht an der ersten Aufnahme.

Fast immer nur an einer Stelle: bei Zahlungen. Ein Unternehmen braucht selten gemeinsamen Zustand mit Parteien, denen es misstraut. Wenn es Krypto annimmt, ist die Abwicklungsschicht per Definition eine Blockchain. Der praktikable Aufbau ist das oben beschriebene Hybridmuster: Die Chain wickelt Werte ab, alles Operative bleibt in Ihrer Datenbank, verbunden über eine API statt über einen eigenen Node.

Sie lesen die Chain nicht bei jeder Anfrage. Explorer und Wallets fragen Indizes ab: Chain-Daten, die in gewöhnliche Datenbanken kopiert und von dort mit Datenbankgeschwindigkeit ausgeliefert werden. Zahlungssysteme machen dasselbe, Webhook für Webhook. Sie schreiben jede bestätigte Einzahlung in ihre eigenen Tabellen und lesen Salden von da an lokal. Die Chain ist die Quelle der Wahrheit, die Datenbank die Arbeitskopie.
