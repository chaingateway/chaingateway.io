Einen Ethereum-Node einrichten (Anleitung 2026)

Ethereum-Node betreiben: Hardware-Anforderungen, Setup mit Geth und Lighthouse per systemd, Sync-Dauer, Kosten und wann eine API die bessere Wahl ist.

Kapitel

Blockchain-Experten

Geprüft von Maurice Sobiera

Ein Ethereum-Node ist ein Computer, der einen Execution-Client und einen Consensus-Client betreibt, eine geprüfte Kopie der Blockchain hält und JSON-RPC für das Lesen der Chain und das Senden von Transaktionen bereitstellt. Laut ethereum.org braucht ein Full Node mindestens 16 GB RAM und eine 2-TB-NVMe-SSD. Diese Anleitung richtet einen Node mit Geth und Lighthouse ein.

Ein eigener Node gibt Ihnen einen JSON-RPC-Endpunkt ohne Rate Limits des Providers, und kein Dritter sieht Ihre Abfragen. Die Anleitung führt von einem leeren Ubuntu-Server zu einem synchronisierten Node mit Copy-paste-Befehlen. Beide Clients laufen über systemd. Außerdem behandelt sie Hardware, Sync-Modi, laufende Kosten und den Punkt, ab dem eine API die bessere Wahl ist.

Was ist ein Ethereum-Node?

Ein Ethereum-Node ist ein Computer, auf dem Ethereum-Client-Software läuft. Er speichert eine Kopie der Blockchain, prüft jeden eingehenden Block gegen die Protokollregeln und beantwortet JSON-RPC-Anfragen von Wallets und Anwendungen. Die Ethereum-Entwicklerdokumentation beschreibt diese Software als Client und erklärt die Rollen der beiden Schichten.

Seit dem Merge im September 2022 besteht ein Node aus zwei Programmen, die nebeneinander laufen. Der Execution-Client (Geth, Nethermind, Besu, Erigon oder Reth) hält den State, führt Transaktionen aus und beantwortet JSON-RPC-Aufrufe. Der Consensus-Client (Lighthouse, Prysm, Teku, Nimbus oder Lodestar) übernimmt Proof of Stake. Er folgt der Beacon Chain und teilt dem Execution-Client mit, welcher Block der aktuelle Head ist.

Die beiden sprechen über einen authentifizierten lokalen Port (8551) und erkennen sich mit einem gemeinsamen JWT-Secret. Ein Node ohne den anderen funktioniert nicht. Dieses Detail stolpert die meisten Erstbetreiber.

Es gibt drei Speicherprofile.

  • Ein Full Node behält den aktuellen State und entfernt alte Daten per Pruning.
  • Ein Archive-Node hält jeden historischen State. Die Tabelle von ethereum.org nennt 12 TB oder mehr für Geth, Nethermind und Besu sowie etwa 2,2 bis 2,5 TB für Reth und Erigon.
  • Ein Light Node lädt nur Header herunter. Laut Geth-Dokumentation funktioniert Light Sync seit dem Wechsel zu Proof of Stake derzeit nicht. Deshalb ist er kein praktikabler Zugangsweg.

Welche Anforderungen gelten für einen Ethereum-Node?

Ein Full Node braucht mindestens 16 GB RAM und eine 2-TB-NVMe-SSD. Diese Angaben stammen aus dem Node-Leitfaden von ethereum.org. Für die Empfehlungsspalte nennt er außerdem die Hardware-Angaben aus EIP-7870. Ein Archive-Node ist ein eigenes Projekt. Ein Validator braucht mehr CPU, RAM und Upload-Bandbreite als ein reiner Full Node.

KomponenteMinimumEmpfohlen (EIP-7870)
CPU2+ Kerne4+ Kerne (8+ bei Validierung)
RAM16 GB (32 GB für Stabilität empfohlen)32 GB (64 GB bei Validierung)
Storage2 TB NVMe SSD4 TB NVMe SSD, keine DRAM-losen oder QLC-Platten
Netzwerk25+ Mbit/s50 Mbit/s Download, 15+ Mbit/s Upload (25+ Upload bei Validierung)

Zwei Zeilen brauchen eine Erklärung.

Storage muss NVMe sein. Beim Sync werden viele kleine zufällige Datenblöcke mit hoher Rate geschrieben. Die Geth-Dokumentation warnt, dass HDDs und günstigere SSDs Mühe haben können, die Chain zu synchronisieren. Cloud-Volumes mit Standard-IOPS fallen oft in dieselbe Kategorie. ethereum.org fügt hinzu, dass 2 TB bis 2027 wahrscheinlich überschritten werden. Planen Sie deshalb für Wachstum.

Der Speicherplatz ist der Engpass. Die Tabelle von ethereum.org nennt 500 GB oder mehr für eine per Snap-Sync gefüllte Geth- oder Nethermind-Datenbank und 800 GB oder mehr für Besu. Der Consensus-Client braucht weitere 200 GB oder so für die Beacon-Daten. Die Geth-Dokumentation gibt an, dass die Datenbank bei der Standard-Cache-Größe um etwa 14 GB pro Woche wächst, Stand September 2022. Prüfen Sie die Größe Ihres eigenen Datenverzeichnisses nach dem ersten Sync, statt sich auf eine veröffentlichte Zahl zu verlassen.

Auch der Traffic zählt. ethereum.org empfiehlt eine ungedrosselte Verbindung, weil der initiale Sync und die Daten, die Ihr Node verbreitet, eine Obergrenze überschreiten können. Linux, macOS und Windows funktionieren. Jeder Befehl unten setzt Ubuntu 24.04 voraus, einen verbreiteten Server-Standard.

Wege, einen Node zu betreiben

Sie müssen nicht alles von Hand zusammenbauen. Plug-and-play-Boxen wie DappNode und Avado sind vorkonfigurierte Maschinen mit Dashboard: kaufen, anschließen, dem Assistenten folgen. ARM-Boards funktionieren ebenfalls. Ethereum on ARM stellt Images mehrerer Execution- und Consensus-Clients für Raspberry Pi und andere ARM-Boards bereit. Launcher automatisieren den manuellen Weg: eth-docker (Docker-basiert, Terminal-Kenntnisse nötig), Stereum (installiert Clients per SSH auf einem entfernten Server, mit GUI), NiceNode (Client wählen, in wenigen Klicks starten) und Sedge (ein CLI-Assistent von Nethermind, der eine Docker-Konfiguration erzeugt).

Cloud oder lokal? Ein VPS reicht für die Entwicklung. ethereum.org weist darauf hin, dass schon ein großer Teil der Nodes bei Cloud-Anbietern läuft, was für das Netzwerk einen Single Point of Failure bedeutet. Wenn Zensurresistenz zu Ihrer Motivation gehört, betreiben Sie den Node auf eigener Hardware.

Der Rest dieser Anleitung beschreibt das manuelle Setup. Es lehrt Sie am meisten, und alles, was Sie dabei lernen, lässt sich auf die Launcher übertragen.

Wie lange dauert der Sync?

Lighthouse startet mit Checkpoint-Sync von einem aktuellen, finalisierten State und füllt die historischen Blöcke im Hintergrund auf. Geth lädt im Snap-Sync-Modus (dem Standard) den aktuellen State von Peers herunter und baut den State-Trie lokal neu auf. Die Dauer hängt vor allem von Platte und Bandbreite ab, und das Geth-Log zeigt ETA-Werte für den State-Download. Das Ende bildet die Phase „State heal”, die sich nicht messen lässt, weil der Umfang der Fehler erst feststeht, wenn der State fertig neu erzeugt ist. Läuft sie tagelang ohne Abschluss, ist Ihre Platte zu langsam. Siehe Fehlerbehebung.

Nach dem initialen Sync beruhigt sich die Lage. Seit Version 1.14.0 wechselte Geth den Standard-State-Scheme von hash auf path, laut den Release Notes. Ältere Anleitungen warnen vor einer Datenbank, die so lange wächst, bis man sie offline prunt. Das gilt für das alte Hash-basierte Layout. Geth 1.17 kann außerdem Pre-Merge-Historie mit --history.chain postmerge verwerfen, wie die Release Notes zu v1.17.1 zeigen. Das gibt Platz frei, falls er knapp wird.

Welcher Sync-Modus ist der richtige?

Das Flag --syncmode in der Geth-Unit bestimmt, wie viel der Chain Sie selbst prüfen und wie viel Speicherplatz Sie dafür zahlen. Es gibt drei Modi. Welcher passt, ergibt sich aus den Fragen, die der Node beantworten soll.

Snap-Sync ist der Standard und der Modus, den diese Anleitung nutzt. Laut der Geth-Dokumentation zu den Sync-Modi startet Geth bei einem aktuellen Block, lädt den State von Peers herunter und heilt danach den State-Trie. Das Ergebnis ist ein nutzbarer Full Node deutlich früher als bei einem Block-für-Block-Sync ab dem Genesis-Block.

Full Sync (--syncmode full) führt jeden Block seit dem Genesis-Block erneut aus, statt den State herunterzuladen. Das Ergebnis auf der Platte ist dieselbe geprunte Datenbank, aber der Sync dauert weit länger als Snap-Sync. Man wählt ihn aus einem Grund: Man will dem State-Download nicht vertrauen und die gesamte Historie auf der eigenen Maschine neu berechnen. Das ist eine Forschungshaltung und keine betriebliche Notwendigkeit.

Der Archive-Modus liegt auf einer anderen Achse: --gcmode archive auf einem Full Sync behält jeden Zwischenstate, statt zu prunen. Nur ein Archive-Node beantwortet Fragen wie „Wie hoch war dieser Kontostand bei Block 15.000.000?“ oder führt tiefe Traces ohne Neuberechnung aus. Indexer, Steuer-Tools und Analytics-Plattformen brauchen genau das.

Laut der Tabelle von ethereum.org braucht ein vollständiger Archive-Node bei Geth, Nethermind und Besu 12 TB oder mehr. Erigon und Reth speichern die Historie anders und liegen bei etwa 2,5 TB beziehungsweise 2,2 TB. Geth v1.16.0 brachte einen experimentellen, pfadbasierten Archive-Modus. Laut den Release Notes braucht die vollständige State-Historie des Mainnets damit etwa 1,9 TB (ohne die Indizes für Transaktionen und Logs). Standardmäßig behält der Modus nur die letzten 90.000 Blöcke an Historie.

Welche Clients sollte ich betreiben?

Geth plus Lighthouse ist eine solide Standardwahl, und genau diese Beliebtheit ist der Haken. Die Seite zur Client-Vielfalt auf ethereum.org erklärt das Risiko. Ein Bug in einem Consensus-Client mit über 33 Prozent der Nodes könnte verhindern, dass die Consensus-Schicht finalisiert. Ein kritischer Bug in einem Client mit Zweidrittelmehrheit könnte dazu führen, dass die Chain sich spaltet und falsch finalisiert wird. Validatoren auf der falschen Chain drohen dann Slashing.

Aktuelle Anteile finden Sie auf clientdiversity.org und nicht in einer Zahl aus einer Anleitung. Die Verteilung ändert sich, und ethereum.org sagt, dass idealerweise kein Client mehr als 33 Prozent erreichen sollte. Das Netzwerk wird jedes Mal sicherer, wenn ein Betreiber einen Minderheits-Client wählt. Der Betreiber verliert dabei wenig, denn alle Execution-Clients sprechen dasselbe JSON-RPC und alle Consensus-Clients dieselbe Beacon-API.

Für einen ersten Node ist die Kombination aus dieser Anleitung in Ordnung. Für einen zweiten Node oder einen professionellen Betrieb wählen Sie eine Minderheits-Kombination wie Nethermind mit Teku oder Reth mit Nimbus. Das Setup oben lässt sich fast eins zu eins übertragen. Jede Kombination braucht dasselbe JWT-Secret und dieselbe Engine-API-Verdrahtung. Nur Binaries, Flags und Datenverzeichnisse ändern sich.

Was kostet der Betrieb eines Ethereum-Nodes?

Die Kosten hängen davon ab, ob Sie eigene Hardware betreiben oder einen Server mieten. Deshalb zeigt dieser Abschnitt die Rechnung statt Preise. Preise ändern sich monatlich und variieren je nach Land.

Eigene Hardware: Ein Rechner in der Anforderungsklasse (4 bis 8 Kerne, 32 GB RAM, 2 bis 4 TB NVMe) ist eine einmalige Anschaffung. Die laufenden Kosten sind der Strom. Multiplizieren Sie die durchschnittliche Leistungsaufnahme des Rechners in Kilowatt mit 720 Stunden und Ihrem Preis pro kWh. Ein Rechner mit 50 W kommt auf 0,05 kW × 720 h = 36 kWh pro Monat, die Sie mit Ihrem Strompreis multiplizieren. Addieren Sie den Internetanschluss, den Sie ohnehin bezahlen.

Gemieteter Server: 2 TB NVMe sind mehr, als viele VPS-Pläne bieten. Deshalb landen Sie womöglich bei einem Dedicated Server. ethereum.org merkt an, dass der Preis eines gemieteten Servers wegen des nötigen Speichers hoch werden kann. Cloud-Instanzen mit provisionierten IOPS kosten meist mehr als die vergleichbare dedizierte Maschine. Vergleichen Sie Angebote deshalb für dieselbe Plattengröße.

Ihre Zeit: Das erste Setup dauert mit dieser Anleitung einen Nachmittag. Danach aktualisieren Sie die Clients und schauen gelegentlich in die Logs. Wenn Sie Ihre Zeit verrechnen, gehört diese Zeile zur Gesamtsumme.

Monitoring und Health Checks

Drei Fragen decken die Gesundheit eines Nodes ab: Läuft der Prozess, ist er synchronisiert, hat er Peers? systemd beantwortet die erste mit systemctl is-active geth lighthouse. Für die beiden anderen gibt es Endpunkte auf beiden Ebenen:

Die REST-API von Lighthouse lauscht über das --http-Flag, das schon in der Unit steht, auf Port 5052. Der Endpunkt /eth/v1/node/health kodiert den Sync-Status im HTTP-Statuscode. Das macht ihn zu einer natürlichen Prüfung für Skripte und Load Balancer. /eth/v1/node/syncing liefert die Distanz in Slots, falls Sie die Zahl brauchen. Ein Cron-Job, der diese Checks und df -h /var/lib/geth ausführt und bei Auffälligkeiten eine Mail schickt, ist für einen persönlichen Node ein vollständiges Monitoring.

Für Dashboards fügen Sie --metrics bei Geth (Prometheus-Endpunkt auf Port 6060) und --metrics bei Lighthouse (Port 5054) hinzu. Halten Sie beide auf localhost und importieren Sie die Grafana-Dashboards, die beide Projekte veröffentlichen. Richten Sie vor allen anderen zwei Alerts ein, was auch immer Sie bauen: Festplattenbelegung über 85 Prozent und eine Blockhöhe, die zehn Minuten lang stillsteht. Diese beiden fangen fast jeden echten Ausfall ab, bevor Ihre Nutzer ihn bemerken.

Wartung und Upgrades

Client-Updates sind nicht optional. Hard Forks erfordern neue Software. Ein Node mit einer alten Version folgt der Chain am Fork-Block einfach nicht mehr. Abonnieren Sie die Release-Feeds von Geth und Lighthouse auf GitHub sowie den Blog der Ethereum Foundation.

Der Ablauf bleibt kurz. Geth aus dem PPA aktualisiert sich mit sudo apt upgrade, danach starten Sie mit sudo systemctl restart geth neu. Bestätigen Sie die Version mit geth version. Lighthouse ist ein einzelnes Binary: Wiederholen Sie den Download aus Schritt 3, ersetzen Sie /usr/local/bin/lighthouse und starten Sie die Unit neu. Lesen Sie die Release Notes vor dem Neustart. Flags werden gelegentlich umbenannt, und ein umbenanntes Flag in einer systemd-Unit bedeutet einen Dienst, der um 2 Uhr nachts nicht mehr startet.

Planen Sie auch das Wachstum des Speicherplatzes ein. Die Geth-Dokumentation nennt etwa 14 GB pro Woche bei der Standard-Cache-Größe, ein Wert von September 2022. Messen Sie Ihr eigenes Wachstum über ein paar Wochen mit du. Auf einer 2-TB-Platte können Sie Platz freigeben, indem Sie Pre-Merge-Historie entfernen (siehe Fehlerbehebung) oder neu synchronisieren. Bei 4 TB ist das Wachstum eine jährliche Position statt eines vierteljährlichen Problems. Der Node muss nicht jede Sekunde online sein, aber je länger er offline ist, desto länger braucht er zum Aufholen.

Ein Full Node ist kein Validator

Die 32 ETH, von denen alle gehört haben, gehören zum Staking, nicht zum Betrieb eines Nodes. Der Node aus dieser Anleitung braucht überhaupt kein ETH. Er validiert Blöcke im Sinne von Prüfen, was Hardware kostet, aber keinen Stake.

Ein Validator ist ein drittes Programm neben den beiden Clients. Er hält Signing-Keys, erstellt Attestations und Blöcke und verdient dafür Belohnungen, mit einer Fee-Recipient-Adresse für das Einkommen. Die 32 ETH sind eine Sicherheit, die das Protokoll bei nachweisbarem Fehlverhalten einziehen kann. Auch der operative Maßstab verschiebt sich. Ein RPC-Node, der ein Wochenende offline ist, holt am Montag einfach auf. Ein Validator, der offline steht, verliert dagegen in jeder Epoche kleine Strafen.

Mit weniger als 32 ETH ist gepooltes Staking der Einstieg. Ein reiner Full Node verdient nichts. Sie betreiben ihn für Unabhängigkeit und Privatsphäre, für die Entwicklung oder als Basis, auf der später ein Validator stehen kann.

Sicherheit: Das Port-Layout ist die Policy

Das gesamte Sicherheitsmodell dieses Setups zeigt sich in den Firewall-Regeln aus Schritt 1. Die Ports 30303 und 9000/9001 sind offen, weil Peer-to-Peer Fremde braucht. 8545 und 8551 binden an 127.0.0.1, weil außerhalb der Maschine niemand dort etwas zu suchen hat. Das JWT-Secret authentifiziert die Engine-API auf 8551. Behandeln Sie es aber als zweite Schicht und nicht als Grund, den Port zu öffnen.

Ein offener Port 8545 ist der schlimmere Fehler, weil der JSON-RPC-Server keine Authentifizierung hat. Die Sicherheitsdokumentation von Geth rät Betreibern, den gesamten Verkehr zum RPC-Port zu blockieren, außer von ausdrücklich vertrauenswürdigen Maschinen. Sie warnt, dass freigegebene Namespaces das Risiko unerwünschter Signieranfragen erhöhen. Lassen Sie --http.api bei den vier Namespaces aus der Unit. Schalten Sie admin, debug und personal auf jeder Maschine ab, deren RPC-Port jemals erreichbar sein könnte.

Wenn andere Maschinen die RPC legitim brauchen, tunneln Sie, statt sie offenzulegen: WireGuard oder ein SSH-Tunnel für Sie selbst, nginx oder Caddy mit TLS und einer IP-Allowlist für ein kleines Team. Die Clients laufen bereits als Systembenutzer ohne Login aus Schritt 1. Ein kompromittierter Client-Prozess erbt daher kein Shell-Konto. Ergänzen Sie unattended-upgrades für OS-Patches, dann kümmert sich der unspektakuläre Teil der Serversicherheit von selbst.

Fehlerbehebung

Lighthouse erreicht Geth nicht (“Unable to connect to execution endpoint”)

Entweder läuft Geth nicht (systemctl status geth), oder die JWT-Secrets unterscheiden sich. Bestätigen Sie, dass beide Units auf denselben jwt.hex-Pfad zeigen. Im Zweifel erzeugen Sie das Secret einmal neu und starten beide Dienste neu.

Geth hängt tagelang bei „State heal in progress”

Die State-Heal-Phase jagt dem Chain-Head hinterher. Eine Platte mit schwacher Random-Write-Leistung holt dabei nie auf. Benchmarken Sie zufällige 4k-Lese- und Schreibzugriffe mit fio und vergleichen Sie das Ergebnis mit den Laufwerkslisten, auf die die Geth-Dokumentation verlinkt. SATA-SSDs und Standard-Cloud-Volumes sind die üblichen Verdächtigen. Die Lösung ist echter NVMe-Speicher. Kein Flag rettet eine langsame Platte.

Peer-Anzahl bleibt bei null

Port 30303 (TCP und UDP) ist blockiert oder wird an Ihrem NAT nicht weitergeleitet. Prüfen Sie außerdem die Systemuhr: timedatectl sollte eine aktive NTP-Synchronisation zeigen, weil eine verschobene Uhr die Peer-Handshakes auf der Consensus-Seite bricht.

Die Festplatte läuft voll

Finden Sie zuerst das Wachstum: du -h --max-depth=2 /var/lib/geth. Ein Datadir, das vor Geth 1.14.0 angelegt wurde, behält das alte Hash-basierte Layout, weil das neue Standard-Layout nur für frische Datenbanken gilt. Die saubere Lösung ist ein Resync, danach bleibt der State automatisch geprunt. Pre-Merge-History-Pruning (--history.chain postmerge, Geth 1.17) gibt mehr Platz frei. Der Ancient Store kann außerdem über --datadir.ancient auf eine günstigere Platte umziehen.

Geth meldet nach einem Absturz eine beschädigte Datenbank

Stromausfall, kill -9 oder ein OOM-Kill mitten im Schreibvorgang führen beim nächsten Start zu Logzeilen über Korruption oder fehlende Daten. Manchmal heilt ein Neustart das. Wiederholt sich die Meldung im Log, hören Sie auf zu reparieren und synchronisieren Sie neu. Verschieben Sie das Datadir beiseite, starten Sie frisch und lassen Sie den Snap-Sync alles neu aufbauen, was meist schneller geht als jeder Reparaturversuch. Vorbeugung steckt bereits in der Unit: TimeoutStopSec=600 gibt Geth Zeit zum Flushen. Ein sauberes systemctl stop ist der einzige Weg, auf dem der Prozess enden sollte.

Der OOM-Killer beendet Geth

journalctl -k | grep -i oom bestätigt den Verdacht. Geths --cache steht seit v1.17.2 standardmäßig auf 4 GB, und die reale Nutzung kann während des Syncs darüber liegen. Addieren Sie Lighthouse und das Betriebssystem, dann kann eine 16-GB-Maschine leer laufen. Setzen Sie --cache 2048 auf kleinen Maschinen und halten Sie eine Swap-Datei als Puffer bereit. Langsam ist besser als abgebrochen, denn ein abgebrochener Geth schreibt nichts mehr auf die Platte und begünstigt den oben beschriebenen Korruptionsfall.

Eigenen Node betreiben oder eine API nutzen?

Das hängt von der Last ab. Chaingateway verkauft die API-Alternative, deshalb nennt dieser Vergleich klar, wo jede Seite passt.

Der Node gewinnt, wenn Sie schweres, dauerhaftes rohes JSON-RPC brauchen: Archive-Abfragen, Tracing, Mempool-Beobachtung oder maximale Privatsphäre und Zensurresistenz. Ein Node hat feste Kosten und keine Abrechnung pro Request. Sobald Ihr Volumen hoch genug ist, wird er deshalb günstiger als ein abgerechnetes RPC-Angebot. Nutzen Sie die Kostenrechnung oben, um diesen Punkt mit Ihren eigenen Preisen zu finden. Außerdem lernt man mit einem eigenen Node gut, wie Ethereum funktioniert.

Die API gewinnt, wenn der Node nur Mittel zum Zweck ist. Für die meisten Unternehmen ist das bei Zahlungen der Fall. Ein synchronisierter Node gibt Ihnen eth_sendRawTransaction und Event-Logs. Er liefert keine Deposit-Adressen pro Kunde, keine Benachrichtigungen bei eingehenden ERC-20-Zahlungen, kein Key-Management und keine Retry-Logik. Das ist Anwendungssoftware, die Sie auf dem Node aufbauen und betreiben müssten.

Die Ethereum-API von Chaingateway füllt genau diese fehlende Schicht. Sie erstellen und importieren Adressen (POST /api/v2/ethereum/addresses/import), senden ERC-20-Tokens (POST /api/v2/ethereum/transactions/erc20) und empfangen HMAC-signierte Webhooks für eingehende Deposits. Fehlgeschlagene Zustellungen landen in einer abfragbaren Liste (GET /api/v2/ethereum/webhooks/notifications/failed) und lassen sich über den Retry-Endpunkt erneut senden.

Der Break-even ist reine Arithmetik: Serverkosten plus Ihre Bau- und Betriebsstunden, verglichen mit einem Tarif auf der Preisseite. Bei Zahlungsabläufen zählen Sie die Stunden für die Erkennung von Deposits und die Schlüsselverwaltung. Für reinen RPC-Verbrauch hat die Node-Seite den Vorteil. Starten Sie mit dem Quickstart und dem Webhook-Guide. Der kostenlose 7-Tage-Test ohne Karte oder KYC reicht, um einen Deposit-Ablauf Ende zu Ende zu prüfen (hier registrieren).
