Transferir NFT por API: pasos, parámetros y errores

Cómo funciona una API de transferencia de NFT: propiedad, parámetros, gas, firma, confirmación y errores frecuentes, con ejemplos ERC-721 para Ethereum y Tron.

Capítulos
C
Chaingateway Team
Expertos en blockchain

Revisado por Maurice Sobiera

Una API de transferencia de NFT permite que su backend mueva un token entre wallets con una sola solicitud HTTP. Comprueba la propiedad, construye la llamada para el estándar del token, firma y difunde la transacción, e informa del resultado. Cada transferencia sigue siendo una transacción on-chain, y el remitente paga la comisión.

Esta guía recorre cada paso, los parámetros que necesita una solicitud y los errores que más tiempo cuestan a los desarrolladores.

TL;DR

  • Una transferencia de NFT cambia el propietario registrado en un contrato de token. En cadenas de estilo Ethereum es una llamada a transferFrom o safeTransferFrom; en Solana es una instrucción del token o de Metaplex.
  • Una solicitud necesita cuatro datos: la wallet remitente, la dirección destinataria, la dirección del contrato (o del mint) y el ID del token. ERC-1155 también necesita una cantidad.
  • Compruebe la propiedad antes de enviar, estime las comisiones antes de firmar y confirme el éxito desde la cadena (recibo y evento Transfer), no solo con la respuesta HTTP.
  • Los fallos más comunes son la cadena equivocada, los contratos destinatarios que no pueden recibir NFT, la falta de gas nativo y una propiedad desactualizada.
  • Una API elimina la fontanería específica de cada cadena. Chaingateway envía transferencias ERC-721, BEP-721 y TRC-721 y ofrece webhooks para la confirmación, así que no necesita sondear. No tiene endpoint ERC-1155 ni endpoint de NFT de Solana.

¿Qué hace una API de transferencia de NFT?

Un NFT es un registro en un contrato inteligente (o, en Solana, una cuenta de token) que indica qué dirección posee qué token. Transferirlo significa cambiar ese registro, y solo puede hacerlo el propietario o alguien autorizado por él.

El estándar ERC-721 define esto a nivel de contrato. Cada token se identifica con un ID, y una transferencia mueve la propiedad de una dirección a otra cuando la inicia el propietario, una dirección aprobada o un operador. Después, el contrato emite un evento Transfer, la señal que escuchan la mayoría de indexadores y sistemas de notificación.

Una API se sitúa encima de eso. Una buena se encarga de cinco tareas por usted:

  1. Verificación de propiedad: confirmar que la wallet remitente posee el token en este momento.
  2. Construcción de la llamada: codificar la función correcta para el estándar y la cadena.
  3. Estimación de comisiones: calcular el gas o las comisiones de red y comprobar que la wallet puede pagarlas.
  4. Firma y difusión: firmar con la clave de la wallet y enviar la transacción.
  5. Informe de estado: devolver un hash de transacción e indicar cuándo la transferencia es definitiva.

La alternativa es ejecutar su propio nodo, mantener bibliotecas web3 para cada cadena y escribir la codificación usted mismo. Eso funciona para una cadena y una colección. Se encarece al añadir una segunda red.

¿Qué estándares de NFT y cadenas puede cubrir una API de transferencia?

No todos los NFT son el mismo tipo de objeto, así que una API debe hablar más de un dialecto.

Estándar / modeloCadenasCómo funciona la transferencia
ERC-721Ethereum, Polygon, Arbitrum y otras cadenas EVMUn ID de token por token; transferFrom o safeTransferFrom
ERC-1155Ethereum y cadenas EVMContrato multi-token; la transferencia incluye una cantidad por ID de token, con transferencias por lotes
Token SPL con suministro uno + metadatos de MetaplexSolanaTransferencia mediante el programa de tokens; metadatos guardados por separado

ERC-1155 merece una mirada más detenida si gestiona objetos de juego o entradas. Un solo contrato contiene tipos fungibles y no fungibles, su interfaz incluye transferencias individuales y por lotes seguras, y cada transferencia lleva una cantidad para el ID de token. Un token con suministro de uno se comporta como un NFT clásico. Una edición con suministro de 500, en cambio, es otro caso: debe enviar una cantidad, no solo un ID.

Solana funciona de otra manera. Normalmente no despliega un contrato separado por colección. Los NFT son tokens del Token Program con suministro de uno, y los metadatos de Metaplex contienen los detalles del NFT. Así que en Solana transfiere por dirección de mint, no por contrato más ID de token, y el destinatario necesita una cuenta de token para ese mint.

Al evaluar cualquier proveedor, pregunte qué modelos de estos tres admite y en qué cadenas. El archivo OpenAPI de Chaingateway enumera estos endpoints de NFT:

CadenaEndpointEstándar
EthereumPOST /api/v2/ethereum/transactions/erc721ERC-721
PolygonPOST /api/v2/polygon/transactions/erc721ERC-721
ArbitrumPOST /api/v2/arbitrum/transactions/erc721ERC-721
BNB Smart ChainPOST /api/v2/bsc/transactions/bep721BEP-721

No hay endpoint ERC-1155. En Solana, POST /api/v2/solana/transactions/SPL envía tokens SPL fungibles y no cubre metadatos de NFT ni la gestión de ediciones. Compruebe su colección contra ese endpoint antes de confiar en él.

¿Cómo se transfiere un NFT mediante una API, paso a paso?

El flujo es el mismo sea cual sea el proveedor. Lo que cambia es cuánto de él escribe usted mismo.

1. Verificar la propiedad

Antes de construir una transacción, confirme que el remitente posee realmente el token. Para ERC-721 esto significa preguntar al contrato quién posee el ID de token. Para ERC-1155, significa comprobar el saldo de ese ID para la dirección. En Solana, revise la cuenta de token que contiene el mint.

Hágalo justo antes de enviar, no a partir de una fila en caché de su base de datos. Los NFT pueden venderse o moverse en los segundos entre su última sincronización y su solicitud. Una transferencia desde una wallet que ya no posee el token fallará y, en algunos casos de fallo, seguirá costando comisiones.

2. Comprobar la autorización

El estándar permite iniciar una transferencia al propietario, a una dirección aprobada o a un operador. Si su servicio mueve NFT desde wallets de usuarios que usted no controla, necesita antes una aprobación. Si su servicio tiene las claves de las wallets que creó (como en flujos custodiales), la wallet remitente es la propietaria y no hace falta aprobación.

3. Construir y estimar

Elija la función y codifique los argumentos. Después, estime la comisión.

En cadenas EVM eso significa un límite de gas multiplicado por un precio de gas. En Solana, es una pequeña comisión por firma y, posiblemente, el alquiler de una cuenta de token nueva. Los endpoints de Chaingateway aceptan los campos opcionales gas, gasprice, maxFeePerGas y maxPriorityFeePerGas, y las cadenas EVM tienen un endpoint GET .../gasprice. Evite fijar un límite de gas en el código, porque falla cuando el destinatario es un contrato con lógica adicional. Pruebe en testnet cuánto cuesta una solicitud sin esos campos.

Confirme también que la wallet tiene suficiente moneda nativa. Una dirección con diez NFT y cero ETH no puede mover ninguno.

4. Firmar y difundir

La transacción debe estar firmada con la clave privada del propietario. O bien firma usted localmente y envía la transacción en bruto, o bien la API firma por una wallet que ella gestiona. Las wallets gestionadas son más sencillas para flujos de backend, porque sus servidores nunca manejan claves en bruto.

5. Confirmar

Un hash de transacción significa que la red aceptó su envío, no que la transferencia haya tenido éxito. Espere un recibo que muestre éxito y el evento Transfer con el remitente, el destinatario y el ID de token esperados. Para NFT de alto valor, espere varias confirmaciones antes de actualizar su propia base de datos o de entregar algo a cambio.

¿Qué necesita una solicitud de transferencia?

Sean cuales sean los nombres de campo del proveedor, la solicitud lleva la misma información.

ParámetroPor qué se necesitaNotas
Cadena / redLa misma dirección existe en muchas cadenas EVMMainnet frente a testnet es lo primero que hay que revisar cuando un token “desaparece”
Wallet remitenteIdentifica quién firma y pagaDebe poseer el token y tener gas nativo
Dirección destinatariaDestinoValide formato y checksum; nunca acepte texto libre sin comprobaciones
Dirección del contrato o del mintIdentifica la colecciónContrato en EVM, mint en Solana
ID de tokenIdentifica el token individualNo se usa en Solana, donde el mint es el token
CantidadCantidad a moverObligatoria en ERC-1155; uno en ERC-721
Ajustes de comisiónLímite y precio de gas, o comisión prioritariaDeje que la API estime, salvo que tenga un motivo para no hacerlo
Idempotencia o referenciaEvita envíos duplicados al reintentarGuarde su propia referencia junto al hash de la transacción

Esa última fila importa más de lo que parece. Si su solicitud agota el tiempo de espera, no sabe si la transacción llegó a difundirse. Reintentar a ciegas puede enviar una segunda transacción. Para un NFT único, esa segunda fallará sin más; en una edición ERC-1155, puede mover copias adicionales. Consulte antes el intento anterior.

¿Cómo se estiman y pagan las comisiones de transferencia de NFT?

En redes EVM, el remitente paga el gas en la moneda nativa de la cadena, y el coste varía con la congestión de la red y la complejidad de la llamada. Un transferFrom simple es barato comparado con una acuñación o una venta en un marketplace. Pero un contrato destinatario con una función receptora pesada puede elevarlo.

Reglas prácticas:

  • Estime justo antes de enviar y añada un margen moderado, en lugar de usar un número fijo.
  • Mantenga un saldo nativo mínimo en cada wallet que envíe NFT, y genere una alerta cuando baje de ese mínimo.
  • Si transfiere en nombre de usuarios, decida de antemano quién paga: usted (recargando la wallet) o el usuario (descontando de un saldo). Las sorpresas aquí acaban en tickets de soporte.
  • En Solana, recuerde que el destinatario puede necesitar una cuenta de token nueva, lo que tiene un coste único.

¿Cómo se protegen las transferencias de NFT?

Las transferencias de NFT son irreversibles. No hay devoluciones de cargo ni servicio de atención on-chain, así que las salvaguardas viven en su código.

Proteja la ruta de firma. Autentique cada llamada a la API. Chaingateway usa un token portador en la cabecera Authorization, según define la RFC 6750. Guarde el token en una bóveda, rótelo y nunca lo incluya en una aplicación de navegador o móvil. Las wallets creadas con contraseña guardan la clave cifrada del lado de Chaingateway. Las wallets sin contraseña devuelven la clave privada al crearse, y usted debe guardarla a salvo.

Valide el destinatario. Compruebe el formato de la dirección y la cadena. Ofrezca un paso de confirmación para artículos de alto valor. Cuando la política lo exija, filtre las direcciones antes de enviar.

Tenga en cuenta los contratos receptores. La especificación ERC-721 describe safeTransferFrom como una llamada a onERC721Received en un contrato destino, y como una reversión si el valor devuelto no es correcto. Esto le protege de dejar un token bloqueado en un contrato que no puede moverlo. El transferFrom simple deja esa comprobación en manos de quien llama. La referencia de la API de Chaingateway no indica cuál de las dos funciones llama su endpoint ERC-721. Por eso, pruebe en testnet una transferencia a una dirección de contrato antes de depender de cualquiera de los dos comportamientos.

Limite la exposición. Mantenga una wallet caliente solo con los NFT necesarios para las transferencias a corto plazo, y el resto en una wallet más restringida. Aplique límites por solicitud y diarios en su propia capa.

Registre todo. Anote quién solicitó la transferencia, los parámetros, el hash y el resultado. Cuando un cliente impugna una transferencia, la cadena demuestra lo ocurrido, y sus registros demuestran quién lo pidió.

La mayoría de estos casos se detectan con dos hábitos: comprobar primero la propiedad y el saldo, y tratar el recibo on-chain como única prueba de éxito.

¿Cómo se confirman las transferencias con webhooks en lugar de sondear?

Consultar el hash de una transacción cada pocos segundos funciona en un prototipo, pero desperdicia solicitudes en producción. Con webhooks, el proveedor llama a su endpoint cuando detecta una transferencia que coincide. En Chaingateway registra un webhook con type igual a ERC721 (o TRC721, BEP721) y un contractaddress, además de un filtro de dirección from o to. La notificación incluye from, to, contractaddress, tokenid, txid y blocknumber.

Verifique la cabecera X-Signature, responda rápido y procese los eventos de forma idempotente. Las notificaciones fallidas no se reintentan automáticamente, así que revise también la lista de notificaciones fallidas. La firma cubre solo el txid, así que compruebe el ID de token y el destinatario contra sus propios registros. Si quiere entender cómo son estos eventos a nivel de log, nuestro recorrido por el evento Transfer de ERC-20 explica la estructura y los topics. El evento ERC-721 sigue el mismo patrón, con el ID de token indexado.

¿Qué debe revisar antes del lanzamiento?

Antes de permitir que usuarios reales inicien transferencias de NFT, recorra esta lista primero en testnet:

  1. Transfiera un token que posea a una wallet normal y confirme el recibo y el evento Transfer.
  2. Transfiera a un contrato que no pueda recibir NFT y confirme que su código muestra el fallo.
  3. Intente una transferencia desde una wallet sin moneda nativa y confirme que el error es claro.
  4. Envíe dos veces la misma solicitud y confirme que su comprobación de idempotencia bloquea la segunda.
  5. Apague su endpoint de webhook durante un minuto, vuélvalo a encender y confirme que no se pierden ni se procesan dos veces los eventos.
  6. Revise quién puede llamar al endpoint, con qué límites, y dónde se guarda el secreto.
