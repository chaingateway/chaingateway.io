TRC20-Adresse API: Adressen erzeugen und auf Deposits überwachen

Eine TRC20-Adresse ist eine gewöhnliche TRON-Kontoadresse: 34 Zeichen in Base58Check-Form, beginnend mit T. Sie hält TRX und jedes TRC-20-Token wie USDT. Dieselbe Adresse hat eine Hex-Schreibweise mit 42 Zeichen, die mit 41 beginnt. Das Senden von ihr kostet Energy und Bandwidth, das Empfangen ist kostenlos.

Wie sieht eine TRC20-Adresse aus?

Eine TRC20-Adresse ist eine TRON-Kontoadresse in ihrer Base58Check-Form, zum Beispiel TNPeeaaFB7K9cmo4uQpcU32zGK8G1NYqeL. Sie hat 34 Zeichen und beginnt mit T. Die Konten-Dokumentation von TRON definiert den zugrunde liegenden Wert als 21 Byte: ein führendes Präfix-Byte 0x41, dann 20 Byte, die der Ethereum-Adresse aus demselben Public Key entsprechen.

Dieselbe Adresse hat deshalb eine Hex-Schreibweise mit 42 Zeichen, die mit 41 beginnt. Node-APIs liefern oft diese Form, Wallets und Explorer zeigen die Base58Check-Form. TronWeb wandelt mit tronWeb.address.toHex() und fromHex() zwischen beiden um.

„TRC20“ bezeichnet den Token-Standard, nicht die Adresse. TRC-20 ist der Standard für fungible Token auf TRON und auf Schnittstellenebene mit Ethereums ERC-20 kompatibel. Eine TRON-Adresse hält TRX und jedes TRC-20-Token.

Ist eine TRC20-Adresse dasselbe wie eine TRC20-Contract-Adresse?

Nein. Eine Wallet-Adresse ist ein Konto, das ein Private Key kontrolliert. Eine Contract-Adresse gehört zu deployntem Code, und niemand hält einen Key dafür. Die TRON-Dokumentation führt beide als Kontotypen, und beide werden als T-Strings geschrieben, am String ist der Unterschied also nicht zu erkennen.

Die Contract-Adresse bestimmt, welches Token bewegt wird. Sie ist nie das Ziel eines Transfers. Der TRC-20-Contract von USDT ist TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t, und Token, die an eine Contract-Adresse gehen, sind in fast allen Fällen nicht wiederherstellbar. Der Blog-Guide erklärt den Unterschied genauer.

Warum erscheint eine neue TRC20-Adresse nicht auf Tronscan?

Weil TRON ein Konto erst nach der Aktivierung kennt. Laut der Konten-Dokumentation von TRON existiert ein frisch erzeugtes Schlüsselpaar nur lokal, und die Adresse lässt sich weder über die API noch in einem Block-Explorer abrufen, bis sie aktiviert ist.

Die Aktivierung geschieht, wenn ein bestehendes Konto der neuen Adresse einen beliebigen Betrag TRX oder ein TRC-10-Token sendet und der Absender eine Gebühr für die Kontoerstellung zahlt. Die Dokumentation nennt diese Gebühr zum Zeitpunkt des Schreibens mit 1 TRX im Mainnet. Prüfen Sie den aktuellen Wert, bevor Sie einen Auszahlungsablauf darauf aufbauen. Für Deposits und Webhooks genügt eine erzeugte Adresse. Erwarten Sie nur nicht, dass ein Explorer sie vor der ersten Aktivierung anzeigt.

Endpoints für TRC20-Adressen: erstellen, lesen, beobachten, senden

Vier Aufgaben und die Routen dafür. Adresserstellung und Webhook-Registrierung brauchen gar keinen Private Key, nur das Senden.

POST /api/v2/tron/addressesNeue TRON-Adresse generieren
POST /api/v2/tron/addresses/importVorhandenen Private Key importieren, damit die API für diese Adresse signieren kann
POST /api/v2/tron/addresses/{address}Passwort ändern, das einen gespeicherten Key verschlüsselt
DELETE /api/v2/tron/addresses/{address}Adresse aus Ihrem Konto entfernen
GET /api/v2/tron/balances/{address}TRX-Guthaben der Adresse

GET /api/v2/tron/balances/{address}/trc10/{token_id}Guthaben eines TRC-10-Tokens
POST /api/v2/tron/webhooksTRX-, TRC-10-, TRC-20- oder TRC-721-Transfers für die Adresse abonnieren

POST /api/v2/tron/transactions/trc20Ein TRC-20-Token wie USDT von der Adresse senden

Das ist die gesamte Oberfläche, die ein Deposit-System berührt. Die vollständige TRON-Referenz mit allen 40 Operationen, einschließlich Staking und Self-Signing, steht auf der TRON-API-Seite. Das Feld type beim Webhook und die eigene Route /transactions/trc10 gibt es, weil TRON zwei Token-Standards führt. Der Vergleich TRC10 gegen TRC20 zeigt, auf welchem Standard Sie ein eigenes Token ausgeben sollten, statt ein bestehendes anzunehmen.

Wie generiere ich eine TRC20-Adresse per REST?

POST /api/v2/tron/addresses erzeugt eine. Der Body hat ein einziges optionales Feld, password, und dieses Feld bestimmt das Verwahrungsmodell. Senden Sie ein Passwort, wird der Private Key verschlüsselt dahinter gespeichert, und spätere Transfers authentifizieren sich mit dem Passwort statt mit dem Key. Lassen Sie es weg, gibt die Antwort den Private Key direkt zurück, damit Sie ihn in Ihrem eigenen Vault ablegen. Die Referenz hält ausdrücklich fest, dass Passwörter nicht gespeichert werden: Geht es verloren, lässt sich die Wallet nicht wiederherstellen. Von der anderen Seite gelesen heißt das, niemand sonst kann sie entsperren.

curl -X POST https://app.chaingateway.io/api/v2/tron/addresses \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"password": "a-strong-password-per-wallet"}'

Erzeugt Ihre Plattform Keys bereits selbst, passt die zweite Route besser: POST /api/v2/tron/addresses/import registriert eine anderswo abgeleitete Adresse samt Private Key und Verschlüsselungspasswort, und die API kann ab dann für sie signieren. Adressen, die Sie nur beobachten wollen, brauchen keinen der beiden Aufrufe, denn ein Webhook-Abonnement verweist per String auf die Adresse.

Zwei Verwaltungsrouten gehören zum selben Satz. POST /api/v2/tron/addresses/{address} ändert das Verschlüsselungspasswort eines gespeicherten Keys. DELETE /api/v2/tron/addresses/{address} entfernt die Adresse aus Ihrem Konto, und laut Referenz sinkt dadurch auch die Zahl der genutzten Adressen. Binden Sie das in den Job ein, der abgelaufene Deposit-Adressen ausmustert, wenn Sie nah an einem Plan-Limit arbeiten.

Wie überwache ich eine TRC20-Adresse auf eingehendes USDT?

Tronscan nach Deposits abzufragen geht unbemerkt kaputt, POST /api/v2/tron/webhooks skaliert. url ist das einzige Feld, das die Referenz als Pflichtfeld ausweist. to begrenzt das Abonnement auf Deposits an Ihre Adresse, from auf Transfers, die sie verlassen, und contractaddress auf ein einzelnes Token. type wählt die Asset-Klasse und akzeptiert TRX, TRC10, TRC20 oder TRC721. In reference passen bis zu 255 Zeichen eigener Text, dorthin gehört die Bestell- oder Kunden-ID, damit die Benachrichtigung Ihren Suchschlüssel schon mitbringt.

curl -X POST https://app.chaingateway.io/api/v2/tron/webhooks \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://your-backend.example/hooks/tron",
    "to": "TYourDepositAddress",
    "type": "TRC20",
    "contractaddress": "TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t",
    "reference": "customer-4711"
  }'

Hinterlegen Sie in Ihrem Konto ein persönliches Secret, dann trägt jede Zustellung einen X-Signature-Header: ein Base64-kodiertes HMAC-SHA256 über die txid der Nutzlast. Prüfen Sie ihn, bevor Sie sonst etwas parsen. Eine fehlgeschlagene Zustellung wird nicht von selbst wiederholt. GET /api/v2/tron/webhooks/notifications/failed listet, was nie angekommen ist, und POST /api/v2/tron/webhooks/notifications/{id}/retry sendet eine erneut.

Ein Eintrag verlässt die Fehlerliste, wenn sein Retry startet, und kehrt nur zurück, wenn auch dieser Retry scheitert. Ein Retry liefert dasselbe Event ein zweites Mal. Speichern Sie deshalb den Transaktions-Hash jedes gutgeschriebenen Deposits unter einem Unique-Constraint und lassen Sie die Datenbank das Duplikat abweisen. Signaturcode und Payload-Formate stehen im Webhook-Guide.

Wie sende ich USDT-TRC20 von der Adresse?

POST /api/v2/tron/transactions/trc20 verlangt vier Felder: from, to, contractaddress und amount. Der Betrag ist eine einfache Zahl in Token-Einheiten, 25 USDT sind also 25 und nicht ein mit den sechs Dezimalstellen des Contracts skalierter Wert. Dazu senden Sie entweder password für einen Key, den die API verschlüsselt hält, oder privatekey, wenn Sie den Key selbst verwahren.

Im Feld contractaddress wird der Unterschied zwischen Wallet-Adresse und Token-Contract-Adresse zur konkreten Integrationsregel: Die Contract-Adresse bestimmt, welches Token bewegt wird, und ist nie das Ziel. Die von USDT lautet TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t und gehört in contractaddress, nie in to. Token, die an eine Contract-Adresse gehen, sind in fast allen Fällen nicht wiederherstellbar. Der Blog-Guide erklärt, warum beide gleich aussehen: Beide sind T-Strings, und am String ist der Unterschied nicht zu erkennen.

Senden kostet Energy und Bandwidth, Empfangen ist kostenlos. Ein Deposit-System zahlt deshalb beim Einsammeln und nicht beim Deposit. Der TRON-Gebührenrechner berechnet den Preis eines konkreten Transfers. GET /api/v2/tron/chainparameters liefert die aktuellen Ressourcenpreise, damit Ihr Code keine Konstante festschreibt, die eine Governance-Abstimmung ungültig machen kann.

Wie validiere ich eine TRC20-Adresse vor dem Senden?

Prüfen Sie das Ziel in dem Moment, in dem ein Nutzer es eingibt, nicht erst nach dem Broadcast. Eine TRC-20-Adresse hat 34 Zeichen, beginnt mit T und trägt eine Base58Check-Prüfsumme, die schon ein einzelnes falsch getipptes Zeichen bricht. Ein wohlgeformter String lässt sich so von einem Tippfehler unterscheiden, ohne das Netzwerk zu berühren. Der Adress-Validator führt diese Prüfung für TRC-20, ERC-20 und BEP-20 im Browser aus, wenn Sie eine Adresse von Hand prüfen wollen.

Eine TRON-Adresse wird dabei nicht versehentlich mit einer EVM-Adresse verwechselt, weil die Formate sichtbar verschieden sind: Ein T-String besteht Ethereums Validierung nicht, ein 0x-String nicht die von TRON. Die TVM von TRON führt viel für die EVM geschriebenes Solidity aus, ist aber eine eigene Laufzeitumgebung mit eigener Ressourcenmessung, Energy und Bandwidth statt Gas, und mit eigener Adresskodierung. Wer „TRON-EVM“ wörtlich nimmt, baut damit die ersten Adressfehler zwischen den Chains ein.
