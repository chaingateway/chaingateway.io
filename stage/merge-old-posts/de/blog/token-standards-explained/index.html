Token-Standards erklärt: ERC-20, ERC-721, ERC-1155

Token-Standards im Überblick: Was ERC-20, ERC-721, ERC-1155, TRC-20 und SPL festlegen, wie Dezimalstellen funktionieren und was Sie vor der Integration prüfen.

Kapitel
C
Chaingateway Team
Blockchain-Experten

Geprüft von Maurice Sobiera

Ein Token-Standard ist eine veröffentlichte Spezifikation, die einem Token-Vertrag vorgibt, welche Funktionen er bereitstellen und welche Ereignisse er auslösen muss. Wallets, Börsen und Apps können dann jedes konforme Token ohne Sonder-Code verarbeiten. Dieser Leitfaden behandelt ERC-20, ERC-721, ERC-1155 und ihre Entsprechungen auf Tron und Solana sowie Dezimalstellen und Integrationsprüfungen.

TL;DR

  • Ein Token-Standard definiert eine Schnittstelle (Funktionen und Ereignisse) sowie Verhaltensregeln, damit Software mit jedem konformen Token auf dieselbe Weise interagieren kann.
  • ERC-20 gilt für fungible Token, ERC-721 für einzigartige NFTs und ERC-1155 für viele Token-Typen in einem Vertrag.
  • TRC-20 bildet ERC-20 auf Tron ab, und Solana nutzt sein eigenes SPL-Token-Programm. „Gleicher Standard“ heißt also nie „gleiche Chain“.
  • On-Chain-Beträge sind Ganzzahlen. Der optionale Wert decimals gibt an, wo für die Anzeige das Dezimalzeichen sitzt.
  • Konformität ist nicht garantiert. Testen Sie das tatsächliche Verhalten jedes Tokens, bevor Sie sich darauf verlassen.

Was legt ein Token-Standard fest?

Ein Token ist keine native Coin. Es ist ein Eintrag in einem Smart Contract: wer wie viel hält und welche Regeln das Verschieben bestimmen. Ohne gemeinsame Spezifikation würde jedes Token eigene Funktionsnamen bereitstellen, und jede Wallet bräuchte individuellen Code, um Guthaben zu lesen oder Überweisungen zu senden.

Ein Standard behebt das. Laut der Token-Standards-Seite von ethereum.org legen Standards fest, wie sich Token verhalten und interagieren. Das hält Smart Contracts kombinierbar und lässt neue Token mit bestehenden dezentralen Börsen und Anwendungen funktionieren. Der Überblick zum Token-Design des NIST beschreibt ERCs als Bereitsteller von Funktions- und Ereignisdeklarationen, Einschränkungen und Anforderungen und manchmal von Referenzimplementierungen.

In der Praxis liefert ein Standard vier Dinge:

  1. Aufrufbare Funktionen, etwa das Lesen eines Guthabens oder das Verschieben von Token.
  2. Ereignisse, die der Vertrag auslöst, damit externe Software die Aktivität verfolgen kann.
  3. Datentypen und Einschränkungen, etwa wie Beträge dargestellt werden.
  4. Verhaltensanforderungen, etwa welche Aufrufe welches Ereignis auslösen müssen.

Auf Ethereum werden diese Spezifikationen als ERCs vorgeschlagen, der Anwendungsebenen-Kategorie der Ethereum Improvement Proposals. Andere Chains haben eigene Verfahren und Namen, aber die Idee überträgt sich.

Was ist der ERC-20-Standard?

ERC-20 entstand 2015 und definiert eine Standard-API für Token innerhalb von Smart Contracts, damit Wallets und dezentrale Börsen sie wiederverwenden können. „Fungibel“ bedeutet, dass jede Einheit mit jeder anderen austauschbar ist, wie Dollar oder Kilogramm Gold. Stablecoins, Governance-Token und die meisten Zahlungs-Token folgen diesem Standard.

Die Schnittstelle, wie sie in der ERC-20-Dokumentation aufgeführt ist, umfasst:

Funktion oder EreignisWas es tut
totalSupplyGibt die Gesamtzahl der existierenden Token zurück
balanceOfGibt das Guthaben einer Adresse zurück
transferVerschiebt Token vom Aufrufer an eine andere Adresse
approveErlaubt einer anderen Adresse (einem Spender), bis zu einer festgelegten Menge Ihrer Token zu verschieben
allowanceGibt zurück, wie viel ein Spender im Auftrag eines Eigentümers noch verschieben darf
transferFromVerschiebt Token im Auftrag eines Eigentümers anhand einer Genehmigung
name, symbol, decimalsBeschreibende Metadaten, üblicherweise vorhanden
Transfer, Approval-EreignisseWerden bei Überweisungen und Genehmigungen ausgelöst

Die Spezifikation schreibt vor, dass Überweisungen das Ereignis Transfer und erfolgreiche approve-Aufrufe das Ereignis Approval auslösen müssen. Diese Regel macht die Zahlungserkennung möglich: Sie können auf Ereignisse warten, statt jede Adresse per Polling abzufragen. Mehr dazu finden Sie in unserem Leitfaden zum ERC-20-Transfer-Ereignis, und unsere Übersicht zum ERC-20-Standard führt durch die vollständige Schnittstelle.

Das Muster aus approve und transferFrom

Das zweistufige Muster verwirrt Einsteiger. Bei transfer sendet der Token-Inhaber die Token direkt. Bei approve plus transferFrom autorisiert der Inhaber zuerst einen Spender, und der Spender holt die Token später ab. So nimmt eine dezentrale Börse oder ein Abo-Vertrag Zahlungen entgegen, ohne Ihre Schlüssel zu halten. Wenn Sie nur Token aus einer Wallet senden müssen, die Sie kontrollieren, genügt transfer. Unsere Anleitung zum Senden von ERC-20-Token vergleicht die Wege über Wallet, Code und API.

Wie funktionieren ERC-20-Dezimalstellen?

Smart Contracts speichern keine Bruchteile. Jedes Guthaben ist eine Ganzzahl, und decimals sagt Ihnen, wie viele der rechten Ziffern der Nachkommateil sind. Die ERC-20-Spezifikation macht die Methode optional und nennt ein Beispiel: Bei 8 Dezimalstellen teilen Sie den Token-Betrag durch 100000000, um die Darstellung für Nutzer zu erhalten.

Das hat drei praktische Folgen.

Lesen Sie die Dezimalstellen immer aus dem Vertrag. Tragen Sie nicht für alle Token einen festen Wert ein. Zwei Token, die beide als „1,00“ angezeigt werden, können als sehr unterschiedliche Ganzzahlen gespeichert sein.

Rechnen Sie mit Ganzzahlen oder Big-Number-Typen. Rohbeträge können über das hinausgehen, was eine normale Gleitkommazahl exakt hält. Verwenden Sie BigInt, BigNumber oder den Dezimaltyp Ihrer Sprache, und formatieren Sie erst im letzten Schritt für die Anzeige.

Behandeln Sie eine fehlende Methode decimals als Fall, den Sie abfangen müssen. Da die Methode optional ist, muss ein konformes Token sie nicht bereitstellen. Legen Sie einen Fallback fest, etwa das Token abzulehnen oder eine manuelle Konfiguration zu verlangen, statt stillschweigend einen Standardwert anzunehmen.

Ein durchgerechnetes Beispiel: Ein Token mit 6 Dezimalstellen zeigt ein Rohguthaben von 2500000. Die Division durch 10^6 ergibt 2,5 Token. Um 0,75 Token zu senden, übermitteln Sie 750000, nicht 0.75. Übermitteln Sie versehentlich den Anzeigewert, wird ein verschwindend kleiner Betrag gesendet, und die Transaktion läuft trotzdem erfolgreich durch.

ERC-721: Nicht fungible Token

Während ERC-20 jede Einheit gleich behandelt, ist ERC-721 eine Schnittstelle für nicht fungible Token, etwa einzigartige Kunstwerke oder Songs. Jedes Token hat innerhalb seines Vertrags eine eigene Kennung, sodass das Eigentum pro Token statt als Guthaben verfolgt wird. Typische Einsatzfälle sind Sammlerstücke, Tickets, Spielgegenstände und Eigentumsnachweise.

Der Preis dafür sind Kosten und Komplexität. Wer zehn voneinander unabhängige NFTs verschiebt, braucht zehn einzelne Überweisungen. Zu den Details der Schnittstelle lesen Sie unseren Leitfaden zum ERC-721-Standard.

ERC-1155: Viele Token-Typen in einem Vertrag

ERC-1155 ist eine Multi-Token-Schnittstelle. Ein einzelner bereitgestellter Vertrag kann beliebig viele fungible, nicht fungible oder semifungible Token-Typen abbilden, jeweils identifiziert durch eine Token-ID, die eigene Metadaten und einen eigenen Vorrat haben kann. Die Spezifikation unterstützt außerdem die Übertragung mehrerer Token-Typen in einer einzigen Operation.

Das passt natürlich zu Spielen, in denen ein einzelner Vertrag eine Währung, eine Reihe von Verbrauchsgütern und ein paar einzigartige Gegenstände halten kann. Sie stellen einmal bereit und können Bewegungen bündeln, statt pro Asset-Typ eine Transaktion zu senden.

Token-Standards auf anderen Chains

Die Namen wechseln von Chain zu Chain, aber die Idee bleibt dieselbe.

Tron: TRC-20 und TRC-10. TRC-20 ist der Standard für fungible Token auf TRON und auf Schnittstellenebene mit ERC-20 kompatibel, sodass die meisten Ethereum-Token-Verträge dort mit wenigen Änderungen laufen. Tron kennt außerdem das ältere TRC-10 auf Protokollebene. Die praktischen Unterschiede erklären wir in TRC-10 vs TRC-20.

BNB Chain: BEP-20. BEP-20 ist von ERC-20 abgeleitet und läuft auf einer EVM-kompatiblen Chain, daher wirken Funktionsnamen und Ereignisformen vertraut.

Solana: SPL-Token. Solana stellt nicht für jedes Token einen neuen Vertrag bereit. Token entstehen über das gemeinsame SPL-Token-Programm, und laut der SPL-Token-Dokumentation ist ein NFT schlicht ein Token-Typ, von dem genau ein Token geprägt wurde. Das mentale Modell unterscheidet sich von Ethereum, obwohl das Ziel der Interoperabilität dasselbe ist.

Cosmos-Ökosystem: CW20. Die CW20-Spezifikation behandelt Guthaben und Überweisungen mit Uint128-Ganzzahlen und überlässt die Behandlung der Dezimalstellen der Oberfläche. Das ist dieselbe Trennung von Ganzzahl und Anzeige wie bei ERC-20.

Ein gleichnamiger Standard auf einer anderen Chain ist nie austauschbar mit dem Original. Ein TRC-20-USDT und ein ERC-20-USDT sind verschiedene Assets auf verschiedenen Netzwerken, und beim Senden an das falsche Netzwerk können Gelder verloren gehen. Ordnen Sie in Ihrem Datenmodell jede Adresse immer ihrem Netzwerk zu.

Was sollten Sie vor der Integration eines Tokens prüfen?

Ein Standard beschreibt, was ein Token tun sollte, nicht, was jeder bereitgestellte Vertrag tatsächlich tut. Die Checkliste zur Token-Integration auf ethereum.org ist eine gute Grundlage. Sie fordert Entwickler auf, Folgendes zu prüfen:

  • Konformität und Rückgabewerte der Standardfunktionen,
  • optionale Funktionen und Dezimalstellen,
  • Maßnahmen gegen Race Conditions bei Genehmigungen,
  • externe Aufrufe innerhalb des Tokens,
  • Gebühren oder Zinsen, die bei Überweisungen abgezogen werden,
  • Upgrade-Fähigkeit, Prägung, Pausierung und Sperrlisten-Befugnisse,
  • Risiken durch Eigentümer und Team sowie Konzentration des Vorrats.

Bei einem Zahlungsprodukt sind es am häufigsten diese drei Punkte, die Probleme machen: Gebühren bei Überweisungen (der empfangene Betrag ist kleiner als der gesendete), Sperrlisten (eine Überweisung kann nachträglich blockiert werden) und nicht standardkonforme Rückgabewerte. Testen Sie jedes Token, das Sie unterstützen wollen, auf einem Testnet mit echten Überweisungen, und schreiben Sie Einzahlungen nach dem tatsächlich erhaltenen Betrag gut, nicht nach dem angeforderten.

Einordnung: Warum Standards nur die halbe Arbeit sind

Standards lösen das Problem, wie ein Token mit einer Chain spricht. Sie lösen nicht das Problem, ein Produkt über mehrere Chains hinweg zu betreiben. Wenn Sie Zahlungen auf Ethereum, Tron und Solana akzeptieren, haben Sie weiterhin unterschiedliche Adressformate, unterschiedliche Gebührenmodelle, unterschiedliche Ereignisstrukturen und unterschiedliche Node-Infrastruktur.

Chaingateway haben wir um diese Lücke herum gebaut. Entwickler sollten keine chain-spezifischen Endpunkte oder eigenen Nodes brauchen, nur um zu wissen, dass ein Kunde bezahlt hat. Wir liefern dekodierte Daten, sodass eine Überweisung als lesbare Felder statt als rohe Log-Topics ankommt, und wir signieren Webhooks mit HMAC, damit Ihr Backend prüfen kann, dass eine Zahlungsbenachrichtigung echt ist.

Unser Rat für Teams am Anfang: Wählen Sie den Standard, der zu Ihrem Asset passt (fungibel, einzigartig oder gemischt), lesen Sie die Dezimalstellen jedes Mal aus dem Vertrag, und bauen Sie die Zahlungserkennung auf Ereignisse statt auf Polling.

Häufig gestellte Fragen

Eine Coin wie ETH ist nativ für ihre Blockchain und bezahlt Transaktionsgebühren. Ein Token wird von einem Smart Contract erzeugt, der einem Standard folgt und auf dieser Chain aufsetzt. Zum Verschieben von Token brauchen Sie weiterhin die native Coin für das Gas, was wir in unserer Ethereum-Übersicht behandeln.

Nein. Die ERC-20-Spezifikation kennzeichnet sie als optional. Die meisten Token implementieren sie, aber Ihr Code sollte den Fall abfangen, dass sie fehlt, statt einen Standardwert anzunehmen.

Beide Chains nutzen dasselbe Adressformat, daher kann dieselbe Adresse auf beiden existieren, aber die Guthaben sind getrennt. Gelder, die im falschen Netzwerk gesendet wurden, erscheinen nicht im anderen. Unser Leitfaden zur ERC-20-Adresse erklärt das Format und wie Sie Guthaben auslesen.

Nutzen Sie ERC-20 (oder das Äquivalent TRC-20 oder BEP-20) für austauschbare Einheiten wie ein Zahlungs- oder Utility-Token. Nutzen Sie ERC-721, wenn jedes Objekt einzigartig sein muss, und ERC-1155, wenn ein Vertrag mehrere Arten von Assets verwalten soll. Wählen Sie zuerst die Chain, denn Tooling und Gebühren jeder Chain prägen die Entscheidung.
