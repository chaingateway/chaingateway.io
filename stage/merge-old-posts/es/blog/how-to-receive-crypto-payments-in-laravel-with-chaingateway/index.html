Recibir pagos cripto en Laravel con Tron

Tutorial para crear una pasarela de pago en Laravel para TRX y tokens TRC20: una dirección por sesión, webhook de Chaingateway, firma y verificación.

Capítulos
C
Chaingateway Team
Expertos en blockchain

Revisado por Maurice Sobiera

Una pasarela de pago cripto en Laravel crea una dirección de blockchain por sesión de pago, registra en ella un webhook y marca la sesión como pagada cuando llega una notificación verificada. Este tutorial lo construye para TRX y el token JST (TRC20) en Tron con la API de Chaingateway. El código es una demostración, no un sistema de producción.

El mismo patrón funciona para Bitcoin, Ethereum, BNB Smart Chain y Polygon con pequeños cambios en los endpoints. El código de la demostración está disponible en el repositorio chaingateway-crypto-payment-demo-laravel.

No utilice este código en producción. La demostración guarda las claves privadas en texto plano, algo que nunca debe ocurrir en un entorno de producción. Chaingateway también puede crear direcciones protegidas con contraseña, en las que usted envía un password en lugar de guardar una clave privada.

¿Qué construye el tutorial?

El resultado es una pequeña pasarela de pago con estas partes:

  1. Un formulario que inicia una sesión de pago con un importe y una moneda (TRX o JST).
  2. Una nueva dirección de wallet para cada sesión.
  3. Una página de sesión que muestra la dirección, el estado, el importe esperado y el importe recibido.
  4. Un endpoint de webhook que verifica la firma, comprueba la transacción, actualiza la sesión y, de forma opcional, reenvía los fondos a una cold wallet.

¿Cómo obtengo una clave API?

Usted crea un token de API en el panel de cuenta de Chaingateway. Inicie sesión en app.chaingateway.io, abra los ajustes de usuario y seleccione API Tokens. Haga clic en Create Token, póngale un nombre (por ejemplo “Payment Gateway”) y copie el valor. Cada solicitud lo envía como bearer token. El portal para desarrolladores y la referencia de la API describen los endpoints en detalle.

También necesita un proyecto Laravel con una base de datos configurada. Si empieza desde cero, siga la guía de instalación de Laravel. Bastan conocimientos básicos de modelos, migraciones, controladores y rutas.

Paso 2: ¿Cómo defino las rutas?

Cuatro rutas cubren el flujo: la página de pago, el inicio de una sesión, la vista de la sesión y el receptor del webhook. Añádalas a routes/web.php. La ruta del webhook necesita un nombre, porque el controlador construye su URL con route('handleWebhook').

Laravel rechaza las solicitudes POST sin token CSRF, y Chaingateway no puede enviar uno. Excluya la ruta del webhook en bootstrap/app.php. La documentación de CSRF de Laravel describe el mismo ajuste para versiones anteriores.

La URL de su webhook debe ser accesible desde Internet público. Durante el desarrollo local, exponga el servidor de desarrollo mediante un túnel.

Paso 4: ¿Cómo funciona el PaymentController?

El controlador crea la wallet, registra el webhook y gestiona las notificaciones entrantes. Genérelo con php artisan make:controller PaymentController.

Crear una sesión supone dos llamadas a la API. POST /api/v2/tron/addresses devuelve una dirección nueva y, sin contraseña, su clave privada. POST /api/v2/tron/webhooks registra un webhook para las transacciones entrantes a esa dirección y devuelve el ID del webhook en data.webhook.

El manejador del webhook hace cuatro cosas en orden. Verifica la cabecera X-Signature. Busca la sesión por la dirección receptora. Pide a la API la transacción y comprueba que ret[0].contractRet sea SUCCESS. Solo entonces actualiza la sesión.

La comprobación de Pending le protege frente a una notificación repetida, algo que puede ocurrir cuando usted reenvía una notificación fallida. Una notificación que su servidor no acepta no se reintenta automáticamente. Aparece en la lista de notificaciones fallidas en GET /api/v2/tron/webhooks/notifications/failed, y puede reenviarla con POST /api/v2/tron/webhooks/notifications/{id}/retry.

¿Cómo verifico la firma del webhook?

Calcule un HMAC-SHA256 sobre el txid con su secreto personal y compárelo con la cabecera X-Signature. La cabecera contiene el resultado codificado en Base64. HMAC está especificado en la RFC 2104. El método signatureIsValid de arriba lo implementa con hash_hmac y compara con hash_equals, que tarda un tiempo constante. La documentación de la firma muestra la misma comprobación en otros lenguajes.

La demostración rechaza todas las notificaciones si no hay un secreto configurado. Una solicitud sin firma válida podría venir de cualquiera que conozca la URL de su webhook, así que no debería omitir la comprobación.

Paso 6: ¿Cómo pruebo el flujo?

Pruebe primero en la testnet. Inicie el servidor con php artisan serve y siga estos pasos.

  1. Abra /payment e inicie una nueva sesión.
  2. Envíe fondos de testnet a la dirección de la wallet que muestra la página de sesión.
  3. Espere al webhook, o envíe usted mismo una notificación firmada a /webhook.
  4. Recargue la página de sesión y compruebe que el estado ha cambiado.

Para simular una notificación, envíe un payload como el de la documentación de webhooks con una cabecera X-Signature válida. Recuerde que la comprobación de la transacción consulta a la API el txid, de modo que un ID de transacción inventado termina en el estado Failed.

¿Qué debo añadir antes de producción?

Sustituya los atajos de la demostración antes de aceptar pagos reales.

  • Cree las direcciones con una contraseña para que no se guarde ninguna clave privada en su base de datos.
  • Acredite un pago solo tras el número de confirmaciones que exija su política de riesgo.
  • Compare los importes en la unidad mínima del token y verifique la dirección del contrato en cada token.
  • Concilie con la API las sesiones abiertas de forma periódica, porque un webhook puede perderse.

Para el flujo de depósitos con más detalle, lea cómo funcionan los webhooks de pagos cripto y las garantías de entrega de webhooks. Si tiene preguntas, consulte la página de soporte.
