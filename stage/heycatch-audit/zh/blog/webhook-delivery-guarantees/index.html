Webhook 交付保证：你可以信赖的内容

Webhook 提供商实际承诺的内容：至少一次交付、重试机制、不保证顺序、可能重复。以及如何构建一个能应对所有这些情况的接收端。

章节
C
Chaingateway Team
区块链专家

大多数 Webhook 提供商充其量只能保证“至少一次”投递。您的端点将收到大多数事件，有时会收到两次，有时会延迟，有时会乱序。在 HTTP 协议上无法期望“恰好一次”投递。可靠的集成会接受这一现实，并将防护措施放在接收端：快速确认、签名校验、按事件 ID 去重、按时间戳排序，以及定期通过提供商的 API 进行对账。

本指南用通俗易懂的语言解释每种保证，展示真实提供商文档的承诺，并以一份清单结尾，您可将其应用于任何 Webhook 集成，包括加密货币支付事件。

TL;DR

  • “至少一次”是现实的上限。 提供商会重试直到您返回 2xx 响应，因此重复事件是常态，您必须处理它们。
  • 不保证顺序。 早期事件超时可能导致其在后续事件之后到达，因此请按事件自带的时间戳或序列字段排序。
  • 先确认，后处理。 校验签名、持久化存储事件、返回 2xx，然后异步执行繁重工作。
  • 按事件 ID 去重。 在产生任何副作用（如入账）前，利用唯一索引记录事件 ID。
  • 将 Webhook 视为通知而非账本。 按计划通过 API 对关键记录进行对账，以捕获重试遗漏的内容。

What the three delivery guarantees mean

投递语义源自分布式系统，可直接映射到 Webhook 场景。

GuaranteeWhat the sender doesWhat can go wrongWhat you build
At-most-once仅发送一次事件，绝不重试若您的端点宕机，事件将丢失通过 API 进行对账
At-least-once持续重试，直到收到确认或耗尽重试预算重复、延迟到达、乱序幂等处理器、去重机制
Exactly-once理论上仅投递一次，无丢失无重复在不可靠的网络边界上无法实现At-least-once 加去重

采用 At-most-once 时，一次失败即意味着事件丢失。这对发送方简单，但对涉及资金的业务不安全。

采用 At-least-once 时，发送方会持续重试，直到看到成功响应或耗尽重试预算。丢失变得罕见，但有个陷阱：假设您的处理器入账后、返回 200 前崩溃。发送方未收到确认，便会再次发送该事件。从发送方角度这是正确行为；从您的角度看，除非您加以防范，否则会造成重复入账。

恰好一次 是所有人想要却没人能在 HTTP 上承诺的。发送方无法在连接中断时知道你的服务器是否已处理请求。实际的替代方案是“至少一次”投递，配合能忽略重复的接收端。这种组合能给你带来恰好一次的效果，而这才是真正重要的。

提供商实际承诺的内容

阅读任何严肃的 Webhook 提供商文档中的投递部分，都会看到相同的模式。

Adobe I/O Events 称每个事件至少针对每个注册投递一次，可能发送重复事件，且不保证事件顺序。美国银行 API Column 声明 Webhook 事件不保证按创建顺序到达。一个超时的早期事件可能落在后一个事件之后，因为每次重试都是独立重新调度的。

最后这个细节解释了大多数顺序问题。事件 A 失败一次，安排一分钟后重试。事件 B 在之后创建，立即成功。你的系统先看到 B，再看到 A。提供商那边没什么坏掉。担保根本就没覆盖顺序。

顺序：使用事件的时钟，而非投递时钟

Wise 的 Webhook 指南建议从事件时间戳或（如有）单调递增的序列 ID 重建时间顺序，而不是从通知发送的时间。其文档指出，发送时间可能与事件发生时间不同，尤其是在重试期间。

实践中：

  1. 将事件的业务时间戳或序列号与负载一起存储。
  2. 事件到达时，将其与你持有的该对象的最新状态比较。
  3. 如果传入事件比你已应用的更旧，记录它但不要让它覆盖较新的状态。

对于从待处理变为已确认的支付状态，这能阻止迟到的“待处理”事件将已确认的支付回滚。

重试如何工作及何时停止

重试策略各异，但形态一致：指数退避、上限和硬性停止。

提供商重试行为（来自其文档）
Column三天内最多 25 次重试，指数退避，失败投递一分钟后首次重试
Probo最多 12 次尝试，以 30 秒为基础的指数退避加完全抖动，上限四小时
Stripe对暂时不可用的端点自动重试，最长三天

来源：Column、Probo 和 Stripe 文档。

Probo 的文档增加了有用细节。它会重试网络错误、超时、以及 408、425、429 或 5xx 响应，并遵守 Retry-After 头（不超过其上限）。尝试耗尽后，投递标记为失败且不再重新入队。

有两条经验教训。第一，您端点的错误代码是信号：5xx 告诉发送方重试，因此仅在您确实希望重试时才返回它。第二，重试窗口是有限的。如果您的服务宕机时间超过该窗口，这些事件将从重试队列中移除，您需要另一种方式来恢复它们。关于设计调度的更深入探讨，请参阅这份 webhook 重试策略设计指南，其中涵盖了确认响应、超时和瞬态故障。

快速确认，稍后处理

当您返回 2xx 状态码时，交付即视为成功。Column 认为在 10 秒内收到 2xx 即视为事件已送达，并建议在接收后立即返回，而在进行大量处理之前。NestJS 的文档 将 2xx 视为成功，将其他所有情况（包括重定向、超时和拒绝连接）视为失败。

因此，处理程序的职责很窄：

  1. 读取原始请求体。
  2. 验证签名。
  3. 检查事件类型和 ID。
  4. 将事件写入持久化存储（数据库行或队列消息）。
  5. 返回 200、202 或 204。

其他所有操作，例如更新余额、发送邮件或调用其他服务，均由从该存储读取的工作进程运行。如果您在内联处理中执行耗时工作，缓慢的数据库查询会变成超时，超时会变成重试，重试会变成重复。关于在长时间运行的处理之前先用成功代码响应的同一观点，也见于这篇关于 业务系统中的 webhook 的文章。摄入、排队和扇出的方法在我们自己的文章 webhook 与 WebSocket 中有介绍。

使重复无害

因为至少一次交付意味着会有重复，您的处理程序必须是幂等的。标准方法很简单。

Probo 的指导是 验证签名、确认预期的组织和事件类型，然后在任何副作用发生前以原子方式记录事件 ID 并加上唯一索引。后续携带已记录 ID 的请求将被忽略。Stripe 给出相同建议：记录已处理的事件 ID 并跳过已处理的任何事件。许多提供商通过在每个负载中包含唯一 ID 使这变得容易。例如，Adobe 在负载中放入 UUID 并在 x-adobe-event-id 头中重复它。

最小模式：

  1. 将事件 ID 插入带有唯一约束的表中。
  2. 如果因 ID 已存在而插入失败，返回 200 并停止。
  3. 如果成功，将工作入队。

顺序很重要。先记录，后行动。如果您先行动且在记录前崩溃，重试会重复该行动。如果您先记录且在行动前崩溃，您的工作进程应在重启时拾取未完成的记录，因此事件不会被静默丢弃。

对于资金流转，增加第二层：使业务操作本身也幂等。以交易哈希和日志索引或支付 ID 作为存款入账的键，这样即使事件表中有 bug 也不会对同一笔付款入账两次。

验证每个请求

Webhook 端点是一个公开的 URL，用于触发您系统中的操作。除非您检查请求的发送者，否则任何人都可以向其发送请求。

Stripe 要求使用 原始请求体、签名头和您的端点密钥 进行验证。Probo 的建议是使用未经修改的请求体，在解析 JSON 之前先验证签名，然后应用时间戳新鲜度检查。在验证之前解析并重新序列化请求体，是导致签名永远无法匹配的典型原因。

可靠的验证流程：

  • 使用您的密钥，基于接收到的精确字节计算 HMAC。
  • 使用恒定时间比较将其与头部值进行对比。
  • 拒绝时间戳超出短容差窗口的请求，以限制重放攻击。
  • 只有在此之后，才解析 JSON 并检查事件类型。

如果您想了解区块链事件的签名请求如何工作，请阅读关于我们的 Webhook 安全功能 的介绍。

恢复重试遗漏的事件

即使是完美的接收端，在某些场景下也会丢失事件：超出重试窗口的停机、配置错误的防火墙、返回 500 错误持续数小时的部署。恢复选项因提供商而异。Probo 没有手动重放功能，也不会将失败的投递重新入队；它期望您对失败发出警报，并通过其 API 进行对账。Stripe 指出，操作员 可以手动处理积压 以加快恢复。Column 表示，当故障需要对账时，缺失或额外的事件 可以通过其事件 API 获取。

正如 ThriveDesk 的开发者文档 所明确陈述的通用设计原则：将 Webhook 视为通知，而非唯一的事件账本。持久化存储载荷，异步处理它们，并定期通过 REST API 对关键记录进行对账。

对账任务可以很简单：

  1. 按计划，从提供商的 API 列出上一个时间窗口内重要的对象（支付、钱包、订单）。
  2. 将它们的状态与您自己的记录进行比较。
  3. 通过 Webhook 处理程序使用的同一幂等代码路径应用任何差异。
  4. 如果任务频繁发现缺口，则发出警报，因为这指向端点问题。

由于后续事件通常携带对象的完整当前状态，因此遗漏的中间事件可能无论如何都会被下一个事件覆盖。对账覆盖了没有下一个事件的情况。

将其应用于加密货币支付事件

链上支付提高了风险，因为遗漏或重复的事件意味着遗漏或重复的入账。无论提供商是谁，以下几个习惯都有帮助：

  • 关键点：链上标识符。 使用交易哈希加上其中的转账索引，而不仅仅是 Webhook 的投递 ID。
  • 将状态建模为一种演进。 待处理、已确认和最终确定是有顺序的状态。绝不允许旧状态覆盖新状态。
  • 基于自身数据进行匹配。 在入账前，在您的数据库中查找接收地址或引用；忽略您不拥有的地址的事件。
  • 对账余额。 定期将您的账本与 API 返回的钱包余额进行比对，可捕获事件流遗漏的任何内容。

我们关于使用 Webhook 自动处理存款的演示将这些步骤置于支付流程中，而 Polygon Webhook 指南则展示了在特定链上轮询的事件驱动替代方案。

我们的观点

我们为转移资金的开发者构建 Webhook，因此我们每天都在思考投递保障。我们的观点是：没有诚实的提供商能承诺精确一次投递，正确的做法是建立清晰的契约：事件是通知，签名请求证明其来源，而 API 始终作为事实来源存在。

这就是为什么我们将实时事件通知与跨链统一的 REST API 相结合。Webhook 告知您发生了什么。API 让您确认它、获取解码后的交易数据，并在需要时进行对账。我们的请求经过 HMAC 签名，以便您的接收端验证，且数据预先解码，让您的处理程序将时间花在业务逻辑上，而不是解析原始日志。

我们还认为，团队不应被迫运行自己的节点，或为了集成而应对特定链的端点。一次集成、一套签名方案、一种跨 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Chain 和 Arbitrum 查询状态的方式，意味着投递边缘情况藏身之处更少。

常见问题

Webhook 能否实现精确一次投递？

在不可靠的 HTTP 连接上无法实现。当响应丢失时，发送方无法判断您的服务器是否已处理请求。实用的方法是至少一次投递加上基于事件 ID 的去重，这能在您的系统中产生精确一次的效果。

我的 Webhook 端点应返回什么状态码？

一旦您验证并持久化存储了事件，请尽快返回 2xx 代码，如 200、202 或 204。像 Column 这样的提供商仅在 10 秒内收到 2xx 时才视为投递成功。仅当您希望发送方重试时，才返回 5xx。

为什么 Webhook 事件会乱序到达？

重试是针对每个事件独立安排的。如果事件 A 超时而事件 B 成功，B 会先到达，而 A 会在重试后出现。Adobe 和 Column 等提供商明确指出不保证顺序，因此请按事件的时间戳或序列字段进行排序。

如果发送 Webhook 时我的服务器宕机了会怎样？

我们审阅的文档显示，大多数提供商会在有限的时间窗口内（从几小时到约三天）使用指数退避进行重试。在此之后，事件可能不会重新入队，因此请针对提供商的 API 运行定期的对账任务，以恢复任何遗漏的内容。

我需要验证 Webhook 签名吗？

需要。您的端点是公开可访问的，使用原始请求体和您的密钥进行签名检查，是确认请求来自提供商的方式。请添加时间戳容差以降低重放攻击风险。
