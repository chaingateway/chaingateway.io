Blockchain frente a base de datos: diferencias clave

Diferencias entre blockchain y base de datos: modelo de escritura, consenso, latencia y coste por escritura, con una lista de decisión y un patrón híbrido.

Capítulos
C
Chaingateway Team
Expertos en blockchain

Revisado por Maurice Sobiera

Una blockchain es un libro mayor copiado en muchos nodos independientes que deben ponerse de acuerdo en cada bloque nuevo. Una base de datos es un almacén gestionado por un solo operador, que decide quién puede leer y escribir. La diferencia es la confianza: una blockchain funciona sin un operador de confianza, y una base de datos depende de uno. La mayoría de las aplicaciones necesitan una base de datos.

Mucha gente sigue usando ambos términos como sinónimos, o dice que «la blockchain es solo otra base de datos». Ese planteamiento provoca errores de arquitectura, porque las tecnologías responden a preguntas distintas. Una base de datos responde a cómo almacenar y consultar datos de forma eficiente. Una blockchain responde a cómo pueden ponerse de acuerdo varias partes que no confían unas en otras sobre datos compartidos.

Este artículo compara ambas en una tabla de 10 filas y después examina cada diferencia por separado. Termina con el patrón que usan la mayoría de los sistemas en producción: una base de datos y una blockchain trabajando juntas.

¿Qué es una blockchain (y una «base de datos blockchain»)?

Una blockchain es un libro mayor distribuido: un registro de transacciones replicado en muchos nodos independientes de una red peer-to-peer. Cada nodo participa en la administración del libro mayor. Cuando hay que añadir datos nuevos, la mayoría de los nodos debe llegar primero a un consenso. Ese paso de acuerdo es lo que hace tan difícil la manipulación: un atacante tendría que dominar a la mayor parte de la red, no hackear un solo servidor.

Cada transacción recibe una marca de tiempo y una posición en la cadena, así que cualquier nodo puede rastrear y verificar el historial completo. Esta combinación de replicación y verificabilidad es lo que se quiere decir con «base de datos blockchain». El término es impreciso, porque, como veremos, una blockchain renuncia a gran parte de lo que define a una base de datos en el sentido cotidiano.

¿Qué es una base de datos tradicional?

Una base de datos tradicional usa una arquitectura cliente-servidor. Los clientes se conectan a un servidor central, y el operador de ese servidor decide quién puede leer y escribir. El administrador verifica la identidad de un usuario antes de conceder acceso y puede modificar cualquier registro en cualquier momento.

La centralización es a la vez una debilidad y una fortaleza. Si la autoridad central se ve comprometida, todo el conjunto de datos queda comprometido, y por eso existen las copias de seguridad. Como una sola parte controla todo, los datos son fáciles de gestionar, rápidos de consultar y baratos de almacenar. Postgres y MySQL ejecutan la mayoría de las aplicaciones que usa.

El resto del artículo desarrolla las filas que deciden las arquitecturas: el control, el modelo de escritura y el rendimiento.

Control

La diferencia más grande entre una blockchain y una base de datos es quién manda. En una base de datos tradicional, una autoridad central verifica y autentica a los usuarios antes de concederles acceso. El poder sobre los datos recae en una parte, o en un grupo pequeño.

Una blockchain no tiene esa autoridad. Cada nodo contribuye a operar el libro mayor, y los nodos intercambian información sin un administrador que supervise. Los datos nuevos solo entran en la cadena después de que los nodos lleguen a un consenso. Nadie puede reescribir discretamente un registro, porque todos los demás tienen una copia que dice lo contrario.

Arquitectura

Una base de datos tradicional funciona con una arquitectura cliente-servidor. El modelo escala desde un portátil hasta un centro de datos. Toda la comunicación pasa por una conexión con el servidor central. No existe un paso de consenso, porque la palabra del administrador es definitiva.

Una blockchain funciona como una red peer-to-peer. Los pares se conectan entre sí directamente y cooperan para acordar el siguiente bloque mediante un algoritmo de consenso. El clásico es Proof of Work, en el que los participantes gastan potencia de cálculo para validar transacciones; Bitcoin, tal como se describe en el libro blanco de Bitcoin, todavía lo usa. Ethereum pasó a Proof of Stake en 2022, que sustituye la carrera de cálculo por una garantía económica. En ambos casos, el paso de acuerdo existe precisamente porque no hay un administrador cuya palabra pueda ser definitiva.

Modelo de escritura: CRUD frente a solo añadir

Una base de datos centralizada admite las cuatro operaciones CRUD: crear, leer, actualizar y eliminar. El manejo de datos es sencillo, porque todo es editable.

Una blockchain admite dos: leer y escribir. Una vez que una transacción está en la cadena, no hay actualización ni eliminación posibles. Esta inmutabilidad es precisamente el sentido, porque impide la manipulación y da a cada participante un historial verificable. Pero el efecto es de doble filo. Un error que escribe datos incorrectos no se puede corregir con una sentencia UPDATE, y los datos personales que deben poder borrarse a petición (artículo 17 del RGPD) no tienen nada que hacer en la cadena desde el principio.

Rendimiento y coste por escritura

Las bases de datos tradicionales son más rápidas, y no hay comparación posible. Una escritura en una base de datos es una operación de disco en una sola máquina. Una escritura en una blockchain pasa por la verificación de firmas, el consenso y la replicación en todos los nodos antes de contar. En las cadenas públicas, eso tarda segundos o minutos, no milisegundos.

Las escrituras además tienen un precio. Cada transacción de blockchain cuesta una comisión, pagada en la moneda nativa de la cadena, y la comisión existe para compensar a los nodos que hacen el trabajo de verificación. Las comisiones varían según la cadena y la carga. En TRON, una transferencia de token consume Energy y Bandwidth, que se obtienen con staking o se pagan en TRX. Una escritura en una base de datos sobre hardware que ya tiene no cuesta nada que se pueda desglosar en una factura. Si su carga son miles de escrituras por segundo, eso por sí solo decide la cuestión blockchain frente a base de datos a favor de la base de datos.

¿Cuánto tarda en liquidarse una escritura?

Un commit en una base de datos tarda milisegundos. En una blockchain, el tiempo hasta que una escritura es final depende de las reglas de consenso de la cadena. La tabla enumera las dos cadenas que este artículo usa como ejemplo.

Las cifras de rendimiento de las cadenas son más difíciles de comparar. Las cifras publicadas de transacciones por segundo suelen citar picos teóricos y dependen de la mezcla de transacciones, así que no las incluimos. Las cadenas también cambian sus parámetros con el tiempo, así que consulte la documentación de la propia cadena antes de basarse en una cifra.

La distancia con una base de datos sigue siendo grande. Incluso las cadenas con tiempos de liquidación de pocos segundos cobran una comisión por escritura y ejecutan una ronda de consenso para cada una. Las cadenas compiten entre sí en estas cifras. No compiten con las bases de datos.

ACID frente a finalidad por consenso

Los expertos en bases de datos y los de blockchain dicen ambos «la transacción se ha completado» y se refieren a garantías distintas.

En una base de datos, las garantías son las propiedades ACID. Atomicidad: se aplican todos los cambios de una transacción, o ninguno. Consistencia: las restricciones se cumplen antes y después. Aislamiento: las transacciones concurrentes no ven el trabajo a medio hacer de las demás. Durabilidad: una vez confirmados, los datos sobreviven a un fallo, porque se han escrito en el write-ahead log en disco. Las cuatro se entregan en el momento del commit, milisegundos después de haberlo pedido.

Una cadena de contratos inteligentes se acerca sorprendentemente a las tres primeras. Una llamada a un contrato es atómica: si algún paso se revierte, se revierte toda la transacción. La consistencia reside en el código del contrato en lugar de en las restricciones del esquema. El aislamiento es el más fuerte posible: el consenso obliga a que todas las transacciones sigan un único orden global, y eso es también exactamente lo que limita el rendimiento, porque un orden total no deja nada que paralelizar con seguridad.

La durabilidad es donde los modelos se separan. Una escritura en una base de datos es duradera en el commit. Una escritura en un bloque nuevo de una blockchain todavía puede desaparecer, porque los bloques competidores pueden ganar y reorganizar la cadena.

Lo que sustituye a la durabilidad es la finalidad: el momento a partir del cual el protocolo garantiza que la transacción ya no puede ser desplazada. En TRON eso tarda 19 bloques, unos 57 segundos. En Ethereum tarda dos épocas de attestations de validadores, unos 15 minutos. Los bloques intermedios son probablemente seguros, pero no demostrablemente seguros. La regla para los sistemas de pago se deduce directamente: acredite al cliente en la finalidad, no en la primera inclusión, o implemente un manejo de reversiones que le resultará muy difícil probar.

Dónde encaja CAP

El teorema CAP dice que un sistema distribuido que sufre una partición de red debe elegir entre mantenerse consistente y mantenerse disponible. Un Postgres de un solo nodo evita la cuestión por completo, porque no hay nada que particionar, y esa es una razón poco reconocida por la que las bases de datos de un solo nodo siguen siendo agradables de operar. Las bases de datos distribuidas eligen un lado y lo documentan.

Las blockchains son sistemas distribuidos, así que también deben elegir. Los diseños de cadena más larga, como Bitcoin, eligen la disponibilidad: durante una partición, ambos lados siguen produciendo bloques, y la consistencia se repara después, cuando gana una de las ramas, que es precisamente lo que es una reorganización. Los diseños basados en finalidad se inclinan hacia el otro lado: si son inalcanzables demasiados validadores, Ethereum deja de finalizar y los Super Representantes de TRON dejan de solidificar bloques, sacrificando el avance para evitar respuestas permanentes en conflicto. Ninguna de las dos opciones es incorrecta. Pero eso significa que «blockchain» no es una escapatoria de las compensaciones de los sistemas distribuidos; es un conjunto concreto de ellas, pagado con latencia y comisiones.

En qué es bueno cada lado y qué le cuesta

Las fortalezas de la base de datos se acumulan. Las consultas en milisegundos y las escrituras baratas son la parte visible. Debajo hay décadas de herramientas: copias de seguridad, recuperación a un punto en el tiempo, replicación, migraciones e índices ajustados a sus patrones de consulta. Los datos son privados por defecto y pueden eliminarse bajo demanda, algo que la normativa a veces exige.

El coste de esta comodidad es una confianza concentrada. El operador puede editar cualquier cosa, así que un registro de auditoría es tan creíble como lo sea el operador. Dos empresas que no confían una en la otra no pueden compartir un único Postgres como fuente de verdad, porque una de ellas tiene que alojarlo.

Las fortalezas de la blockchain son justo la pieza que falta. Nadie la opera en solitario, así que nadie puede reescribirla en solitario. Cualquiera con un nodo puede verificar el historial, incluidos los externos que nunca dio de alta. Para los pagos, ofrece un canal de liquidación donde cualquier wallet puede pagar a cualquier otra sin que un intermediario apruebe a ninguna de las dos partes.

Los costes reflejan las comodidades de la base de datos. Cada escritura se mide por comisión y la marca el consenso. El almacenamiento es solo de adición, y todo es público salvo que lo diseñe para evitarlo. La red de seguridad operativa desaparece: ningún ticket de soporte revierte una transacción, y una clave perdida es valor perdido, no un restablecimiento de contraseña.

Las dos listas apenas se solapan, así que ninguna gana por puntos. Una pregunta decide: ¿tiene su sistema un operador de confianza, o debe funcionar sin uno?

Cuándo usar cada una: una lista de decisión

  • Si una sola parte controla los datos y sus usuarios lo aceptan, use una base de datos. Es más rápida, más barata y más fácil de operar.
  • Si varias partes necesitan escribir en un estado compartido sin confiar entre sí ni en un intermediario, una blockchain justifica su sobrecoste. Es el único trabajo que las bases de datos no pueden hacer.
  • Si los registros deben ser demostrablemente inalterados para externos (auditorías, liquidación entre empresas), una blockchain lo proporciona sin notario.
  • Si necesita actualizar y eliminar, o guarda datos personales sujetos a solicitudes de borrado, guárdelos en una base de datos.
  • Si necesita baja latencia o un alto rendimiento de escritura, base de datos, sin discusión.
  • Si acepta o envía pagos cripto, la capa de liquidación es una blockchain nos guste o no. Lo sensato es mantener todo lo demás fuera de la cadena, lo que lleva al patrón híbrido.

Tres arquitecturas, probadas en la práctica

Los criterios abstractos son más fáciles de aplicar cuando se prueban con sistemas concretos. Aquí tiene tres, una por arquitectura.

Un programa de puntos de fidelidad: solo base de datos

Un minorista emite puntos, los clientes los canjean en caja y el equipo de marketing ajusta los saldos cuando una promoción sale mal. Todas las propiedades de este sistema apuntan en la misma dirección. Una empresa controla los puntos y los clientes lo aceptan, así que no hay una brecha de confianza que salvar. El volumen de escritura es alto, la latencia en la caja debe ser invisible y los datos de cuenta están sujetos a las normas de borrado.

Postgres lo gestiona todo sin ceremonias. Una versión en cadena pagaría una comisión por cada punto abonado y esperaría el consenso en caja. No podría atender una solicitud de borrado del RGPD. Todo empeora en una blockchain, así que la decisión lleva un minuto.

Un exchange descentralizado: solo en cadena

Ahora invierta todas las suposiciones. Un DEX existe para que desconocidos puedan operar sin que ningún operador retenga sus fondos. Si añade un operador de base de datos de confianza, el producto no tiene razón de existir.

Por eso todo el estado vive en los contratos: saldos, reservas de pools y lógica de intercambio. Cada operación paga su coste mediante el consenso. Las restricciones de la cadena moldean entonces el diseño. Los libros de órdenes clásicos requieren colocar, modificar y cancelar órdenes con tanta frecuencia que las escrituras con comisión resultan demasiado caras. Esa es una parte importante de por qué los creadores de mercado automatizados se impusieron en la cadena.

Los usuarios pagan comisiones y esperan segundos por cada operación, porque la ausencia de confianza es el producto que vinieron a buscar. Note lo que el DEX sigue sin poner en la cadena: su interfaz web, su analítica y sus gráficos de precios funcionan en servidores y bases de datos normales, incluso aquí.

Cobros cripto para un SaaS: el híbrido

El caso comercial habitual se sitúa entre los extremos. Un SaaS quiere aceptar USDT de clientes de todo el mundo; sus suscripciones, facturas y cuentas de usuario ya viven en una base de datos y deben seguir ahí. La cadena es inevitable exactamente una vez, en la liquidación, y todo lo demás se mantiene deliberadamente fuera de ella. Este tercer escenario es el patrón que la mayoría de los equipos acaba construyendo, así que tiene el recorrido detallado que sigue.

El patrón híbrido: base de datos fuera de la cadena, liquidación en la cadena

Los sistemas de pago en producción casi nunca eligen una cosa u otra. Reparten el trabajo: la blockchain liquida el valor y la base de datos hace todo lo demás. Los registros de clientes, los pedidos, los saldos y los datos de sesión viven en Postgres o MySQL, donde se pueden consultar y editar. Solo el movimiento real de fondos toca la cadena, a través de una API, así que la aplicación nunca ejecuta su propio nodo.

Un flujo de depósito concreto tiene este aspecto:

  1. Un cliente quiere pagar. Su backend le asigna una dirección de depósito dedicada mediante una llamada a la API y guarda en su base de datos la relación entre dirección y cliente.
  2. El cliente envía USDT a esa dirección. No consulta la cadena; en su lugar, se dispara un webhook cuando se detecta la transferencia.
  3. Su endpoint verifica la cabecera X-Signature del webhook, escribe el depósito en su propia base de datos y acredita allí el saldo del cliente.

El manejador es deliberadamente poco espectacular:

La carga útil del webhook incluye txid, from, to, amount, contractaddress y blocknumber, así que el insert no necesita nada más que el cuerpo de la petición. A partir de ahí, la lógica de su aplicación lee los saldos de sus propias tablas, a velocidad y coste de base de datos. La cadena solo se vuelve a consultar cuando los fondos salen.

Chaingateway firma los webhooks con una cabecera X-Signature una vez que fija un secreto personal, tal como se describe en Verificar las firmas de los webhooks. Los webhooks no se reintentan automáticamente. Las entregas fallidas se listan en GET /api/v2/tron/webhooks/notifications/failed. Usted reenvía cada una con POST /api/v2/tron/webhooks/notifications/{id}/retry. Las notificaciones anteriores se pueden obtener con GET /api/v2/tron/webhooks/notifications para conciliar tras una caída.

La guía de webhooks tiene la configuración completa, y el inicio rápido cubre la primera llamada a la API.

Entonces, ¿cuál gana?

Cada una es mejor en lo que la otra no puede hacer. La base de datos gana sin discusión en el manejo de datos: rendimiento, escalabilidad, potencia de consulta y coste operativo. La blockchain gana donde no existe un operador de confianza: es resistente a la manipulación, auditable por cualquiera y fácil de automatizar, ya que cada wallet habla el mismo protocolo.

La respuesta práctica para la mayoría de los equipos es ambas, unidas por una API: base de datos para la aplicación, blockchain para la liquidación. Preguntas frecuentes

¿Es blockchain una base de datos?

Solo en el sentido más laxo: almacena datos de forma duradera. No cumple la definición cotidiana, porque no se pueden actualizar ni eliminar registros, las consultas son limitadas y las escrituras cuestan dinero y tardan segundos en finalizar. Llamarla «una máquina de confianza con almacenamiento» se acerca más que llamarla base de datos.

¿Puede una blockchain sustituir a una base de datos tradicional?

En una aplicación normal, no. La latencia, las comisiones por escritura y la falta de las operaciones UPDATE y DELETE la descartan como almacén de datos principal. Una blockchain sustituye la capa de liquidación y el notario, no a Postgres.

¿Qué es una base de datos blockchain?

El término suele referirse al propio libro mayor: el historial de transacciones replicado entre nodos. Algunos productos también indexan los datos de la cadena en una base de datos normal para poder consultarlos con SQL, lo cual es útil, pero entonces está consultando de nuevo una base de datos, no una blockchain.

¿Por qué una blockchain es mucho más lenta que una base de datos?

Porque cada escritura debe firmarse, propagarse, acordarse por consenso y replicarse en todos los nodos antes de ser final. Una escritura en una base de datos es una máquina escribiendo en su propio disco. La lentitud es el precio de eliminar al operador de confianza, no un defecto de implementación que vaya a desaparecer con la optimización.

¿Tiene una blockchain transacciones ACID?

Parcialmente. Una transacción de contrato inteligente es atómica (se aplica por completo o se revierte por completo), el código del contrato garantiza la consistencia y el consenso da un orden total, que es un aislamiento más fuerte que el que usan la mayoría de las bases de datos. La durabilidad es la excepción: una transacción solo queda liquidada al alcanzar la finalidad, de segundos a minutos después de su inclusión según la cadena, y hasta entonces una reorganización puede desplazarla. Los sistemas que acreditan dinero deben basarse en la finalidad, no en la primera inclusión.

¿Cuándo tiene sentido una blockchain para un negocio normal?

Casi siempre en un solo punto: los pagos. Un negocio rara vez necesita un estado compartido con partes en las que no confía, pero aceptar cripto significa que la capa de liquidación es, por definición, una blockchain. La configuración viable es el patrón híbrido descrito arriba, en el que la cadena liquida el valor y todo lo operativo permanece en su base de datos, conectada mediante una API y no mediante un nodo propio.

Si las cadenas son lentas, ¿cómo muestran las aplicaciones datos de blockchain al instante?

No leen la cadena en cada petición. Los exploradores y las wallets consultan índices: datos de la cadena copiados a bases de datos normales y servidos desde ahí a velocidad de base de datos. Los sistemas de pago hacen lo mismo, un webhook cada vez, escribiendo cada depósito confirmado en sus propias tablas y leyendo los saldos localmente a partir de entonces. La cadena es la fuente de verdad; la base de datos es la copia de trabajo.
