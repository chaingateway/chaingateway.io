Cómo crear una cartera cripto con una API: Guía 2026

Aprenda a crear carteras cripto mediante una API: opciones de custodia, seguridad de claves, diseño de direcciones, webhooks y un plan de construcción paso a paso para desarrolladores.

Capítulos
C
Chaingateway Team
Expertos en blockchain

Para crear una cartera cripto con una API, envía una solicitud autenticada a un servicio que genera un par de claves, almacena la clave privada y devuelve una dirección pública que puede mostrar al usuario. La parte difícil no es esa llamada. Es decidir quién custodia las claves, cómo protege las credenciales que las rodean y cómo se entera de cuándo llega el dinero. Esta guía recorre esos tres puntos, con los compromisos que un equipo de producción debe resolver antes del lanzamiento.

TL;DR

  • Una API de cartera genera claves y devuelve una dirección. Sus verdaderas decisiones de diseño son la custodia, el almacenamiento de claves y la detección de pagos.
  • Asigne a cada usuario o a cada factura su propia dirección, y registre el hash de cada transacción entrante como clave única en su base de datos.
  • Utilice webhooks firmados en lugar de sondeo (polling), verifique cada firma y haga que su gestor sea idempotente.
  • La generación de claves debe usar una fuente aleatoria criptográficamente segura, y las claves de producción pertenecen a almacenamiento no exportable, como un HSM.
  • Una API unificada multi-cadena le evita ejecutar nodos y mantener una integración separada por red.

Qué hace realmente una API de cartera

Una cartera blockchain es software que gestiona claves. La visión general de tecnología blockchain del NIST la describe como una herramienta que puede almacenar claves privadas, claves públicas y direcciones, y que ayuda a los usuarios a trabajar con los activos que esas claves controlan. Una API de cartera traslada ese trabajo del dispositivo del usuario a su backend.

En la práctica, una API de cartera cubre cuatro tareas:

  1. Crear: genera un nuevo par de claves y devuelve la dirección para una red determinada.
  2. Leer: informa de saldos e historial de transacciones para esa dirección.
  3. Enviar: construye, firma y difunde una transferencia, incluida una estimación de la comisión.
  4. Notificar: avisa a su aplicación cuando ocurre algo en la dirección.

La guía para desarrolladores de Bitcoin sobre procesamiento de pagos señala algo que se aplica a cualquier cadena: antes de solicitar un pago, su aplicación debe crear una dirección u obtenerla de otra parte, y cada paso del proceso puede externalizarse a APIs de terceros. Externalizar es una opción de ingeniería legítima. Intercambia control sobre la infraestructura por velocidad y menos piezas móviles.

Toda integración de cartera comienza con una pregunta: ¿quién puede firmar una transacción?

La mayoría de startups y agencias que construyen funciones de pago quieren la fila del medio. Los usuarios depositan en direcciones que su app controla, su backend envía los pagos, y nadie tiene que ejecutar un nodo ni escribir código de firma para seis redes.

La custodia puede acarrear consecuencias legales que dependen de su país y modelo de negocio. Si va a custodiar fondos de clientes, hable con un abogado que conozca las normas de transmisión de dinero y activos virtuales en su jurisdicción antes de lanzar. Este artículo cubre solo el aspecto técnico.

Una nota sobre la abstracción de cuentas

Si construye sobre Ethereum se encontrará con wallets de contrato inteligente. La hoja de ruta de abstracción de cuentas de Ethereum describe permitir que las cuentas lleven seguridad programable y mejores experiencias de usuario, en lugar de depender de una única clave privada en bruto. Eso puede habilitar funciones como gas patrocinado y recuperación flexible. Es una opción sólida para apps de consumo donde los usuarios poseen sus wallets. Para un backend que crea miles de direcciones de depósito y barre fondos, la cuenta de propiedad externa clásica sigue siendo el modelo más simple, y es el que funciona de la misma manera en Bitcoin, Tron y cadenas EVM. La propia documentación de Ethereum explica los dos tipos de cuentas, cuentas de propiedad externa y cuentas de contrato, si necesita un repaso.

Paso a paso: creando su primera wallet a través de una API

Los endpoints exactos difieren según el proveedor, así que lea la referencia de la API que elija. La secuencia a continuación permanece igual.

1. Obtenga las credenciales y manténgalas en el lado del servidor

Regístrese, obtenga una API key y, si el proveedor usa firma de peticiones, un secreto. Estas credenciales pueden mover dinero, así que trátelas como contraseñas de base de datos. Cárguelas desde un gestor de secretos, nunca desde código del lado del cliente, nunca desde un repositorio público. La guía de OWASP para pruebas de SDK recomienda verificar que las credenciales tengan alcance y sean revocables, lo cual es una buena regla para cualquier integración: si una clave se filtra, debería poder revocarla sin reconstruir su app.

2. Cree la wallet o dirección

Llame al endpoint de creación para la red que necesite. Obtendrá una dirección, y normalmente un identificador que su sistema puede usar para referirse a la wallet después. Almacene tres cosas en su propia base de datos de inmediato:

  • la dirección,
  • la red a la que pertenece,
  • el usuario interno, pedido o factura a la que está vinculada.

No almacene la clave privada usted mismo a menos que haya construido el almacenamiento seguro para custodiarla. Con un modelo hosted, ese es el trabajo del proveedor.

3. Muestre la dirección y prevenga errores

Muestre la dirección con el nombre de su red en texto plano. El ticket de soporte más común en pagos con criptomonedas es un usuario que envió un token a través de la red incorrecta. Una dirección USDT en Ethereum y otra en Tron no se parecen en nada, pero los usuarios siguen cometiendo errores. Añada la etiqueta de la red junto al código QR y considere un breve paso de confirmación antes de mostrarlo.

4. Suscríbase a eventos para esa dirección

Registre un webhook para que su backend se entere de los depósitos sin necesidad de sondeo. La siguiente sección explica cómo construir el extremo receptor de forma segura.

5. Pruebe primero en una red de prueba

Ejecute el bucle completo en una testnet: cree una dirección, envíe fondos de prueba, reciba el evento, acredite la cuenta y, a continuación, realice un pago. Solo entonces cambie las credenciales y la red a mainnet, y comience con cantidades pequeñas.

Una dirección por usuario o una por factura?

La reutilización es el atajo que causa problemas contables más adelante. La guía para desarrolladores de Bitcoin aborda el enfoque estándar de asignar a cada solicitud de pago su propia dirección, de modo que un pago entrante se vincule claramente al pedido que lo originó.

Los patrones habituales:

  • Una dirección por factura. Conciliación más limpia. Ideal para flujos de pago con un importe esperado y un tiempo de expiración.
  • Una dirección por usuario. Sencillo para funciones de depósito, como una recarga de saldo. Cada transferencia entrante acredita la misma cuenta.
  • Dirección agrupada con memo o etiqueta. Solo para redes y activos que lo admitan, y más difícil de implementar correctamente.

Si genera direcciones a partir de un esquema determinista jerárquico, la estructura está estandarizada. BIP 44 define la disposición de la ruta de propósito, tipo de moneda, cuenta, cambio e índice, lo que permite que una semilla produzca un árbol predecible de direcciones. Una API alojada normalmente se encarga de esto, pero conocer la disposición ayuda cuando audita o migra.

Seguridad de claves: donde los proyectos de monedero realmente fallan

Rara vez es el protocolo de red lo que hace que un producto de monedero sea hackeado. El grupo de seguridad de contratos inteligentes de OWASP señala que el mayor riesgo es la aleatoriedad y el almacenamiento de las claves privadas. Una semilla predecible conduce a un compromiso total y silencioso, porque un atacante puede reconstruir las claves sin conexión. Su consejo de prueba es confirmar que toda la generación de claves utiliza el generador de números aleatorios criptográficamente seguro de la plataforma.

Siguen tres reglas prácticas.

Nunca implemente su propia generación de claves. Utilice una biblioteca verificada o un proveedor cuyo trabajo sea hacerlo. Una semilla Math.random() es un desastre esperando a suceder.

Mantenga las claves de firma en almacenamiento no exportable. La guía de carteras de NIST apunta a módulos protegidos por hardware que impiden que un procesador host extraiga claves secretas. Para cualquier cosa que usted ejecute por su cuenta, eso significa un HSM o un elemento seguro similar, no variables de entorno ni una columna de base de datos. Si desea comprender cómo funciona la protección de claves respaldada por hardware en la práctica, esta guía sobre la protección de una clave raíz con un HSM (en portugués) explica los principios utilizando claves de autoridad de certificación como ejemplo. La misma lógica se aplica a las claves de firma de carteras.

Proteja el factor humano del acceso. Las llaves de seguridad de hardware para las cuentas de administrador que pueden crear claves API, cambiar URLs de webhook o aprobar pagos eliminan una gran clase de riesgo de phishing. Separe los roles, de modo que la persona que despliega el código no pueda también liberar fondos.

Detección de pagos con webhooks

Crear la dirección es la mitad del trabajo. También necesita saber cuándo alguien la paga. Consultar cada dirección según un calendario desperdicia solicitudes y retrasa la confirmación. Los webhooks envían el evento a usted en el momento en que el proveedor lo detecta. Recorremos un flujo completo en cómo procesar depósitos automáticamente con webhooks.

El endpoint receptor es donde ocurren los errores de seguridad, así que constrúyalo con cuidado. La Hoja de trucos de seguridad de webhooks de OWASP es la referencia a seguir, y sus puntos principales son estos:

  • Verifique la firma en cada entrega. Recálcule el HMAC sobre el cuerpo sin procesar con su secreto compartido y compárelo con la cabecera de firma. Use una comparación de tiempo constante para evitar ataques de temporización.
  • Exija HTTPS. Una firma demuestra quién envió el mensaje pero no lo cifra, por lo que cualquiera en la ruta de red puede leer una entrega HTTP sin cifrar.
  • Mantenga los secretos fuera de la URL. Las URLs terminan en registros de balanceadores de carga y proxies que usted puede no controlar. Coloque la autenticación en las cabeceras.
  • Trate los eventos como idempotentes. Las entregas pueden repetirse tras reintentos de red. Un único pago nunca debe acreditarse dos veces.

Ese último punto merece un patrón concreto. Almacene el hash de la transacción como clave única e indexada. El consejo de conciliación de la guía de Bitcoin, que se adapta a cualquier cadena, es verificar su base de datos en busca de un hash existente antes de ejecutar cualquier lógica de acreditación, en lugar de confiar en que cada devolución de llamada llegue exactamente una vez. En SQL, eso es una restricción única en el hash y una inserción que ignora duplicados.

Un gestor fiable sigue este orden:

  1. Lea el cuerpo de la solicitud sin procesar antes de cualquier análisis.
  2. Verifique la firma HMAC. Rechace si no coincide.
  3. Inserte el hash de la transacción. Si ya existe, devuelva éxito y deténgase.
  4. Espere el número de confirmaciones que requiera su política de riesgo antes de acreditar los fondos.
  5. Acredite la cuenta en la misma transacción de base de datos que la inserción.
  6. Responda rápidamente con un código de éxito y envíe el trabajo lento a una cola.

Realidades multi-cadena con las que se encontrará

Una cartera que funciona en una cadena es fácil. Una cartera que funciona en varias es donde crece el coste de integración, porque cada red tiene su propio formato de dirección, modelo de comisiones y estándares de tokens.

  • Comisiones. En las cadenas EVM, una transferencia de token necesita la moneda nativa para el gas. Una dirección recién creada que recibe USDT no puede enviarlo hasta que también tenga algo de ETH, BNB o el equivalente en MATIC para las comisiones. Planifique un paso de financiación para pagos y barridos.
  • Activación de cuenta en Tron. Las direcciones de Tron se comportan de forma diferente: una cuenta no activada puede no aparecer en la cadena hasta que reciba una pequeña cantidad de TRX, y las transferencias TRC-20 consumen recursos, así que pruebe esta ruta pronto.
  • Estándares de tokens. ERC-20, BEP-20 y TRC-20 parecen iguales para los usuarios, pero difieren en las llamadas a contratos y formatos de eventos. Los NFTs añaden ERC-721 encima.
  • Datos decodificados. Los registros de transacciones sin procesar son hexadecimales. Si su proveedor devuelve valores decodificados, se ahorra escribir análisis de ABI para cada token.

Nuestra perspectiva

Vemos el mismo patrón con la mayoría de los equipos que vienen a nosotros. Subestiman la fontanería y sobreestiman la criptografía. Generar una clave es un problema resuelto. Lo que hunde los proyectos es un mes gastado en sincronización de nodos, las rarezas de comisiones de una cadena, un gestor de webhook que acredita un depósito dos veces, o un importe decodificado que está mal por un factor de diez debido a los decimales del token.

Por eso creamos Chaingateway como una única API REST para varias redes, en lugar de una integración por cadena. Usted crea carteras, envía transferencias de tokens, estima el gas automáticamente y recibe datos de transacciones predecodificados con la misma estructura, independientemente de la red que utilice. Las peticiones se firman con HMAC, y las notificaciones por webhook informan a su backend sobre los pagos en tiempo real, por lo que no necesita ejecutar sus propios nodos ni hacer sondeos.

Nuestro consejo es sencillo. Decida la custodia primero. Asigne a cada pagador su propia dirección. Haga que su gestor de webhooks sea idempotente desde el primer día, no después del primer abono duplicado. Y pruebe todo el bucle en una testnet antes de que se mueva una sola moneda real.

Lista de comprobación para el lanzamiento

Antes de pasar a producción, confirme cada punto:

  • Las credenciales de la API residen en un gestor de secretos y pueden rotarse.
  • Cada dirección se almacena con su red, propietario y hora de creación.
  • Su endpoint de webhook usa HTTPS, verifica las firmas y las compara en tiempo constante.
  • Una restricción única sobre el hash de la transacción evita los abonos dobles.
  • Espera un umbral de confirmaciones adecuado al importe en riesgo.
  • Las carteras de pagos están financiadas con la moneda nativa necesaria para las comisiones.
  • Las cuentas de administrador usan autenticación multifactor fuerte, idealmente claves de hardware.
  • Ha dejado por escrito quién puede aprobar pagos y cómo se revoca una clave filtrada.
  • Ha buscado asesoramiento legal sobre custodia cuando guarda fondos de terceros.

Preguntas frecuentes

¿Puedo crear una cartera de criptomonedas con una API sin ejecutar un nodo?

Sí. Una API de cartera alojada ejecuta los nodos y la infraestructura de firma por usted y devuelve direcciones mediante llamadas REST. Usted sigue necesitando proteger sus propias credenciales de API y su endpoint de webhook, porque ahora son las puertas de acceso a sus fondos.

¿Es una cartera creada por API custodial?

Normalmente lo es, en el sentido de que el servicio guarda las claves y sus credenciales autorizan las acciones. Si eso le convierte en custodio en sentido legal depende de si guarda fondos de sus clientes y de su jurisdicción. Consulte a un abogado especializado en regulación de activos virtuales antes de lanzar al público.

¿Cómo sé cuándo ha llegado un depósito?

Suscríbase a las notificaciones por webhook para la dirección. Verifique la firma HMAC, registre el hash de la transacción en una columna con índice único y abone la cuenta solo cuando se cumpla su requisito de confirmaciones. Como las entregas pueden repetirse, la comprobación del hash es lo que le evita pagar dos veces.

¿Debo generar una dirección por usuario o por pago?

Por pago ofrece la conciliación más limpia, ya que cada dirección se corresponde con un pedido. Por usuario es más sencillo para recargas de saldo. Evite compartir una dirección entre muchos pagadores a menos que la red admita un memo o etiqueta y usted lo gestione correctamente.

¿Dónde deben almacenarse las claves privadas en producción?

En almacenamiento no exportable, como un HSM o un elemento seguro, o con un proveedor que gestione ese almacenamiento por usted. Las variables de entorno, los archivos de configuración y las filas ordinarias de base de datos no son adecuadas para claves que controlan fondos reales.
