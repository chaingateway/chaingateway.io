如何搭建以太坊节点（2026 指南）

搭建以太坊节点：硬件要求，使用 systemd 的 Geth 与 Lighthouse 可复制粘贴配置，同步模式，运行成本，以及何时使用 API 更合适。文中还包括端口安全、监控和升级的做法，并说明初始同步需要多长时间。

章节
C
Chaingateway Team
区块链专家

审核： Maurice Sobiera

以太坊节点是一台计算机，它运行一个执行客户端和一个共识客户端，保存一份经过验证的区块链副本，并提供用于读取链上数据和发送交易的 JSON-RPC。根据 ethereum.org，全节点至少需要 16 GB 内存和 2 TB NVMe SSD。本指南使用 Geth 和 Lighthouse 搭建节点。

运行自有节点可以获得不受服务商速率限制的 JSON-RPC 端点，也不会有第三方看到您的查询。本指南从一台空白的 Ubuntu 服务器讲起，直到得到一个已同步的节点，全部提供可复制粘贴的命令，两个客户端均由 systemd 管理。文中还涵盖硬件、同步模式、运行成本，以及何时改用 API 更好。

什么是以太坊节点？

以太坊节点是一台运行以太坊客户端软件的计算机。它保存一份区块链副本，依照协议规则检查每一个新区块，并为钱包和应用程序提供 JSON-RPC 请求服务。以太坊开发者文档把这类软件称为客户端，并说明了两个层各自的作用。

自 2022 年 9 月合并（Merge）以来，节点由两个并行运行的程序组成。执行客户端（Geth、Nethermind、Besu、Erigon 或 Reth）保存状态、执行交易，并响应 JSON-RPC 调用。共识客户端（Lighthouse、Prysm、Teku、Nimbus 或 Lodestar）负责权益证明。它跟随信标链，并告诉执行客户端当前的链头区块是哪一个。

两个客户端通过一个经过认证的本地端口（8551）通信，并使用共享的 JWT 密钥相互识别。只有其中一个并不能构成可用的节点。大多数首次运行节点的人都会在这一细节上出错。

存在三种存储模式。

  • 全节点保存最近的状态，并修剪旧数据。
  • 归档节点保存每一个历史状态。ethereum.org 的表格列出 Geth、Nethermind 和 Besu 需要 12 TB 或更多，Reth 和 Erigon 约需 2.2 至 2.5 TB。
  • 轻节点只下载区块头。Geth 文档指出，自转向权益证明以来，轻同步目前已无法工作，因此它不是一条实用的访问途径。

以太坊节点有哪些要求？

全节点至少需要 16 GB 内存和 2 TB NVMe SSD。这些数字来自 ethereum.org 节点指南，其中的推荐列还引用了 EIP-7870 的硬件指引。归档节点是另一个独立的项目，而验证者比普通全节点需要更多的 CPU、内存和上传带宽。

组件最低要求推荐（EIP-7870）
CPU2 核以上4 核以上（若参与验证则 8 核以上）
内存16 GB（为稳定起见建议 32 GB）32 GB（若参与验证则 64 GB）
存储2 TB NVMe SSD4 TB NVMe SSD，不用无 DRAM 或 QLC 硬盘
网络25 Mbit/s 以上下行 50 Mbit/s，上行 15 Mbit/s 以上（若参与验证则上行 25 Mbit/s 以上）

有两行需要解释。

存储必须是 NVMe。同步时会以高频率写入许多小的随机数据块。Geth 文档警告，机械硬盘和较便宜的 SSD 可能难以完成同步。默认 IOPS 的云存储卷通常也属于这一类。ethereum.org 补充说，2 TB 很可能会在 2027 年前被超出，因此请为增长做好规划。

磁盘空间是瓶颈。ethereum.org 的表格显示，快照同步的 Geth 或 Nethermind 数据库需要 500 GB 或更多，Besu 则需要 800 GB 或更多。共识客户端还需要约 200 GB 用于信标数据。Geth 文档指出，截至 2022 年 9 月，在默认缓存大小下，数据库每周增长约 14 GB。在首次同步完成后，请检查您自己的数据目录大小，而不要依赖已公布的数字。

流量也很重要。ethereum.org 建议使用不限流量的网络连接，因为初始同步以及节点广播的数据可能超过流量上限。Linux、macOS 和 Windows 均可使用。下面的每条命令都假设使用 Ubuntu 24.04，这是常见的服务器默认系统。

运行节点的方式

您不必亲手组装所有东西。DappNode 和 Avado 等即插即用设备是预先配置好的机器，附带仪表板：购买、连接，然后按照向导操作即可。ARM 开发板同样可用。Ethereum on ARM 为树莓派和其他 ARM 开发板提供多种执行和共识客户端的镜像。启动器可以自动完成手动流程：eth-docker（基于 Docker，需要一定的终端知识）、Stereum（通过 SSH 在远程服务器上安装客户端，带有图形界面）、NiceNode（选择客户端，几次点击即可启动）以及 Sedge（Nethermind 推出的命令行向导，可生成 Docker 配置）。

使用云服务还是本地设备？VPS 适合开发用途。ethereum.org 指出，很大一部分节点已经运行在云服务商上，这对网络而言是单点故障。如果抗审查是您的动机之一，请在您自己拥有的硬件上运行。

本指南其余部分介绍手动搭建。它能让您学到最多，您所学的一切也都可以套用到各类启动器上。

同步需要多长时间？

使用检查点同步的 Lighthouse 从最近的已最终确定状态开始，并在后台补齐历史区块。快照同步模式（默认）的 Geth 从对等节点下载当前状态，并在本地重建状态树。耗时主要取决于您的磁盘和带宽，Geth 日志会为状态下载打印预计剩余时间。最后阶段是“状态修复”，无法准确监控，因为在状态重新生成之前，错误的范围是未知的。如果它运行了数天仍未完成，说明您的磁盘太慢。请参阅故障排除。

初始同步完成后，情况会趋于平稳。根据 Geth 1.14.0 发布说明，Geth 1.14.0 将默认状态方案从 hash 改为 path。较早的指南会警告数据库会不断增长，直到您离线修剪它，这适用于旧的基于哈希的布局。根据 v1.17.1 发布说明，Geth 1.17 还可以使用 --history.chain postmerge 删除合并前的历史，如果磁盘空间紧张，这能释放空间。

应选择哪种同步模式？

Geth 单元中的 --syncmode 参数决定了您自己验证多少链数据，以及为此付出多少磁盘空间。存在三种模式，合适的选择取决于您希望节点回答哪些问题。

快照同步是默认模式，也是本指南所用的模式。根据 Geth 同步模式文档，Geth 从最近的区块开始，从对等节点下载状态，然后修复状态树。与从创世区块逐块同步相比，它能更快得到一个可提供服务的全节点。

全量同步（--syncmode full）从创世区块开始重新执行每一个区块，而不是下载状态。最终磁盘上的数据库相同，都是修剪后的版本，但同步时间远长于快照同步。选择它只有一个理由：您不信任状态下载，并希望在自己的机器上重新计算完整的历史。这是一种研究立场，而不是运营上的要求。

归档模式处于另一个维度：在全量同步的基础上加上 --gcmode archive，保留每一个中间状态，而不是修剪。只有归档节点能回答“区块 15,000,000 时的余额是多少”，或者无需重新计算即可运行深度追踪。索引器、税务工具和分析平台都需要这种能力。根据 ethereum.org 的表格，完整归档节点在 Geth、Nethermind 和 Besu 上需要 12 TB 或更多，Erigon 和 Reth 以不同方式存储历史，列出的数值分别约为 2.5 TB 和 2.2 TB。Geth v1.16.0 新增了一种实验性的基于路径的归档模式。根据发布说明，主网的完整状态历史在该模式下约需 1.9 TB（不含交易和日志索引），并且默认只保留最近 90,000 个区块的历史。

模式磁盘（ethereum.org 估算）初始同步历史状态查询
快照（默认）Geth 上 500 GB 或更多在 Geth 各模式中最快仅最近 128 个区块
全量相同的修剪后大小远慢于快照同步仅最近 128 个区块
Geth（基于哈希）、Nethermind、Besu 的归档模式12 TB 或更多最慢支持
Erigon 或 Reth 的归档模式2.2 至 2.5 TB 或更多未说明支持

对于支付后端，快照同步可以满足所有需求：当前余额、新区块和交易收据。归档模式则适用于您需要重建过去数据的时候。

应运行哪些客户端？

Geth 加 Lighthouse 是一个可靠的默认选择，而它的普及程度恰恰是问题所在。ethereum.org 关于客户端多样性的页面解释了这一风险。如果某个占节点数超过 33% 的共识客户端出现漏洞，共识层可能无法完成最终确定。占据三分之二多数的客户端若出现严重漏洞，可能导致链分叉并错误地完成最终确定，而身处错误链上的验证者将面临罚没。

请查看 clientdiversity.org 以了解当前的客户端占比，而不是相信某本指南中的数字。分布会不断变化，ethereum.org 表示，理想情况下没有任何一个客户端应超过 33%。每当一位运营者选择少数派客户端，网络就会更安全一些。运营者几乎没有什么损失，因为所有执行客户端都使用相同的 JSON-RPC，所有共识客户端都使用相同的信标 API。

客户端层语言
Geth执行层Go
Nethermind执行层C#
Besu执行层Java
Reth执行层Rust
Erigon执行层Go
Lighthouse共识层Rust
Prysm共识层Go
Teku共识层Java
Nimbus共识层Nim

对于第一个节点，本指南中的组合没有问题。对于第二个节点，或任何专业用途，请选择少数派的组合，例如 Nethermind 搭配 Teku，或 Reth 搭配 Nimbus。上述配置几乎可以一对一地套用。每种组合都需要相同的 JWT 密钥和引擎 API 配置。变化的只是二进制文件、参数和数据目录。

运行以太坊节点需要多少成本？

成本取决于您使用自有硬件还是租用服务器，因此本节给出的是计算方法，而不是价格。价格每月都在变化，且因国家而异。

自有硬件：符合要求等级（4 至 8 核、32 GB 内存、2 至 4 TB NVMe）的机器是一次性购买。持续成本是电费。将机器的平均功耗（千瓦）乘以 720 小时，再乘以每千瓦时的电价。一台功耗为 50 W 的机器，每月耗电为 0.05 kW × 720 h = 36 kWh，再乘以您的电价即可。另外加上您已经在支付的网络连接费用。

租用服务器：2 TB NVMe 超出了许多 VPS 套餐的提供范围，因此您可能需要独立服务器。ethereum.org 指出，由于所需存储容量较大，租用服务器的价格可能会很高。带有预配 IOPS 的云实例，通常比同等的独立服务器更贵，因此请针对相同的磁盘容量比较报价。

您的时间：借助本指南，首次搭建需要一个下午。之后您只需偶尔更新客户端并查看日志。如果您对自己的时间计费，请把这一项加入总成本。

监控与健康检查

三个问题即可覆盖节点的健康状况：进程是否在运行，是否已同步，是否有对等节点。systemd 可通过 systemctl is-active geth lighthouse 回答第一个问题。另外两个问题可通过两个层的端点获取：

Lighthouse 的 REST API 通过单元中已有的 --http 参数监听 5052 端口。/eth/v1/node/health 端点把同步状态编码在 HTTP 状态码中，因此很适合作为脚本和负载均衡器的探针；如果您想要具体数字，/eth/v1/node/syncing 会返回与链头相差的时隙数。一个定时任务运行这些检查，再加上 df -h /var/lib/geth，并在出现异常时发送邮件，对于个人节点而言就是完整的监控。

如需仪表板，请为 Geth 添加 --metrics（Prometheus 端点位于 6060 端口），为 Lighthouse 添加 --metrics（位于 5054 端口），两者都只绑定在 localhost 上，并导入两个项目发布的 Grafana 仪表板。无论您搭建什么，都应优先设置两个告警：磁盘使用率超过 85%，以及区块高度在十分钟内停滞不前。这两项几乎能在用户察觉之前捕获所有真实故障。

维护与升级

客户端更新不是可选的。硬分叉需要新版本的软件，运行旧版本的节点会在分叉区块处停止跟随链。请订阅 GitHub 上 Geth 和 Lighthouse 的发布动态，以及以太坊基金会博客。

操作步骤很简单。通过 PPA 安装的 Geth 使用 sudo apt upgrade 更新，再执行 sudo systemctl restart geth；用 geth version 确认。Lighthouse 是单个二进制文件：重复第 3 步的下载，替换 /usr/local/bin/lighthouse，然后重启单元。在重启之前请先阅读发布说明，因为参数偶尔会被重命名，而 systemd 单元中一个被重命名的参数，意味着服务会在凌晨两点拒绝启动。

还要为磁盘增长做好预算。Geth 文档给出的默认缓存大小下的增长量约为每周 14 GB，这是 2022 年 9 月的数字。请用 du 在几周内测量您自己的增长。在 2 TB 硬盘上，您可以通过修剪合并前的历史（参见故障排除）或重新同步来释放空间。在 4 TB 硬盘上，增长会成为每年的一项预算，而不是每季度的问题。节点不必每秒都在线，但离线时间越长，追赶所需的时间就越长。

全节点不等于验证者

人人都听说过的 32 ETH 属于质押，而不属于运行节点。本指南中的节点完全不需要 ETH。它所做的验证，是检查区块，这消耗的是硬件，而非质押资金。

验证者是与两个客户端并列的第三个程序：它持有签名密钥，生成证明和区块，并因此获得奖励，同时配置一个用于接收收益的手续费接收地址。32 ETH 是协议可因可证明的不当行为而罚没的抵押品。运维的门槛也随之提高：一个 RPC 节点在周末离线，周一补齐即可；而验证者离线，则会在每个纪元被扣除少量罚金。

如果 ETH 不足 32 个，质押池协议就是入门途径。普通全节点本身不产生收益。您运行它是为了独立性和隐私、用于开发，或者作为将来成为验证者的基础。

安全：端口布局即策略

这套配置的全部安全模型，都体现在第 1 步的防火墙规则中。开放 30303 以及 9000/9001，是因为点对点网络需要陌生节点的连接；8545 和 8551 绑定到 127.0.0.1，是因为机器之外的任何东西都无需访问它们。JWT 密钥用于认证 8551 上的引擎 API，但应把它视为第二道防线，而不是暴露该端口的理由。

对外暴露 8545 是更严重的错误，因为 JSON-RPC 服务没有任何身份认证。Geth 安全文档建议运营者阻止除明确信任的机器之外的所有 RPC 端口流量。它警告，暴露的命名空间会增加虚假签名请求的风险。请将 --http.api 保持在单元中的四个命名空间。对于 RPC 端口可能被访问的任何机器，请关闭 admin、debug 和 personal。

当其他机器确实需要访问 RPC 时，应使用隧道而不是直接暴露：自己使用 WireGuard 或 SSH 隧道；小型团队则可使用带 TLS 和 IP 白名单的 nginx 或 Caddy。从第 1 步起，客户端已以无登录权限的系统用户运行，因此被攻破的客户端进程没有可继承的 shell 账户。再加上 unattended-upgrades 用于系统补丁，服务器安全中枯燥的部分就能自行运转。

故障排除

Lighthouse 无法连接 Geth（“Unable to connect to execution endpoint”）

要么 Geth 没有运行（systemctl status geth），要么两边的 JWT 密钥不一致。请确认两个单元指向同一个 jwt.hex 路径。如有疑问，请重新生成一次密钥，并重启两个服务。

Geth 在“State heal in progress”中停滞数日

状态修复阶段要追赶链头，而随机写入性能弱的磁盘永远追赶不上。请用 fio 对随机 4k 读写进行基准测试，并与 Geth 文档链接的硬盘列表进行比较。SATA SSD 和默认云存储卷是常见的罪魁祸首。解决办法是真正的 NVMe 存储，没有任何参数能拯救一块慢速磁盘。

对等节点数始终为零

端口 30303（TCP 和 UDP）被阻止，或未在 NAT 上转发。另请检查系统时钟：timedatectl 应显示 NTP 同步已启用，因为时钟偏移会破坏共识层的对等节点握手。

磁盘写满

先找出增长的来源：du -h --max-depth=2 /var/lib/geth。在 Geth 1.14.0 之前创建的数据目录会保留旧的基于哈希的布局，因为新的默认值只适用于全新的数据库。最彻底的解决办法是重新同步，之后状态会自动保持修剪。删除合并前的历史（--history.chain postmerge，Geth 1.17）可以释放更多空间，而历史数据存储（ancient store）还可以通过 --datadir.ancient 迁移到更便宜的硬盘上。

崩溃后 Geth 报告数据库损坏

断电、kill -9 或内存不足（OOM）杀死进程，都可能在写入中途留下损坏或数据缺失的日志行，并在下次启动时出现。有时重启即可修复；如果日志反复出现，请停止修复，改为重新同步：将数据目录移到一旁，从头开始，让快照同步重建一切。这通常比任何恢复尝试都快。预防措施已在单元中设置：TimeoutStopSec=600 给了 Geth 充足的刷写时间，而干净的 systemctl stop 是进程唯一应该结束的方式。

内存不足杀手终止了 Geth

journalctl -k | grep -i oom 可以证实这一怀疑。自 v1.17.2 起，Geth 的 --cache 默认为 4 GB，而实际占用在同步期间可能超过该设置。再加上 Lighthouse 和操作系统，16 GB 的机器可能会耗尽内存。在小型机器上将 --cache 设为 2048，并保留一个交换文件作为缓冲。慢比被杀死要好，因为被杀死的 Geth 不会刷写任何数据，并会引发上面所述的损坏问题。

常见问题

简单来说，以太坊节点是什么？

一台计算机，保存着它自己经过验证的以太坊区块链副本，让您无需任何人许可即可读取链上数据并发送交易。从技术上讲，它是两个协同工作的程序：执行客户端和共识客户端。

2026 年运行以太坊节点需要多少磁盘空间？

ethereum.org 将 2 TB NVMe SSD 列为全节点的最低要求，将 EIP-7870 中的 4 TB 列为推荐配置。快照同步的 Geth 数据库需要几百 GB 或更多，另外共识客户端的信标数据约需 200 GB，并且数据会随时间增长。

我可以在树莓派上运行以太坊节点吗？

如果开发板满足要求，可以。ethereum.org 指出，客户端可以在单板计算机上运行，而 Ethereum on ARM 为树莓派和其他 ARM 开发板提供镜像。您仍然需要 16 GB 内存和一块高速 NVMe 硬盘。预计初始同步会较慢，并且在承受繁重的 RPC 负载时余量很小。

运行以太坊节点能赚钱吗？

不能。奖励归验证者所有，成为验证者除了运行节点之外，还需要质押 32 ETH，或参与质押池。普通的全节点有助于网络健康，并为您提供无需信任的访问方式，但不产生收益。

我需要在路由器上开放端口吗？

为了获得健康的对等节点数量，请为 Geth 转发 30303，为 Lighthouse 转发 9000/9001。没有这些端口，节点仍能同步，只是速度更慢。切勿将 8545 或 8551 暴露到互联网上。

应该自己运行节点，还是使用 API？

这取决于工作负载。Chaingateway 提供的是 API 这一替代方案，因此本比较会说明双方各自适用的场景。

当您需要大量、持续的原始 JSON-RPC 时，节点更有优势：归档查询、追踪、内存池监控，或最高程度的隐私和抗审查能力。节点的成本是固定的，且没有请求计量，因此一旦您的用量足够高，它就会比按量计费的 RPC 服务更便宜。请使用上面的成本计算方法，结合您自己的价格，找到这个临界点。搭建节点也是学习以太坊工作原理的好方法。

当节点只是达成目的的手段时，API 更有优势。对大多数企业而言，这通常意味着付款。同步好的节点可以提供 eth_sendRawTransaction 和事件日志，但它不提供每位客户的充值地址、ERC-20 付款到账时的通知、密钥管理或重试逻辑。这些都是您必须在节点之上自行构建和运营的应用软件。

Chaingateway 的以太坊 API 正是缺失的这一层：创建并导入地址（POST /api/v2/ethereum/addresses/import），发送 ERC-20 代币（POST /api/v2/ethereum/transactions/erc20），并为入账的充值接收经 HMAC 签名的 Webhook。投递失败的通知会列在一个可查询的列表中（GET /api/v2/ethereum/webhooks/notifications/failed），并可通过重试端点重新发送。盈亏平衡点是一道算术题：服务器成本加上您搭建和运营所花的时间，与价格页面上的套餐进行比较。对于付款流程，请计算构建充值检测和密钥处理所需的工时。对于原始 RPC 的使用，节点一方更有优势。可以从快速入门和 Webhook 指南开始。
