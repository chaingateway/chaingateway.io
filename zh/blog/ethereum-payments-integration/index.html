以太坊支付集成：开发者指南

如何集成以太坊支付：选择 ETH 或代币、创建支付请求、检测并确认交易、处理 Gas、保护密钥以及测试。

集成以太坊支付意味着要可靠地完成四件事：为每位客户提供唯一的付款地址、检测交易到账、决定何时视为最终确认，以及将其与订单进行对账。你可以在节点和 JSON-RPC 之上自行构建，也可以调用统一 API 来处理钱包、Gas 和通知。本指南涵盖这两条路径，助你睁大眼睛做选择。

TL;DR

  • 以太坊支付是一笔移动 ETH 或代币的已签名交易。提交交易不等于确认交易：你必须检查收据。
  • 先决定：仅接受 ETH、稳定币和 ERC-20 代币，还是你自己的代币。该选择决定了你的事件处理和 Gas 策略。
  • 每个订单或用户使用一个专用充值地址，并通过 Webhook 监听事件，而非轮询。
  • 将私钥、Webhook 签名和合约代码视为三大主要安全攻击面。
  • 统一 API（如 Chaingateway）可替代节点、Gas 和解码工作，套餐价格从每月 €49 起。

以太坊支付的本质是什么

以太坊支付是账户发出的一条加密签名指令，用于更新网络状态，例如转移 ETH 或代币。根据 ethereum.org 的交易文档，验证者会检查交易并将其打包进区块。只有在此之后，资金才真正存在于接收方地址。

对你的应用而言，这有一个实际后果：客户并非直接支付给你。他们向网络广播一笔交易，你的系统必须察觉到它。集成中的一切，本质上都是围绕这一观察问题的变体。

你将遇到两类支付：

  1. 原生 ETH 转账。 交易本身携带接收方和金额。简单直接，可在交易及其收据中直接看到。
  2. 代币转账（ERC-20 等）。 交易发往代币合约，由合约在内部更新余额。标准为此定义了 Transfer 事件，详见 ethereum.org 上的 ERC-20 规范。你的系统通过该事件日志得知支付，而非交易自带的 value 字段。

大多数稳定币结算属于第二类。如果你只监控地址收到的 ETH，就会漏掉它们。

编写代码前必须做的决策

将接受哪些资产？

从最能满足客户需求的最小资产集合开始。仅支持 ETH 是最容易实现的。增加一种稳定币可将价格波动排除在外，这对发票和订阅制业务至关重要。如果您发行自己的代币，还需了解其精度、合约地址，以及它是否表现得像标准 ERC-20 代币。

每增加一种资产，就要多监控一个合约地址、多应用一个精度值、多制定一条定价规则。维护一个小型允许名单，并有意拒绝名单之外的任何资产。

托管结账、支付链接还是 API？

有三种集成形态，它们在控制权与速度之间做权衡：

方式适用场景您控制的内容您放弃的内容
托管结账或支付链接快速上线、低交易量对流程几乎无控制权品牌化、托管、自定义逻辑
自有前端中的钱包连接用户已持有 ETH 的 Dapp用户体验检测与对账仍由您负责
带钱包和 Webhook 的后端 API应用、市场、SaaS 计费地址、金额、订单逻辑运营自有基础设施

如果您是将支付功能集成到产品中的开发者，通常最终会选择第三行。评估服务商时的实用清单：是否提供沙箱环境、清晰的错误格式、文档化的速率限制，以及适配您技术栈的 Webhook？

托管与合规

谁掌握私钥？如果您的平台为客户生成充值钱包，即意味着您在处理资金，根据您的司法管辖区和商业模式，这可能带来牌照或报告义务。请在上线前咨询熟悉您目标市场的律师，而非上线后。本指南侧重工程实现，不构成法律建议。

核心支付流程，分步详解

以下是经得起生产环境考验的流程序列，无论您是自建还是采购方案均适用。

1. 创建支付请求

当客户进入结账页时，创建一条包含金额、资产和过期时间的订单记录。随后为该订单分配一个唯一的接收地址。为每笔订单使用唯一地址，可让您在无需客户粘贴备注或参考号的情况下，将链上转账与正确的客户匹配。

以稳定计价单位为订单定价；若接受波动性资产，则在短时间窗口内锁定 ETH 金额，并将两个数值均存储下来。

2. 客户签名并提交

若客户通过浏览器钱包支付，您的前端会请求使用其账户的权限、构建交易对象并提交。MetaMask 的 eth_sendTransaction 参考文档描述了这一顺序：获取账户授权、提交交易、保存返回的哈希值。若客户改从交易所或移动钱包向您展示的地址发送资金，您将完全看不到这一步，只能在链上看到结果。

无论哪种方式，交易哈希都是支付的凭证编号。请妥善存储。

3. 检测交易

您有三种方式来感知支付：

  • 轮询。 每隔几秒向节点请求一次收据或地址余额。简单，但浪费资源，且难以大规模应用。
  • 订阅。 向节点打开 WebSocket 并订阅新区块或合约日志。go-ethereum 关于实时事件的文档 介绍了专门用于此目的的 eth_subscribe。您必须自行处理连接断开和重放错过的区块。
  • Webhook。 服务监控链上活动，当发生相关事件时调用您的服务器。这是维护成本最低的选项，也是大多数团队的选择。

对于代币，您监控的是事件日志。以太坊文档指出，应用程序可以通过 JSON-RPC API 监听合约事件 并对其发出的日志采取行动。

4. 确认结果

提交不等于确认。MetaMask 发送交易指南 展示了该模式：通过哈希轮询收据；无收据意味着交易仍在待处理，状态 0x1 表示成功，0x0 表示失败。eth_getTransactionReceipt 参考文档 补充说明收据包含区块号、已用 Gas 和日志。

您的订单状态机应明确反映这一点：

  1. awaiting_payment（等待付款）：地址已生成，未检测到任何交易。
  2. pending（待处理）：检测到匹配交易，但尚未打包入块。
  3. confirmed（已确认）：找到收据，状态成功，金额和资产匹配。
  4. final（最终确认）：已过足够多的额外区块，满足您的风险容忍度。
  5. failed（失败）、underpaid（付款不足）、overpaid（付款过多）或 expired（过期）：需要制定规则处理的情况，而非置之不理。

等待多少个区块后再发货是业务决策。几美元以下的数字商品可在首次确认后发货。高价值订单应等待更久，因为区块偶尔会在网络最终确定前发生重组。

5. 对账

每天将数据库中已确认付款的总和与链上显示到达您地址的金额进行比对。任何差异都是 Bug、遗漏的 Webhook 或客户支付了错误的资产。数据工具在此处能提供帮助：ethereum.org 的数据与分析板块 列出了提供历史事件日志和可查询实时数据的索引器，可减少您自行维护的工作量。

Gas、失败交易与退款

Gas 是许多初次集成时容易踩坑的地方。正如交易文档 所述，每笔交易都需支付由基础费用和优先费用组成的手续费，由发送方承担。这对您有三个后果。

客户可能付费不足或导致交易停滞。 如果他们设置的费用过低，交易将一直处于待处理状态。只要有效交易在进行中，您的订单就不应过期。

失败的交易仍会消耗 Gas。 代币转账回滚会生成状态为失败的收据，客户的资金不会转移。仅因看到了哈希就将订单标记为已付款是错误的。

从您这边发送需要成本。 退款、从充值地址归集到金库钱包以及付款都需要 Gas，代币地址移动代币也需要 ETH。发送前先估算费用，并为其预留预算。我们的指南 如何在以太坊和其他链上估算 Gas 费用 详细介绍了估算方法。

如果您希望客户无需持有 ETH 即可付款，账户抽象允许开发者赞助交易，详见 ethereum.org 关于赞助 Gas 费用的教程。这会增加合约复杂度，因此仅建议用于 Gas 摩擦真正导致转化率下降的产品。

对于退款，请提前制定政策。仅在确认发送地址并非您无法控制的交易所充值地址后，才退回至该地址，或者要求客户提供退款地址。公开扣除网络费，或由您承担，但务必将规则书面化。

保护密钥、签名和合约

私钥

谁持有密钥，谁就控制资金。在加固环境中生成密钥，绝不记录日志，绝不提交代码库，并将热钱包（小额余额，用于付款）与冷存储（大部分资金）隔离。按计划将充值地址归集到冷存储端。

Webhook 真实性验证

Webhook 端点是一个公开 URL，可将订单标记为已支付。任何发现它的人都可以发布伪造事件。在每个请求上验证签名（HMAC 签名是常用方法），拒绝过期时间戳，并使处理程序幂等，以免重复投递导致订单被重复记账。然后，在发货前，可选择通过直接查询再次确认交易。

智能合约代码

如果您编写自己的支付合约，风险就转移到了代码上。以太坊官方安全报告指出，审计、经过测试的库、形式化验证和静态分析 都能提升合约安全性，而用于高级控制的自定义代码可能增加漏洞风险。实用原则：当普通地址和标准代币事件足以满足您的用例时，请勿部署自定义合约。

关于应用层面审计的深入了解，Web 应用审计服务包含哪些内容 这篇指南提供了很好的检查清单，说明应要求哪些内容。

自建还是用 API？

自建路径意味着运行或租用节点、编写地址生成器、为接受的每种代币构建日志解码器、估算 Gas、处理重组，并维持所有这些持续运行。对于产品就是支付基础设施的团队，这是一条合理的路径。

对于其他所有人，成本是时间和持续维护。架构问题与企业连接合作伙伴时面临的相同：实时推送事件，而非事后批量对账，这种权衡在 实时 B2B 数据的 API 一文中有很好的阐述。支付只是将同一逻辑应用于更小的规模。

如果您想在决定前先了解选项概览，我们的区块链 API 类型对比及适用场景列出了各类别，而以太坊概览则为初接触该链的团队讲解了 ETH、Gas 与 ERC-20 代币。

我们的视角

在几乎每一次集成沟通中，我们都看到相同的模式。团队为“快乐路径”预算：客户发送 ETH，订单标记为已支付，随后却将大部分工程时间花在周边事务上：解码代币日志、估算 Gas、重试遗漏的通知、保障钱包安全。

这就是 Chaingateway 设计为跨链单一 REST API、而非一组链特定端点的原因。您只需一次调用即可创建钱包，一次调用即可发送 ETH 或代币，并能收到已解码的交易，无需自行解析原始日志。Gas 自动估算，请求采用 HMAC 签名，且您无需运行节点。相同的调用适用于 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Chain 和 Arbitrum，因此后续新增网络仅是配置变更，而非重写代码。

我们的建议：将工程工时投入到订单逻辑、退款策略和对账上，因为这些才是客户真正感知到的。让基础设施成为别人的工作。

上线前后的测试与监控

演示跑通不代表支付集成就完成了。请先在测试网跑一遍下列清单，再用小额真实资金再跑一遍：

  • 精确支付、少付 和 多付，针对 ETH 及每种接受的代币均需测试。
  • 订单过期后的 延迟支付，以及向同一地址的 重复支付。
  • 设置低 Gas 限制导致的 交易失败，以便看到失败收据并确认订单不会完成。
  • 重复且乱序的 Webhook，刻意重放测试。
  • 自身停机：停服十分钟、发起支付、重启服务，验证无数据丢失。
  • 前端钱包流程。QA 团队可使用 ethereum.org 的 Impersonator.xyz 页面 列出的工具，在不持有私钥的情况下对其进行回归测试。

上线后，针对三个信号配置告警：订单在 pending 状态停留时间超过阈值、数据库总额与链上总额存在差距、Webhook 投递失败。第一个信号捕获手续费问题，第二个捕获遗漏事件，第三个捕获自身故障。

常见问题

我需要运行自己的以太坊节点来接受支付吗？

不需要。节点提供直接的链上访问，但你也必须承担其维护、同步和监控工作。大多数团队使用提供商 API 或由服务监控链并在支付到账时调用 Webhook。

如何确认收到的是代币支付，而不仅仅是 ETH 支付？

监听代币合约针对你的收款地址发出的 Transfer 事件。ERC-20 标准定义了该事件，代币转账不会在交易中体现为 ETH 金额。解码 API 会直接返回发送方、接收方和金额。

应该等待多少个区块确认？

没有统一的标准数字。这取决于订单价值和你对极少见的链重组的容忍度。低价值数字商品可提前释放，高价值订单应等待更久。将阈值写入订单逻辑，避免由客服逐案决定。

谁支付 Gas 费？

由发送方支付，因此客户承担其自身支付的手续费，而你在发起退款、归集或付款时承担费用。通过账户抽象实现的赞助 Gas 可将特定流程的成本转移给你。

同一套集成能否支持其他区块链？

可以，前提是你选择的接口不绑定单一链。使用统一 API 时，后续支持 Polygon、Tron 或 Arbitrum 可复用相同的钱包、转账和 Webhook 逻辑，而非重新搭建技术栈。
