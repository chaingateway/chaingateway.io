区块链与数据库：主要区别详细解释

区块链与传统数据库的区别：写入模型、共识、延迟和每次写入的成本，并逐项说明原因。文章给出一份决策清单，并通过三个案例（纯数据库、纯链上与混合模式）说明应使用哪种技术，以及为什么。另附支付场景中的入账时点建议，适合开发者与架构师阅读。

章节
C
Chaingateway Team
区块链专家

审核： Maurice Sobiera

区块链是一份分布在众多独立节点上的账本，每个新区块都必须获得这些节点的共识。数据库是由单一运营方运行的存储系统，由该运营方决定谁可以读写。两者的区别在于信任：区块链无需可信的运营方即可工作，数据库则依赖于它。大多数应用需要的是数据库。

人们仍然把两个术语混用，或者说“区块链只是另一种数据库”。这种说法会导致架构错误，因为两种技术回答的是不同的问题。数据库回答的是如何高效地存储和查询数据。区块链回答的是互不信任的多方如何就共享数据达成一致。

本文先用一张 10 行的表格对比两者，再逐一讨论各项差异。最后介绍大多数生产系统采用的模式：数据库与区块链协同工作。

什么是区块链（以及“区块链数据库”）？

区块链是一种分布式账本：交易记录被复制到点对点网络中众多独立的节点上。每个节点都参与账本的维护。新数据加入之前，大多数节点必须先达成共识。正是这一共识步骤让篡改变得极其困难：攻击者需要压倒网络中的大多数节点，而不是入侵一台服务器。

每笔交易都会获得时间戳和在链中的位置，因此任何节点都能追溯并验证完整的历史。人们说“区块链数据库”时，指的正是这种复制与可验证性的结合。这个术语并不严谨，因为正如下文所见，区块链放弃了日常意义上定义数据库的大部分特性。

什么是传统数据库？

传统数据库采用客户端-服务器架构。客户端连接到中央服务器，由服务器的运营方决定谁可以读写。管理员在授予访问权限之前会验证用户身份，并且可以随时修改任何记录。

集中化既是弱点，也是优势。一旦中心机构被攻破，整个数据集都会失守，这正是需要备份的原因。由于一方控制一切，数据易于管理、查询快速、存储成本低。你日常使用的大多数应用都运行在 Postgres 和 MySQL 之上。

控制权

区块链与数据库最大的区别在于：谁说了算。在传统数据库中，中心机构验证并认证用户，然后授予访问权限。数据的控制权掌握在一方或一小群人手中。

区块链没有这样的机构。每个节点都参与账本的运行，节点之间无需监管管理员即可交换信息。新数据只有在节点达成共识后才会进入链上。没有人能悄悄改写一条记录，因为其他所有人都持有内容不同的副本。

架构

传统数据库采用客户端-服务器架构。该模型可从一台笔记本扩展到数据中心。所有通信都经由与中央服务器的连接进行。不存在共识步骤，因为管理员的决定就是最终结论。

区块链以点对点网络运行。节点之间直接相连，并通过共识算法协作，就下一个区块达成一致。最经典的算法是工作量证明：参与者通过消耗算力来验证交易。比特币在比特币白皮书中描述的正是这种机制，目前仍在使用。以太坊于 2022 年切换到权益证明，用经济抵押取代了算力竞争。无论哪种方式，共识步骤之所以存在，恰恰是因为不存在一个可以拍板定案的管理员。

写入模型：CRUD 与只追加

中心化数据库支持四种 CRUD 操作：创建、读取、更新、删除。由于一切都可编辑，数据处理很简单。

区块链只支持两种操作：读取和写入。交易一旦进入链上，就不会再有更新或删除。这种不可变性正是其意义所在：它防止篡改，并让每个参与者都拥有可验证的历史。但它也有另一面。写入错误数据的漏洞无法用 UPDATE 语句修复；而依法必须可删除的个人数据（GDPR 第 17 条），本就不应放在链上。

性能与每次写入的成本

传统数据库更快，差距很大。数据库写入只是一台机器上的一次磁盘操作。区块链写入则要经过签名验证、共识，并复制到每个节点之后才算生效。在公链上，这需要数秒至数分钟，而非毫秒。

写入还要付费。每笔区块链交易都需要支付手续费，以链上原生币结算，手续费用于补偿执行验证工作的节点。手续费因链和网络负载而异。在 TRON 上，一次代币转账会消耗能量（Energy）和带宽（Bandwidth），这些资源需要通过质押获取，或用 TRX 支付。在你已经拥有的硬件上进行数据库写入，几乎不产生需要单独计费的成本。如果你的负载是每秒数千次写入，仅这一点就足以决定区块链与数据库之争的结果，倾向数据库。

写入需要多久才能最终确认？

数据库提交只需毫秒级。在区块链上，写入达到最终状态所需的时间取决于该链的共识规则。下表列出了本文用作示例的两条链。

ACID 与共识最终性

数据库领域和区块链领域的人都会说“交易已经成功”，但他们指的是不同的保证。

在数据库中，这些保证即 ACID 特性。原子性：事务的所有修改要么全部生效，要么全部不生效。一致性：约束在事务前后都成立。隔离性：并发事务彼此看不到对方未完成的工作。持久性：一旦提交，即使发生崩溃，数据也会保留，因为它已写入磁盘上的预写日志。这四项保证都在提交时兑现，即你发出请求后的数毫秒内。

智能合约链在前三项上的表现出人意料地接近。合约调用是原子的：如果任何一步回滚，整个交易都会回滚。一致性由合约代码而非表结构约束来保证。隔离性是可能的最强级别：共识迫使所有交易进入同一个全局顺序，这也正是吞吐量受限的原因，因为全序无法安全地并行处理。

持久性是两种模型分道扬镳的地方。数据库写入在提交时即已持久。而区块链上新区块中的写入仍可能消失，因为竞争区块可能胜出并重组链。

取代持久性的是最终性：协议保证交易此后不会再被推翻的那一刻。在 TRON 上，这需要 19 个区块，约 57 秒。在以太坊上，需要两个周期的验证者见证，约 15 分钟。中间的区块大概率是安全的，但并非可证明安全。对支付系统而言，规则随之而来：应在最终性确认后为客户入账，而不是在首次打包时入账，否则就得自行构建回滚处理，而这类代码很难测试。

CAP 理论的位置

CAP 定理指出，遭遇网络分区的分布式系统必须在一致性与可用性之间做出选择。单节点 Postgres 完全避开了这个问题，因为它根本不存在可分区的部分，这也是单节点数据库一直易于运维的一个被低估的原因。分布式数据库会选择一方，并将其写入文档。

区块链也是分布式系统，因此同样必须做出选择。像比特币这样的最长链设计选择了可用性：分区期间两侧都会继续产生区块，待其中一个分支胜出后，一致性才会重新修复，这正是重组的含义。基于最终性的设计则偏向另一侧：如果有过多验证者不可达，以太坊将停止最终性确认，TRON 的超级代表（Super Representatives）也会停止固化区块。即以牺牲进度为代价，避免产生相互冲突的永久结论。两种选择都没有错。但这意味着“区块链”并不能摆脱分布式系统的权衡，它只是其中一组特定的权衡，代价是延迟和手续费。

各自的优势与代价

数据库的优势会不断累积。毫秒级查询和低成本写入只是表面。底层是数十年的工具积累：备份、时间点恢复、复制、迁移，以及针对查询模式调优的索引。数据默认保持私密，并可按需删除，而法规有时要求这样做。

这种舒适的代价是集中的信任。运营方可以编辑任何内容，因此审计记录的可信度只取决于运营方。两家互不信任的公司无法共用一个 Postgres 作为事实来源，因为其中一方必须托管它。

区块链的优势正是缺失的那一块。没有人单独运营它，因此也没有人能单独改写它。任何拥有节点的人都能验证历史，包括你从未接纳过的外部人员。对支付而言，它提供了一条结算通道：任何钱包都可以向任何其他钱包付款，无需中间人批准任何一方。

代价则与数据库的舒适相对应。每次写入都要计费，并受共识节奏的限制。存储只能追加，除非另行设计，否则所有数据都是公开的。运维上的安全网也消失了：没有任何客服工单能撤销一笔交易，丢失的私钥就是丢失的资产，而不是一次密码重置。

两份清单几乎没有重叠，因此无法按得分判定胜负。一个问题即可决定：你的系统是否有一个可信的运营方，还是必须在没有运营方的情况下运行？

何时使用哪种：决策清单

  • 如果由一方控制数据，且用户接受这一点，请使用数据库。它更快、更便宜，也更易于运维。
  • 如果多方需要写入共享状态，且彼此之间或与中间人都不互信，区块链的额外开销是值得的。这正是数据库无法完成的工作。
  • 如果记录必须能够向外部人员证明未被篡改（审计、公司之间的结算），区块链无需公证人即可提供这种证明。
  • 如果你需要更新和删除，或者你存储的是可能被请求删除的个人数据，请将其保存在数据库中。
  • 如果你需要低延迟或高写入吞吐量，直接选数据库，无需讨论。
  • 如果你接受或发送加密货币付款，无论你是否愿意，结算层都是区块链。明智的做法是让其他一切都保留在链下，这就引出了下面的混合模式。

三种架构的推演

抽象的标准在具体系统上运行后会更容易理解。下面是三个例子，分别对应一种架构。

积分会员计划：纯数据库

一家零售商发放积分，顾客在收银台兑换，而营销团队在促销出错时调整余额。这个系统的每项特性都指向同一个结论。积分由一家公司控制，顾客也接受这一点，因此不存在需要跨越的信任鸿沟。写入量很大，结账时的延迟必须不可察觉，账户数据还受删除规则约束。

Postgres 不需要任何额外设计就能处理所有这些需求。若改用链上版本，每次积分入账都要付费，并且在收银台要等待共识。它也无法满足 GDPR 的删除请求。在区块链上，每一项都会变得更糟，因此决定只需约一分钟。

去中心化交易所：纯链上

现在颠倒所有假设。去中心化交易所的存在，是为了让陌生人无需任何运营方持有资金即可交易。若加入一个可信的数据库运营方，这个产品就失去了存在的理由。

因此，整个状态机都位于合约中：余额、资金池储备和兑换逻辑。每笔交易都要经过共识并支付费用。链的约束进而塑造了设计。经典的订单簿需要频繁地下单、修改和撤单，以至于按次计费的写入变得过于昂贵。这在很大程度上是自动做市商在链上取代订单簿的原因。

用户为交易支付手续费，并等待数秒，因为无需信任正是他们来到这里所寻求的产品。请注意，即使是这样的交易所，仍有部分内容不上链：网页前端、分析数据和价格图表依然运行在普通服务器与数据库上。

SaaS 的加密货币存款：混合模式

常见的商业场景介于两个极端之间。一家 SaaS 希望接受全球客户以 USDT 付款；其订阅、发票和用户账户已经存放在数据库中，并应继续留在那里。链只在结算这一环节不可避免地被使用，其他一切都刻意留在链下。这第三种场景正是大多数团队最终实际构建的模式，因此下文会详细展开。

混合模式：链下数据库，链上结算

生产环境中的支付系统几乎从不二选一。它们分工协作：区块链负责结算价值，数据库负责其余一切。客户档案、订单、余额和会话数据保存在 Postgres 或 MySQL 中，便于查询和编辑。只有资金的实际转移才通过 API 触达链，因此应用本身无需运行自己的节点。

一个典型的存款流程如下：

  1. 客户准备付款。你的后端通过 API 调用为其分配一个专用存款地址，并把“地址与客户”的映射存入你的数据库。
  2. 客户向该地址发送 USDT。你无需轮询链上数据；转账被检测到时，会触发一个 Webhook。
  3. 你的端点验证 Webhook 的 X-Signature 请求头，将存款写入你自己的数据库，并在那里为客户的余额入账。

处理函数刻意保持朴素：

Webhook 载荷包含 txid、from、to、amount、contractaddress 和 blocknumber，因此插入操作只需请求体中的内容即可完成。此后，应用逻辑从你自己的数据表中读取余额，速度和成本都与数据库相当。只有资金转出时，才会再次查询链。

设置个人密钥后，Chaingateway 会在 X-Signature 请求头中为 Webhook 签名，具体见验证 Webhook 签名。Webhook 不会自动重试。失败的投递列在 GET /api/v2/tron/webhooks/notifications/failed 下。你可以通过 POST /api/v2/tron/webhooks/notifications/{id}/retry 逐条重新发送。停机后，可通过 GET /api/v2/tron/webhooks/notifications 获取历史通知，用于对账。

Webhook 指南包含完整的设置步骤，快速入门则介绍第一次 API 调用。

那么哪一种更好？

两者各自擅长对方做不到的事。数据库在数据处理上毫无悬念地胜出：性能、可扩展性、查询能力和运维成本。区块链则在不存在可信运营方的场景中胜出：它防篡改，任何人都可以审计，并且易于自动化对接，因为每个钱包都使用同一套协议。

对大多数团队来说，实际的答案是两者兼用，并以 API 相连：数据库支撑应用，区块链负责结算。选择该 API 层时，可参阅我们对区块链 API 服务商的比较；Chaingateway 的套餐见价格页。

常见问题

区块链是数据库吗？

只在最宽泛的意义上是：它持久地存储数据。但按日常定义，它并不合格，因为你无法更新或删除记录，查询能力有限，写入需要付费，并且要等几秒钟才能最终确认。把它称为「带存储的信任机器」比称为「数据库」更贴切。

区块链能取代传统数据库吗？

对普通应用而言不能。延迟、每次写入的手续费，以及缺失的 UPDATE 和 DELETE 操作，使它无法充当主数据存储。区块链取代的是结算层和公证人的角色，而不是 Postgres。

什么是区块链数据库？

这个术语通常指账本本身：在节点之间复制的交易历史。有些产品还会把链上数据索引到普通数据库中，以便用 SQL 查询。这很有用，但此时你查询的已经是数据库，而不是区块链。

为什么区块链比数据库慢得多？

因为每次写入在最终确认前，都必须经过签名、广播、共识，并复制到每个节点。数据库写入只是一台机器写入它自己的磁盘。这种慢是去除可信运营方所付出的代价，而不是会随优化消失的实现缺陷。

区块链具有 ACID 事务吗？

部分具备。智能合约交易是原子的（要么完全生效，要么完全回滚），合约代码保证一致性，共识提供全局排序，其隔离性强于大多数数据库的运行级别。持久性是例外：交易只有在最终性确认后才算结算，根据链的不同，需要数秒到数分钟，在此之前，重组可能使其被取代。记账的系统应以最终性为依据，而不是首次打包。

对普通企业而言，何时使用区块链才有意义？

几乎只在一个场景中：支付。企业很少需要与不信任的一方共享状态，但接受加密货币意味着结算层按定义就是区块链。可行的方案是上文描述的混合模式：链负责结算价值，所有运营相关的数据都留在你的数据库中，并通过 API 连接，而不是通过你自己的节点。

如果链很慢，应用如何即时显示区块链数据？

它们不会在每次请求时都读取链。浏览器和钱包查询的是索引：链上数据被复制到普通数据库中，并以数据库的速度提供服务。支付系统做的是同样的事情，只是逐个 Webhook 处理：将每笔已确认的存款写入自己的数据表，此后在本地读取余额。链是事实来源，数据库是工作副本。
