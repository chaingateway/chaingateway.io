地址监控 API：工作原理与构建指南

加密货币地址监控 API 的功能是什么，Webhook 如何推送充值与提币事件，以及如何处理确认数、重试和安全问题。文章还区分了运营监控与合规监控，说明确认阈值的设定方式、签名验证与速率限制，并给出最小实施清单和选型标准。

地址监控 API 是一种服务，它监视区块链地址，并在这些地址上发生事件时通知你的应用：例如收到一笔付款、资金转出、代币发生转移，或交易获得确认。你注册一个地址和一个回调 URL，服务随后会发送携带交易详情的 Webhook，因此你无需自行轮询节点或解析日志。

“地址监控”其实指两项不同的工作。第一项是运营层面的：了解资金何时到达或离开你的应用所控制的地址，以便为客户入账或放行订单。第二项是合规层面的：长期分析地址行为，发现有风险的活动。本文讲的是第一项，这也是大多数产品团队需要的，并说明第二项从哪里开始。

TL;DR

  • 地址监控 API 跟踪你选定的区块链地址，并通过 Webhook 将事件推送到你的服务器，因此你无需运行节点，也无需轮询。
  • 事件应当已解码：发送方、接收方、代币、金额和状态，而不是原始的十六进制日志。
  • 验证每个 Webhook 的签名，按交易 ID 去重，并且只在你选定的确认级别之后才入账。
  • Chaingateway 的 Webhook 不会自动重试。请与 API 对账，以发现遗漏的事件。
  • 运营监控（付款）与合规监控（长期风险模式）不同。许多团队需要两者，并借助不同的工具。
  • Chaingateway 为 Ethereum、Bitcoin、Tron、Polygon、BNB Smart Chain 和 Arbitrum 提供钱包、转账、已解码的交易数据和已签名的 Webhook。Solana 受支持，但不提供 Webhook。

地址监控 API 究竟做什么

区块链是一本公开账本，但它不会在事情发生时主动通知你。协议本身不会因为地址 0xABC... 收到 250 USDT 而向你的后端推送消息。必须有人读取新区块，筛选出你关心的地址，将结果解码为有意义的信息，然后通知你。地址监控 API 就是以服务形式提供的这个角色。

在实践中，该 API 做以下五件事：

  1. 注册地址。 你添加需要监视的地址，通常是为客户、发票或内部钱包生成的地址。
  2. 读取链上数据。 服务商为每个网络运行节点或索引器，并扫描每一个新区块。
  3. 匹配活动。 它找出涉及你所监视地址的原生币转账和代币转账。
  4. 解码数据。 原始交易和事件日志被转换为可读字段：方向、代币符号、按正确小数位换算的金额、手续费、区块和状态。
  5. 投递事件。 它把事件发送到你的端点，通常是 HTTPS POST Webhook，同时允许你按需查询相同的数据。

它能检测到的内容取决于链。在 Bitcoin 上，它检测支付给某个地址的输出。在 Ethereum 及其他 EVM 网络上，它检测原生转账以及 ERC-20 Transfer 日志等代币事件。在 Tron 上，它覆盖 TRX 和 TRC-20 代币。我们的 TRC20 地址 API 页面展示了在该网络上生成地址与监控地址如何配合。

运营监控与合规监控

这个说法在合规领域同样出现，两者不应混为一谈。专注合规的服务商将交易监控描述为对一段时间内区块链活动的持续分析，寻找诸如拆分交易（structuring）、分层转移（layering）、异常交易速度、混币器使用、规避制裁以及休眠钱包活动等模式。风险体现在许多笔交易的行为之中，由人工调查预警。

运营监控 API 回答的是一个更简单的问题：“我在等待的付款是否已经到账，并且已经最终确认？”如果你经营受监管的业务，很可能两层都需要。运营层为你的账本和客户体验提供数据，合规层为你的风控团队提供数据。当一条预警需要深入查看，例如跨多个跳转追踪资金，这项工作属于专业人士，而不属于付款 Webhook。

为什么不直接运行自己的节点并轮询？

这是个合理的问题，对于少数团队来说，答案正是这样做。以下是自建时需要承担的内容。

  • 节点运维。 每条链都需要自己的节点或托管端点，并需要管理升级、存储增长和可用性。每增加一个网络，就要多一次部署。
  • 链特定的逻辑。 Bitcoin 的 UTXO 模型、Ethereum 的日志、Tron 的资源模型以及 Solana 的账户模型，各自都需要专门的解析代码。
  • 解码。 代币金额以需要正确小数位换算的整数形式出现。合约事件需要 ABI。内部转账和批量交易很容易被遗漏。
  • 重组处理。 最近的区块可能会被替换。你的扫描器必须能够发现并自我纠正。
  • 投递。 检测到事件之后，你仍需要队列、重试机制和签名方案，才能安全地将其投递给你自己的服务。

监控 API 能把其中大部分工作合并为一次集成。代价是依赖服务商，因此应从可靠性、数据质量以及事件交付的清晰程度来评估。若想更全面地了解各种替代方案，可参阅我们对六类区块链 API 及其适用场景的比较。

基于 Webhook 的地址监控如何工作

典型流程包含四个步骤，无论你是自建还是购买，都是如此。

1. 创建或注册地址

对于付款场景，最清晰的模式是为每位客户、每张发票或每笔订单分配一个地址。当付款落到唯一的地址上时，你无需要求客户填写备注或参考号，就能知道是谁付的款。使用 Chaingateway 时，你可以通过 API 创建钱包，并直接使用生成的地址。如果客户提供自己的地址用于提现，请先进行验证。我们的免费加密地址验证工具覆盖 Tron、Ethereum 和 BSC 的地址格式，在你构建自己的校验时可作为参考。

2. 订阅事件

你告诉 API 哪些地址和事件类型重要，以及将事件发送到哪里：你的 HTTPS 端点。订阅可以窄到一个地址和一种代币，也可以宽到你账户中的所有地址。关于这一模型的详情，请见区块链 Webhook 与事件通知页面。

3. 接收已解码的载荷

一个有用的载荷无需再次查询，就能告诉你发送方、接收方、资产、金额、区块和交易哈希。Chaingateway 为 TRC-20 转账发送的 Webhook 如下所示（Webhook 指南）：

你的服务器验证签名，存储事件，快速返回 2xx 响应，然后异步处理业务逻辑。此后的一切，例如为账户入账或发货，都取决于你为确认数设定的规则。

应支持哪些网络与地址类型？

在确定之前，请列出你的产品在未来一年内会涉及的范围，而不仅仅是今天。在一个网络上以 USDT 开始的结账流程，往往在几个月内就会被要求支持另一个网络。

请检查以下方面的覆盖情况：

  • 原生币与代币。 Bitcoin、ETH、TRX、SOL、MATIC 网络和 BNB 链上的资产，以及 ERC-20、BEP-20 和 TRC-20 等代币标准。
  • NFT。 如果你发行或接受收藏品或票券，还需要类似 ERC-721 的转账事件。
  • 地址格式。 Bitcoin 有多种格式；EVM 链则在各网络之间共用同一种格式，当客户在错误的网络上发送时可能出错。你的应用应在每个充值地址旁边标明预期的网络。
  • 转出活动。 许多工具只能捕获充值。如果你需要发放款项，你就需要同样解码过的转出交易视图及其状态。

Chaingateway 通过一个区块链 API覆盖 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Smart Chain 和 Arbitrum，包括主要的代币标准和 NFT 转账。除 Solana 外，所有链都提供 Webhook。Solana 集成必须轮询其地址的余额或交易。

确认、延迟与重组：付款何时才算真实？

第一条通知并不是最终结论。一笔交易可能先在内存池中被看到，然后被打包进区块，之后才达到你认为安全的最终性水平。各链在这方面差异很大：Bitcoin、Ethereum、Tron 和 Solana 的区块时间、确认惯例和最终性模型各不相同，因此你的阈值应按网络和金额分别设定。

一种实用的策略如下：

阶段含义你的应用应做什么
已检测交易已被看到，但尚未进入区块显示“付款待处理”；不要放行商品
已打包交易已进入区块，确认数较少如果风险可接受，小额可先记入待结算余额
已确认已达到你选定的确认深度为账户入账，放行订单
失败或丢弃交易已被替换、回滚或从未被挖出撤销待处理状态，并告知客户

两条规则能帮你避开麻烦。第一，确认要求应与所涉金额相匹配：小额订阅付款可以接受比大额提现更低的阈值。第二，在数据库中明确定义状态机。“待处理”“已确认”和“失败”应当是被存储的状态，而不是被推断出来的状态。

同时，也要预期事件可能迟到或乱序到达。确认通知可能会在一个处理缓慢的处理器完成检测通知之前到达你这里。应以交易哈希和状态为事实来源，而不是依赖到达顺序。

处理重试与重复通知

Chaingateway 不会自动重试 Webhook。如果你的服务器超时或返回错误，该通知会被记录为失败。你可以按链列出失败的通知，例如 GET /api/v2/tron/webhooks/notifications/failed，并通过 POST /api/v2/tron/webhooks/notifications/{id}/retry 重新发送。在你这样做之前，你的系统并不知道该事件的存在。

重复也仍可能发生，例如你重新发送了一条你的服务器已经处理过的通知。应从第一天起就针对这两种情况进行设计。其他服务商可能会自行重试，因此同一套处理器设计可以适用于不同的服务商。

  • 让处理器具有幂等性。 为每个事件存储一个唯一键，例如交易哈希加日志索引，或投递 ID，并加上唯一数据库约束。如果该键已存在，则返回成功，不做其他操作。
  • 快速响应。 先将原始事件写入队列或数据表，返回 2xx 状态码，然后再处理。处理缓慢会导致超时，而每次超时都会变成一次失败的通知。
  • 对账。 在你自己停机期间，Webhook 可能会丢失。运行一个定期任务，列出失败的通知以及最近的通知（GET /api/v2/<chain>/webhooks/notifications），并与你的记录进行比对。这样，丢失的事件就从事故变成了可延迟修复的问题。
  • 记录一切。 保留原始载荷、签名请求头以及你的处理结果。当客户说他已经付款时，你会希望在一分钟内而非一小时内拿到证据。
  • 对沉默发出警报。 如果一个通常有交易的地址在异常长的时间内没有产生任何事件，请检查整条管道。

安全、身份验证与速率限制

一个按请求为你入账的端点就是攻击目标。应当以此对待它。

验证每个 Webhook

任何找到你 URL 的人都可以发送一条伪造的“已收到付款”消息，因此应要求签名。在个人资料中设置个人密钥后，Chaingateway 会为每个 Webhook 添加 X-Signature 请求头。该请求头是以你的个人密钥为键，对交易 ID 计算的 Base64 编码 HMAC-SHA256。你的服务器会重新计算该值，并拒绝任何不匹配的请求（签名指南）。比较数值时应使用恒定时间函数，例如 Python 中的 hmac.compare_digest。HMAC 本身的定义见 RFC 2104。

保护你的 API 密钥

将密钥保存在密钥管理服务或环境变量中，切勿放在客户端代码或代码仓库里。为每个环境使用独立的密钥，并按计划轮换，同时在人员变动后轮换。我们在使用区块链 API 的六条安全建议中整理了更多类似的做法。

加固端点

  • 仅通过 HTTPS 提供服务。
  • 使用难以猜测的路径；如果服务商公布了源 IP 段，则只允许这些地址。
  • 拒绝超大的请求体和意外的内容类型。
  • 对于未与你自己的记录进行匹配的 Webhook，切勿信任其中的金额或地址：该地址必须是你签发的，金额必须与订单相符。

规划速率限制

在进行对账或批量地址查询时，任何服务商都会遇到请求限制。对不变的内容进行缓存，在 API 允许的情况下批量处理，遇到限流响应时进行指数退避，并把定时任务错开，而不是都在整点触发。上线前就要了解你套餐的限制，而不是在第一次流量高峰时才发现。

应自行构建监控还是使用 API？

自己扫描链上数据，在第一个版本中是可行的。问题会在之后出现：重组导致一笔付款被入账，随后又消失；某个小数位不寻常的代币显示了错误的金额；节点在繁忙时段落后；客服还在追查一位声称已付款的客户。

使用 Chaingateway，你可以创建钱包、为其地址创建 Webhook，并接收已解码、已签名的事件。Ethereum、Bitcoin、Tron、Polygon、BNB Smart Chain 和 Arbitrum 的请求格式相同，因此新增一条网络只是一项配置更改。你无需运行节点。

有三个习惯比你选择的服务商更重要：尽早确定确认策略，在第一笔真实付款之前写好幂等的处理器，并按计划对账。监控 API 应当让这些工作更容易，而不是取代它们的必要性。

最小实施清单

在第一笔真实付款之前，请逐项检查以下内容。

  1. 为每张发票或每位客户生成一个地址，并在旁边显示预期的网络。
  2. 将这些地址订阅到转入和转出事件。
  3. 提供一个验证 X-Signature 请求头的 HTTPS 端点。
  4. 以唯一键存储每个事件，并忽略重复的事件。
  5. 通过已存储的状态推进付款：待处理、已确认、失败。
  6. 按网络和金额分别设置确认阈值。
  7. 安排一个与 API 交易历史进行对账的任务。
  8. 对失败的投递、长时间的沉默和签名验证失败发出警报。
  9. 在你支持的每个网络和每种代币上，用小额真实资金进行测试，包括一次错误网络的充值，以便提前掌握客服的应答方式。

常见问题

什么是地址监控 API？

它是一种服务，监视区块链地址，并通过 Webhook 和查询端点将这些地址上的活动报告给你的应用。你无需自行运行节点，即可获得已解码的事件，例如转入的代币转账或已确认的提现。

地址监控与合规交易监控是一回事吗？

不是。运营层面的地址监控告诉你的应用付款已到账或已转出。合规交易监控则长期分析行为，标记有风险的模式，并由人工调查预警。受监管的企业通常两者都会使用。

我应当等待多少个确认？

这取决于网络和所涉风险金额，因此没有统一的数字。为每条链设置阈值，金额越大阈值越高，并在数据库中将“待处理”和“已确认”作为两个独立状态存储。

如何防止重复的 Webhook 让客户被入账两次？

为每个事件设置唯一键，例如交易哈希加日志索引，或投递 ID，并通过唯一约束强制执行。如果你的处理器发现某个键已经存储过，就返回成功，不做其他任何事。

能否用一次集成监控多条区块链？

可以，前提是该 API 支持多链。Chaingateway 通过一个 REST API 覆盖 Ethereum、Bitcoin、Tron、Solana、Polygon、BNB Smart Chain 和 Arbitrum。除 Solana 外，所有链都提供 Webhook。
