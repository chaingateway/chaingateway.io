以太坊节点是保存链上完整状态副本的软件，让你可以直接查询它或广播交易，而不必经过别人的服务器。搜索「ethereum node」通常出于两种原因之一：你想在投入服务器预算之前弄清楚运行一个节点意味着什么，或者你以为节点是读取和发送以太坊数据的唯一方式，想验证这个假设。本页会解答这两个问题。以下数据来自以太坊官方节点运行文档，核实时间为 2026 年 8 月，而非某个销售页面。

什么是以太坊节点？

以太坊节点是运行中的客户端软件实例，它保存链上数据、验证新区块，并向点对点网络的其他节点转发交易。自合并（The Merge）以来，一套完整配置需要两个程序配合：负责状态和交易的执行客户端（Geth、Nethermind、Besu、Erigon 或 Reth），以及负责权益证明证明的共识客户端（Lighthouse、Prysm、Teku、Nimbus 或 Lodestar）。两者持续运行，并通过本地 RPC 连接互相通信。以太坊节点有几种存储配置：完整节点保留近期状态并修剪旧数据，归档节点保留写入过的每一个历史状态，轻节点只获取区块头——以太坊官方文档指出，在主网上这种模式的服务节点太少，实际并不可行。

以太坊节点要求

Ethereum.org 的节点运行指南（核实时间为 2026 年 8 月）列出了以下配置，作为运行一个执行客户端和一个共识客户端的完整节点的基准：

组件最低配置推荐配置
CPU2 核以上高速 CPU，4 核以上
内存8 GB16 GB 以上
存储2 TB SSD高速 SSD，2 TB 以上
带宽10 Mbit/s 以上25 Mbit/s 以上，不限流量

来自同一文档的两个细节在配置服务器时很容易被忽略。第一，存储需求因客户端而异：在快照同步（snap sync）下，Geth、Nethermind 和 Besu 各自仅执行数据就需要大约 500 GB 以上，而归档节点——保留全部历史状态而不只是当前状态——在这几个客户端上会达到 12 TB 以上，或者在存储方式不同的 Erigon 和 Reth 上大约是 2–2.5 TB。第二，共识客户端是单独的一项预算：在执行客户端的占用之上，再为信标链数据预留大约 200 GB。这些都不是一次性成本——只要节点保持在线，以太坊节点的磁盘占用就会持续增长，因为链在不断产生新区块。同步本身所需时间取决于硬件、网络速度和所选的同步模式；官方文档没有公布固定时长，我们也不会给出，所以在别处看到的任何具体天数都应视为猜测，而非规格说明。

如何运行以太坊节点，概览层面

运行以太坊节点分解为一系列持续的职责，而不是一次安装步骤。选择并安装匹配的执行/共识客户端组合。按照上表配置硬件——存储配置不足是最常见的错误，因为节点持续同步的每一个月，安全余量都会不断缩小。启动两个客户端，让它们指向彼此的本地 RPC 端点，并在依赖该节点做任何事情之前，让初始同步跑完。之后，工作就转为运维性质：及时应用客户端更新（硬分叉要求这样做）、监控节点数和磁盘余量，并保持机器 7×24 小时可访问，因为一个长时间离线的节点必须先追上进度才能重新可用。这些都不是基础设施运维中不寻常的事情——它和运行任何其他有状态服务的维护特征相同，只是事后纠正状态的空间更小。

如需带复制粘贴命令、Geth 与 Lighthouse 配置以及 systemd 单元的分步搭建说明，请参阅博客上的 以太坊节点搭建指南。

在 ARM 上运行以太坊：可行，但不能豁免同样的限制

客户端团队确实发布了 ARM64 版本，Raspberry Pi 5 级别的开发板可以运行完整节点。这是真的，但并不会改变上面的要求表——树莓派仍然需要一块外接 NVMe 硬盘，容量要满足同样的 2TB 以上要求，内存对客户端软件而言仍是硬性下限，而更慢的 CPU 往往会比同等的 x86 机器更拖长初始同步时间。ARM 是在家中更便宜、更安静地运行节点的方式，而不是用更少资源运行节点的方式。

什么时候你真正需要自己的节点

当你在运行验证者、为分析业务索引整条链、需要归档级别的历史状态，或者有合规要求你的基础设施在链访问上永远不依赖第三方时，自托管节点是正确的选择。这些需求都不适合用 API 来替代——它们本质上是不同的工作。如果你的需求更窄一些——生成存款地址、发送 ETH 或 ERC-20 代币、在资金到账时收到通知——那正是支付 API 所面向的场景，无需承担与之相关的存储和在线时间承诺。

如果你的真实需求是发送 ERC-20 代币并监控存款，创建免费账户，在配置 2TB SSD 之前先通过 REST 试试同样的工作。
