Ethereum-Zahlungsintegration: Ein Leitfaden für Entwickler

Wie Sie Ethereum-Zahlungen integrieren: ETH oder Tokens wählen, Zahlungsanfragen erstellen, Transaktionen erkennen und bestätigen, Gas handhaben, Schlüssel sichern und testen.

Die Integration von Ethereum-Zahlungen bedeutet, vier Dinge zuverlässig zu erledigen: jedem Kunden einen eindeutigen Zahlungsort bereitzustellen, die Transaktion bei Eintreffen zu erkennen, zu entscheiden, wann sie als endgültig gilt, und sie mit Ihrer Bestellung abzugleichen. Sie können dies selbst auf Basis von Nodes und JSON-RPC aufbauen oder eine einheitliche API aufrufen, die Wallets, Gas und Benachrichtigungen für Sie übernimmt. Dieser Leitfaden deckt beide Wege ab, damit Sie mit offenen Augen eine Entscheidung treffen können.

TL;DR

  • Eine Ethereum-Zahlung ist eine signierte Transaktion, die ETH oder Tokens bewegt. Das Absenden ist nicht dasselbe wie die Bestätigung: Sie müssen den Beleg (Receipt) prüfen.
  • Entscheiden Sie zuerst: Nur ETH, Stablecoins und ERC-20-Tokens oder Ihr eigener Token. Diese Wahl bestimmt Ihre Ereignisbehandlung und Ihre Gas-Strategie.
  • Verwenden Sie eine Einmal-Einzahlungsadresse pro Bestellung oder Nutzer und lauschen Sie über Webhooks auf Ereignisse, statt zu pollen.
  • Behandeln Sie private Schlüssel, Webhook-Signaturen und Vertragscode als die drei wichtigsten Sicherheitsflächen.
  • Eine einheitliche API wie Chaingateway ersetzt die Node-, Gas- und Decodierungsarbeit, mit Plänen ab 49 € pro Monat.

Was eine Ethereum-Zahlung tatsächlich ist

Eine Ethereum-Zahlung ist eine kryptografisch signierte Anweisung eines Kontos, die den Zustand des Netzwerks aktualisiert, beispielsweise durch Übertragung von ETH oder Tokens. Laut der Transaktionsdokumentation von ethereum.org prüft ein Validator die Transaktion und nimmt sie in einen Block auf. Erst danach existiert das Geld an der Adresse des Empfängers.

Für Ihre Anwendung hat dies eine praktische Konsequenz. Der Kunde zahlt nicht Ihnen direkt. Er sendet eine Transaktion an das Netzwerk, und Ihr System muss diese bemerken. Alles in einer Integration ist eine Variation dieses Beobachtungsproblems.

Es gibt zwei Arten von Zahlungen, denen Sie begegnen werden:

  1. Native ETH-Überweisungen. Die Transaktion selbst trägt Empfänger und Wert. Einfach und direkt in der Transaktion und ihrem Beleg sichtbar.
  2. Token-Überweisungen (ERC-20 und verwandte). Die Transaktion geht an den Vertrag des Tokens, der die Salden intern aktualisiert. Der Standard definiert dafür ein Transfer-Ereignis, wie in der ERC-20-Spezifikation auf ethereum.org festgelegt. Ihr System erfährt von der Zahlung über dieses Ereignisprotokoll, nicht über das Wert-Feld der Transaktion.

Die meisten Stablecoin-Checkouts sind der zweiten Art. Wenn Sie nur auf eingehendes ETH an einer Adresse achten, werden Sie diese verpassen.

Entscheidungen, bevor Sie Code schreiben

Welche Assets akzeptieren Sie?

Beginnen Sie mit dem engsten Set, das Ihre Kunden bedient. ETH allein ist am einfachsten zu implementieren. Die Hinzufügung eines Stablecoins nimmt die Preisschwankung aus der Gleichung, was für Rechnungen und Abonnements relevant ist. Wenn Sie einen eigenen Token ausgeben, müssen Sie auch dessen Dezimalstellen, seine Vertragsadresse und wissen, ob er sich wie ein Standard-ERC-20 verhält.

Jedes zusätzliche Asset fügt eine zu überwachende Vertragsadresse, einen anzuwendenden Dezimalwert und eine Preisregel hinzu. Halten Sie eine kleine Positivliste und lehnen Sie alles andere bewusst ab.

Verwahrung und Compliance

Wer hält die Schlüssel? Wenn Ihre Plattform Einzahlungswallets für Kunden generiert, verwalten Sie Gelder, und je nach Ihrer Rechtsordnung und Ihrem Geschäftsmodell kann dies Lizenz- oder Meldepflichten nach sich ziehen. Fragen Sie vor dem Start einen Anwalt, der Ihren Markt kennt, nicht danach. Dieser Leitfaden behandelt die Technik, keine Rechtsberatung.

Der Kernzahlungsablauf, Schritt für Schritt

Hier ist die Sequenz, die in der Produktion Bestand hat, egal ob Sie sie bauen oder kaufen.

1. Zahlungsanfrage erstellen

Wenn der Kunde den Checkout erreicht, erstellen Sie einen Bestelldatensatz mit Betrag, Asset und Ablaufzeit. Weisen Sie dann eine eindeutige Empfangsadresse dieser Bestellung zu. Eine eindeutige Adresse pro Bestellung ermöglicht es Ihnen, eine eingehende Überweisung dem richtigen Kunden zuzuordnen, ohne dass dieser einen Memo oder eine Referenz einfügen muss.

Bepreisen Sie die Bestellung in einer stabilen Einheit, sperren Sie einen ETH-Betrag für ein kurzes Zeitfenster, wenn Sie volatile Assets akzeptieren, und speichern Sie beide Zahlen.

2. Der Kunde signiert und sendet

Wenn der Kunde über eine Browser-Wallet zahlt, bittet Ihr Frontend um Erlaubnis zur Nutzung seines Kontos, erstellt ein Transaktionsobjekt und sendet es ab. Die MetaMask-Referenz zu eth_sendTransaction beschreibt diese Reihenfolge: Kontoberechtigung einholen, Transaktion senden, zurückgegebenen Hash behalten. Wenn der Kunde stattdessen von einer Börse oder einer mobilen Wallet an Ihre angezeigte Adresse sendet, sehen Sie diesen Schritt nie. Sie sehen nur das Ergebnis on-chain.

In jedem Fall ist ein Transaktions-Hash die Quittungsnummer der Zahlung. Speichern Sie ihn.

3. Transaktion erkennen

Sie haben drei Möglichkeiten, eine Zahlung zu bemerken:

  • Polling. Fragen Sie einen Node alle paar Sekunden nach dem Receipt oder dem Kontostand der Adresse ab. Einfach, aber verschwenderisch und bei Skalierung anfällig.
  • Subscriptions. Öffnen Sie eine WebSocket-Verbindung zu einem Node und abonnieren Sie neue Blöcke oder Contract-Logs. Die go-ethereum-Dokumentation zu Echtzeit-Events beschreibt eth_subscribe genau dafür. Sie müssen abgebrochene Verbindungen und das Nachholen verpasster Blöcke selbst handhaben.
  • Webhooks. Ein Dienst überwacht die Chain und ruft Ihren Server auf, wenn etwas Relevantes passiert. Dies ist die wartungsärmste Option und die, die die meisten Teams wählen.

Bei Tokens überwachen Sie Event-Logs. Die Ethereum-Dokumentation weist darauf hin, dass Anwendungen über die JSON-RPC-API auf Contract-Events lauschen und auf die emittierten Logs reagieren können.

4. Das Ergebnis bestätigen

Einreichung ist keine Bestätigung. Der MetaMask-Leitfaden zum Senden von Transaktionen zeigt das Muster: Pollen Sie den Receipt anhand des Hashes ab; kein Receipt bedeutet, die Transaktion ist noch ausstehend, ein Status von 0x1 bedeutet Erfolg, und 0x0 bedeutet, sie ist fehlgeschlagen. Die eth_getTransactionReceipt-Referenz ergänzt, dass der Receipt die Blocknummer, das verbrauchte Gas und die Logs enthält.

Ihr Bestell-Statusautomat sollte dies explizit abbilden:

  1. awaiting_payment: Adresse ausgestellt, noch nichts gesehen.
  2. pending: Eine passende Transaktion ist sichtbar, aber noch nicht in einem Block.
  3. confirmed: Receipt gefunden, Status erfolgreich, Betrag und Asset stimmen überein.
  4. final: Genug zusätzliche Blöcke sind vergangen für Ihre Risikotoleranz.
  5. failed, underpaid, overpaid oder expired: Die Fälle, die eine Regel brauchen, kein Achselzucken.

Wie viele Blöcke Sie warten, bevor Sie Waren freigeben, ist eine Geschäftsentscheidung. Digitale Güter unter wenigen Dollar können bei der ersten Bestätigung versendet werden. Hochwertige Bestellungen verdienen eine längere Wartezeit, da ein Block gelegentlich reorganisiert werden kann, bevor sich das Netzwerk darauf einigt.

5. Abgleichen

Vergleichen Sie täglich die Summe der bestätigten Zahlungen in Ihrer Datenbank mit dem, was die Chain an Ihren Adressen als eingegangen anzeigt. Jede Differenz ist ein Bug, ein verpasster Webhook oder ein Kunde, der das falsche Asset gezahlt hat. Data-Tooling kann hier helfen: Der Bereich Daten und Analysen auf ethereum.org listet Indexer auf, die historische Event-Logs und abfragbare Echtzeitdaten bereitstellen, was reduziert, wie viel Sie selbst warten müssen.

Gas, fehlgeschlagene Transaktionen und Rückerstattungen

Gas ist der Punkt, an dem viele Erst-Integrationen überrascht werden. Jede Transaktion zahlt eine Gebühr, die aus einer Base Fee und einer Priority Fee besteht, und der Sender zahlt sie, wie die Transaktions-Dokumentation erklärt. Daraus folgen drei Konsequenzen für Sie.

Kunden können zu wenig zahlen oder steckenbleiben. Wenn sie eine zu niedrige Gebühr setzen, bleibt die Transaktion ausstehend. Ihre Bestellung sollte nicht ablaufen, solange eine gültige Transaktion in der Pipeline ist.

Fehlgeschlagene Transaktionen kosten trotzdem Gas. Ein reverted Token-Transfer erzeugt einen Receipt mit fehlgeschlagenem Status, und die Mittel des Kunden bewegen sich nicht. Markieren Sie die Bestellung nicht als bezahlt, nur weil Sie einen Hash gesehen haben.

Das Senden von Ihrer Seite kostet Sie. Rückerstattungen, Sweeps von Einzahlungsadressen zu einer Treasury-Wallet und Auszahlungen erfordern alle Gas, und Token-Adressen benötigen ETH, um Tokens zu bewegen. Schätzen Sie die Gebühr vor dem Senden und planen Sie dafür ein Budget ein. Unser Leitfaden zur Schätzung von Gas-Gebühren auf Ethereum und anderen Chains führt durch die Schätzmethoden.

Wenn Sie möchten, dass Kunden bezahlen, ohne überhaupt ETH zu halten, ermöglicht Account Abstraction Entwicklern, Transaktionen zu sponsern, wie im ethereum.org Tutorial zum Sponsern von Gas-Gebühren beschrieben. Dies fügt Vertragskomplexität hinzu, daher reservieren Sie es für Produkte, wo die Gas-Reibung wirklich Conversions kostet.

Für Rückerstattungen legen Sie die Richtlinie im Voraus fest. Erstatten Sie nur an die sendende Adresse, nachdem Sie geprüft haben, dass es sich nicht um eine Börsen-Einzahlungsadresse handelt, die Sie nicht kontrollieren können, oder fragen Sie den Kunden nach einer Rückerstattungsadresse. Ziehen Sie die Netzwerkgebühr offen ab oder übernehmen Sie sie, aber schreiben Sie die Regel fest.

Schlüssel, Signaturen und Verträge sichern

Private Schlüssel

Wer den Schlüssel hält, kontrolliert die Mittel. Generieren Sie Schlüssel in einer gehärteten Umgebung, loggen Sie sie niemals, committen Sie sie niemals, und trennen Sie Hot Wallets (kleine Beträge, für Auszahlungen verwendet) von Cold Storage (der Großteil der Mittel). Sweepen Sie Einzahlungsadressen planmäßig auf die Cold-Seite.

Webhook-Echtheit

Ein Webhook-Endpunkt ist eine öffentliche URL, die Bestellungen als bezahlt markieren kann. Jeder, der sie findet, kann ein gefälschtes Event posten. Verifizieren Sie eine Signatur bei jeder Anfrage (HMAC-Signierung ist der gängige Ansatz), weisen Sie veraltete Zeitstempel zurück, und machen Sie den Handler idempotent, damit eine doppelte Zustellung eine Bestellung nicht zweimal gutschreibt. Bestätigen Sie dann optional die Transaktion mit einem direkten Lookup, bevor Sie Waren freigeben.

Smart Contract Code

Wenn Sie Ihre eigenen Zahlungsverträge schreiben, verlagert sich das Risiko auf den Code. Ethereums eigener Sicherheitsbericht stellt fest, dass Audits, getestete Bibliotheken, formale Verifikation und statische Analyse die Vertragssicherheit verbessern, und dass benutzerdefinierter Code für erweiterte Kontrollen das Verwundbarkeitsrisiko erhöhen kann. Die praktische Regel: Stellen Sie keinen benutzerdefinierten Vertrag bereit, wenn eine einfache Adresse und Standard-Token-Events für Ihren Anwendungsfall ausreichen.

Für einen tieferen Blick auf die Anwendungsebene ist ein Leitfaden zu dem, was ein Web-Application-Audit-Service abdeckt, eine gute Checkliste dafür, wonach Sie fragen sollten.

Selbst bauen oder API nutzen?

Der Do-it-yourself-Pfad bedeutet, Nodes zu betreiben oder zu mieten, einen Adressgenerator zu schreiben, den Log-Decoder für jeden akzeptierten Token zu bauen, Gas zu schätzen, Reorgs zu handhaben und all das am Laufen zu halten. Es ist ein vernünftiger Pfad für ein Team, dessen Produkt die Zahlungsinfrastruktur ist.

Für alle anderen sind die Kosten Zeit und laufende Wartung. Die Architekturfrage ist dieselbe, der sich Unternehmen stellen, wenn sie sich generell mit Partnern verbinden: Events in Echtzeit pushen statt später batchweise abzugleichen, ein Trade-off, der in diesem Artikel zu APIs für Echtzeit-B2B-Daten gut behandelt wird. Zahlungen folgen derselben Logik, nur in kleinerem Maßstab.

Wenn Sie vor der Entscheidung einen Überblick über die Optionen wünschen, zeigt unser Vergleich der Blockchain-API-Typen und wann Sie welchen einsetzen die Kategorien auf, und der Ethereum-Überblick erklärt ETH, Gas und ERC-20-Tokens für Teams, die neu in der Chain sind.

Teams planen für den Idealfall: Ein Kunde sendet ETH, die Bestellung wird als bezahlt markiert, und dann verbringen sie den Großteil ihrer Entwicklungszeit mit allem Drumherum: Dekodieren von Token-Logs, Schätzen von Gas, Wiederholen verpasster Benachrichtigungen und Absichern von Wallets.

Deshalb ist Chaingateway als eine REST-API über alle Chains hinweg konzipiert und nicht als Satz chain-spezifischer Endpunkte. Sie erstellen eine Wallet mit einem Aufruf, senden ETH oder Tokens mit einem Aufruf und empfangen Transaktionen bereits dekodiert, sodass Sie keine Raw-Logs parsen müssen. Gas wird automatisch geschätzt, Anfragen werden HMAC-signiert, und Sie betreiben keinen eigenen Node. Derselbe Aufruf funktioniert auf Ethereum, Bitcoin, Tron, Solana, Polygon, BNB Chain und Arbitrum, sodass das Hinzufügen eines zweiten Netzwerks später eine Konfigurationsänderung ist, kein Rewrite.

Testen und Monitoring vor und nach dem Launch

Eine Zahlungsintegration ist nicht abgeschlossen, wenn die Demo funktioniert. Arbeiten Sie diese Liste zunächst in einem Testnetz durch, dann erneut mit kleinen echten Beträgen:

  • Exakte Zahlung, Unterzahlung und Überzahlung sowohl bei ETH als auch bei jedem akzeptierten Token.
  • Späte Zahlung nach Ablauf der Bestellung und doppelte Zahlung an dieselbe Adresse.
  • Fehlgeschlagene Transaktion mit einem zu niedrigen Gas-Limit, damit Sie einen fehlgeschlagenen Receipt sehen und bestätigen können, dass die Bestellung nicht abgeschlossen wird.
  • Doppelte und Out-of-Order-Webhooks, absichtlich erneut abgespielt.
  • Eigene Downtime: Stoppen Sie Ihren Server für zehn Minuten, senden Sie eine Zahlung, starten Sie neu, und prüfen Sie, dass nichts verloren geht.
  • Wallet-Flows im Frontend. QA-Teams können diese regressionssicher testen, ohne Private Keys zu halten, mithilfe von Tools wie dem auf der Impersonator.xyz-Seite von ethereum.org aufgeführten.

Nach dem Start auf drei Signale alarmieren: Aufträge, die länger als ein Schwellenwert in pending verbleiben, eine Diskrepanz zwischen Datenbank- und On-Chain-Gesamtsummen sowie Webhook-Zustellfehler. Das erste erkennt Gebührenprobleme, das zweite verpasste Events, das dritte Ihre eigenen Ausfälle.

Häufig gestellte Fragen

Nein. Ein Knoten gibt Ihnen direkten Zugriff auf die Kette, aber Sie erben auch dessen Wartung, Synchronisierung und Überwachung. Die meisten Teams nutzen eine Provider-API oder einen Dienst, der die Kette für sie überwacht und einen Webhook aufruft, wenn eine Zahlung eintrifft.

Beobachten Sie das Transfer-Event des Token-Vertrags für Ihre Empfangsadresse. Der ERC-20-Standard definiert dieses Event, und eine Token-Übertragung taucht nicht als ETH-Wert in der Transaktion auf. Eine Decoding-API liefert Ihnen Absender, Empfänger und Betrag direkt.

Es gibt keine einzelne richtige Zahl. Es hängt vom Bestellwert und Ihrer Toleranz gegenüber der seltenen Kettenreorganisation ab. Geringwertige digitale Güter können früh freigegeben werden, während hochwertige Aufträge länger warten sollten. Schreiben Sie die Schwellenwerte in Ihre Bestelllogik, damit der Support nicht fallweise entscheiden muss.

Der Absender zahlt sie, daher decken Kunden die Gebühr bei ihren eigenen Zahlungen und Sie decken sie, wenn Sie Rückerstattungen, Sweeps oder Auszahlungen senden. Gesponserte Gas-Gebühren durch Account Abstraction können diesen Kosten für bestimmte Flows auf Sie verlagern.
