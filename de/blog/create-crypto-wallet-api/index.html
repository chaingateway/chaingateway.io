Wie man eine Krypto-Wallet mit einer API erstellt: Leitfaden 2026

Erfahren Sie, wie Sie Krypto-Wallets über eine API erstellen: Verwahrungsoptionen, Schlüsselsicherheit, Adressdesign, Webhooks und ein schrittweiser Bauplan für Entwickler.

Kapitel

Um eine Krypto-Wallet über eine API zu erstellen, senden Sie eine authentifizierte Anfrage an einen Dienst, der ein Schlüsselpaar generiert, den privaten Schlüssel speichert und eine öffentliche Adresse zurückgibt, die Sie einem Benutzer anzeigen können. Der schwierige Teil ist nicht dieser Aufruf. Es ist die Entscheidung, wer die Schlüssel verwahrt, wie Sie die Anmeldedaten rund um diese Schlüssel sichern und wie Sie erfahren, wann Geld eingeht. Dieser Leitfaden behandelt alle drei Aspekte mit den Kompromissen, die ein Produktionsteam vor dem Start klären muss.

TL;DR

  • Eine Wallet-API generiert Schlüssel und gibt eine Adresse zurück. Ihre eigentlichen Designentscheidungen sind Verwahrung, Schlüsselspeicherung und Zahlungserkennung.
  • Geben Sie jedem Benutzer oder jeder Rechnung eine eigene Adresse und speichern Sie jeden eingehenden Transaktions-Hash als eindeutigen Schlüssel in Ihrer Datenbank.
  • Verwenden Sie signierte Webhooks statt Polling, verifizieren Sie jede Signatur und machen Sie Ihren Handler idempotent.
  • Die Schlüsselgenerierung muss eine kryptografisch sichere Zufallsquelle verwenden, und Produktionsschlüssel gehören in nicht exportierbaren Speicher wie ein HSM.
  • Eine einheitliche Multi-Chain-API erspart Ihnen das Betreiben von Nodes und die Pflege separater Integrationen pro Netzwerk.

Was eine Wallet-API tatsächlich tut

Eine Blockchain-Wallet ist Software, die Schlüssel verwaltet. Der NIST-Überblick zur Blockchain-Technologie beschreibt sie als Werkzeug, das private Schlüssel, öffentliche Schlüssel und Adressen speichern kann und Benutzern hilft, mit den Assets zu arbeiten, die diese Schlüssel kontrollieren. Eine Wallet-API verlagert diese Aufgabe vom Gerät des Benutzers in Ihr Backend.

In der Praxis deckt eine Wallet-API vier Aufgaben ab:

  1. Erstellen: Generieren eines neuen Schlüsselpaars und Rückgabe der Adresse für ein bestimmtes Netzwerk.
  2. Lesen: Ausgeben von Kontoständen und Transaktionsverlauf für diese Adresse.
  3. Senden: Erstellen, Signieren und Übertragen einer Überweisung, einschließlich Gebührenschätzung.
  4. Benachrichtigen: Informieren Ihrer Anwendung, wenn etwas mit der Adresse geschieht.

Der Bitcoin-Entwicklerleitfaden zur Zahlungsverarbeitung macht einen Punkt, der für jede Kette gilt: Bevor Sie eine Zahlung anfordern, muss Ihre Anwendung eine Adresse erstellen oder eine von anderswo beziehen, und jeder Schritt des Prozesses kann an Drittanbieter-APIs ausgelagert werden. Auslagerung ist eine legitime technische Entscheidung. Sie tauscht Kontrolle über Infrastruktur gegen Geschwindigkeit und weniger bewegliche Teile.

Entscheiden Sie über Verwahrung, bevor Sie Code schreiben

Die meisten Startups und Agenturen, die Zahlungsfunktionen entwickeln, möchten die mittlere Zeile. Nutzer zahlen auf Adressen ein, die Ihre App kontrolliert, Ihr Backend führt Auszahlungen durch, und niemand muss einen Node betreiben oder Signaturcode für sechs Netzwerke schreiben.

Verwahrung kann rechtliche Konsequenzen haben, die von Ihrem Land und Geschäftsmodell abhängen. Wenn Sie Gelder für Kunden halten werden, sprechen Sie vor dem Launch mit einem Anwalt, der die Geldtransmissions- und Virtual-Asset-Regeln in Ihrer Jurisdiktion kennt. Dieser Artikel behandelt nur die technische Seite.

Ein Hinweis zu Account Abstraction

Wenn Sie auf Ethereum aufbauen, werden Sie auf Smart-Contract-Wallets treffen. Die Account-Abstraction-Roadmap von Ethereum beschreibt, dass Konten programmierbare Sicherheit und bessere Nutzererfahrungen ermöglichen sollen, anstatt sich auf einen einzelnen rohen privaten Schlüssel zu verlassen. Das kann Funktionen wie gesponsertes Gas und flexible Wiederherstellung ermöglichen. Es ist gut für Consumer-Apps geeignet, bei denen Nutzer ihre Wallets besitzen. Für ein Backend, das Tausende von Einzahlungsadressen erstellt und Gelder einsammelt, ist das klassische externally owned account (extern verwaltetes Konto) immer noch das einfachere Modell, und es funktioniert auf die gleiche Weise bei Bitcoin, Tron und EVM-Chains. Die eigene Dokumentation von Ethereum erklärt die zwei Kontotypen, externally owned accounts und contract accounts, falls Sie eine Auffrischung benötigen.

Schritt für Schritt: Ihre erste Wallet über eine API erstellen

Die genauen Endpunkte unterscheiden sich je nach Anbieter, lesen Sie daher die Referenz der von Ihnen gewählten API. Die Abfolge unten bleibt gleich.

1. Zugangsdaten beschaffen und serverseitig aufbewahren

Registrieren Sie sich, erhalten Sie einen API-Schlüssel und, falls der Anbieter Request-Signing nutzt, ein Secret. Diese Zugangsdaten können Geld bewegen, behandeln Sie sie daher wie Datenbankpasswörter. Laden Sie sie aus einem Secrets Manager, niemals aus clientseitigem Code, niemals aus einem öffentlichen Repository. Die OWASP-Leitlinien für SDK-Tests empfehlen zu prüfen, dass Zugangsdaten begrenzt und widerrufbar sind, was eine gute Regel für jede Integration ist: wenn ein Schlüssel geleakt wird, sollten Sie ihn unschädlich machen können, ohne Ihre App neu bauen zu müssen.

2. Wallet oder Adresse erstellen

Rufen Sie den Create-Endpunkt für das benötigte Netzwerk auf. Sie erhalten eine Adresse zurück und meistens einen Identifier, den Ihr System später verwenden kann, um auf die Wallet zu verweisen. Speichern Sie sofort drei Dinge in Ihrer eigenen Datenbank:

  • die Adresse,
  • das Netzwerk, zu dem sie gehört,
  • der interne Nutzer, die Bestellung oder die Rechnung, mit der sie verknüpft ist.

Speichern Sie den privaten Schlüssel nicht selbst, es sei denn, Sie haben den sicheren Speicher dafür gebaut. Bei einem gehosteten Modell ist das die Aufgabe des Anbieters.

3. Adresse anzeigen und vor Fehlern schützen

Zeigen Sie die Adresse zusammen mit ihrem Netzwerknamen in Klartext an. Das häufigste Support-Ticket bei Krypto-Zahlungen betrifft einen Nutzer, der einen Token über das falsche Netzwerk gesendet hat. Eine USDT-Adresse auf Ethereum und eine auf Tron sehen völlig unterschiedlich aus, dennoch machen Nutzer Fehler. Fügen Sie das Netzwerk-Label neben dem QR-Code hinzu und erwägen Sie einen kurzen Bestätigungsschritt, bevor Sie ihn anzeigen.

4. Abonnieren Sie Events für diese Adresse

Registrieren Sie einen Webhook, damit Ihr Backend von Einzahlungen erfährt, ohne zu pollen. Der nächste Abschnitt erklärt, wie Sie die empfangende Seite sicher aufbauen.

5. Testen Sie zuerst auf einem Testnetzwerk

Führen Sie den vollständigen Ablauf auf einem Testnet durch: Erstellen Sie eine Adresse, senden Sie Testgelder, empfangen Sie das Event, schreiben Sie dem Konto gut, und führen Sie dann eine Auszahlung durch. Wechseln Sie erst dann die Anmeldedaten und das Netzwerk auf Mainnet und beginnen Sie mit kleinen Beträgen.

Eine Adresse pro Nutzer oder eine pro Rechnung?

Wiederverwendung ist der Shortcut, der später zu Buchhaltungsproblemen führt. Der Bitcoin-Entwicklerleitfaden beschreibt den Standardansatz, jeder Zahlungsanforderung ihre eigene Adresse zuzuweisen, damit eine eingehende Zahlung sauber der Bestellung zugeordnet werden kann, die sie verursacht hat.

Die gängigen Muster:

  • Eine Adresse pro Rechnung. Sauberster Abgleich. Am besten für Checkout-Flows mit einem erwarteten Betrag und einer Ablaufzeit.
  • Eine Adresse pro Nutzer. Einfach für Einzahlungsfunktionen, wie das Aufladen eines Guthabens. Jede eingehende Überweisung schreibt demselben Konto gut.
  • Gepoolte Adresse mit Memo oder Tag. Nur für Netzwerke und Assets, die dies unterstützen, und schwieriger richtig umzusetzen.

Wenn Sie Adressen aus einem hierarchisch-deterministischen Schema generieren, ist die Struktur standardisiert. BIP 44 definiert das Pfad-Layout von Purpose, Coin Type, Account, Change und Index, wodurch ein Seed einen vorhersagbaren Baum von Adressen erzeugen kann. Eine gehostete API übernimmt dies normalerweise für Sie, aber das Verständnis des Layouts hilft bei Audits oder Migrationen.

Schlüsselsicherheit: Wo Wallet-Projekte wirklich scheitern

Das Netzwerkprotokoll ist selten das, wodurch ein Wallet-Produkt gehackt wird. Die Smart-Contract-Sicherheitsgruppe von OWASP weist darauf hin, dass das größte Risiko in der Zufälligkeit und Speicherung privater Schlüssel liegt. Ein vorhersagbarer Seed führt zu einer stillen, totalen Kompromittierung, da ein Angreifer die Schlüssel offline rekonstruieren kann. Ihr Testrat lautet zu bestätigen, dass die gesamte Schlüsselgenerierung den kryptografisch sicheren Zufallszahlengenerator der Plattform verwendet.

Daraus folgen drei praktische Regeln.

Entwickeln Sie niemals Ihre eigene Schlüsselgenerierung. Nutzen Sie eine geprüfte Bibliothek oder einen Anbieter, dessen Aufgabe dies ist. Ein Math.random()-Seed ist eine Katastrophe, die nur auf ihren Termin wartet.

Signaturschlüssel in nicht exportierbarem Speicher aufbewahren. Die Wallet-Leitlinien des NIST verweisen auf hardwaregeschützte Module, die verhindern, dass ein Host-Prozessor geheime Schlüssel extrahiert. Für alles, was Sie selbst betreiben, bedeutet das ein HSM oder ein ähnliches sicheres Element – nicht Umgebungsvariablen oder eine Datenbankspalte. Wenn Sie verstehen möchten, wie hardwaregestützter Schlüsselschutz in der Praxis funktioniert, erklärt dieser Leitfaden zum Schutz eines Root-Schlüssels mit einem HSM (auf Portugiesisch) die Prinzipien am Beispiel von Zertifizierungsstellen-Schlüsseln. Dieselbe Logik gilt für Wallet-Signaturschlüssel.

Die menschliche Seite des Zugriffs schützen. Hardware-Sicherheitsschlüssel für die Admin-Konten, die API-Schlüssel erstellen, Webhook-URLs ändern oder Auszahlungen genehmigen können, eliminieren eine große Klasse von Phishing-Risiken. Rollen trennen, sodass die Person, die Code bereitstellt, nicht auch Gelder freigeben kann.

Für die tägliche API-Hygiene ist unsere eigene Checkliste mit Sicherheitstipps für die Verwendung einer Blockchain-API ein guter Begleiter.

Zahlungen mit Webhooks erkennen

Die Erstellung der Adresse ist nur die halbe Arbeit. Sie müssen auch wissen, wann jemand daran zahlt. Das geplante Abfragen jeder Adresse verschwendet Anfragen und verzögert die Bestätigung. Webhooks senden das Ereignis in dem Moment an Sie, in dem der Anbieter es sieht. Wir führen einen vollständigen Ablauf in wie man Einzahlungen automatisch mit Webhooks verarbeitet durch.

Der empfangende Endpunkt ist der Ort, an dem Sicherheitsfehler passieren, daher bauen Sie ihn sorgfältig auf. Das OWASP Webhook Security Cheat Sheet ist die Referenz, der Sie folgen sollten, und seine Hauptpunkte sind folgende:

  • Die Signatur bei jeder Zustellung prüfen. Berechnen Sie den HMAC über den rohen Body mit Ihrem gemeinsamen Geheimnis neu und vergleichen Sie ihn mit dem Signatur-Header. Verwenden Sie einen zeitkonstanten Vergleich, um Timing-Angriffe zu vermeiden.
  • HTTPS erfordern. Eine Signatur beweist, wer die Nachricht gesendet hat, verschlüsselt sie aber nicht, sodass jeder im Netzwerkpfad eine unverschlüsselte HTTP-Zustellung lesen kann.
  • Geheimnisse aus der URL fernhalten. URLs landen in Load-Balancer- und Proxy-Protokollen, die Sie möglicherweise nicht kontrollieren. Authentifizierung in Header legen.
  • Ereignisse als idempotent behandeln. Zustellungen können nach Netzwerk-Wiederholungen wiederholt werden. Eine einzelne Zahlung darf niemals zweimal gutgeschrieben werden.

Dieser letzte Punkt verdient ein konkretes Muster. Speichern Sie den Transaktions-Hash als eindeutigen, indizierten Schlüssel. Der Abgleichsratgeber des Bitcoin-Leitfadens, der für jede Kette gilt, empfiehlt, in Ihrer Datenbank nach einem bestehenden Hash zu suchen, bevor Sie irgendeine Gutschriftslogik ausführen, anstatt darauf zu vertrauen, dass jeder Callback genau einmal eintrifft. In SQL ist das eine Unique-Constraint auf dem Hash und ein Insert, das Duplikate ignoriert.

Ein zuverlässiger Handler folgt dieser Reihenfolge:

  1. Lesen Sie den rohen Anfrage-Body vor jeglichem Parsing.
  2. Prüfen Sie die HMAC-Signatur. Bei Nichtübereinstimmung ablehnen.
  3. Fügen Sie den Transaktions-Hash ein. Falls er bereits existiert, geben Sie Erfolg zurück und stoppen Sie.
  4. Warten Sie auf die Bestätigungsanzahl, die Ihre Risikopolitik verlangt, bevor Sie Guthaben gutschreiben.
  5. Schreiben Sie das Konto in derselben Datenbank-Transaktion gut, in der Sie den Eintrag einfügen.
  6. Antworten Sie schnell mit einem Erfolgscode und schieben Sie langsame Arbeit in eine Warteschlange.

Multi-Chain-Realitäten, auf die Sie stoßen werden

Eine Wallet, die auf einer Chain funktioniert, ist einfach. Eine Wallet, die auf mehreren funktioniert, ist der Punkt, an dem die Integrationskosten steigen, da jedes Netzwerk sein eigenes Adressformat, Gebührenmodell und Token-Standards hat.

  • Gebühren. Auf EVM-Chains benötigt ein Token-Transfer die native Coin für Gas. Eine frisch erstellte Adresse, die USDT empfängt, kann diese nicht senden, bis sie auch etwas ETH, BNB oder MATIC-Äquivalent für Gebühren hält. Planen Sie einen Finanzierungsschritt für Auszahlungen und Sweeps ein.
  • Tron-Konto-Aktivierung. Tron-Adressen verhalten sich anders: ein nicht aktiviertes Konto erscheint möglicherweise nicht on-chain, bis es eine kleine Menge TRX erhält, und TRC-20-Transfers verbrauchen Ressourcen, daher testen Sie diesen Pfad frühzeitig.
  • Token-Standards. ERC-20, BEP-20 und TRC-20 sehen für Nutzer ähnlich aus, unterscheiden sich aber in Vertragsaufrufen und Ereignisformaten. NFTs fügen ERC-721 hinzu.
  • Dekodierte Daten. Rohe Transaktions-Logs sind Hexadezimalwerte. Wenn Ihr Anbieter dekodierte Werte zurückgibt, sparen Sie sich das Schreiben von ABI-Parsing für jeden Token.

Selbst bauen vs. kaufen: ein ehrlicher Vergleich

Sie können Ihre eigenen Nodes und Signatur-Services betreiben. Manche Teams sollten das tun. Hier ist, wie die Entscheidung meist ausfällt.

InfrastrukturNodes, Indexer, Monitoring für jede ChainKeine auf Ihrer Seite
SchlüsselverwaltungIhre Aufgabe zu designen und zu auditierenWird vom Anbieter gehandhabt, mit Ihren gesicherten Zugangsdaten
KostenstrukturEngineering-Zeit und ServerVorhersehbares Abonnement

Wenn Wallets der Kern-Unterschied Ihres Produkts sind oder Regulierung Sie zwingt, Schlüssel in Ihrer eigenen Umgebung zu halten, bauen Sie selbst. Wenn Wallets ein Feature sind, das Zahlungen, Einzahlungen oder Auszahlungen unterstützt, ist die gesparte Integrationszeit anderswo besser investiert.

Unsere Perspektive

Wir sehen bei den meisten Teams, die zu uns kommen, das gleiche Muster. Sie unterschätzen die Rohrleitungsarbeit und überschätzen die Kryptographie. Einen Schlüssel zu erzeugen ist ein gelöstes Problem. Was Projekte scheitern lässt, ist ein Monat, der für Node-Synchronisation draufgeht, die Gebühren-Eigenheiten einer Chain, ein Webhook-Handler, der eine Einzahlung doppelt gutschreibt, oder ein dekodierter Betrag, der um den Faktor zehn daneben liegt, weil Token-Dezimalstellen nicht beachtet wurden.

Deshalb haben wir Chaingateway als eine REST-API für mehrere Netzwerke entwickelt, anstatt für jede Kette eine eigene Integration zu benötigen. Sie erstellen Wallets, senden Token-Transfers, schätzen Gas automatisch und erhalten vorab dekodierte Transaktionsdaten in derselben Struktur, unabhängig vom verwendeten Netzwerk. Anfragen werden mit HMAC signiert, und Webhook-Benachrichtigungen informieren Ihr Backend in Echtzeit über Zahlungen, sodass Sie keine eigenen Nodes betreiben oder pollen müssen.

Unser Rat ist einfach. Entscheiden Sie zuerst über die Verwahrung. Geben Sie jedem Zahler eine eigene Adresse. Machen Sie Ihren Webhook-Handler vom ersten Tag an idempotent, nicht erst nach der ersten doppelten Gutschrift. Und testen Sie den gesamten Ablauf auf einem Testnet, bevor auch nur eine einzige echte Münze bewegt wird.

Start-Checkliste

Bevor Sie live gehen, bestätigen Sie jeden Punkt:

  • API-Zugangsdaten liegen in einem Secrets Manager und können rotiert werden.
  • Jede Adresse wird mit ihrem Netzwerk, Eigentümer und Erstellungszeitpunkt gespeichert.
  • Ihr Webhook-Endpunkt nutzt HTTPS, verifiziert Signaturen und vergleicht sie in konstanter Zeit.
  • Ein Unique Constraint auf dem Transaktions-Hash verhindert doppelte Gutschriften.
  • Sie warten auf eine Bestätigungsschwelle, die zum risikobehafteten Betrag passt.
  • Auszahlungs-Wallets sind mit der für Gebühren nötigen nativen Münze finanziert.
  • Admin-Konten nutzen starke Multi-Faktor-Authentifizierung, idealerweise Hardware-Keys.
  • Sie haben schriftlich festgehalten, wer Auszahlungen genehmigen darf und wie ein geleakter Key widerrufen wird.
  • Sie haben rechtlichen Rat zur Verwahrung eingeholt, wo Sie Gelder für Dritte halten.

Häufig gestellte Fragen

Ja. Eine gehostete Wallet-API betreibt die Nodes und die Signatur-Infrastruktur für Sie und liefert Adressen über REST-Aufrufe. Sie müssen dennoch Ihre eigenen API-Zugangsdaten und Ihren Webhook-Endpunkt sichern, da diese nun die Türen zu Ihren Geldern sind.

In der Regel ja, in dem Sinne, dass der Dienst die Keys speichert und Ihre Zugangsdaten Aktionen autorisieren. Ob Sie dadurch im rechtlichen Sinne zum Verwahrer werden, hängt davon ab, ob Sie Gelder für Ihre Kunden halten und von Ihrer Jurisdiktion. Fragen Sie vor dem öffentlichen Start einen Anwalt, der auf Regulierung virtueller Vermögenswerte spezialisiert ist.

Abonnieren Sie Webhook-Benachrichtigungen für die Adresse. Verifizieren Sie die HMAC-Signatur, speichern Sie den Transaktions-Hash in einer eindeutig indizierten Spalte und schreiben Sie die Gutschrift erst gut, wenn Ihre Bestätigungsanforderung erfüllt ist. Da Zustellungen sich wiederholen können, ist der Hash-Check das, was Sie vor doppelter Zahlung bewahrt.

Pro Zahlung ermöglicht die sauberste Abstimmung, da jede Adresse genau einer Bestellung zugeordnet ist. Pro Nutzer ist einfacher für Guthaben-Aufladungen. Vermeiden Sie, eine Adresse über viele Zahler zu teilen, es sei denn, das Netzwerk unterstützt ein Memo oder Tag und Sie handhaben es korrekt.

In nicht exportierbarem Speicher wie einem HSM oder einem Secure Element, oder bei einem Anbieter, der diesen Speicher für Sie betreibt. Umgebungsvariablen, Konfigurationsdateien und gewöhnliche Datenbankzeilen sind für Schlüssel, die echte Gelder kontrollieren, nicht geeignet.
