So richten Sie einen Binance Smart Chain (BSC) Node ein

Einen BSC-Node einrichten: offizieller Snapshot, bnb-chain-geth-Fork, systemd-Unit, Hardware, Sicherheit, Sync-Zeit, Kosten und wann eine API passt.

Kapitel
C
Chaingateway Team
Blockchain-Experten

Geprüft von Maurice Sobiera

Ein BSC-Node ist ein Rechner, auf dem der Client der BNB Smart Chain läuft. Er lädt jeden Block herunter, prüft ihn und stellt einen lokalen JSON-RPC-Endpunkt bereit. So kann Ihre Software die Chain lesen und Transaktionen senden, ohne einen Dritten einzubeziehen. Die BNB Smart Chain hieß bis Februar 2022 Binance Smart Chain.

Seit dem Hard Fork Fermi am 14. Januar 2026 erzeugt die Chain alle 0,45 Sekunden einen Block. Maxwell hatte das Intervall Mitte 2025 bereits auf 0,75 Sekunden halbiert. Diese Geschwindigkeit ist für Nutzer angenehm und für Node-Betreiber anspruchsvoll. Falsche Hardware oder die falsche Sync-Strategie führen dazu, dass ein Node den Chain-Head nie erreicht.

Dieser Leitfaden ist die Copy-and-paste-Version, die über die offizielle Dokumentation hinausgeht. Er behandelt ein Setup auf Snapshot-Basis mit dem bnb-chain-geth-Fork, eine systemd-Unit, Sicherheitshinweise für RPC-Nodes, die Rechnung für Sync-Zeit und Kosten sowie die Fälle, in denen Sie gar keinen Node betreiben sollten. Versionsnummern und Größen wurden am 5. November 2026 gegen die GitHub-Repositories des Projekts geprüft.

Was ist ein BSC-Node, und welchen Typ brauchen Sie?

Ein BSC-Node führt den Chain-Client aus, prüft Blöcke und stellt einen lokalen JSON-RPC-Endpunkt mit derselben Schnittstelle wie Ethereum bereit: eth_blockNumber, eth_call, eth_sendRawTransaction und weitere. In der Praxis sind vier Varianten relevant.

  • Ein Full-Node speichert den aktuellen Zustand und bedient RPC. Er ist der Standard und das Thema dieses Leitfadens.
  • Ein Fast-Node ist ein Full-Node, der mit --tries-verify-mode none gestartet wird. Die offizielle Dokumentation empfiehlt ihn für hohe Leistung, wenn Ihnen die Konsistenz des Zustands wenig bedeutet.
  • Ein Archiv-Node speichert jeden historischen Zustand. Er braucht mehrere Terabyte mehr und lohnt sich nur für Indexierung und Analysen.
  • Ein Validator erzeugt Blöcke. Dafür muss er mit gestakten BNB in das kleine gewählte Set aufgenommen werden. Das ist ein eigenes Thema, das über einen Setup-Leitfaden hinausgeht.

Und ein Light-Node? Der Geth-Fork hat Light-Client-Code übernommen. In der Praxis bedient im BSC-Netzwerk jedoch fast niemand Light-Peers. Behandeln Sie „BSC-Light-Node“ deshalb als nicht verfügbar. Wenn selbst ein geprunter Full-Node zu viel ist, spricht das für eine API. Siehe den letzten Abschnitt.

BSC und Geth: eine Codebasis, zwei Chains

Der BSC-Client ist ein Fork von go-ethereum, gepflegt unter github.com/bnb-chain/bsc. Das Binary heißt tatsächlich geth. Es spricht dasselbe JSON-RPC, akzeptiert die meisten gleichen Flags und ergänzt BSC-Besonderheiten. Dazu gehört der Parlia-Consensus, eine Proof-of-Staked-Authority. Der ganze Node ist ein einziger Prozess, anders als bei Ethereum nach dem Merge, wo ein separater Consensus-Client läuft. Hinzu kommen Flags wie --tries-verify-mode. Daraus folgen zwei praktische Konsequenzen:

  • Ihre Ethereum-Werkzeuge funktionieren unverändert mit einem BSC-Node.
  • Sie müssen den bnb-chain-Build verwenden. Upstream-Geth kann BSC nicht synchronisieren. Das ist der häufigste Anfängerfehler bei „BSC Geth“.

Hardware-Anforderungen für einen BSC-Node

Die Basis kommt aus dem README von bnb-chain/bsc. Die rechte Spalte hier ist unser Vorschlag für intensive RPC-Nutzung und keine offizielle Angabe.

KomponenteGeprunter Full-Node (README)Intensive RPC-Nutzung (unser Vorschlag)
CPU16 Kerne16 Kerne, hohe Taktrate
RAM64 GB128 GB
Festplatte3 TB SSD (Angabe im README von Dezember 2023; 4 TB einplanen), 8k IOPS, 500 MB/s, Lese-Latenz unter 1 ms, NVMe für Snap-Sync4 TB+ NVMe, ≥10k IOPS
Netzwerk5 MB/s (rund 40 Mbit/s) hoch und runter100 Mbit/s+, ohne Volumenlimit

Die Zeile, an der die meisten Setups scheitern, ist IOPS, nicht die Kapazität. Bei 0,45-Sekunden-Blöcken schreibt der Node ständig. Cloud-Blockspeicher mit Standard-IOPS fällt hinter den Chain-Head zurück und holt nie wieder auf. Die Referenz im README ist AWS gp3 mit 8.000 IOPS und einer Lese-Latenz unter einer Millisekunde, auf einer Instanz vom Typ m5zn.6xlarge oder r7iz.4xlarge (c2-standard-16 auf Google Cloud). Eine lokale NVMe-Platte in einem dedizierten Server erfüllt diese Anforderung mit Reserve.

Schritt für Schritt: BSC-Full-Node aus dem offiziellen Snapshot

Ein Sync ab Genesis ist möglich, aber eine schlechte Idee. Die Dokumentation zum Full-Node stuft ihn als nicht empfohlen ein. Er braucht leistungsstärkere Hardware und sehr viel Zeit. Der unterstützte Weg: Sie laden den Chain-Daten-Snapshot herunter, starten den Node darauf und lassen ihn aufholen. Die Befehle setzen Ubuntu 24.04 voraus.

1. Server vorbereiten

Port 30311 ist der Peer-to-Peer-Port von BSC und der einzige Blockchain-Port, der offen sein darf. Der RPC-Port bleibt auf localhost beschränkt.

2. bnb-chain-geth-Binary herunterladen

Die Umbenennung des Binarys in geth-bsc verhindert den klassischen Fehler, ein von der Distribution installiertes Upstream-Geth gegen BSC-Daten zu starten.

3. config.toml und genesis.json holen

Hinweis: geth-bsc init genesis.json ist nur beim Sync ab Genesis nötig. Beim Snapshot-Weg überspringen Sie init, denn der Snapshot bringt seine eigene Datenbank mit.

4. Snapshot herunterladen und entpacken

Die Snapshots liegen im offiziellen Repository bsc-snapshots. Am 5. November 2026 listet es zwei Datensätze für Mainnet auf. Beide stammen vom Snapshot vom 9. Oktober 2026 und setzen BSC v1.7.2 oder neuer voraus:

SnapshotGröße (komprimiert)Verwendung
Geprunt (...-pruneancient)rund 1,9 TBNur aktuelle Blöcke. Der richtige für diesen Leitfaden.
Vollständigrund 7,4 TBVollständige Blockhistorie.

Das Repository verlinkt außerdem Snapshots anderer Quellen, etwa einen Snapshot eines geprunten Full-Nodes von rund 900 GB vom BNB48 Club und Reth-BSC-Snapshots für den Reth-Client. Das Repo liefert fetch-snapshot.sh. Es lädt herunter, prüft die MD5-Prüfsumme (-c) und entpackt in einem Befehl. Verwenden Sie -p für den geprunten Snapshot. Der manuelle Weg unten zeigt, was dabei im Hintergrund passiert. Es gibt zwei Wege, das Archiv auf die Platte zu bekommen:

aria2c lädt über acht Verbindungen und setzt nach Unterbrechungen fort (-c). Bei einfachem wget beginnt ein abgebrochener Download von mehreren Terabyte von vorn. Nach dem Entpacken muss die Chain-Datenbank unter /var/lib/bsc/geth/chaindata liegen. Das Layout des Archivs hat sich zwischen den Snapshot-Generationen geändert. Verschieben Sie den inneren Ordner geth deshalb bei Bedarf dorthin.

Prüfen Sie vor dem Entpacken: Vergleichen Sie die MD5 von der Snapshot-Seite oder lassen Sie fetch-snapshot.sh -c die Prüfung übernehmen. Ein Terabyte-Archiv mit einem gekippten Bit kostet Sie einen Tag.

Option A braucht Platz für das Archiv und die entpackten Daten gleichzeitig. Genau das ist der eigentliche Grund für die Empfehlung einer 4-TB-Platte.

5. systemd-Unit

Legen Sie /etc/systemd/system/bsc.service an:

--tries-verify-mode none ist der Fast-Node-Schalter aus der offiziellen Dokumentation, für RPC-Bereitstellung, wenn Sie den Kompromiss bei der Zustandskonsistenz akzeptieren. Entfernen Sie ihn, um einen normalen geprunten Full-Node zu betreiben. --history.transactions 0 indiziert jede Transaktion in den Blöcken, die Ihre Datenbank hält. Ältere Leitfäden nutzen für denselben Zweck das veraltete Flag --txlookuplimit 0.

Das README der bsc-snapshots schlägt für den geprunten Snapshot andere Aufbewahrungs-Flags vor: --syncmode=full --history.transactions=600000 --history.blocks=600000 --history.logs=600000 --tries-verify-mode=local. Bei 0,45-Sekunden-Blöcken entsprechen 600.000 Blöcke rund 3,1 Tagen Historie. Außerdem steht dort, dass das alte Flag --pruneancient veraltet ist. Wählen Sie die Aufbewahrung, die dazu passt, wie weit Ihre Anwendung zurückschauen muss. TimeoutStopSec=600 gibt dem Node beim Herunterfahren zehn Minuten zum Schreiben. Harte Abbrüche beschädigen die Datenbank früher oder später.

6. Starten und prüfen

Gesunde Ausgabe ist ein stetiger Strom von „Imported new chain segment“-Zeilen. Vergleichen Sie Ihre Höhe mit einem öffentlichen Explorer:

Rechnen Sie das Hex-Ergebnis um und vergleichen Sie es mit bscscan.com. Wenn eth_syncing false liefert und die Höhe stimmt, ist der Node live.

Wie sichern Sie einen BSC-RPC-Node ab?

Die Unit oben bindet RPC an 127.0.0.1. Das ist richtig für einen Node, den nur lokale Software nutzt.

Brauchen andere Rechner Zugriff, öffnen Sie Port 8545 nicht ungeschützt ins Internet.

Setzen Sie stattdessen nginx oder Caddy mit TLS davor, dazu ein Auth-Token oder eine IP-Allowlist und ein Rate-Limit. Lassen Sie --http.api bei eth,net,web3. Stellen Sie admin, debug oder txpool auf einem erreichbaren Node nie bereit. Ein offener RPC-Port zieht Missbrauch an. Unbegrenzte eth_getLogs-Aufrufe über große Blockbereiche können selbst starke Hardware überlasten. Der P2P-Port 30311 bleibt der einzige offene Blockchain-Port.

Ein Unterschied zu Ethereum: Hier gibt es keine Engine API und kein JWT-Secret. Parlia braucht keinen separaten Consensus-Client. Firewall und Localhost-Bindung sind der gesamte Schutz, deshalb müssen sie stimmen.

Wie überwachen Sie einen BSC-Node?

Ein BSC-Node scheitert typischerweise auf eine Weise: Der Prozess läuft weiter, während der Node hinter den Head zurückfällt. Prüfungen der reinen Prozesslaufzeit übersehen das vollständig. Prüfen Sie deshalb Sync-Status und Höhe.

Die strengere Prüfung vergleicht Ihr eth_blockNumber alle paar Minuten mit einer zweiten Quelle, etwa einem öffentlichen Endpunkt oder einem Explorer, und schlägt Alarm, wenn die Lücke wächst. Kalibrieren Sie den Schwellenwert auf den Takt von BSC: 400 Blöcke klingen nach viel und sind bei 0,45-Sekunden-Blöcken drei Minuten Chain-Zeit. Schwellenwerte aus Ethereum-Werkzeugen sind hier viel zu lasch.

Der Fork übernimmt den Metrik-Stack von Geth. Starten Sie mit --metrics (Prometheus-Endpunkt auf Port 6060, auf localhost belassen). Die Standard-Grafana-Dashboards von Geth funktionieren größtenteils unverändert. Richten Sie vor jedem Dashboard zwei Alarme ein: Festplattenbelegung über 85 Prozent und lokale Blockhöhe, die fünf Minuten stillsteht. Ein täglicher Befehl journalctl -u bsc --since -24h | grep -ci error im Cron-Mail rundet das Bild ab. Error-Zahlen, die steigen, gehen den meisten Ausfällen um Tage voraus.

Wie lange braucht ein BSC-Node zum Synchronisieren?

Rechnen statt versprechen: Der geprunte Snapshot mit 1,9 TB braucht bei dauerhaft 100 MB/s rund 5,3 Stunden zum Download, bei 50 MB/s rund 10,5 Stunden. Das Entpacken ist plattengebunden und kostet auf NVMe ein paar Stunden. Der Snapshot hängt je nach Startzeitpunkt Tage bis Wochen hinter dem Chain-Head zurück. Ein gesunder Node importiert deutlich schneller als Echtzeit. Insgesamt sollten Sie einen Arbeitstag einplanen.

Ein Sync ab Genesis braucht zum Vergleich weit leistungsstärkere Hardware und sehr viel Zeit. Deshalb empfiehlt die offizielle Dokumentation den Snapshot.

Wie schnell wächst ein BSC-Node, und wie prunen Sie ihn?

Die Datenbank wächst auch nach dem ersten Tag weiter. Der Zustand nimmt mit jedem neuen Contract und Konto zu, und die Blockdaten wachsen im Takt der 0,45-Sekunden-Blöcke. Das genaue Wachstum hängt von der Netzwerkaktivität ab. Statt einer festen Zahl zu vertrauen, führen Sie wöchentlich du -sh /var/lib/bsc/geth/chaindata aus und bauen sich Ihre eigene Trendlinie. Erwarten Sie folgendes Muster: Hunderte GB pro Quartal, nicht pro Jahr.

Drei Werkzeuge halten die Größe im Griff.

geth-bsc snapshot prune-state ist das eingebaute Offline-Pruning. Es verwirft Zustandsknoten, auf die nichts mehr verweist. Auf einer Datenbank mit mehreren Terabyte braucht es viele Stunden, und der Node liefert in dieser Zeit nichts aus. Die Alternative, die viele Betreiber vorziehen, ist Wipe-and-Restore: Alle paar Monate löschen Sie das Datenverzeichnis und spielen den neuesten geprunten Snapshot ein. Die Ausfallzeit ist oft kürzer als beim Pruning. Als Zugabe erhalten Sie eine frisch verdichtete Datenbank.

Das dritte Werkzeug sind inkrementelle Snapshots, spezifiziert in BEP-593. Statt den vollständigen geprunten Snapshot bei jeder Aktualisierung neu zu laden, führen Sie kleine inkrementelle Snapshots auf einen monatlichen Basis-Snapshot zusammen. Der BEP-Text vergleicht einen monatlichen inkrementellen Snapshot von rund 120 GB mit einem Prune-Ancient-Snapshot von über 1,0 TB. Prüfen Sie im README der bsc-snapshots, ob die inkrementellen Dateien derzeit veröffentlicht werden, bevor Sie Ihre Planung darauf stützen.

Was ist mit Erigon auf BSC passiert?

bsc-erigon, der Port von Erigon durch NodeReal, war jahrelang der Archiv-Client. Sein README trägt jetzt einen End-of-Life-Hinweis: Entwicklung und Pflege endeten Ende 2025, und das Repository ist archiviert. Der Hinweis verweist Betreiber auf Reth-BSC, den Rust-basierten Nachfolger, den bnb-chain pflegt.

Am 5. November 2026 listet das README der bsc-snapshots Reth-BSC-Snapshots neben den Geth-Snapshots. Der Mainnet-Archiv-Snapshot vom 2. November 2026 ist 7.789,76 GB groß, der Full-Node-Snapshot 3.621,42 GB und der Fast-Node-Snapshot 840,42 GB.

Für den geprunten RPC-Node aus diesem Leitfaden bleibt der offizielle Geth-Fork die Referenz. Für Archiv-Lasten sollten Sie zuerst Reth-BSC prüfen. Behandeln Sie jede verbleibende bsc-erigon-Maschine als Migration, die auf ihren Termin wartet. Ein nicht mehr gepflegter Client verpasst den nächsten Hard Fork.

Was kostet ein BSC-Node?

Betrachten Sie das als Rechenweg, nicht als Preisliste. Die Klasse 16 Kerne / 64 GB / 4 TB NVMe gehört zu dedizierten Servern. Kein gewöhnlicher VPS-Tarif deckt sie ab. Holen Sie bei zwei oder drei Anbietern dedizierter Server ein Angebot mit diesen Spezifikationen ein. Ein Cloud-Aufbau mit 8k provisionierten IOPS (die AWS-Referenz des README) rechnet die IOPS separat ab. Weisen Sie diese Zeile deshalb gesondert aus.

Rechnen Sie dann Ihre Stunden hinzu. Planen Sie einen Arbeitstag für das Initial-Setup mit diesem Leitfaden ein, dazu einige Stunden pro Monat für Hard-Fork-Updates und Snapshot-Aktualisierungen. Multiplizieren Sie mit Ihrem Stundensatz und stellen Sie das Ergebnis neben das Hosting-Angebot.

Wie halten Sie einen BSC-Node aktuell?

BSC führt Hard Forks in einem Tempo durch, das Ethereum-Betreiber überrascht.

Allein 2025 brachten Lorentz (29. April) und Maxwell (30. Juni). Sie verkürzten das Blockintervall zuerst auf 1,5 und dann auf 0,75 Sekunden.

Fermi folgte am 14. Januar 2026 und senkte die Blöcke von 0,75 auf 0,45 Sekunden. Jeder Fork hat eine minimale Client-Version. Für Fermi war es v1.6.4. Ein Node darunter bleibt am Fork-Block hängen. Das neueste Release am 5. November 2026 ist v1.8.2. Die aktuellen Snapshots setzen mindestens v1.7.2 voraus.

Abonnieren Sie deshalb den Release-Feed von bnb-chain/bsc auf GitHub und behandeln Sie Updates als Routine, nicht als Ereignis.

Das Verfahren ist kurz: Laden Sie das neue geth_linux herunter, prüfen Sie es, stoppen Sie den Dienst, ersetzen Sie /usr/local/bin/geth-bsc und starten Sie neu. Die Datenbank bleibt erhalten. Die Release-Notes weisen auf Konfigurationsänderungen hin. BSC benennt Flags häufiger um als upstream Geth. Lesen Sie die Notes deshalb vor dem Neustart, nicht danach. Planen Sie eine Viertelstunde pro Release ein und rechnen Sie alle paar Monate mit einem Fork.

Für Entwicklungsumgebungen gibt es ein lokales privates Netzwerk über das BSC-Deploy-Toolkit. Dafür braucht man keine Mainnet-Nodes.

Fehlerbehebung

Der Node importiert Blöcke, bleibt aber hinter dem Head zurück

Fast immer IOPS der Festplatte. Testen Sie mit fio und vergleichen Sie mit der Referenz von 8k IOPS. Netzwerkspeicher mit Standard-IOPS ist der übliche Schuldige. Prüfen Sie, dass --tries-verify-mode none gesetzt ist. Liegt die Hardware unter der Anforderungstabelle, schließt kein Flag die Lücke.

„missing trie node“-Fehler, oder der Node beginnt nach einer Snapshot-Wiederherstellung bei Block 0 zu synchronisieren

Das Datenverzeichnis hat das falsche Layout. Die Chain-Datenbank muss unter <datadir>/geth/chaindata liegen. Zeigt das Log „Writing custom genesis block“, hat geth ein leeres Datenverzeichnis gefunden und frisch begonnen. Stoppen Sie den Dienst, verschieben Sie den entpackten Ordner geth an die richtige Stelle und starten Sie neu.

Die Peer-Anzahl bleibt nahe null

Prüfen Sie, dass Port 30311 offen und weitergeleitet ist. Eine veraltete config.toml ist der zweite Verdacht. Bootstrap- und Static-Node-Listen ändern sich mit der Zeit. Laden Sie mainnet.zip deshalb aus dem neuesten Release erneut herunter. Bei Heimanschlüssen prüfen Sie zusätzlich das NAT.

lz4 meldet „Decoding error“ beim Entpacken

Das Archiv ist unvollständig. Setzen Sie den Download mit aria2c -c fort und vergleichen Sie die Dateigröße mit der Angabe auf der Snapshot-Seite, bevor Sie erneut entpacken. Denken Sie daran, dass Option A freien Platz für das Archiv und die entpackten Daten gleichzeitig braucht.

Der OOM-Killer beendet den Node

journalctl -k | grep -i oom klärt die Frage.

Die Unit setzt --cache 8000. Der tatsächliche Speicherbedarf liegt während des Aufholens deutlich über dem Cache-Wert. Auf den empfohlenen 64 GB ist das in Ordnung, auf abgespeckter Hardware nicht. Senken Sie zuerst --cache, bevor Sie anderes ändern.

Lassen Sie Swap als Absturzpuffer aktiv. Ein per OOM beendeter Node schreibt nichts mehr auf die Platte. Der nächste Start kann deshalb den Fall „missing trie node“ von oben auslösen.

Die Festplatte ist voll

Prüfen Sie zuerst df -h, dann du -h --max-depth=2 /var/lib/bsc, um das Wachstum zu finden.

Vergessene Snapshot-Archive sind der häufigste Befund. Das geprunte .tar.lz4 allein ist rund 1,9 TB groß. Option A lässt es liegen, wenn Sie die Aufräumarbeit auslassen. Ist chaindata selbst das Problem, spielen Sie den neuesten geprunten Snapshot neu ein oder starten Offline-Pruning (siehe Abschnitt zum Zustandswachstum). Bei BSCs Wachstumskurve ist eine volle Platte ein Planungsfehler und kein Pech. Der 85-Prozent-Alarm aus dem Monitoring-Abschnitt verschafft Ihnen die Woche, die Sie brauchen.

Sollten Sie einen eigenen Node betreiben oder eine API nutzen?

Chaingateway verkauft die Alternative. Deshalb folgt hier der Vergleich mit seinen Schwächen.

Betreiben Sie einen Node, wenn Sie rohes JSON-RPC in großem, dauerhaftem Umfang nutzen, etwa für Indexierung, Backtesting oder Log-Scans über Millionen Blöcke. Oder wenn zwischen Ihnen und der Chain kein Dritter stehen darf. Ein dedizierter Server ist ein Fixkostenposten ohne Gebühr pro Anfrage. Bei hohem Aufrufvolumen kann er einen Tarif nach Verbrauch schlagen.

Nutzen Sie eine API, wenn der Node nur Infrastruktur für Zahlungen wäre. Ein synchronisierter BSC-Full-Node liefert eth_sendRawTransaction und Logs. Alles, was ein Zahlungssystem tatsächlich braucht, ist Software, die Sie darauf aufbauen und betreiben müssen: Einzahlungsadressen je Kunde, Erkennung eingehender BEP-20-Transfers, signierte Webhooks, Schlüsselspeicherung und Wiederholungen. Zählen Sie diese Entwicklerstunden in den Vergleich ein, mit dem Stundensatz aus dem Kostenabschnitt.

Die BNB-Smart-Chain-API von Chaingateway deckt diese Schicht als REST ab. Sie importiert Adressen (POST /api/v2/bsc/addresses/import), sendet BEP-20-Token (POST /api/v2/bsc/transactions/bep20) und empfängt Einzahlungs-Webhooks. Sobald Sie ein persönliches Secret setzen, tragen Webhooks einen HMAC-Header X-Signature (Anleitung zur Prüfung).

Fehlgeschlagene Zustellungen werden nicht automatisch wiederholt. GET /api/v2/bsc/webhooks/notifications/failed listet sie auf, und jede lässt sich über den Retry-Endpunkt erneut senden. Die Gewinnschwelle in einem Satz: dedizierter Server plus Ihre Stunden für Aufbau und Betrieb gegen einen Tarif auf /pricing/. Die Schnellstart-Anleitung und der Webhook-Leitfaden bringen Sie in Minuten zu einem ersten Test. Die 7-Tage-Testphase braucht kein KYC (Registrierung).
