Krypto-Zahlungs-Webhooks: Wie sie funktionieren und wie Sie sie erstellen

Erfahren Sie, wie Krypto-Zahlungs-Webhooks Einzahlungen erkennen, wie Sie Signaturen verifizieren, Wiederholungen und Duplikate behandeln und Ihren Endpunkt testen, bevor Sie live gehen.

Kapitel
C

Ein Krypto-Zahlungs-Webhook ist eine HTTP-Anfrage, die ein Blockchain-Dienst im Moment eines On-Chain-Ereignisses an Ihren Server sendet, beispielsweise wenn eine Einzahlung in der Wallet eines Kunden eingeht. Anstatt das Netzwerk alle paar Sekunden abzufragen, ob eine Zahlung eingetroffen ist, übergeben Sie dem Anbieter eine URL, und dieser ruft Sie auf. Für den produktiven Betrieb benötigen Sie vier Dinge: einen öffentlichen Endpunkt, Signaturverifizierung, idempotente Behandlung doppelter Ereignisse und einen Fallback für verpasste Zustellungen. Dieser Leitfaden behandelt jeden dieser Punkte.

TL;DR

  • Ein Webhook sendet ein Ereignis an Ihren Server, sobald eine Zahlung oder ein Wallet-Ereignis eintritt, sodass Sie ständiges Polling und die damit verbundene Systemlast vermeiden.
  • Verifizieren Sie jede Anfrage anhand des Signatur-Headers und des rohen Anfrage-Bodys, bevor Sie einem Feld darin vertrauen.
  • Antworten Sie schnell mit einem 2xx-Statuscode und führen Sie die eigentliche Arbeit in einem Hintergrund-Job aus.
  • Behandeln Sie jedes Ereignis als potenziell wiederholt: Speichern Sie Ereignis-IDs und gestalten Sie Ihre Auftragsaktualisierungen idempotent.
  • Führen Sie einen langsamen Abgleichs-Job für ausstehende Zahlungen durch, damit eine verpasste Zustellung keinen Auftrag blockiert.

Was Krypto-Zahlungs-Webhooks sind

Ein Webhook ist ein Callback. Sie registrieren eine URL, teilen dem Anbieter mit, an welchen Ereignissen Sie interessiert sind, und sobald eines eintritt, sendet der Anbieter eine POST-Anfrage mit einem JSON-Body, der es beschreibt. Bei Krypto-Zahlungen umfassen diese Ereignisse üblicherweise eine eingehende Überweisung an eine überwachte Adresse, eine von Ihnen initiierte ausgehende Überweisung, einen Token-Transfer auf einem Contract oder eine Bestätigungsaktualisierung einer bereits gesehenen Transaktion.

Die Alternative ist Polling. Ihr Server ruft eine API timerbasiert auf und vergleicht das Ergebnis mit dem, was er zuvor gesehen hat. Polling ist einfach zu implementieren, aber im Betrieb verschwenderisch. Jede Anfrage, die nichts Neues liefert, kostet Sie Rate-Limits, Rechenleistung und Latenz, und die Verzögerung zwischen einer Zahlung und Ihrer Reaktion entspricht der Länge Ihres Intervalls. Bei mehreren Chains und Tausenden von Kundenadressen vervielfacht sich die Anzahl der Aufrufe schnell.

Webhooks kehren die Richtung um. Der Anbieter überwacht die Chain, gleicht Transaktionen mit den von Ihnen abonnierten Adressen ab und benachrichtigt Sie einmalig. Die Reaktionszeit sinkt auf Sekunden, und Ihre eigene Infrastruktur bleibt untätig, bis es etwas zu tun gibt. Wenn Sie das ausführlichere Argument für dieses Modell im Kontext von Einzahlungen lesen möchten, haben wir es in wie Webhooks Einzahlungen automatisch verarbeiten dargelegt.

Die letzte Zeile ist die praktische Antwort. Webhooks sollten das Hauptsignal sein, und Polling sollte ein langsamer Rückfall sein, der nur die noch ausstehenden Zahlungen prüft. Entwickler, die Krypto-Checkouts betreiben, beschreiben oft genau diese Kombination, mit Webhooks zuerst und einer periodischen Prüfung ausstehender Rechnungen, um alles aufzufangen, was nie angekommen ist, wie in dieser Node.js-Anleitung zu Polling versus Webhooks.

Wie ein Webhook eine Krypto-Zahlung erkennt

Die Anbieter-Seite ist der Teil, den Sie nicht sehen, aber das Verständnis dafür erklärt den größten Teil des Verhaltens, das Sie beim Testen antreffen werden.

  1. Abonnement. Sie erstellen eine Wallet oder registrieren eine Adresse und abonnieren diese dann über die API des Anbieters für Ereignisse. Das Abonnement enthält Ihre Callback-URL und die Ereignistypen.
  2. Überwachung. Der Anbieter betreibt Nodes für jede unterstützte Kette und liest jeden neuen Block. Jede Transaktion wird mit den abonnierten Adressen abgeglichen und, bei Token, mit den Contract-Transfer-Logs.
  3. Dekodierung. Rohdaten der Kette sind nicht benutzerfreundlich. Ein Token-Transfer auf Ethereum ist ein kodierter Log-Eintrag, und Bitcoin hat Inputs und Outputs anstelle von Absender und Empfänger. Gute Anbieter dekodieren dies in eine lesbare Payload mit Betrag, Asset, Absender, Empfänger und Transaktions-Hash.
  4. Zustellung. Der Anbieter signiert die Payload und sendet sie an Ihre URL. Wenn Ihr Server nicht mit einem Erfolgscode antwortet, wird es nach einem Zeitplan wiederholt.

Deshalb sind Kettenunterschiede weniger wichtig, als Sie vielleicht erwarten, wenn die Payload normalisiert ist. Chaingateway deckt Ethereum, Bitcoin, Tron, Solana, Polygon, BNB Chain und Arbitrum über eine REST-API ab, mit vordekodierten Daten, sodass Ihr Handler dieselben Felder lesen kann, egal von welchem Netzwerk die Zahlung kam. Token-Standards wie ERC-20, BEP-20 und TRC-20 werden unterstützt, was wichtig ist, da die meisten realen Zahlungen Stablecoin-Transfers und keine nativen Coins sind.

Ereignisse, die sich lohnen zu abonnieren

Beginnen Sie eng. Die meisten Zahlungsflüsse benötigen nur wenige Ereignisse:

  • Eingehender Transfer an eine Kunden-Einzahlungsadresse. Dies ist das Kernereignis für die Gutschrift eines Kontos oder das Markieren einer Rechnung als bezahlt.
  • Status ausgehender Transfers. Wenn Sie eine Auszahlung tätigen oder Gelder zusammenführen, möchten Sie wissen, wann sie gesendet und wann sie bestätigt sind.
  • Bestätigungsänderungen. Eine Transaktion kann lange in einem Block sichtbar sein, bevor Sie sie als final betrachten. Ihre eigenen Regeln entscheiden, wann sie zählt.
  • Token- und NFT-Transfers. Nützlich für Apps, die eigene Token ausgeben oder digitale Artikel verkaufen.

Unser Beitrag zu Polygon-Webhooks ohne Polling zeigt, wie dies auf einer einzelnen schnellen, gebührenarmen Kette aussieht.

Einrichten und Verarbeiten eines Webhook-Endpunkts

Der Endpunkt ist eine gewöhnliche HTTPS-Route auf Ihrem Server. Der Unterschied zwischen einer Demo und einem Produktions-Handler liegt in wenigen Gewohnheiten.

Anforderungen an den Endpunkt

Die URL muss über HTTPS aus dem öffentlichen Internet erreichbar sein. Localhost-Adressen und private Netzwerke können keine Aufrufe empfangen, daher benötigen Sie während der Entwicklung einen Tunnel, der Ihren lokalen Port verfügbar macht. Halten Sie die Route für Webhooks reserviert, akzeptieren Sie nur POST, und platzieren Sie sie nicht hinter Anmeldeseiten oder CSRF-Middleware, die eine Anfrage von einer Maschine ablehnen würden.

Der Handler sollte schnell antworten. Die gängige Empfehlung, die die Webhook-Dokumentation von OpenAI klar formuliert, lautet: eine öffentliche URL verwenden, die Signatur prüfen, schnell mit 2xx antworten und schwerere Arbeit an einen Hintergrund-Worker übergeben. Dieselbe Regel gilt für Krypto-Ereignisse. Wenn Sie vor der Antwort eine Datenbank aktualisieren, eine E-Mail versenden und ein Buchhaltungssystem aufrufen, wird ein langsamer nachgelagerter Dienst den Anbieter glauben lassen, die Zustellung sei fehlgeschlagen, und das Ereignis erneut senden. Für einen breiteren Blick darauf, was Produktionssysteme von einem Endpunkt erwarten, behandelt dieser Artikel zu ereignisgesteuerter Integration in Geschäftssystemen dieselbe Prompt-Response-Disziplin aus der ERP-Perspektive.

Ein zuverlässiges Muster sieht so aus:

  1. Den rohen Anfrage-Body als Bytes lesen.
  2. Die Signatur prüfen.
  3. Das Ereignis mit seiner ID in eine Warteschlange oder eine Ereignistabelle schreiben.
  4. 200 zurückgeben.
  5. Einen Worker das in die Warteschlange gestellte Ereignis verarbeiten lassen.

Signaturen prüfen

Jeder, der Ihre URL findet, kann JSON dorthin posten. Wenn Ihr Handler ein Konto gutschreibt, weil eine Anfrage besagt, dass eine Einzahlung eingetroffen ist, ist eine gefälschte Anfrage ein Diebstahl. Die Signaturprüfung schließt diese Tür.

Das typische Verfahren ist HMAC. Der Anbieter berechnet einen Hash der Payload mit einem Geheimnis, das nur Sie und er kennen, und sendet das Ergebnis in einem Header. Sie berechnen den Hash neu und vergleichen. Drei Details bereiten häufig Schwierigkeiten:

  • Die ursprünglichen Bytes verwenden. Wenn Sie das JSON parsen und neu serialisieren, können Whitespace und Schlüsselreihenfolge sich ändern und der Hash stimmt nicht mehr. Die Dokumentation von OpenAI weist darauf hin, dass die Prüfung die ursprünglichen Anfrage-Bytes verwendet, und dasselbe gilt für jedes HMAC-Verfahren.
  • In konstanter Zeit vergleichen. Nutzen Sie die sichere Vergleichsfunktion Ihrer Sprache statt einer einfachen Gleichheitsprüfung.
  • Den Zeitstempel prüfen, falls einer mitgeliefert wird. Das Ablehnen alter Zeitstempel begrenzt das Wiederverwenden einer abgefangenen Anfrage.

Chaingateway signiert seine Anfragen mit HMAC, und wir haben über die Stärkung der Webhook-Sicherheit geschrieben, während sich das Produkt weiterentwickelte. Speichern Sie das Geheimnis in einer Umgebungsvariable oder einem Secrets Manager, niemals im Repository, und rotieren Sie es, falls es jemals in einem Log auftaucht.

Umgang mit Wiederholungen, Duplikaten und langsamen Bestätigungen

Netzwerke fallen aus, Deployments starten Server neu, und Anbieter wiederholen die Zustellung. Das Ergebnis ist, dass Ihr Handler früher oder später dasselbe Ereignis zweimal sieht, und manchmal Ereignisse in falscher Reihenfolge. Planen Sie dafür von Anfang an.

Verarbeitung idempotent gestalten

Jedes Ereignis trägt etwas, das es identifiziert, meist eine Ereignis-ID oder die Kombination aus Transaktions-Hash und Ausgabe-Index oder Log-Index. Speichern Sie diesen Identifikator mit einer Unique-Constraint, bevor Sie handeln. Schlägt der Insert fehl, weil der Schlüssel bereits existiert, haben Sie das Ereignis bereits gesehen und können 200 zurückgeben, ohne etwas zu tun.

Machen Sie dann die Geschäftsaktion selbst sicher wiederholbar. „Setze Rechnung 1042 auf bezahlt mit Transaktion X“ ist idempotent. „Füge 50 zum Guthaben hinzu“ ist es nicht. Bevorzugen Sie die erste Form, oder verknüpfen Sie die Guthabenänderung mit dem eindeutigen Ereignisdatensatz in einer einzigen Datenbanktransaktion.

Bestätigungstiefe respektieren

Eine Transaktion, die in einem Block erscheint, ist nicht dasselbe wie eine Zahlung, gegen die Sie Waren versenden können. Ketten unterscheiden sich darin, wie schnell ein Block unwahrscheinlich wird, rückgängig gemacht zu werden, und der richtige Schwellenwert hängt vom Betrag und dem Asset ab. Definieren Sie eine Richtlinie pro Kette und pro Bestellgröße, und speichern Sie den Status jeder Zahlung: erkannt, wird bestätigt, bestätigt, fehlgeschlagen. Der Webhook, der die Erkennung ankündigt, sollte einen Auftrag auf „Zahlung gesehen“ setzen, nicht auf „erfüllt“.

Unterzahlungen, Überzahlungen und falsche Tokens

Kunden senden häufiger als erwartet den falschen Betrag. Ihr Handler sollte den empfangenen Betrag und das Asset mit der Rechnung vergleichen und verzweigen: exakte Übereinstimmung, zu wenig, zu viel oder ein unerwartetes Token. Entscheiden Sie im Voraus, ob Sie die Differenz automatisch gutschreiben, zur Prüfung zurückhalten oder erstatten. Eine decodierte Payload mit Asset und Betrag als getrennten Feldern macht diesen Vergleich zu wenigen Codezeilen statt zu einer Parsing-Übung.

Ein Sicherheitsnetz behalten

Auch mit Wiederholungsversuchen kann eine Zustellung lange genug fehlschlagen, bis der Anbieter aufgibt. Führen Sie einen geplanten Job alle paar Minuten aus, der sich Rechnungen ansieht, die noch über eine angemessene Zeit hinaus ausstehen, und deren Adressguthaben oder Transaktionshistorie über die API prüft. Wenn er eine Zahlung findet, die Ihr Webhook nie gemeldet hat, führt er sie durch denselben Verarbeitungspfad. Ein Codepfad für beide Quellen bedeutet einen Satz an Fehlern.

Testen, Überwachung und Fehlerbehebung

Bauen Sie Vertrauen in Schichten auf.

Lokaler Test. Schreiben Sie ein kleines Skript, das eine Beispiel-Payload mit Ihrem Test-Secret signiert und an Ihren Endpunkt sendet. Bestätigen Sie, dass eine gültige Signatur besteht, ein geänderter Body fehlschlägt und ein alter Zeitstempel dort fehlschlägt, wo anwendbar.

Testnet-Lauf. Erstellen Sie eine Wallet in einem Testnetzwerk, abonnieren Sie sie, und senden Sie eine kleine Überweisung von einem Faucet. Sie werden die echte Ereignissequenz sehen, einschließlich der Verzögerung zwischen Erkennung und Bestätigung, die Ihnen keine Beispiel-Payload beibringt.

Duplikat-Test. Senden Sie dasselbe gültige Ereignis fünf Mal. Ihre Rechnung sollte sich einmal ändern, und Ihre Logs sollten vier übersprungene Duplikate anzeigen.

Fehler-Test. Lassen Sie Ihren Handler absichtlich 500 zurückgeben, und stellen Sie ihn dann wieder her. Prüfen Sie, ob der Wiederholungsversuch des Anbieters eintrifft und einmal verarbeitet wird.

Sobald live, protokollieren Sie jede eingehende Ereignis-ID, das Verifikationsergebnis, das Verarbeitungsergebnis und die benötigte Zeit. Alarmieren Sie bei drei Dingen: Signaturfehlern (ein falsch konfiguriertes Secret oder ein Angreifer), einer wachsenden Warteschlange (Worker hinken hinterher) und Rechnungen, die weit länger als normal ausstehen (stille Zustellprobleme).

Warum wir Webhooks in eine API integriert haben

Die meisten Teams, die zu uns kommen, haben den Do-it-yourself-Weg bereits ausprobiert: ein Knoten pro Kette, ein Block-Scanner, ein Decoder für jeden Token-Standard und eine Warteschlange, um alles zusammenzuhalten. Das funktioniert bis zur zweiten oder dritten Netzwerk, und dann bringt jede Kette ihre eigenen Eigenheiten und ihren eigenen On-Call-Pager mit sich.

Wir haben Chaingateway so konzipiert, dass ein Entwickler eine Wallet erstellen, ihre Events abonnieren und eine signierte, vorab dekodierte Benachrichtigung erhalten kann, ohne diese Infrastruktur betreiben zu müssen. Unser Ziel ist es, dass die Payload für eine USDT-Einzahlung auf Tron für jemanden, der bisher nur Ethereum gehandhabt hat, vertraut aussieht, und dass die Gebührenschätzung automatisch erfolgt, wenn Sie Gelder wieder auszahlen.

Wir sind der Meinung, dass Webhooks das richtige primäre Signal für Zahlungen sind, und bauen das Produkt rund um diese Überzeugung auf: HMAC-signierte Anfragen, eine REST-API für Ethereum, Bitcoin, Tron, Solana, Polyggon, BNB Chain und Arbitrum sowie Event-Daten, die Sie ohne das Schreiben eines Decoders verwenden können.

Häufig gestellte Fragen

Ja, aber nur leicht. Nutzen Sie Webhooks als primäres Signal und führen Sie eine geplante Prüfung noch ausstehender Zahlungen durch, damit eine nie zugestellte Zahlung keinen Auftrag hängen lässt. Die Prüfung sollte jede gefundene Zahlung durch denselben Verarbeitungscode wie Webhook-Events leiten.

Prüfen Sie den Signatur-Header anhand des rohen Anfrage-Bodys mithilfe Ihres gemeinsamen Secrets und weisen Sie Anfragen zurück, die fehlschlagen oder einen veralteten Zeitstempel tragen. Vertrauen Sie niemals dem Inhalt einer unsignierten Anfrage, auch wenn die URL geheim ist.

Geben Sie einen 2xx-Status zurück, sobald Sie das Event verifiziert und gespeichert haben. Führen Sie langsame Arbeiten wie E-Mails, Ledger-Updates und Drittanbieter-Aufrufe in einem Background-Worker aus. Eine langsame oder fehlschlagende Antwort lädt zu Retries und doppelten Zustellungen ein.

Das ist möglich, wenn Ihr Anbieter die Daten normalisiert. Mit einer einheitlichen API wie Chaingateway, die Ethereum, Bitcoin, Tron, Solana, Polygon, BNB Chain und Arbitrum abdeckt, kann ein Handler Events von allen verarbeiten, wobei ketten-spezifische Bestätigungsregeln in Ihrer eigenen Logik angewendet werden.
