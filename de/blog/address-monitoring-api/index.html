Address Monitoring API: Funktionsweise und Aufbau

Was eine Address-Monitoring-API leistet, wie Webhooks Einzahlungen und Auszahlungen melden und wie Sie Bestätigungen und Sicherheit handhaben.

Geprüft von Maurice Sobiera

Eine Address-Monitoring-API ist ein Dienst, der Blockchain-Adressen beobachtet und Ihre Anwendung benachrichtigt, wenn etwas passiert: eine Einzahlung, ein Abgang von Geldern, ein Token-Transfer oder eine bestätigte Transaktion. Sie registrieren eine Adresse und eine Callback-URL. Der Dienst schickt dann ein Webhook mit den Transaktionsdetails. Sie müssen also weder Nodes abfragen noch Logs selbst decodieren.

„Address Monitoring“ umfasst zwei verschiedene Aufgaben. Die erste ist operativ: Sie wissen, wann Geld eine Adresse erreicht oder verlässt, die Ihre App kontrolliert. So können Sie einen Kunden gutschreiben oder eine Bestellung freigeben. Die zweite ist Compliance: Sie analysieren das Verhalten von Adressen über die Zeit, um riskante Aktivitäten zu erkennen. Dieser Artikel behandelt die erste Aufgabe, die die meisten Produktteams brauchen, und zeigt, wo die zweite beginnt.

TL;DR

  • Eine Address-Monitoring-API verfolgt ausgewählte Blockchain-Adressen und schickt Events per Webhook an Ihren Server. Sie müssen also keine Nodes betreiben und nicht pollen.
  • Events sollten decodiert ankommen: Absender, Empfänger, Token, Betrag und Status, nicht rohe Hex-Logs.
  • Prüfen Sie die Signatur jedes Webhooks und deduplizieren Sie anhand der Transaktions-ID. Schreiben Sie Gelder erst nach der gewählten Bestätigungsstufe gut.
  • Chaingateway-Webhooks werden nicht automatisch wiederholt. Gleichen Sie mit der API ab, um verpasste Events zu finden.
  • Operatives Monitoring (Zahlungen) unterscheidet sich von Compliance-Monitoring (Risikomuster über die Zeit). Viele Teams brauchen beides, aus unterschiedlichen Tools.
  • Chaingateway bietet Wallets, Transfers, decodierte Transaktionsdaten und signierte Webhooks für Ethereum, Bitcoin, Tron, Polygon, BNB Smart Chain und Arbitrum. Solana wird unterstützt, hat aber keine Webhooks.

Was eine Address-Monitoring-API tatsächlich tut

Eine Blockchain ist ein öffentliches Hauptbuch, meldet sich aber nicht von selbst, wenn etwas passiert. Kein Protokoll schickt Ihrem Backend eine Nachricht, weil die Adresse 0xABC... 250 USDT erhalten hat. Jemand muss neue Blöcke lesen, sie nach Ihren Adressen filtern, das Ergebnis in verständliche Felder übersetzen und Sie benachrichtigen. Eine Address-Monitoring-API ist dieser Jemand, als Dienst angeboten.

In der Praxis erledigt die API fünf Aufgaben:

  1. Adressen registrieren. Sie legen die Adressen an, die überwacht werden sollen. Meist sind das Adressen, die Sie für Kunden, Rechnungen oder interne Wallets erzeugt haben.
  2. Die Chain lesen. Der Anbieter betreibt Nodes oder Indexer für jedes Netzwerk und prüft jeden neuen Block.
  3. Aktivität zuordnen. Die API findet Transfers der nativen Coins und Token, die Ihre überwachten Adressen betreffen.
  4. Daten decodieren. Rohe Transaktionen und Event-Logs werden in lesbare Felder übersetzt: Richtung, Token-Symbol, Betrag mit korrekten Dezimalstellen, Gebühr, Block und Status.
  5. Events zustellen. Die API schickt sie an Ihren Endpunkt, meist als HTTPS-POST-Webhook. Zusätzlich können Sie dieselben Daten jederzeit abfragen.

Was erkannt wird, hängt von der Chain ab. Bei Bitcoin sind es Ausgaben an eine Adresse. Bei Ethereum und anderen EVM-Netzwerken sind es native Transfers sowie Token-Events wie ERC-20-Transfer-Logs. Bei Tron deckt es TRX und TRC-20-Token ab. Unsere Seite zur TRC20-Adress-API zeigt, wie Erzeugen und Überwachen von Adressen in diesem Netzwerk zusammenpassen.

Operatives Monitoring versus Compliance-Monitoring

Der Begriff taucht auch in der Compliance-Welt auf, und die beiden sollten nicht verwechselt werden. Compliance-Anbieter beschreiben Transaktionsmonitoring als laufende Analyse von Blockchain-Aktivität über die Zeit. Gesucht wird nach Mustern wie Structuring, Layering, ungewöhnlicher Geschwindigkeit, Mixer-Nutzung, Sanktionsumgehung und Aktivität in ruhenden Wallets. Das Risiko zeigt sich im Verhalten über viele Transaktionen hinweg. Menschen untersuchen die Alarme.

Eine operative Monitoring-API beantwortet eine einfachere Frage: „Ist die Zahlung angekommen, auf die ich warte, und ist sie endgültig?“ Wenn Sie ein reguliertes Geschäft betreiben, brauchen Sie wahrscheinlich beide Ebenen. Die operative Ebene speist Ihr Hauptbuch und das Kundenerlebnis. Die Compliance-Ebene speist Ihr Risikoteam. Wenn ein Alarm genauer geprüft werden muss, etwa weil Gelder über mehrere Stationen verfolgt werden sollen, ist das Aufgabe von Spezialisten und nicht eines Zahlungs-Webhooks.

Warum nicht einfach eigene Nodes betreiben und pollen?

Das ist eine berechtigte Frage, und für einige Teams lautet die Antwort genau das. Dabei kommt auf Sie zu:

  • Node-Betrieb. Jede Chain braucht einen eigenen Node oder einen gehosteten Endpunkt. Dazu kommen Updates, wachsender Speicherbedarf und Verfügbarkeit. Jedes weitere Netzwerk bedeutet einen weiteren Aufbau.
  • Chain-spezifische Logik. Das UTXO-Modell von Bitcoin, die Logs von Ethereum, das Ressourcenmodell von Tron und das Kontenmodell von Solana brauchen jeweils eigenen Parser-Code.
  • Decodierung. Token-Beträge kommen als Ganzzahlen, die die richtigen Dezimalstellen brauchen. Contract-Events brauchen ABIs. Interne Transfers und gebündelte Transaktionen werden leicht übersehen.
  • Reorg-Behandlung. Neuere Blöcke können ersetzt werden. Ihr Scanner muss das erkennen und sich selbst korrigieren.
  • Zustellung. Ist ein Event erkannt, brauchen Sie immer noch eine Warteschlange, Wiederholungen und ein Signaturverfahren, um es sicher an Ihre Dienste zu liefern.

Eine Monitoring-API fasst das meiste davon in einer einzigen Integration zusammen. Der Preis ist die Abhängigkeit von einem Anbieter. Beurteilen Sie ihn deshalb nach Zuverlässigkeit, Datenqualität und danach, wie sauber er Events übergibt. Einen breiteren Blick auf die Alternativen bietet unser Vergleich von sechs Arten von Blockchain-APIs und wann welche passt.

Wie webhook-basiertes Address Monitoring funktioniert

Der typische Ablauf hat vier Schritte. Er ist derselbe, ob Sie das Monitoring selbst bauen oder kaufen.

1. Adresse anlegen oder registrieren

Für Zahlungen ist das sauberste Muster eine Adresse pro Kunde, Rechnung oder Bestellung. Landet eine Zahlung auf einer eindeutigen Adresse, wissen Sie, wer gezahlt hat, ohne nach einem Verwendungszweck oder einer Referenz zu fragen. Mit Chaingateway erzeugen Sie Wallets über die API und verwenden die Adressen direkt. Liefern Kunden eigene Adressen für Auszahlungen, prüfen Sie diese zuerst. Unser kostenloser Krypto-Adressvalidator deckt Tron-, Ethereum- und BSC-Formate ab und ist beim Bau eigener Prüfungen eine praktische Referenz.

2. Events abonnieren

Sie teilen der API mit, welche Adressen und Event-Typen wichtig sind und wohin sie gesendet werden sollen: an Ihren HTTPS-Endpunkt. Abonnements können so eng sein wie eine Adresse und ein Token oder so breit wie alle Adressen Ihres Kontos. Details zu diesem Modell finden Sie auf der Seite zu Blockchain-Webhooks und Event-Benachrichtigungen.

3. Decodierte Nutzlast empfangen

Eine brauchbare Nutzlast nennt Ihnen ohne weitere Abfragen den Absender, den Empfänger, das Asset, den Betrag, den Block und den Transaktions-Hash. Ein Chaingateway-Webhook für einen TRC-20-Transfer sieht so aus (Webhook-Anleitung):

Die id kennzeichnet die Benachrichtigung, die txid die Transaktion. Hier liegt der Unterschied zwischen decodierten und rohen Chain-Daten. Bei Rohdaten schreiben Sie den Parser selbst. Bei decodierten Daten lesen Sie ein Feld. Die Nutzlast enthält keinen Bestätigungszähler. Deshalb entscheidet Ihr eigener Code, wann eine Transaktion als endgültig gilt.

4. Quittieren, prüfen und handeln

Ihr Server prüft die Signatur, speichert das Event und antwortet zügig mit einem 2xx-Status. Die Geschäftslogik verarbeitet er asynchron. Alles Weitere, etwa das Gutschreiben auf ein Konto oder der Versand einer Bestellung, richtet sich nach Ihren Regeln für Bestätigungen.

Welche Netzwerke und Adresstypen sollte die API unterstützen?

Bevor Sie sich festlegen, listen Sie auf, was Ihr Produkt im nächsten Jahr berühren wird, nicht nur heute. Ein Checkout, der mit USDT in einem Netzwerk startet, wird oft innerhalb weniger Monate auch für ein anderes Netzwerk gefordert.

Prüfen Sie die Abdeckung von:

  • Nativen Coins und Token. Bitcoin, ETH, TRX, SOL, Assets im Polygon-Netzwerk und BNB Chain sowie Token-Standards wie ERC-20, BEP-20 und TRC-20.
  • NFTs. Wenn Sie Sammlerstücke oder Tickets ausgeben oder annehmen, brauchen Sie auch Transfer-Events im ERC-721-Stil.
  • Adressformate. Bitcoin hat mehrere Formate. EVM-Chains teilen sich ein Format über Netzwerke hinweg. Das führt zu Fehlern, wenn ein Kunde im falschen Netzwerk sendet. Ihre App sollte das erwartete Netzwerk neben jeder Einzahlungsadresse angeben.
  • Ausgehende Aktivität. Viele Tools erfassen nur Einzahlungen. Wenn Sie Auszahlungen senden, wollen Sie dieselbe decodierte Sicht auf ausgehende Transaktionen und ihren Status.

Chaingateway deckt Ethereum, Bitcoin, Tron, Solana, Polygon, BNB Smart Chain und Arbitrum über eine einzige Blockchain-API ab, einschließlich der wichtigsten Token-Standards und NFT-Transfers. Webhooks gibt es für alle Chains außer Solana. Eine Solana-Integration muss Salden oder Transaktionen ihrer Adressen per Polling abfragen.

Bestätigungen, Verzögerungen und Reorgs: Wann ist eine Zahlung echt?

Die erste Benachrichtigung ist nicht das letzte Wort. Eine Transaktion kann im Mempool gesehen, in einen Block aufgenommen und später auf eine Finalitätsstufe gebracht werden, die Sie für sicher halten. Die Chains unterscheiden sich stark. Blockzeiten, Bestätigungskonventionen und Finalitätsmodelle sind bei Bitcoin, Ethereum, Tron und Solana nicht gleich. Deshalb sollten Sie Schwellenwerte je Netzwerk und je Betrag festlegen.

Zwei Regeln halten Sie aus Schwierigkeiten heraus. Erstens: Skalieren Sie die Bestätigungsanforderung mit dem Wert, der auf dem Spiel steht. Eine kleine Abo-Zahlung verträgt eine niedrigere Schwelle als eine große Auszahlung. Zweitens: Machen Sie den Zustandsablauf in Ihrer Datenbank explizit. „Ausstehend“, „bestätigt“ und „fehlgeschlagen“ sollten gespeicherte Zustände sein, keine abgeleiteten.

Rechnen Sie außerdem damit, dass Events verspätet oder in falscher Reihenfolge ankommen. Eine Bestätigungsmeldung kann bei Ihnen eintreffen, bevor ein langsamer Handler die Erkennungsmeldung abgeschlossen hat. Nehmen Sie den Transaktions-Hash und den Status als maßgebliche Quelle, nicht die Reihenfolge der Ankunft.

Umgang mit Wiederholungen und doppelten Benachrichtigungen

Chaingateway wiederholt Webhooks nicht automatisch. Antwortet Ihr Server nicht rechtzeitig oder mit einem Fehler, wird die Benachrichtigung als fehlgeschlagen gespeichert. Fehlgeschlagene Benachrichtigungen listen Sie pro Chain auf, etwa mit GET /api/v2/tron/webhooks/notifications/failed, und senden sie mit POST /api/v2/tron/webhooks/notifications/{id}/retry erneut. Bis dahin weiß Ihr System nichts von diesem Event.

Doppelte Zustellungen können dennoch vorkommen, etwa wenn Sie eine Benachrichtigung erneut senden, die Ihr Server bereits verarbeitet hat. Planen Sie von Anfang an für beide Fälle. Andere Anbieter wiederholen Zustellungen womöglich selbst. Dasselbe Handler-Design funktioniert deshalb anbieterübergreifend.

  • Handler idempotent gestalten. Speichern Sie einen eindeutigen Schlüssel je Event, etwa den Transaktions-Hash plus den Log-Index oder die Zustell-ID, mit einer Eindeutigkeitsbedingung in der Datenbank. Existiert der Schlüssel bereits, geben Sie Erfolg zurück und tun nichts weiter.
  • Schnell antworten. Schreiben Sie das rohe Event in eine Warteschlange oder Tabelle, antworten Sie mit einem 2xx-Status und verarbeiten Sie danach. Langsame Handler führen zu Zeitüberschreitungen, und jede Zeitüberschreitung wird zu einer fehlgeschlagenen Benachrichtigung.
  • Abgleichen. Webhooks können während eigener Ausfallzeiten verloren gehen. Lassen Sie einen periodischen Job fehlgeschlagene und aktuelle Benachrichtigungen (GET /api/v2/<chain>/webhooks/notifications) abrufen und mit Ihren Datensätzen vergleichen. So wird ein verlorenes Event aus einem Vorfall zu einer verzögerten Korrektur.
  • Alles protokollieren. Speichern Sie die rohe Nutzlast, den Signatur-Header und Ihr Verarbeitungsergebnis. Behauptet ein Kunde, er habe bezahlt, brauchen Sie den Nachweis in einer Minute, nicht in einer Stunde.
  • Bei Stille alarmieren. Liefert eine Adresse, die sonst Verkehr bekommt, ungewöhnlich lange keine Events, prüfen Sie die Pipeline.

Sicherheit, Authentifizierung und Ratenbegrenzungen

Ein Endpunkt, der auf Anfrage Geld gutschreibt, ist ein Ziel. Behandeln Sie ihn entsprechend.

Jedes Webhook prüfen

Wer Ihre URL findet, kann eine gefälschte Meldung „Zahlung eingegangen“ senden. Verlangen Sie deshalb eine Signatur. Sobald Sie in Ihrem Profil ein persönliches Geheimnis setzen, fügt Chaingateway jedem Webhook einen X-Signature-Header hinzu.

Der Header ist ein Base64-kodierter HMAC-SHA256 der Transaktions-ID, geschlüsselt mit Ihrem persönlichen Geheimnis. Ihr Server berechnet ihn neu und weist alles ab, was nicht übereinstimmt (Signatur-Anleitung). Vergleichen Sie die Werte mit einer zeitkonstanten Funktion, etwa hmac.compare_digest in Python. HMAC selbst ist in RFC 2104 definiert.

API-Keys schützen

Bewahren Sie Keys in einem Secrets-Manager oder in Umgebungsvariablen auf, nie in clientseitigem Code oder in Repositories. Verwenden Sie für jede Umgebung eigene Keys. Rotieren Sie sie nach Zeitplan und nach jedem Personalwechsel. Weitere Gewohnheiten dieser Art finden Sie in unseren sechs Sicherheitstipps für die Nutzung einer Blockchain-API.

Den Endpunkt absichern

  • Nur über HTTPS bereitstellen.
  • Einen schwer zu erratenden Pfad verwenden und, wo Ihr Anbieter Quell-IP-Bereiche veröffentlicht, nur diese zulassen.
  • Übergroße Bodies und unerwartete Content-Types ablehnen.
  • Beträge oder Adressen aus einem Webhook nie vertrauen, bevor sie mit Ihren eigenen Datensätzen abgeglichen sind. Die Adresse muss eine sein, die Sie ausgegeben haben, und der Betrag muss zur Bestellung passen.

Ratenbegrenzungen einplanen

Für Abgleich oder Sammelabfragen von Adressen stoßen Sie bei jedem Anbieter auf Anfragelimits. Cachen Sie, was sich nicht ändert. Bündeln Sie Anfragen, wo die API es erlaubt. Warten Sie bei Drosselungsantworten exponentiell und verteilen Sie geplante Jobs, statt alle zur vollen Stunde zu starten. Kennen Sie die Limits Ihres Tarifs vor dem Start, nicht erst während der ersten Lastspitze.

Sollten Sie das Monitoring selbst bauen oder eine API nutzen?

Die Chain selbst zu scannen funktioniert in einer ersten Version. Später treten Probleme auf: Ein Reorg schreibt eine Zahlung gut, die danach verschwindet. Ein Token mit ungewöhnlichen Dezimalstellen zeigt den falschen Betrag. Ein Node fällt in einer Stoßzeit zurück. Und der Support jagt einem Kunden hinterher, der sagt, er habe bezahlt.

Mit Chaingateway erstellen Sie ein Wallet, legen einen Webhook für seine Adresse an und erhalten decodierte, signierte Events. Die Anfrageformate sind bei Ethereum, Bitcoin, Tron, Polygon, BNB Smart Chain und Arbitrum gleich. Ein weiteres Netzwerk ist deshalb eine Konfigurationsänderung. Einen Node betreiben Sie nicht.

Drei Gewohnheiten zählen mehr als der Anbieter, den Sie wählen. Legen Sie Ihre Bestätigungsregel früh fest. Schreiben Sie idempotente Handler vor der ersten Live-Zahlung. Gleichen Sie nach Zeitplan ab. Eine Monitoring-API soll das erleichtern, nicht den Bedarf dafür ersetzen.

Eine minimale Checkliste zur Umsetzung

Gehen Sie diese Liste vor Ihrer ersten Live-Zahlung durch.

  1. Erzeugen Sie eine Adresse pro Rechnung oder Kunde, und zeigen Sie das erwartete Netzwerk daneben an.
  2. Abonnieren Sie diese Adressen für eingehende und ausgehende Events.
  3. Stellen Sie einen HTTPS-Endpunkt bereit, der den Header X-Signature prüft.
  4. Speichern Sie jedes Event mit einem eindeutigen Schlüssel, und ignorieren Sie Wiederholungen.
  5. Bewegen Sie Zahlungen über gespeicherte Zustände: ausstehend, bestätigt, fehlgeschlagen.
  6. Legen Sie Bestätigungsschwellen je Netzwerk und je Betrag fest.
  7. Planen Sie einen Abgleichsjob gegen die Transaktionshistorie der API.
  8. Alarmieren Sie bei fehlgeschlagenen Zustellungen, langen Phasen ohne Events und Signaturfehlern.
  9. Testen Sie mit kleinen echten Beträgen auf jedem Netzwerk und jedem Token, das Sie unterstützen. Schließen Sie eine Einzahlung im falschen Netzwerk ein, damit Sie die Antwort für den Support schon kennen.
